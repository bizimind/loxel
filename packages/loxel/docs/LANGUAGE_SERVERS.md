# Language Servers and Language Intelligence

How Loxel provides language features: language-server subprocesses bridged to Monaco over WebSockets, project-wide TypeScript diagnostics, formatting, JSON/YAML/TOML schemas and syntax highlighting.

To add a new language server, follow the [add-language-server skill](../../../.agents/skills/add-language-server/SKILL.md) and its [per-server quirks reference](../../../.agents/skills/add-language-server/references/existing-integrations.md). This doc is the architecture that skill assumes; it does not repeat the checklist. For the end-user view see the site's [TypeScript Intelligence](../../site/src/content/docs/typescript-intelligence.md) page.

## Data flow

```
Monaco model ──(MonacoLspClient, JSON-RPC over WS)──▶ /ws/<lang>-lsp[?wt=<path>]
   ▲                                                       │ server.ts routes by ws.data.type
   │                                                       ▼
   └──────── providers / markers ◀── WS ◀── <Lang>LspManager (StdioLspManager subclass)
                                                           │ Content-Length framed stdio
                                                           ▼
                                                 language-server subprocess (cwd = worktree)
```

The server is a thin proxy. It owns process lifetime, framing and a small set of message rewrites (initialize parameters, URI translation, capability scrubbing). All LSP feature logic on the client lives in the `monaco-lsp-client` fork, which registers Monaco providers from the server's advertised capabilities.

## Server side

### `StdioLspManager` base class

[stdio-lsp-manager.ts](../src/server/stdio-lsp-manager.ts) bridges one WebSocket to one subprocess. Public API: `handleMessage(ws, data)`, `detach(ws)` (kill and forget), `destroy()` (kill all, used on server shutdown). Subclasses add their own entry points (`createSession(ws, wtPath)` / `destroySession(ws)` for worktree-scoped managers, `attach(ws)` for YAML) that call the protected `startSession(ws, context)`. `WorktreeLspManager` supplies the one-server-per-worktree plumbing (those entry points, a `WtLspSession`, `wtPath` as the session key, workspace and `cwd`); the managers whose session holds more state (Python, ruff) extend `StdioLspManager` directly.

- **Session model.** `sessions: Map<ServerWebSocket, TSession>`. `BaseLspSession` holds the `ws`, the `proc`, the stdout reassembly buffer and `documentContents` (used only for full-text sync). `WtLspSession` adds `wtPath`.
- **Dedup by key.** `getSessionKey(context)` returns a key (worktree managers return `wtPath`; YAML returns `null`). `startSession` keeps at most one live session per key: if another WebSocket already owns the key, that session is detached and its socket closed with code `4000` ("Replaced by newer connection"). A server that cannot start (no binary, or `Bun.spawn` throwing because it cannot be executed) releases its key and closes the socket with `4001`, so the client's `initialize` fails instead of hanging.
- **Spawn.** `Bun.spawn([resolveBinary(context), ...spawnArgs()])` with piped stdio, `cwd` from `spawnOptions(context)` and the environment from `buildSpawnEnv()` in [shell-env.ts](../src/server/shell-env.ts) (the login-shell `PATH`, so servers that run user tools such as basedpyright's interpreter or terraform-ls's `terraform` find them when Loxel was launched from Finder) with `NODE_OPTIONS` cleared. Server startup waits up to `LOGIN_SHELL_ENV_WAIT_MS` for that `PATH` before serving, so the first sessions do not race it. Default args are `["--stdio"]`. `resolveBinary` may return a promise (ruff looks in the worktree's environment); the client's frames that arrive meanwhile, starting with `initialize`, are held and replayed once the process is spawned, and dropped if the socket closes or a newer one claims the key first.
- **Framing.** `writeToStdin` adds the `Content-Length` header and flushes the `FileSink` per message. `drainMessages` parses frames out of stdout and hands each body to `handleServerFrame`.
- **`initialize` rewriting.** When `getSessionWorkspace(session)` returns a path, missing `rootUri` / `rootPath` / `workspaceFolders` are filled in (client values win), with `file://` URIs percent-encoded the way Monaco writes them (`fileUri` in [lsp-file-uri.ts](../src/server/lsp-file-uri.ts)). `getInitializationOptions(session)` is merged one level deep into the client's `initializationOptions` (client values win). Config that the server only accepts by push goes in `onClientInitialized`, which runs after the client's `initialized` notification is forwarded and typically sends `workspace/didChangeConfiguration`.
- **Workspace folders.** monaco-lsp-client does not implement `workspace/workspaceFolders` either, so when `getSessionWorkspace(session)` returns a path the base answers that request itself with the session's single folder, the same one it injects into `initialize` (Tombi asks for it).
- **Pulled configuration.** monaco-lsp-client does not implement `workspace/configuration`, so a subclass that defines `workspaceConfiguration(session, section)` gets the `workspace.configuration` capability injected into `initialize`, and the base answers the server's requests itself, one section at a time (asynchronously, dropped if the session is gone). `notifyConfigurationChanged(session)` sends `workspace/didChangeConfiguration` with `settings: null`, which makes such a server pull again.
- **Watched files.** monaco-lsp-client cannot watch files, so without help a server never hears about changes to files that are not open: new modules, `git checkout`, an agent's edits, `pyrightconfig.json` / `tsconfig.json`. A subclass that sets `forwardWatchedFiles` (basedpyright, ruff, TypeScript and Tombi) gets the `workspace.didChangeWatchedFiles` capability (`dynamicRegistration: true`, without `relativePatternSupport`, which keeps servers from asking for most directories outside the worktree; globs that still point outside it never match) injected into `initialize` by `handleMessage`, before `handleClientData`. `drainMessages` takes the server's `workspace/didChangeWatchedFiles` entries out of `client/registerCapability` / `client/unregisterCapability` before `handleServerFrame`, so overriding subclasses need no wiring: their glob watchers are kept in the `WatchedFilesForwarder` each session gets when it starts, from [lsp-watched-files.ts](../src/server/lsp-watched-files.ts), and the request is answered directly, or forwarded with only the remaining registrations. The worktree's `ProjectFilesService` reports each watcher batch through `onPathsChanged`; `server.ts` hands it to every worktree manager's `notifyWatchedFilesChanged(wtPath, paths)`, and the forwarder matches it against the watchers (plain globs and absolute globs that spell out the worktree path relative to the worktree, with that path taken literally rather than as glob syntax, other absolute globs from the file system root, relative patterns under their base; case-insensitively on macOS and Windows, where TypeScript registers lowercased paths), drops paths no watcher wants (until the server has registered a watcher, up to 10,000 changed paths are kept, and each later registration takes the ones its watchers want, since a server reads the disk before it registers: tsc only once its project has loaded), and sends one `workspace/didChangeWatchedFiles` with `file://` URIs after 250 ms of quiet or at most 1 s after the oldest queued change. The watcher does not say whether a path is new, so the type comes from `stat`: missing is deleted; a last write within 1 s of the birth time (where the file system records none, the first time the session's forwarder sees the path), or a metadata change more than 1 s after the last write (a file renamed or moved into place), is created; anything else is changed. Atomic saves therefore arrive as creations. The distinction matters: basedpyright only re-resolves imports for created files. Only changes inside the session's worktree and outside its git-ignored directories are reported, and only while a client is subscribed to that worktree (when its file watcher runs).
- **Session teardown.** `onSessionClosed(session)` fires when a session is detached, destroyed or its process exits (possibly more than once) for releasing per-session resources such as watchers.
- **`disableSemanticTokens`.** Strips the semantic-tokens client capability from `initialize`, deletes `semanticTokensProvider` from the initialize response, and filters semantic-token entries out of `client/registerCapability`.
- **`suppressedFeatures`.** LSP features (formatting, range formatting, semantic tokens) Monaco must not get from a server: their capability is deleted from the initialize response and their `client/registerCapability` entries are filtered out the same way, since servers differ in which way they advertise them (ruff before 0.17 statically, later dynamically); when no registration is left the base answers the server directly.
- **`requiresFullTextSync`.** The base tracks text from `didOpen`, applies incremental `didChange` ranges locally (clamped), and forwards a single full-text change. A `didChange` for an untracked URI is forwarded unchanged with a warning.
- **Errors.** JSON-RPC error responses from the server are logged at info level before forwarding.
- **stderr.** Each session reads stderr line by line through a token bucket from [stderr-throttle.ts](../src/server/stderr-throttle.ts) (burst 200 lines, refill 50 lines/s, "suppressed N" summary every 5 s and on exit) so a chatty server cannot flood the shared log ring buffer. The last 20 lines are kept regardless and logged as a warning if the process exits non-zero.

### Python environment

basedpyright's own environment discovery covers only a root `.venv` and it ignores Loxel's `initializationOptions`; without an interpreter it runs `python3` from its `PATH`. [python-env.ts](../src/server/python-env.ts) is the single resolver of a worktree's interpreter, for every Python feature (language servers, terminals, format on save, the status bar), and returns a `PythonEnv` from [python-env-model.ts](../src/api/python-env-model.ts) (`source`, absolute `pythonPath`, `envPath` prefix or null; a venv's bin directory is `dirname(pythonPath)`).

- **`resolvePythonEnv(wtPath, { overridePath?, env? })`** tries, first hit wins: the override (by default the worktree's chosen interpreter from [python-override-store.ts](../src/server/python-override-store.ts); `null` skips it), `VIRTUAL_ENV` then `CONDA_PREFIX` only when they lie inside the worktree (the environment Loxel was launched from must not apply to every worktree), `UV_PROJECT_ENVIRONMENT` (relative to the worktree) then a `.venv` / `venv` / `env` directory with `pyvenv.cfg` at the worktree root (covers uv, uv workspaces with one root venv, PDM, `python -m venv`), `.pixi/envs/default`, Poetry's `poetry env info --path` and Pipenv's `pipenv --venv` (each only with its lock file at the root and the tool on `PATH`, run with the activated environment hidden, 10 s timeout), the virtual environment of a Python project directory below the root when exactly one has one (a monorepo interim: with several, which applies depends on the file, so none is picked), then `python3` / `python` on the login-shell `PATH` (scanned entry by entry). Each process-spawning lookup runs at most once per resolution or listing. A candidate, including the `PATH` interpreter and the override, counts only if its interpreter is executable (a dangling venv symlink does not) and `isEnvShippedByRepo` finds no part of its environment tracked by git: no file inside the environment directory (when the interpreter is in one; for an environment created at the worktree root only its own `pyvenv.cfg`, `conda-meta` and `site-packages`, since the directory also holds the repository) and neither the interpreter nor its symlink target. Git is asked through the innermost repository that contains each path (so submodules, nested repositories and an environment that is a repository itself count) about its physical path wherever it is (a committed symlink can reach another checkout of the repository, while a `.venv` linked to another worktree's ignored environment is fine), and a git error, or a path that vanished meanwhile, counts as tracked while the path is inside the worktree, so resolution moves on to the next candidate: real environments are never committed, and basedpyright executes the interpreter, so a committed `.venv/bin/python`, or a startup hook in its `site-packages`, would otherwise run repository code when a Python file is opened. The override is held to the same rules. It never runs the interpreter itself and never throws.
- **Trust-check cache.** Every caller of the trust rule (resolver, formatter, terminals, ruff) shares one cache of git answers per worktree and physical path, each valid while the index files it read are unchanged: the worktree's repository's and the innermost one's (`git rev-parse --show-toplevel --absolute-git-dir` gives both, and git replaces the index file on every commit, checkout, pull, `git add` or submodule update). The worktree's repository is looked up once, concurrent questions about one path share one git run, and only clear answers are kept, so a failure is asked again. A hit costs a `realpath` and a `stat` per index file.
- **Shared resolution.** `subscribePythonEnv(wtPath, listener)` keeps a worktree's resolution memoized and watched while anyone is subscribed; subscribing resolves nothing, the first `getPythonEnv(wtPath)` does (an unsubscribed worktree resolves afresh, since nothing would keep a memo current). The memo is replaced when its `watchPythonEnv` watch fires, on `refreshPythonEnv`, on `refreshAllPythonEnvs(changedNames)` when a login-shell variable that resolution reads changed (`PATH`, `VIRTUAL_ENV`, `UV_PROJECT_ENVIRONMENT`, `CONDA_*`, `PYENV_*`, `PIPENV_*`, `POETRY_*`), when the stored override differs from the one it was resolved with, or when `getPythonEnv` finds that the settled environment now fails the trust rule (cheap through the cache above; it is then withdrawn until the new resolution lands). Listeners hear every finished resolution as `{ env, first, changed }`, also when the interpreter stayed the same, since packages may have been installed into it. `getPythonEnvNow` answers with the last finished resolution while a newer one runs. Subscribers are each worktree's resources in [server.ts](../src/server/server.ts), which send `python_env_changed` to the worktree's clients when `changed`, and every basedpyright and ruff session.
- **Choosing an interpreter.** `listPythonEnvs(wtPath)` returns `{ candidates, automatic }`, the candidates without duplicates: the automatic choice, then `.venv` / `venv` / `env` and every `.pixi/envs/*` at the root and in project directories up to three levels deep (directories holding a `pyproject.toml`, `setup.py`, `setup.cfg`, `requirements.txt`, `Pipfile` or `pixi.toml`, found with `git ls-files --cached --others --exclude-standard` so ignored trees are skipped), Poetry's environment, the `PATH` interpreter (the resolution and the listing share their Poetry and `PATH` lookups), and last the stored override when it is none of those, all under the same executable and not-tracked rules. `normalizePythonOverride(wtPath, input)` turns a path the user entered (`~/` allowed, or an environment directory) into an interpreter path, or throws a user-facing error. The override route also requires `--version` to report a Python version. The choice is stored per worktree in `stores.db` under `python-interpreter:<wtPath>` (read back only if absolute) and deleted with the worktree; `onPythonOverrideChange` reports writes. Because the resolver reads it, every Python feature gets the choice without state of its own.
- **Version.** [python-version.ts](../src/server/python-version.ts) runs `<python> --version` (CPython prints it before reading configuration or importing `site`) for interpreters the resolver accepted, in the worktree, so a version-manager shim (pyenv, asdf) reports the version the worktree's `.python-version` selects. It is cached by path, file identity and directory, so a recreated venv or an upgraded interpreter is read again; a failed read is not cached.
- **`watchPythonEnv(wtPath, current, onChange, { env?, projectDirs? })`** sets non-recursive watches for the next change: each candidate environment's (the root ones, `UV_PROJECT_ENVIRONMENT`, and the venv names in the project directories the resolution searched for a sub-project environment) deepest existing ancestor (for the next path segment) or, once it exists, its `bin` / `pyvenv.cfg` / `conda-meta` entries and the contents of its `bin` (conda and Pixi create `bin` before the interpreter), the root `poetry.lock` and `Pipfile.lock`, and `current`'s directory entry, `bin` and `site-packages` (which also covers environments outside the worktree), debounced by 1 s. The shared resolution re-resolves and re-watches on every change, keeping the old watch until the new one is armed and passing a `hasPendingChange` to the new watch's debounce with `nudge()`, so changes made during resolution are neither lost nor re-resolved back to back.
- **basedpyright.** `PythonLspManager` spawns basedpyright with the worktree's own directories removed from `PATH` (`pathOutsideWorktree`), so its fallback `python3` lookup when nothing resolved cannot pick a committed interpreter either. Each session subscribes to the shared resolution and starts it when the session spawns, and answers the `python` section with only `pythonPath` from `getPythonEnvNow`, so the resolver stays the source of truth and a re-resolution in flight does not hold up the first analysis. When nothing resolved it answers a `venvPath` of the worktree with no `venv` instead: that turns off basedpyright's own root `.venv` detection, which would run a committed interpreter, without selecting an environment. After `initialized`, every finished re-resolution calls `notifyConfigurationChanged` (except the first one, which the configuration answer waits for, unless it differs from what was answered), so basedpyright re-pulls and re-resolves imports: this covers `uv sync` creating `.venv`, packages installed later and a changed override. A `pyrightconfig.json` / `[tool.basedpyright]` / `[tool.pyright]` `venv` still wins inside basedpyright over the interpreter Loxel passes, whether detected or chosen. The worktree file watcher skips git-ignored directories such as `.venv`, so this environment watch, not watched files, is what tells basedpyright about installed packages.
- **basedpyright settings.** The `basedpyright` section sets `analysis.typeCheckingMode` to `standard` (basedpyright's default `recommended` flags ordinary code) and repeats `autoSearchPaths: true`, which any `analysis` section otherwise resets. basedpyright ignores these analysis settings when the project has a config file, so the project's rules, and basedpyright's own defaults for anything the file leaves out, win.
- **Ruff.** `RuffLspManager` runs `ruff server` next to basedpyright for lint diagnostics, quick fixes, fix all and organize imports (basedpyright offers no organize-imports code action, so they never compete). `pickRuffBinary` takes the `ruff` next to the resolved interpreter (`dirname(pythonPath)`, the chosen interpreter when there is one), so the project's pinned version and rules apply, else the bundled one from [download-ruff.ts](../scripts/download-ruff.ts) through `resolveBundledBinary`. A ruff in an environment counts only when `isEnvShippedByRepo` (the resolver's trust rule above) clears the whole environment; one outside any environment (a system interpreter's directory, the bundled one) is checked as a single file with `isShippedByRepo`, since its directory can belong to an unrelated repository such as Homebrew's prefix. Either must also report 0.5.3 or newer from `ruff --version`, the first release with a stable `ruff server`. The session subscribes to the shared resolution and picks again after each re-resolution, and once after it starts in case one landed while it spawned; when the path or version differs (but not when only the version of the environment's ruff, still trusted and in place, could not be read), it detaches and closes the socket with `LSP_RESTART_CLOSE_CODE` ([ws-protocol.ts](../src/api/ws-protocol.ts)), on which [lsp-client.ts](../src/lib/lsp-client.ts) reconnects, so the new session spawns the new binary and the client re-initializes and re-opens its documents. Ruff finds its configuration per file, nearest `.ruff.toml` / `ruff.toml` / `pyproject.toml` first, so monorepo subprojects need nothing from Loxel, and it reloads that configuration when a config file changes, which reaches it as watched files. Syntax errors are left to basedpyright (`showSyntaxErrors: false`), and its formatting capabilities are suppressed so format on save stays the only Python formatter (see [Formatting](#formatting)), choosing between ruff and black per project.
- **Override changes.** [server.ts](../src/server/server.ts) subscribes `refreshPythonEnv` to `onPythonOverrideChange`, so the change reaches every subscriber of the worktree's resolution (basedpyright re-pulls, ruff re-picks, the UI gets one `python_env_changed`) without a restart. An interpreter outside any environment is watched by its directory entry so its removal is noticed. Only a worktree's subscribers get the message, so the renderer invalidates its cached interpreters whenever it subscribes to a worktree ([useWsSubscription.ts](../src/hooks/useWsSubscription.ts)).
- **Terminals.** New terminal shells get their worktree's environment from the shared resolution at spawn, override included, and activate it (see [TERMINALS.md](TERMINALS.md#python-environment)).
- **API.** `GET /api/python-env?wt=` returns `{ env, overridePath }` with `env` (the shared resolution) carrying its `version`; `GET /api/python-env/candidates?wt=` returns `{ candidates, automaticPath, overridePath }`; `POST /api/python-env/override` with `{ worktreePath, pythonPath }` validates and stores the choice (`null` clears it) and answers like the first route. `wt` must be a worktree of a registered project, since resolution may run `poetry` there. The renderer side is [python-interpreter.ts](../src/lib/python-interpreter.ts) (labels and the picker, run by the `python.selectInterpreter` action) and [PythonInterpreterStatus.tsx](../src/components/panels/PythonInterpreterStatus.tsx) in the status bar, shown while the active editor's file resolves to Python. Both act on the worktree of the active editor's panel (`params.worktreePath`), not the active worktree, which differs right after a switch; the action falls back to the active worktree when no editor is active.

### Binary resolution and packaging

`resolveBundledBinary(name, devPath?)` checks, in order: a sibling of `process.execPath` (the packaged layout, where `loxel-server` and all servers are copied side by side), then `devPath` if given (downloaded binaries under `build/`) or else `node_modules/.bin/<name>`, then the login-shell `PATH`. TypeScript uses its own resolver: `typescript-lib/tsc` next to the executable when packaged, else the `@typescript/native` Node shim in dev.

`build:server:standalone` in [package.json](../package.json) produces every binary under `build/`, and [electron-builder.yml](../electron-builder.yml) `extraResources` copies them next to `loxel-server` (plus basedpyright's `typeshed-fallback` and the whole `typescript-lib/`, since the native compiler reads its sibling `lib.*.d.ts`). The scripts fall into three kinds:

- Bun-compiled from npm packages: [build-yaml-lsp.ts](../scripts/build-yaml-lsp.ts), [build-basedpyright-lsp.ts](../scripts/build-basedpyright-lsp.ts), [build-astro-ls.ts](../scripts/build-astro-ls.ts) (bundle with `Bun.build`, using plugins where UMD module loading defeats the bundler, then `bun build --compile`; basedpyright's single pre-bundled file is compiled through a wrapper entry that also replaces `v8.getHeapStatistics`, which is too slow under Bun; packages located with [resolve-package.ts](../scripts/resolve-package.ts)).
- Downloaded native binaries with per-platform SHA256 pins verified before writing or extracting: [download-docker-lsp.ts](../scripts/download-docker-lsp.ts), [download-terraform-ls.ts](../scripts/download-terraform-ls.ts), [download-xml-lsp.ts](../scripts/download-xml-lsp.ts) (GraalVM-native LemMinX, no JRE), [download-ruff.ts](../scripts/download-ruff.ts) and [download-tombi.ts](../scripts/download-tombi.ts) (both through [download-release-binary.ts](../scripts/download-release-binary.ts), which extracts only the binary from the release archive; Tombi publishes static musl builds for Linux).
- Copied: [copy-typescript.ts](../scripts/copy-typescript.ts) copies the platform `@typescript/typescript-<platform>-<arch>` `lib/` directory, so TypeScript ships in lockstep with the server.

Packaging and signing of these extra binaries is covered in [ELECTRON.md](ELECTRON.md) and [RELEASE_SIGNING.md](RELEASE_SIGNING.md).

### WebSocket routes

[server.ts](../src/server/server.ts) creates one instance of each manager at startup. In `fetch`, `/ws/yaml-lsp` upgrades with `data: { type: "yaml-lsp" }`. The `worktreeLspTypes` array (`ts-lsp`, `docker-lsp`, `terraform-lsp`, `python-lsp`, `ruff-lsp`, `astro-lsp`, `xml-lsp`, `toml-lsp`) maps `/ws/<type>` to an upgrade with `data: { type, wtPath }`, rejecting requests without `?wt=` with 400. `WorktreeLspType` is derived from the `WsData` union in [server-state.ts](../src/server/server-state.ts), so adding a type there and to the array is what makes a route exist. The `websocket.open` / `close` / `message` handlers dispatch on `ws.data.type` to `createSession` / `destroySession` / `handleMessage`; only string frames are forwarded.

### Lifecycle

- **Spawn** happens when a client opens the socket. **Kill** happens when the socket closes (client disposed its transport), when a newer socket claims the same worktree key, or in `shutdown()`.
- **Worktree switch** is driven by the client: it disposes the old client and transport (see [Client side](#client-side)) and connects with the new `wt`; the close handler kills the old subprocess.

## Client side

- [lsp-client.ts](../src/lib/lsp-client.ts) `createWorktreeLspClient(wsPath, languageId)` returns an idempotent `connect(wtPath)` / `disconnect()` pair around one `WebSocketTransport` and one `MonacoLspClient`. It guards against a double spawn while a connect is in flight and discards a transport that resolves after the path changed. `getConnectedLspClients(wtPath)` lists the clients connected for a worktree at the moment, which is how features that span servers (Go to Symbol, see [EDITOR.md](EDITOR.md#search)) reach them. Both the worktree switch and `disconnect()` call the client's `dispose()` (unregistering providers and closing synced documents) before disposing the transport, so its `textDocument/didClose` notifications still go out over the live socket. Every client passes [live-editor-model.ts](../src/lib/live-editor-model.ts) `isLiveEditorModel` as the `modelFilter`, so only editor tabs' live models (`file://` or `loxel://HEAD/` without a query or fragment, see [URI schemes](#uri-schemes)) are synced to servers; diff, history and compare sides are not, and get no LSP features. Every worktree client also passes `workspaceFileSystem: createLspWorkspaceFiles(wtPath)`, an `onWorkspaceEditFailure` that shows the reason as a toast, and its route as `markerOwner` (`python-lsp`, `ruff-lsp`), so the next client of a route takes over the diagnostics owner of the one before. A socket the server closes with `LSP_RESTART_CLOSE_CODE` (the server is being restarted, see Ruff above) is torn down and connected again; other closes are final.
- [lsp-workspace-files.ts](../src/lib/lsp-workspace-files.ts) `createLspWorkspaceFiles(wtPath)` is the disk side of language-server workspace edits (rename, code actions, `workspace/applyEdit`) for files with no editor model. It reads through `GET /api/file-content` and writes through `POST /api/file-write` without `format` and with a fresh nonce, so an open editor of the file sees an ordinary external change. Creates, renames, moves and deletes go through the files-panel routes and the shared helpers in [file-operations.ts](../src/lib/file-operations.ts), so tabs follow and the files panel's undo history records them; missing parent folders are created first. `stat` enforces the scope for every resource an edit touches except an open file only text-edited, whose model changes like typing wherever the file is (a file operation on it is checked): `file://` or `loxel://HEAD/` paths strictly inside the worktree, not under a dependency, environment, git or nested-worktree folder (`PROTECTED_SEGMENTS`: `node_modules`, `site-packages`, `.venv`, `.pixi`, `.git`, `.worktrees` and the like), checked lexically and again on the real path (`GET /api/path-info`, the nearest existing folder for a path that does not exist yet), so a symlink cannot lead an edit outside. A file that does not read back as UTF-8 is refused, since the content route decodes it lossily. A create route that picked a free name because the path appeared meanwhile has its stray file removed. A move to another folder under a new name is one `moveFile` call, so an open tab with unsaved edits follows it in one step. Text writes to unopened files are not on any undo stack. The YAML client has no worktree and no file system, so its edits are limited to open models.
- The per-language modules ([ts-lsp-client.ts](../src/lib/ts-lsp-client.ts), [python-lsp-client.ts](../src/lib/python-lsp-client.ts), [ruff-lsp-client.ts](../src/lib/ruff-lsp-client.ts), [astro-lsp-client.ts](../src/lib/astro-lsp-client.ts), [docker-lsp-client.ts](../src/lib/docker-lsp-client.ts), [terraform-lsp-client.ts](../src/lib/terraform-lsp-client.ts), [xml-lsp-client.ts](../src/lib/xml-lsp-client.ts), [toml-lsp-client.ts](../src/lib/toml-lsp-client.ts)) only bind a route and Monaco language IDs. TypeScript binds `typescript`, `javascript`, `tsx`, `jsx`, `json`, `jsonc`; Docker binds `dockerfile` and `dockerbake`. Python models get two clients, basedpyright and ruff, each with its own lazy connector. [yaml-lsp-client.ts](../src/lib/yaml-lsp-client.ts) is separate: one connection per renderer, no `wt`, no disconnect, with the same `modelFilter`.
- [monaco-env.ts](../src/lib/monaco-env.ts) is the single wiring point, imported for its side effects. It disables all of Monaco's built-in TS/JS features (no TS worker; the JSON, CSS and HTML workers stay), registers the language IDs Monaco does not ship (`terraform`, `astro`, `tsx`, `jsx`, `dockerbake`, `toml`), and connects the servers. YAML connects at load. TypeScript is eager: it connects to the active worktree and reconnects whenever `activeWorktreePath` changes. Every other server goes through `createLazyLspConnector`, which counts live models (`isLiveEditorModel`) of its languages in the active worktree (plus those of files outside every project, served by the active worktree's server) and connects on the first one, disconnecting at zero. Diff, history and compare models are not counted. It also registers the editor opener from [editor-opener.ts](../src/lib/editor-opener.ts), which turns go-to-definition results and document or hover links to an editor file (`editorFilePath`, see [URI schemes](#uri-schemes)) in another model into `dispatchOpenFile`, which opens files outside every project (stdlib, installed packages) as external files; a target in the source's own model is left to Monaco to reveal in place.
- [packages/monaco-lsp-client](../../monaco-lsp-client/README.md) is a fork of `@vscode/monaco-lsp-client` consumed as TypeScript source. Its main local changes for Loxel are the `languageId` option (`TextDocumentSynchronizer` only syncs models whose language is in the set, which is what lets several servers coexist on one Monaco instance) and the `modelFilter` option above; its README lists the other local changes, including how `workspace/executeCommand` and workspace edits (rename, code actions, `workspace/applyEdit`) are handled. Diagnostics from the server become Monaco markers under the client's `markerOwner` (the route, see above), so servers sharing a model keep separate markers, and a disposed client removes its own.
- [ws-shim.ts](../src/lib/ws-shim.ts) is aliased to `ws` in [vite.config.ts](../vite.config.ts) because `@hediet/json-rpc-websocket` imports the Node `ws` package; the browser uses the native `WebSocket`.

## URI schemes

[CodeEditorPanel.tsx](../src/components/code-editor/CodeEditorPanel.tsx) picks the model URI per Monaco language. `useFileScheme` (yaml, json, dockerfile, dockerbake, terraform, astro, xml, python, toml) gives `file://<abs path>`, which those servers need for schema matching, workspace indexing and import resolution. Every other language gets `loxel://HEAD/<abs path>`. Git diff views ([GitSideBySideDiffView.tsx](../src/components/diff-viewer/GitSideBySideDiffView.tsx)) use `loxel://<ref or HEAD>/<repo-relative path>#<side>`, and compare panels ([CompareFilesPanel.tsx](../src/components/compare/CompareFilesPanel.tsx)) `loxel://compare/<abs path>#<panel id>-<side>`; both render through [diff/EditorPanel.tsx](../src/components/diff/EditorPanel.tsx).

Only the TypeScript manager translates (`toServerUris` / `toClientUris` in [ts-lsp-manager.ts](../src/server/ts-lsp-manager.ts)): client-to-server it replaces `loxel://head/` (case-insensitive) with `file:///`; server-to-client it replaces `file:///` with `loxel://HEAD/` except for `.json` / `.jsonc` paths, whose editor models use `file://`. No other manager rewrites URIs, so every other server sees and returns the live models' own `file://` URIs. monaco-lsp-client sends document URIs percent-encoded (Monaco's `Uri.toString()`), the way servers write them, and matches the URIs servers send back to models after re-encoding them the same way, since servers differ in what they escape; the server side builds `rootUri`, `workspaceFolders` and watched-file URIs with `fileUri`, which encodes exactly like Monaco, so they also match document URIs as strings. Paths with spaces, `#`, `%` or non-ASCII characters therefore reach every server intact. One function decides which URIs are editor files: `editorFilePath` in [live-editor-model.ts](../src/lib/live-editor-model.ts) accepts `file:` and `loxel://HEAD` (any casing) with no query or fragment and returns the path. `isLiveEditorModel` (the clients' `modelFilter` and the lazy connector's check), the editor opener, Go to Symbol and the workspace-edit file system all use it.

## Diagnostics

There are two TypeScript diagnostic paths:

- **Live, per file.** The TS LSP publishes diagnostics, which `monaco-lsp-client` turns into markers under the client's owner.
- **Project-wide snapshot.** `GET /api/diagnostics?wt=&ref=&worktree=` ([routes.ts](../src/server/routes.ts) `handleDiagnostics`) calls `getDiagnostics` in [diagnostics.ts](../src/server/diagnostics.ts), which runs `tsc --noEmit --pretty false` (30 s timeout) and parses lines into `TypeScriptDiagnostic` from [diagnostics-model.ts](../src/api/diagnostics-model.ts) (repo-relative file, 1-based line and column, code, severity, `node_modules` excluded). The code editor and the diff view apply these as `typescript` markers, and only request the snapshot for files `hasTypeScriptDiagnostics` in [typescript-files.ts](../src/lib/typescript-files.ts) accepts: TS/JS sources (`TS_SOURCE_EXTENSIONS`, which the TS manager's routing also extends) and `tsconfig*.json`, where `tsc` reports config errors.

The server skips `tsc` and returns no diagnostics when the worktree, or the `ref`'s tree, has no root `tsconfig.json`. For the working tree (no `ref`) `tsc` runs directly in the worktree and nothing is cached on the server. For a `ref` the server validates it against `REF_PATTERN`, deduplicates concurrent requests, checks the tree for `tsconfig.json` with `git ls-tree` (caching an empty result when it is missing), creates a detached temporary worktree named `${INTERNAL_WORKTREE_PREFIX}diag-<sha8>` in a `mktemp -d` directory, symlinks `node_modules` from the source checkout, runs `tsc`, caches the result by ref in memory for the server's lifetime, and force-removes the worktree. `INTERNAL_WORKTREE_PREFIX` ([worktree-utils.ts](../src/server/worktree-utils.ts)) hides these worktrees from worktree lists, and `pruneOrphanedTempWorktrees` in `server.ts` force-removes all of them when a project is initialized, to clean up after crashes.

On the client the snapshot is a TanStack query under `queryKeys.diagnostics(...)`.

## Formatting

Formatting runs on the server as part of `POST /api/file-write` when the request carries `format: true` and valid `formattingSettings` ([FormattingSettings](../src/lib/formatting-model.ts)). Editors set `saveOptionsRef` (explicit save) and `autoSaveOptionsRef` (auto-save, only when `formatOnAutoSave`) through [use-disk-synced-content.ts](../src/hooks/use-disk-synced-content.ts); [save-editor-content.ts](../src/lib/save-editor-content.ts) sends them, and the response's formatted `content` is merged back into the editor as a programmatic "format-echo" edit (see [EDITOR.md](EDITOR.md#disk-synced-content) for the save state machine). When the save went out unformatted for a reason the user can fix, the response also carries a `formatNotice`, which the client shows as a toast once per distinct message per session. Only files inside the worktree's own tree are formatted; Others folders, drafts and external files are written as-is.

[format-service.ts](../src/server/format-service.ts) `FormatService.format()` returns a `FormatResult` whose `content` is `null` (write unformatted) when disabled, over 1 MB, without an extension, with no match, or when the formatter fails. Only a binary that is missing or cannot start (`Bun.spawn` throws: `ENOENT` for a missing binary or interpreter, which `Bun.which` tells apart, any other code such as `EACCES` / `ENOEXEC` for a file that is not runnable) and a timeout set its `notice`; a non-zero exit or empty output, typically a syntax error the language server already flags, is only logged so it does not repeat on every save. Resolution order:

1. **Manual overrides** from settings, first entry whose comma-separated extension list contains the file's extension. Always run as a command.
2. **Auto-detection** (if `autoDetect`), by config files at the worktree root, evaluated in `DETECTION_RULES` order, first formatter claiming the extension wins: prettier (config files or a `prettier` key in `package.json`), oxfmt (`.oxfmtrc.*` or an `oxfmt` dependency), rustfmt, clang-format, deno. Prettier and oxfmt share `SHARED_FORMAT_EXTENSIONS`; prettier adds `svelte` and `astro`, oxfmt adds `toml`. Because prettier is first, a project with both uses prettier for every shared extension. Detection is cached per worktree, keyed by a fingerprint of config-file sizes and mtimes.
3. **Python** (`.py`, `.pyi`, if `autoDetect`) is resolved per file instead, by `detectPythonFormatter` in [python-formatter.ts](../src/server/python-formatter.ts), walking from the file's directory up to the worktree root so monorepo subprojects are found. Because a ruff config or dependency often exists for the linter alone while black only formats, the nearest directory with a formatting signal decides: a ruff config (`.ruff.toml` / `ruff.toml` or `[tool.ruff]`) with a `format` table selects ruff, a `[tool.black]` table or black dependency selects black. A ruff config without `format`, or a ruff dependency, selects ruff only when no such signal exists up to the root. Dependencies are read from `pyproject.toml` (PEP 621 dependencies and extras, PEP 735 groups, uv, Poetry and PDM dev dependencies, Hatch environments). A bare `pyproject.toml` formats nothing, matching the opt-in signal prettier and oxfmt need. ruff runs as `ruff format --force-exclude --stdin-filename {file}` (without `--force-exclude` ruff ignores its `exclude` settings for stdin) and black as `black --quiet --stdin-filename {file} -`; both resolve their own nested config and infer stub style from the file name. This walk is uncached: a few `existsSync` calls and small TOML parses per save. `getDetectedFormatters` lists the Python formatter detected at the worktree root.

Each rule has a `BackendMode` from [formatter-backends.ts](../src/server/formatter-backends.ts). `command` spawns the tool per request with content on stdin, `{file}` / `{ext}` substituted, the worktree's `node_modules/.bin` prepended to `PATH` (for Python files run by command name, `findVenvBin` in [python-formatter.ts](../src/server/python-formatter.ts) prepends the environment directory holding that command ahead of it, so a project-pinned ruff or black beats a global one: the nearest sub-project `.venv` / `venv` / `env` with a `pyvenv.cfg` between the file's directory and the worktree root, else the worktree's shared resolution (`dirname(pythonPath)`, when it is an environment), else a venv at the root; environments are skipped by the trust rule and its cache, `isEnvShippedByRepo` in [python-env.ts](../src/server/python-env.ts)), and a 5 s timeout. The two persistent backends are cached per `(worktree, command)`, restarted if dead, and on a `null` result destroyed and replaced by command mode for that request:

- [oxfmt-lsp-backend.ts](../src/server/oxfmt-lsp-backend.ts) keeps an `oxfmt --lsp` process (worktree `node_modules/.bin` first, then `PATH`) and formats via `didOpen` / `textDocument/formatting` / `didClose`, applying the returned edits.
- [prettier-lib-backend.ts](../src/server/prettier-lib-backend.ts) dynamically imports the worktree's own `node_modules/prettier` and calls `resolveConfig` (with `editorconfig: true`, as the prettier CLI does, so a project's `.editorconfig` shapes the output like it shapes the editor, and `useCache: false`, since nothing would clear prettier's config cache when a config file changes) + `format` in-process.

`invalidateCache(wtPath)` (called from worktree teardown) drops detection and destroys backends; `destroy()` runs at shutdown. `GET /api/detected-formatters?wt=` exposes detection to the settings UI.

## Schemas and JSON validation

- [schema-service.ts](../src/server/schema-service.ts) resolves a schema from an HTTP(S) URL (1 h TTL, 5 MB cap, 10 s timeout) or a local path (relative to a base directory, revalidated by mtime). Other URL schemes are rejected.
- `POST /api/schemas/sync` receives the enabled schema settings and routes each glob by `classifySchemaGlob` in [schema-glob.ts](../src/lib/schema-glob.ts) (also behind the Languages column of Settings > Schemas): a glob ending in `.json` / `.jsonc`, `.yml` / `.yaml` or `.toml` (brace alternatives included) goes to those languages, any other glob (`**/*`, `**/Pipfile`) to all three. JSON schemas are resolved inline through the schema service and returned for Monaco. YAML and TOML get a `url → globs` map (absolute local paths as `file://` URLs) pushed to `YamlLspManager.updateSchemas` and `TomlLspManager.updateSchemas`; those servers fetch the schemas themselves, since schemas such as SchemaStore's `pyproject.json` `$ref` siblings by relative URL. `GET /api/schemas/resolve` resolves a single schema.
- [schema-sync.ts](../src/lib/schema-sync.ts) calls the sync endpoint after the settings store hydrates and when settings are saved, coalescing overlapping calls. `selectEffectiveSchemas` lists user mappings before built-in ones: JSON and YAML combine every matching schema, but Tombi applies the first one, so a user mapping overrides a built-in for the same TOML file.
- [json-schema-registry.ts](../src/lib/json-schema-registry.ts) owns the single global `monaco.json.jsonDefaults` schema list (Monaco replaces it wholesale), merging configured glob schemas with per-file `$schema` schemas. `CodeEditorPanel` detects `$schema` in JSON models (debounced), resolves it through the server, and registers it under the URL Monaco's JSON worker would compute relative to the file's `file://` URI; this is one reason JSON is in `useFileScheme`.
- Monaco's JSON diagnostics are permissive (comments and trailing commas ignored) so JSONC files work. [json-strict-validator.ts](../src/lib/json-strict-validator.ts) re-parses files resolved as strict `json` with `jsonc-parser` and adds `json-strict` markers for comments and trailing commas.

### TOML (Tombi)

[toml-lsp-manager.ts](../src/server/toml-lsp-manager.ts) runs [Tombi](https://github.com/tombi-toml/tombi) per worktree. Tombi was chosen over Taplo (Even Better TOML's server) because it is actively released, supports current JSON Schema drafts, and serves pull diagnostics, code actions, go-to-definition and inlay hints besides completion, hover, symbols and folding; Taplo has not had a release since 0.10.0 (May 2025) and takes associations only as regular expressions.

- **Associations.** The schema map reaches Tombi as editor configuration, a `workspace/didChangeConfiguration` with a `tombi` section (`tombiSettings`), sent on `initialized` and on every `updateSchemas()`. Each Loxel glob becomes Tombi patterns (`toTombiPatterns`): brace alternatives are expanded, since Tombi's glob matcher has none, and a plain name (`pyproject.toml`, `.cargo/config.toml`) gets `**/` so it matches at any depth, as Monaco's JSON `fileMatch` does. Tombi matches against the canonical absolute path and its `*` also matches `/`, so a pattern with wildcards is anchored at the session's worktree instead (`config/*.toml` becomes `<worktree>/**/config/*.toml`), keeping it from matching through an ancestor directory; within the worktree a TOML glob's `*` still spans directories, which JSON's does not. Editor configuration replaces the previous one wholesale, so updates and removals apply live, unlike `tombi/associateSchema`, which only appends.
- **Catalogs and strict mode off.** The same configuration sets `schema.catalog.paths = []`, so neither SchemaStore's catalog nor Tombi's embedded one associates schemas: the Schemas settings are the only automatic associations, and disabling a built-in removes its schema. Tombi may still fetch SchemaStore's catalog once while it starts (it loads its default configuration before this one arrives, and caches the catalog for a day); its associations go unused. `schema.strict = false` keeps JSON Schema semantics (Tombi's strict mode treats a missing `additionalProperties` as `false`), so a schema validates TOML as it validates JSON and YAML. `#:schema` directives in a file take precedence over the configuration.
- **Tombi's own configuration wins.** Tombi uses editor configuration only for files that no Tombi config governs: a `tombi.toml` / `.tombi.toml` / `.config/tombi.toml` or a `pyproject.toml` with `[tool.tombi]` in the file's directory or above, or the user's `~/.config/tombi/config.toml`. Those projects keep the behavior of the `tombi` CLI, catalogs included.
- **Diagnostics refresh.** Tombi caches each open document's diagnostics per version, and a configuration change does not clear the cache. After each push the manager therefore sends a `tombi/associateSchema` with no file patterns (it matches nothing), which resets the cache and makes Tombi send `workspace/diagnostic/refresh`, so Monaco pulls fresh diagnostics without an edit. Tombi takes that association only after the configuration is in place (it holds the association list's read lock until then), and keeps every association, so each push leaves one inert entry for the session's lifetime.
- **Flags.** Semantic tokens are off (the TextMate grammar highlights TOML), formatting is suppressed because format on save owns it and Tombi's formatter reorders keys by the schema's `x-tombi-table-keys-order`, and watched files are forwarded so Tombi reloads changed config files and local schemas.

## Highlighting and language resolution

- [highlighter.ts](../src/lib/highlighter.ts) holds a singleton Shiki highlighter (themes `loxel-dark` and `github-dark`, a fixed `BUNDLED_LANGUAGES` list), the `FILENAME_TO_LANG` and `EXT_TO_LANG` tables, `detectLanguage()` (case-insensitive filename, `.d.ts`, `.env*`, then extension) and `highlightCode()` for HTML token output. Language IDs here are Shiki IDs; `toMonacoLanguage()` in [monaco-theme.ts](../src/lib/monaco-theme.ts) maps the few that differ (for example `jsonc` → `json`, `dotenv` → `ini`).
- `monaco-env.ts` passes the highlighter to `shikiToMonaco`, which attaches a TextMate tokenizer to every Monaco-registered language ID that Shiki has loaded, replacing Monarch. Languages Monaco does not ship (`tsx`, `jsx`, `astro`, `terraform`, `toml`) are registered there first so they get one. Languages Shiki does not know get Monarch tokenizers: [hcl-monarch.ts](../src/lib/hcl-monarch.ts) for `dockerbake` and [pip-requirements-monarch.ts](../src/lib/pip-requirements-monarch.ts) for `pip-requirements`.
- Editing behavior comes from Monaco language configurations. Monaco registers its built-in ones lazily when a language is first encountered, and registrations merge field by field with the last one winning, so [python-language-config.ts](../src/lib/python-language-config.ts) re-registers Monaco's Python `conf` with extra auto-closing pairs and `onEnterRules` (triple quotes, dedent after `return`/`pass`/`break`/`continue`/`raise`) only after the built-in registration has run; `python-language-config.test.ts` checks that order and the resulting editing behavior, so a Monaco upgrade that changes either fails there. It also adds a keydown hook, for Python and TOML (whose configuration in `monaco-env.ts` also auto-closes triple quotes), that steps over the rest of a triple-quote delimiter, since Monaco overtypes only the first character of a multi-character auto-closed pair.
- [resolve-language.ts](../src/lib/resolve-language.ts) `resolveLanguage(path, associations, content)` is what the code editor uses: enabled file associations first (first glob match wins, matched with `dot: true` so globs cross dot directories; user entries precede built-ins in `selectEffectiveFileAssociations`), then `detectLanguage`, then content sniffing (shebang, XML prolog). The built-in associations in [settings-store.ts](../src/store/settings-store.ts) are generated from `FILENAME_TO_LANG` / `EXT_TO_LANG` plus glob overrides that exact names cannot express (`tsconfig*.json` → `jsonc`, `*.docker-bake.hcl` → `dockerbake`, `requirements*.txt` → `pip-requirements`).
- [textmate-inspector.ts](../src/lib/textmate-inspector.ts) backs the editor's token-scope inspector using `codeToTokensBase` with explanations.
- [file-icons.tsx](../src/lib/file-icons.tsx) has its own filename, filename-pattern, compound-extension and extension maps (JetBrains icon theme) and is independent of language resolution.
