# Language Servers and Language Intelligence

How Loxel provides language features: language-server subprocesses bridged to Monaco over WebSockets, with the watched files, pulled configuration and on-disk workspace edits the bridge supplies, formatting, JSON/YAML/TOML schemas, syntax highlighting and editing behavior. What is specific to one language lives in [languages/](languages/), one file per language that has real detail: [Python](languages/python.md) (environment, interpreter choice, basedpyright, ruff, mypy), [TypeScript](languages/typescript.md) (its manager, diagnostics), [JavaScript](languages/javascript.md) (tool config files; shares the TypeScript manager) and [TOML](languages/toml.md) (Tombi). A new language adds its own file there and edits no index.

To add a new language server, follow the [add-language-server skill](../../../.agents/skills/add-language-server/SKILL.md) and its [per-server quirks reference](../../../.agents/skills/add-language-server/references/existing-integrations.md). This doc is the architecture that skill assumes; it does not repeat the checklist. For the end-user view see the site's [Language Intelligence](../../site/src/content/docs/language-intelligence.md) page.

## Data flow

```
Monaco model ──(MonacoLspClient, JSON-RPC over WS)──▶ /ws/<lang>-lsp[?wt=<path>]
   ▲                                                       │ server.ts routes by ws.data.type
   │                                                       ▼
   └──────── providers / markers ◀── WS ◀── <Lang>LspManager (StdioLspManager subclass)
                                                           │ Content-Length framed stdio
                                                           ▼
                                                 language-server subprocess (cwd = worktree)
```

The server is a thin proxy. It owns process lifetime, framing and a small set of message rewrites (initialize parameters, URI translation, capability scrubbing). All LSP feature logic on the client lives in the `monaco-lsp-client` fork, which registers Monaco providers from the server's advertised capabilities.

## Server side

### `StdioLspManager` base class

[stdio-lsp-manager.ts](../src/server/stdio-lsp-manager.ts) bridges one WebSocket to one subprocess. Public API: `handleMessage(ws, data)`, `detach(ws)` (kill and forget), `destroy()` (kill all, used on server shutdown). Subclasses add their own entry points (`createSession(ws, wtPath)` / `destroySession(ws)` for worktree-scoped managers, `attach(ws)` for YAML) that call the protected `startSession(ws, context)`. `WorktreeLspManager` supplies the one-server-per-worktree plumbing (those entry points, a `WtLspSession`, `wtPath` as the session key, workspace and `cwd`); the managers whose session holds more state (Python, ruff) extend `StdioLspManager` directly.

- **Session model.** `sessions: Map<ServerWebSocket, TSession>`. `BaseLspSession` holds the `ws`, the `proc`, the stdout reassembly buffer and `documentContents` (used only for full-text sync). `WtLspSession` adds `wtPath`.
- **Dedup by key.** `getSessionKey(context)` returns a key (worktree managers return `wtPath`; YAML returns `null`). `startSession` keeps at most one live session per key: if another WebSocket already owns the key, that session is detached and its socket closed with `LSP_REPLACED_CLOSE_CODE` (4000, "Replaced by newer connection"). A server that cannot start (no binary, or `Bun.spawn` throwing because it cannot be executed) releases its key and closes the socket with `LSP_START_FAILED_CLOSE_CODE` (4001), so the client's `initialize` fails instead of hanging. `serverFailureReason(context)` can replace the generic text of that close and of the exit close below, which is cut to the 123 bytes a close frame carries. The close codes live in [ws-protocol.ts](../src/api/ws-protocol.ts); see [Lifecycle](#lifecycle) for what the client does with each.
- **Spawn.** `Bun.spawn([resolveBinary(context), ...spawnArgs(context)])` with piped stdio, `cwd` from `spawnOptions(context)` and the environment from `buildSpawnEnv()` in [shell-env.ts](../src/server/shell-env.ts) (the login-shell environment, see [TERMINALS.md](TERMINALS.md#environment), so servers that run user tools such as basedpyright's interpreter or terraform-ls's `terraform` find them when Loxel was launched from Finder) with `NODE_OPTIONS` cleared. Server startup waits up to `LOGIN_SHELL_ENV_WAIT_MS` for that environment before serving, so the first sessions do not race it. A binary `resolveBundledBinary` cannot find triggers a login-shell refresh, so one installed meanwhile is found on the next start. Default args are `["--stdio"]`; `spawnArgs(context)` gets the session context, for arguments per worktree. `resolveBinary` may return a promise (ruff looks in the worktree's environment); the client's frames that arrive meanwhile, starting with `initialize`, are held and replayed once the process is spawned, and dropped if the socket closes or a newer one claims the key first.
- **Framing.** `writeToStdin` adds the `Content-Length` header and flushes the `FileSink` per message. `drainMessages` parses frames out of stdout and hands each body to `handleServerFrame`.
- **`initialize` rewriting.** When `getSessionWorkspace(session)` returns a path, missing `rootUri` / `rootPath` / `workspaceFolders` are filled in (client values win), with `file://` URIs percent-encoded the way Monaco writes them (`fileUri` in [lsp-file-uri.ts](../src/server/lsp-file-uri.ts)). `getInitializationOptions(session)` is merged one level deep into the client's `initializationOptions` (client values win). Config that the server only accepts by push goes in `onClientInitialized`, which runs after the client's `initialized` notification is forwarded and typically sends `workspace/didChangeConfiguration`.
- **Workspace folders.** monaco-lsp-client does not implement `workspace/workspaceFolders` either, so when `getSessionWorkspace(session)` returns a path the base answers that request itself with the session's single folder, the same one it injects into `initialize` (Tombi asks for it).
- **Pulled configuration.** monaco-lsp-client does not implement `workspace/configuration`, so a subclass that defines `workspaceConfiguration(session, section, scopeUri)` gets the `workspace.configuration` capability injected into `initialize`, and the base answers the server's requests itself, one item at a time (asynchronously, dropped if the session is gone); `scopeUri` is the item's resource, for a server that asks per file. `notifyConfigurationChanged(session)` sends `workspace/didChangeConfiguration` with `settings: null`, which makes such a server pull again.
- **Watched files.** monaco-lsp-client cannot watch files, so without help a server never hears about changes to files that are not open: new modules, `git checkout`, an agent's edits, `pyrightconfig.json` / `tsconfig.json`. A subclass that sets `forwardWatchedFiles` (basedpyright, ruff, TypeScript, Tombi) gets the `workspace.didChangeWatchedFiles` capability injected into `initialize`, without `relativePatternSupport`, which keeps servers from asking for most directories outside the worktree. The base takes the server's watcher registrations out of `client/registerCapability` / `client/unregisterCapability` before `handleServerFrame`, so subclasses need no wiring, and keeps them in the session's `WatchedFilesForwarder` from [lsp-watched-files.ts](../src/server/lsp-watched-files.ts). `server.ts` hands each change batch of the worktree's `ProjectFilesService` (`onPathsChanged`) to every worktree manager's `notifyWatchedFilesChanged(wtPath, paths)`. The forwarder keeps the paths some watcher wants, holds changes that arrive before the server has registered its watchers (a server reads the disk before it registers; tsc only once its project has loaded), and sends them debounced as one `workspace/didChangeWatchedFiles` with `file://` URIs. The file watcher does not say whether a path is new, so the forwarder tells created from changed and deleted with `stat`, and reports a path it judges created (atomic saves, checkouts, reinstalled packages) as changed, then created: basedpyright only re-resolves imports for created files, while TypeScript ignores a creation of a file it has already loaded and keeps its old contents unless the change comes first. Only changes inside the session's worktree are reported, outside its git-ignored directories except for dependency installs and paths a manager asks for (below), and only while a client is subscribed to that worktree (when its file watcher runs). Glob matching, limits and timings are documented in the module. A server that registers no watchers and leaves choosing the files to its client gets them from the manager's `watchedFileGlobs`, worktree-relative globs that add to anything the server registers and apply once the client's `initialized` has passed, with earlier changes held until then; a change one of them takes is not held back for later registrations. `forwardWatchedFiles` also accepts a `RelativePattern` registration, with a URI or a workspace folder as its base, whether or not the capability is advertised, since some servers send one regardless.
- **Dependency installs.** TypeScript registers `<dir>/node_modules/**/*` for each project and watches nothing itself, so without help a package installed, upgraded or removed stays unresolved until the server restarts. The worktree watcher already receives the events inside git-ignored directories; `ProjectFilesService` drops them in its filter and hands each to `onIgnoredPathChanged`, and the worktree's `NodeModulesChanges` from [node-modules-changes.ts](../src/server/node-modules-changes.ts) turns those under `node_modules` into paths for the same `notifyWatchedFilesChanged`, so nothing watches `node_modules` separately. Each package a path lies in (top-level or scoped, at every `node_modules` level, so a monorepo's per-package `node_modules` count) is reported as its directory and its `package.json`, which makes TypeScript resolve it again, plus the changed file itself when it is a type file (`.ts`, `.d.ts`, `.tsx` and their variants, `.json`), because TypeScript reloads a file it already read only when that file is reported. Dot entries are skipped: pnpm's `.pnpm` store is content-addressed and an upgrade relinks the top-level symlink, and `.bin`, caches, install markers and npm's staging directories carry nothing a server needs. A package directory moved into place whole (bun) brings no events for its files, so a package whose own entry changed with nothing reported inside it has its type files listed from disk, unless it is a symlink. Changes go out once `node_modules` has been quiet for a second (at most ten seconds after the first), since a package reported halfway through an install has to be reported again. This needs no package-manager markers or lockfiles and works the same for npm, pnpm, yarn and bun.
- **Ignored paths a manager asks for.** Build output a server reads (`build/compile_commands.json`, `obj/project.assets.json`) also lies in git-ignored directories. `server.ts` hands each `onIgnoredPathChanged` event to every worktree manager's `notifyIgnoredPathChanged(wtPath, relPath)`, and a path one of the session's `watchedIgnoredGlobs` matches goes through `notifyWatchedFilesChanged` like any other change, so a manager that has to act on the file itself can override that. These globs are also ordinary declared watchers, since a directory is not known to be ignored until git has seen it. Apart from dependency installs, nothing else inside ignored directories reaches a server, however broad its registered watchers.
- **`didSaveOnFileChange`.** monaco-lsp-client never sends `textDocument/didSave`, since saving goes through the file routes. With this flag the base tracks the session's open documents and sends the notification, without text, for each one a `notifyWatchedFilesChanged` batch names, whoever changed the file. The client capability stays `didSave: false`: servers that opt in take the notification regardless, and rust-analyzer would otherwise register it dynamically with the client.
- **Session teardown.** `onSessionClosed(session)` fires when a session is detached, destroyed or its process exits (possibly more than once) for releasing per-session resources such as watchers.
- **`disableSemanticTokens`.** Strips the semantic-tokens client capability from `initialize`, deletes `semanticTokensProvider` from the initialize response, and filters semantic-token entries out of `client/registerCapability`.
- **`disableCompletionSnippets`.** Strips `snippetSupport` from `initialize`, for a server whose snippet completions are not valid snippet syntax, so a server that honors it answers in plain text. Monaco parses what a server marks as a snippet, so unescaped text such as `$HOME` in one would be expanded on insertion.
- **`suppressedFeatures`.** LSP features (formatting, range formatting, semantic tokens) Monaco must not get from a server: their capability is deleted from the initialize response and their `client/registerCapability` entries are filtered out the same way, since servers differ in which way they advertise them (ruff before 0.17 statically, later dynamically); when no registration is left the base answers the server directly.
- **`requiresFullTextSync`.** The base tracks text from `didOpen`, applies incremental `didChange` ranges locally (clamped), and forwards a single full-text change. A `didChange` for an untracked URI is forwarded unchanged with a warning.
- **Errors.** JSON-RPC error responses from the server are logged at info level before forwarding.
- **stderr.** Each session reads stderr line by line through a token bucket from [stderr-throttle.ts](../src/server/stderr-throttle.ts), which logs a "suppressed N" summary in place of the excess, so a chatty server cannot flood the shared log ring buffer. The most recent lines are kept regardless and logged as a warning if the process exits non-zero.

### Binary resolution and packaging

`resolveBundledBinary(name, devPath?)` checks, in order: a sibling of `process.execPath` (the packaged layout, where `loxel-server` and all servers are copied side by side), then `devPath` if given (downloaded or source-built binaries under `build/`) or else `node_modules/.bin/<name>`, then the login-shell `PATH`. TypeScript uses its own resolver: `typescript-lib/tsc` next to the executable when packaged, else the `@typescript/native` Node shim in dev.

Each binary is one manifest in [scripts/language-servers/](../scripts/language-servers/), naming the script that produces it and its resources under `build/`. [language-server-binaries.ts](../scripts/language-server-binaries.ts) reads them all: `build` (chained from `build:server:standalone` in [package.json](../package.json), or `pnpm run build:language-servers <manifest>` for one) runs the scripts and stages every resource by its base name in `build/language-servers/`, and `sign` ad-hoc signs the stage. [electron-builder.yml](../electron-builder.yml) `extraResources` and the update archive in [release-loxel.yml](../../../.github/workflows/release-loxel.yml) copy that directory as a whole, so its contents land next to `loxel-server`, including basedpyright's `typeshed-fallback` and the whole `typescript-lib/`, since the native compiler reads its sibling `lib.*.d.ts`. A new binary is a new manifest and script, with no list to edit. The scripts fall into four kinds:

- Bun-compiled from npm packages: [build-yaml-lsp.ts](../scripts/build-yaml-lsp.ts), [build-basedpyright-lsp.ts](../scripts/build-basedpyright-lsp.ts), [build-astro-ls.ts](../scripts/build-astro-ls.ts) (bundle with `Bun.build`, using plugins where UMD module loading defeats the bundler, then `bun build --compile`; basedpyright's single pre-bundled file is compiled through a wrapper entry that also replaces `v8.getHeapStatistics`, which is too slow under Bun; packages located with [resolve-package.ts](../scripts/resolve-package.ts)).
- Built from source: [build-docker-lsp.ts](../scripts/build-docker-lsp.ts) compiles docker-language-server with a Go toolchain pinned by SHA256, downloaded into `build/`, so builds need no Go install. Docker's release binaries embed telemetry and BugSnag keys and use them whatever the server is configured to do; built without the keys, those clients have nowhere to send anything. After changing the pin or the manager, run [audit-docker-lsp.ts](../scripts/network-audit/audit-docker-lsp.ts), which drives the server through the built `loxel-server` under a logger that records and blocks every socket attempt ([connect-log.c](../scripts/network-audit/connect-log.c)) and fails on any outbound attempt. [build-gopls.ts](../scripts/build-gopls.ts) uses the same toolchain, from [go-toolchain.ts](../scripts/go-toolchain.ts), since gopls publishes no release binaries (see [Go](languages/go.md#binary)).
- Downloaded native binaries with per-platform SHA256 pins verified before writing or extracting: [download-terraform-ls.ts](../scripts/download-terraform-ls.ts), [download-xml-lsp.ts](../scripts/download-xml-lsp.ts) (GraalVM-native LemMinX, no JRE), [download-ruff.ts](../scripts/download-ruff.ts) and [download-tombi.ts](../scripts/download-tombi.ts) (both through [download-release-binary.ts](../scripts/download-release-binary.ts), which extracts only the binary from the release archive; Tombi publishes static musl builds for Linux).
- Copied: [copy-typescript.ts](../scripts/copy-typescript.ts) copies the platform `@typescript/typescript-<platform>-<arch>` `lib/` directory, so TypeScript ships in lockstep with the server.

Packaging and signing of these extra binaries is covered in [ELECTRON.md](ELECTRON.md) and [RELEASE_SIGNING.md](RELEASE_SIGNING.md).

### WebSocket routes

[language-servers.ts](../src/server/language-servers.ts) is the single list of worktree-scoped managers: adding a manager there is what makes a route exist. A manager's `name` is its route and log category: [server.ts](../src/server/server.ts) maps `/ws/<name>` to an upgrade with `data: { type, wtPath, manager }`, rejecting requests without `?wt=` with 400, and the `websocket.open` / `close` / `message` handlers call the socket's `manager` (`createSession` / `destroySession` / `handleMessage`); only string frames are forwarded. Shutdown and watched-file changes go over the same list. YAML is global and stays explicit: `/ws/yaml-lsp` upgrades with `data: { type: "yaml-lsp" }` and uses `attach` / `detach`. Any `<name>-lsp` is a valid log category (`LspName` in [log-entry-model.ts](../src/api/log-entry-model.ts)), and the logs panel lists the clients' categories after the fixed `LOG_CATEGORIES`.

### Lifecycle

- **Spawn** happens when a client opens the socket. **Kill** happens when the socket closes (client disposed its transport), when a newer socket claims the same worktree key, or in `shutdown()`.
- **Exit.** A process that exits while its session is still live (a crash, out of memory, killed outside Loxel, not through `detach` / `destroy`) gets its session detached, which releases its key, and its socket closed with `LSP_EXITED_CLOSE_CODE` (4003, "`<name>` exited with code N"). Without that the socket would stay open with nothing answering it.
- **Worktree switch** is driven by the client: it disposes the old client and transport (see [Client side](#client-side)) and connects with the new `wt`; the close handler kills the old subprocess.
- **Reconnect policy.** [lsp-connection.ts](../src/lib/lsp-connection.ts) `createLspConnection` decides, for every socket that closes without the client asking, whether and when to connect again. Each close first disposes the client, so its providers and markers go away instead of hanging or going stale; a reconnect starts a new `MonacoLspClient`, which re-initializes the server, re-opens the synced models and registers providers from the new capabilities. By close code:

  | Close                                                      | Client                                                                                              |
  | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
  | `LSP_RESTART_CLOSE_CODE` (4002)                            | Reconnects at once, without counting a failure                                                      |
  | `LSP_EXITED_CLOSE_CODE` (4003), any other code, open fails | Reconnects after 1 s, doubling per failure in a row; stops (`crashed` / `unreachable`) at the fifth |
  | `LSP_START_FAILED_CLOSE_CODE` (4001)                       | Stops (`start-failed`): starting again would fail the same way                                      |
  | `LSP_REPLACED_CLOSE_CODE` (4000)                           | Stops (`replaced`)                                                                                  |

  A connection that stayed up 60 s ends a run of failures, so a server that crashes now and then always comes back while one that dies on startup stops after about 15 s. A replaced client does not reconnect because the server keeps one session per worktree: the window it took over from would close it with 4000 in turn, and the two windows would trade the server forever. It stays stopped until the user restarts it, which deliberately takes the server back. A Loxel server restart closes every socket abnormally; besides each client's own backoff, [monaco-env.ts](../src/lib/monaco-env.ts) calls `resumeLanguageServers()` on `wsClient.onReconnect`, which reconnects every client waiting to reconnect or stopped for any reason but `replaced`, with a fresh failure count; a client with an attempt in flight retries at once if that attempt fails. Socket closes carry the server's reason, such as "`<name>` exited with code N" or "was killed by SIGKILL".

- **Stopped clients** are listed in [lsp-status.ts](../src/store/lsp-status.ts) by route, which the status bar's `LanguageServerStatus` shows; clicking it calls `restartStoppedLanguageServers()`. A client that stops because its server crashed or could not start also shows a toast, once per stop: the same stop again (a missing binary, met on every reconnect) does not toast again until a connection has stayed up 60 s in between (`createStopToastFilter`), since a socket that opens is no proof the server works. The `language.restartServers` action (Restart Language Servers) calls `restartLanguageServers()`, which restarts every client from scratch.

## Client side

- [lsp-client.ts](../src/lib/lsp-client.ts) `createLspClient({ route, name, languageId, onConnected? })` returns an idempotent `connect(wtPath)` / `disconnect()` pair around one `WebSocketTransport` and one `MonacoLspClient` at a time (`wtPath` null for YAML, which no worktree scopes); `name` is the server's name in notices. Its connection, from `createLspConnection` (see [Lifecycle](#lifecycle)), aborts an attempt that a newer one (another path, a restart) supersedes, closing its socket before a client starts on it, so there is never a second socket for the same route. `getConnectedLspClients(wtPath)` lists the clients connected for a worktree at the moment, which is how features that span servers (Go to Symbol, see [EDITOR.md](EDITOR.md#search)) reach them; `getAllConnectedLspClients()` lists every connected client, YAML's included, which the code action commands use to tell whether the focused file's servers offer a kind (see [KEYBINDINGS.md](KEYBINDINGS.md#editor-code-actions)). Both the worktree switch and `disconnect()` call the client's `dispose()` (unregistering providers and closing synced documents) before disposing the transport, so its `textDocument/didClose` notifications still go out over the live socket. Every client passes [live-editor-model.ts](../src/lib/live-editor-model.ts) `isLiveEditorModel` as the `modelFilter`, so only editor tabs' live models (`file://` or `loxel://HEAD/` without a query or fragment, see [URI schemes](#uri-schemes)) are synced to servers; diff, history and compare sides are not, and get no LSP features. Every worktree client also passes `workspaceFileSystem: createLspWorkspaceFiles(wtPath)`, an `onWorkspaceEditFailure` that shows the reason as a toast, and its route as `markerOwner` (`python-lsp`, `ruff-lsp`, `mypy-lsp`), so the next client of a route takes over the diagnostics owner of the one before. `onConnected(transport)` runs for each connection, reconnects included, and what it returns is disposed with it. A client created with `showMessages` (mypy's) shows the errors and warnings its server sends with `window/showMessage` as toasts, each distinct message once while Loxel runs. What happens when the socket closes on its own is the [reconnect policy](#lifecycle).
- [lsp-workspace-files.ts](../src/lib/lsp-workspace-files.ts) `createLspWorkspaceFiles(wtPath)` is the disk side of language-server workspace edits (rename, code actions, `workspace/applyEdit`) for files with no editor model. Text goes through the regular file-content and file-write routes, unformatted, so an open editor of the file sees an ordinary external change. Creates, renames, moves and deletes go through the files-panel operations in [file-operations.ts](../src/lib/file-operations.ts), so tabs follow and the files panel's undo history records them; missing parent folders are created first. Edits on disk are confined to the user's own text files in the worktree: `stat` refuses, for every resource an edit touches, a path outside the worktree or under a dependency, environment, git or nested-worktree folder, checked by name and again on the real path so a symlink cannot lead an edit outside, and `readFile` refuses a file that does not read back as UTF-8 text, since the content route decodes it lossily. An open file that is only text-edited is exempt, since its model changes like typing wherever the file is. Text writes to unopened files are not on any undo stack. The YAML client has no worktree and no file system, so its edits are limited to open models.
- The per-language modules, `src/lib/<name>-lsp-client.ts`, only bind a route, the server's name for notices and Monaco language IDs. Each lazily started server's module default-exports its `createLspClient(...)`; [lsp-clients.ts](../src/lib/lsp-clients.ts) finds them with `import.meta.glob` as `lazyLspClients`, so a new one edits no shared file. TypeScript binds `typescript`, `javascript`, `tsx`, `jsx`, `json`, `jsonc`, and reports its models' indentation through `onConnected` with `reportDocumentIndentation` from [lsp-document-indentation.ts](../src/lib/lsp-document-indentation.ts) (see the TypeScript manager above); Docker binds `dockerfile` and `dockerbake`. Python models get three clients, basedpyright, ruff and mypy, each with its own lazy connector (mypy's server starts nothing in a project without a mypy config). [yaml-lsp-client.ts](../src/lib/yaml-lsp-client.ts) connects once per renderer, without a `wt` and never disconnecting, through the same `createLspClient`.
- [monaco-env.ts](../src/lib/monaco-env.ts) is the single wiring point, imported for its side effects. It disables all of Monaco's built-in TS/JS features (no TS worker; the JSON, CSS and HTML workers stay), registers the language IDs Monaco does not ship through [monaco-languages.ts](../src/lib/monaco-languages.ts), and connects the servers. YAML connects at load. TypeScript is eager: it connects to the active worktree and reconnects whenever `activeWorktreePath` changes. Every server in `lazyLspClients` goes through `createLazyLspConnector`, which counts live models (`isLiveEditorModel`) of its languages in the active worktree (plus those of files outside every project, served by the active worktree's server) and connects on the first one, disconnecting at zero. Diff, history and compare models are not counted. It also registers the editor opener from [editor-opener.ts](../src/lib/editor-opener.ts), which turns go-to-definition results and document or hover links to an editor file (`editorFilePath`, see [URI schemes](#uri-schemes)) in another model into `dispatchOpenFile`, which opens files outside every project (stdlib, installed packages) as external files; a target in the source's own model is left to Monaco to reveal in place. It installs the peek model resolver too, which lets peek widgets show files no tab has open (see [EDITOR.md](EDITOR.md#peek-widgets)).
- [packages/monaco-lsp-client](../../monaco-lsp-client/README.md) is a fork of `@vscode/monaco-lsp-client` consumed as TypeScript source. Its main local changes for Loxel are the `languageId` option (`TextDocumentSynchronizer` only syncs models whose language is in the set, which is what lets several servers coexist on one Monaco instance) and the `modelFilter` option above; its README lists the other local changes, including how `workspace/executeCommand` and workspace edits (rename, code actions, `workspace/applyEdit`) are handled. Diagnostics from the server become Monaco markers under the client's `markerOwner` (the route, see above), so servers sharing a model keep separate markers, and a disposed client removes its own. A code action request sends back the server's own diagnostics under the requested range as the server sent them (with `code`, `source` and `data`), which is how ruff finds its quick fixes.
- [ws-shim.ts](../src/lib/ws-shim.ts) is aliased to `ws` in [vite.config.ts](../vite.config.ts) because `@hediet/json-rpc-websocket` imports the Node `ws` package; the browser uses the native `WebSocket`.

## URI schemes

[CodeEditorPanel.tsx](../src/components/code-editor/CodeEditorPanel.tsx) picks the model URI per Monaco language. `fileSchemeLanguages` in [lsp-clients.ts](../src/lib/lsp-clients.ts) (json, yaml and the languages of every `lazyLspClients` server) gives `file://<abs path>`, which those servers need for schema matching, workspace indexing and import resolution. Every other language gets `loxel://HEAD/<abs path>`. Git diff views ([GitSideBySideDiffView.tsx](../src/components/diff-viewer/GitSideBySideDiffView.tsx)) use `loxel://<ref or HEAD>/<repo-relative path>#<side>`, and compare panels ([CompareFilesPanel.tsx](../src/components/compare/CompareFilesPanel.tsx)) `loxel://compare/<abs path>#<panel id>-<side>`; both render through [diff/EditorPanel.tsx](../src/components/diff/EditorPanel.tsx).

Only the TypeScript manager translates (`toServerUris` / `toClientUris` in [ts-lsp-manager.ts](../src/server/ts-lsp-manager.ts)): client-to-server it replaces `loxel://head/` (case-insensitive) with `file:///`; server-to-client it replaces `file:///` with `loxel://HEAD/` except for `.json` / `.jsonc` paths, whose editor models use `file://`. No other manager rewrites URIs, so every other server sees and returns the live models' own `file://` URIs. monaco-lsp-client sends document URIs percent-encoded (Monaco's `Uri.toString()`), the way servers write them, and matches the URIs servers send back to models after re-encoding them the same way, since servers differ in what they escape; the server side builds `rootUri`, `workspaceFolders` and watched-file URIs with `fileUri`, which encodes exactly like Monaco, so they also match document URIs as strings. Paths with spaces, `#`, `%` or non-ASCII characters therefore reach every server intact. One function decides which URIs are editor files: `editorFilePath` in [live-editor-model.ts](../src/lib/live-editor-model.ts) accepts `file:` and `loxel://HEAD` (any casing) with no query or fragment and returns the path. `isLiveEditorModel` (the clients' `modelFilter` and the lazy connector's check), the editor opener, the peek model resolver, Go to Symbol and the workspace-edit file system all use it. A peek widget's snapshot of a file has the file's URI but is not live: `isLiveEditorModel` also rejects models marked with `markPreviewModel`.

## Formatting

Formatting runs on the server as part of `POST /api/file-write` when the request carries `format: true` and valid `formattingSettings` ([FormattingSettings](../src/lib/formatting-model.ts)). Editors set `saveOptionsRef` (explicit save) and `autoSaveOptionsRef` (auto-save, only when `formatOnAutoSave`) through [use-disk-synced-content.ts](../src/hooks/use-disk-synced-content.ts); [save-editor-content.ts](../src/lib/save-editor-content.ts) sends them, and the response's formatted `content` is merged back into the editor as a programmatic "format-echo" edit (see [EDITOR.md](EDITOR.md#disk-synced-content) for the save state machine). When the save went out unformatted for a reason the user can fix, the response also carries a `formatNotice`, which the client shows as a toast once per distinct message per session. Only files inside the worktree's own tree are formatted; Others folders, drafts and external files are written as-is.

[format-service.ts](../src/server/format-service.ts) `FormatService.format()` returns a `FormatResult` whose `content` is `null` (write unformatted) when disabled, over 1 MB, without an extension, with no match, or when the formatter fails. Only a binary that is missing or cannot start (`Bun.spawn` throws: `ENOENT` for a missing binary or interpreter, which `Bun.which` tells apart, any other code such as `EACCES` / `ENOEXEC` for a file that is not runnable) and a timeout set its `notice`; a non-zero exit or empty output, typically a syntax error the language server already flags, is only logged so it does not repeat on every save. Resolution order:

1. **Manual overrides** from settings, first entry whose comma-separated extension list contains the file's extension. Always run as a command.
2. **Language modules** (if `autoDetect`): one `LanguageFormatter` from [language-formatter.ts](../src/server/language-formatter.ts) per entry in [language-formatters.ts](../src/server/language-formatters.ts), so a language adds its own module and one line. `detect(dir, wtRoot)` picks the formatter per file, usually from the nearest config (`dirsUpToRoot`); it runs on every save, uncached, and returning null passes the file to the next module claiming the extension, then to the root rules, so a module taking over a language removes its root rule. `spawnOptions(command, dir, wtRoot)` sets the formatter's `cwd`, `env` and `binDirs` for every command formatting those extensions, manual overrides included, since a tool that reads its config from the cwd needs the same `cwd` when the user runs it as an override; the first module claiming an extension provides them. A `cwd` other than the worktree makes `{file}` and a relative command absolute, since both may be relative to the worktree. A module that throws counts as detecting nothing or setting no options, so it cannot fail the save. `binDirs` replaces the default `node_modules/.bin`, so an empty list keeps it off `PATH`. Language modules run command mode only.
3. **Worktree-root rules** (if `autoDetect`), by config files at the worktree root, evaluated in `DETECTION_RULES` order, first formatter claiming the extension wins: prettier (config files or a `prettier` key in `package.json`), oxfmt (`.oxfmtrc.*` or an `oxfmt` dependency), rustfmt, clang-format, deno. Prettier and oxfmt share `SHARED_FORMAT_EXTENSIONS`; prettier adds `svelte` and `astro`, oxfmt adds `toml`. Because prettier is first, a project with both uses prettier for every shared extension. Detection is cached per worktree, keyed by a fingerprint of config-file sizes and mtimes.

**Python** (`.py`, `.pyi`) is such a module, `pythonFormatter` in [python-formatter.ts](../src/server/python-formatter.ts), whose `detectPythonFormatter` walks from the file's directory up to the worktree root so monorepo subprojects are found. Because a ruff config or dependency often exists for the linter alone while black only formats, the nearest directory with a formatting signal decides: a ruff config (`.ruff.toml` / `ruff.toml` or `[tool.ruff]`) with a `format` table selects ruff, a `[tool.black]` table or black dependency selects black. A ruff config without `format`, or a ruff dependency, selects ruff only when no such signal exists up to the root. Dependencies are read from `pyproject.toml` (PEP 621 dependencies and extras, PEP 735 groups, uv, Poetry and PDM dev dependencies, Hatch environments). A bare `pyproject.toml` formats nothing, matching the opt-in signal prettier and oxfmt need. ruff runs as `ruff format --force-exclude --stdin-filename {file}` (without `--force-exclude` ruff ignores its `exclude` settings for stdin) and black as `black --quiet --stdin-filename {file} -`; both resolve their own nested config and infer stub style from the file name. This walk is a few `existsSync` calls and small TOML parses per save. `getDetectedFormatters` lists what each language module detects at the worktree root.

Each rule has a `BackendMode` from [formatter-backends.ts](../src/server/formatter-backends.ts). `command` spawns the tool per request with content on stdin, `{file}` / `{ext}` substituted, the worktree's `node_modules/.bin` prepended to `PATH` unless a language module's `binDirs` says otherwise (for Python files run by command name, `findVenvBin` in [python-formatter.ts](../src/server/python-formatter.ts) prepends the environment directory holding that command ahead of it, so a project-pinned ruff or black beats a global one: the nearest sub-project `.venv` / `venv` / `env` with a `pyvenv.cfg` between the file's directory and the worktree root, else the worktree's shared resolution (`dirname(pythonPath)`, when it is an environment), else a venv at the root; environments that fail the [environment trust rule](languages/python.md#environment-trust-rule) are skipped), and a 5 s timeout. The two persistent backends are cached per `(worktree, command)`, restarted if dead, and on a `null` result destroyed and replaced by command mode for that request:

- [oxfmt-lsp-backend.ts](../src/server/oxfmt-lsp-backend.ts) keeps an `oxfmt --lsp` process (worktree `node_modules/.bin` first, then `PATH`) and formats via `didOpen` / `textDocument/formatting` / `didClose`, applying the returned edits.
- [prettier-lib-backend.ts](../src/server/prettier-lib-backend.ts) dynamically imports the worktree's own `node_modules/prettier` and calls `resolveConfig` (with `editorconfig: true`, as the prettier CLI does, so a project's `.editorconfig` shapes the output like it shapes the editor, and `useCache: false`, since nothing would clear prettier's config cache when a config file changes) + `format` in-process.

`invalidateCache(wtPath)` (called from worktree teardown) drops detection and destroys backends; `destroy()` runs at shutdown. `GET /api/detected-formatters?wt=` exposes detection to the settings UI.

## Toolchain status items

A language whose toolchain the user can see and choose (Python's interpreter) gets a status bar item, a picker, a command and routes through one seam. The shared code loops over three lists, each one import and one entry per language, and knows no language:

- [toolchain-statuses.ts](../src/api/toolchain-statuses.ts) lists each language's `ToolchainStatusDescriptor` ([toolchain-status-model.ts](../src/api/toolchain-status-model.ts)): its id, Monaco languages, changed message and select action. It is static because [ws-protocol.ts](../src/api/ws-protocol.ts) and the [action registry](../src/store/keybindings/action-registry.ts) derive literal types from it. Every select action is unbound by default, enabled while a worktree is active.
- [server/toolchain-statuses.ts](../src/server/toolchain-statuses.ts) lists each language's `ToolchainStatusModule` ([toolchain-status-module.ts](../src/server/toolchain-status-module.ts)): subscribe, refresh, the stored choice and its routes. [server.ts](../src/server/server.ts) holds a subscription per worktree, broadcasts the changed message when `changed`, and refreshes on a new choice or login-shell capture. [routes.ts](../src/server/routes.ts) validates the worktree for each route, then calls the module's handler, and deletes the stored choice with the worktree.
- [lib/toolchain-status-items.ts](../src/lib/toolchain-status-items.ts) lists each language's `ToolchainStatusItem` ([toolchain-status-item.ts](../src/lib/toolchain-status-item.ts)): the status bar component and the picker. An item builds on `useActiveToolchainStatus` ([use-toolchain-status.ts](../src/queries/use-toolchain-status.ts)), which follows the active editor's panel and worktree, and [ToolchainStatusButton.tsx](../src/components/panels/ToolchainStatusButton.tsx). The WebSocket bridge invalidates a toolchain's query on its changed message, and [useWsSubscription.ts](../src/hooks/useWsSubscription.ts) invalidates all of them on subscribing to a worktree, since only subscribers get those messages.

A language calls its own routes from its own client file (`src/api/<language>-*-client.ts`). Python's modules are named in [languages/python.md](languages/python.md#python-environment).

## Schemas and JSON validation

- [schema-service.ts](../src/server/schema-service.ts) resolves a schema from an HTTP(S) URL (1 h TTL, 5 MB cap, 10 s timeout) or a local path (relative to a base directory, revalidated by mtime). Other URL schemes are rejected.
- `POST /api/schemas/sync` receives the enabled schema settings and routes each glob by `classifySchemaGlob` in [schema-glob.ts](../src/lib/schema-glob.ts) (also behind the Languages column of Settings > Schemas): a glob ending in `.json` / `.jsonc`, `.yml` / `.yaml` or `.toml` (brace alternatives included) goes to those languages, any other glob (`**/*`, `**/Pipfile`) to all three. JSON schemas are resolved inline through the schema service and returned for Monaco. YAML and TOML get a `url → globs` map (absolute local paths as `file://` URLs) pushed to `YamlLspManager.updateSchemas` and `TomlLspManager.updateSchemas`; those servers fetch the schemas themselves, since schemas such as SchemaStore's `pyproject.json` `$ref` siblings by relative URL. `GET /api/schemas/resolve` resolves a single schema.
- [schema-sync.ts](../src/lib/schema-sync.ts) calls the sync endpoint after the settings store hydrates and when settings are saved, coalescing overlapping calls. `selectEffectiveSchemas` lists user mappings before built-in ones: JSON and YAML combine every matching schema, but Tombi applies the first one, so a user mapping overrides a built-in for the same TOML file.
- [json-schema-registry.ts](../src/lib/json-schema-registry.ts) owns the single global `monaco.json.jsonDefaults` schema list (Monaco replaces it wholesale), merging configured glob schemas with per-file `$schema` schemas. `CodeEditorPanel` detects `$schema` in JSON models (debounced), resolves it through the server, and registers it under the URL Monaco's JSON worker would compute relative to the file's `file://` URI; this is one reason JSON is in `fileSchemeLanguages`.
- Monaco's JSON diagnostics are permissive (comments and trailing commas ignored) so JSONC files work. [json-strict-validator.ts](../src/lib/json-strict-validator.ts) re-parses files resolved as strict `json` with `jsonc-parser` and adds `json-strict` markers for comments and trailing commas.

## Highlighting and language resolution

- [highlighter.ts](../src/lib/highlighter.ts) holds a singleton Shiki highlighter (themes `loxel-dark` and `github-dark`, a fixed `BUNDLED_LANGUAGES` list), the `FILENAME_TO_LANG` and `EXT_TO_LANG` tables, `detectLanguage()` (case-insensitive filename, `.d.ts`, `.env*`, the case-sensitive `.C` for C++, then case-insensitive extension) and `highlightCode()` for HTML token output. Language IDs here are Shiki IDs; `toMonacoLanguage()` in [monaco-theme.ts](../src/lib/monaco-theme.ts) maps the few that differ (for example `jsonc` → `json`, `dotenv` → `ini`).
- `monaco-env.ts` passes the highlighter to `shikiToMonaco`, which attaches a TextMate tokenizer to every Monaco-registered language ID that Shiki has loaded, replacing Monarch. Languages Monaco does not ship (`tsx`, `jsx`, `astro`, `terraform`, `toml`, `make`, `just`, `cmake`, `objective-cpp`) are registered first by [monaco-languages.ts](../src/lib/monaco-languages.ts) so they get one. Languages Shiki does not know get Monarch tokenizers: [hcl-monarch.ts](../src/lib/hcl-monarch.ts) for `dockerbake`, [go-monarch.ts](../src/lib/go-monarch.ts) for `go.mod`, `go.work` and `go.sum`, and [pip-requirements-monarch.ts](../src/lib/pip-requirements-monarch.ts) for `pip-requirements`.
- Editing behavior (comments, bracket matching and auto-closing, on-enter rules) comes from Monaco language configurations, which `shikiToMonaco` does not set. `monaco-languages.ts` registers one with each language it adds, reusing Monaco's built-in TypeScript, JavaScript and HCL `conf` for `tsx`, `jsx`, `terraform` and `dockerbake`; `monaco-languages.test.ts` fails when a built-in file association resolves to an unregistered language or a language Loxel adds has no configuration (`go.sum`, which has no comments or brackets, is the one exception). Monaco registers its built-in ones lazily when a language is first encountered, and registrations merge field by field with the last one winning, so [python-language-config.ts](../src/lib/python-language-config.ts) re-registers Monaco's Python `conf` with extra auto-closing pairs and `onEnterRules` (triple quotes, dedent after `return`/`pass`/`break`/`continue`/`raise`) only after the built-in registration has run; `python-language-config.test.ts` checks that order and the resulting editing behavior, so a Monaco upgrade that changes either fails there. [monaco-env.ts](../src/lib/monaco-env.ts) finds each `<language>-language-config.ts` with `import.meta.glob` and calls its `registerLanguageConfiguration()`, so a new one edits no shared file. The Python module also adds a keydown hook, for Python, TOML and Kotlin (whose configurations also auto-close triple quotes) and languages that join it with `stepOverTripleQuotesIn`, that steps over the rest of a triple-quote delimiter, since Monaco overtypes only the first character of a multi-character auto-closed pair.
- [c-language-config.ts](../src/lib/c-language-config.ts) does the same for `c`, `cpp` and `objective-c`, adding doc comment auto-closing and `onEnterRules` to their built-in `conf`; `monaco-languages.ts` applies the same extension to the C++ `conf` for `objective-cpp`, which Monaco does not ship.
- [resolve-language.ts](../src/lib/resolve-language.ts) `resolveLanguage(path, associations, content)` is what the code editor uses: enabled file associations first (first glob match wins, matched with `dot: true` so globs cross dot directories; user entries precede built-ins in `selectEffectiveFileAssociations`), then `detectLanguage`, then content sniffing (shebang, XML prolog). The built-in associations in [settings-store.ts](../src/store/settings-store.ts) are generated from `FILENAME_TO_LANG` / `EXT_TO_LANG` plus glob overrides that exact names cannot express (`tsconfig*.json` → `jsonc`, `*.docker-bake.hcl` → `dockerbake`, `requirements*.txt` → `pip-requirements`, extensionless C++ standard library headers → `cpp`).
- [textmate-inspector.ts](../src/lib/textmate-inspector.ts) backs the editor's token-scope inspector using `codeToTokensBase` with explanations.
- [file-icons.tsx](../src/lib/file-icons.tsx) has its own filename, filename-pattern, compound-extension and extension maps (JetBrains icon theme) and is independent of language resolution.
