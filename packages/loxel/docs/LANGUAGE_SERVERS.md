# Language Servers and Language Intelligence

How Loxel provides language features: language-server subprocesses bridged to Monaco over WebSockets (and mypy, served in-process over the same protocol) (with the watched files, pulled configuration and on-disk workspace edits the bridge supplies), the per-worktree Python environment and interpreter choice shared by every Python feature, project-wide TypeScript diagnostics, formatting, JSON/YAML/TOML schemas, syntax highlighting and editing behavior.

To add a new language server, follow the [add-language-server skill](../../../.agents/skills/add-language-server/SKILL.md) and its [per-server quirks reference](../../../.agents/skills/add-language-server/references/existing-integrations.md). This doc is the architecture that skill assumes; it does not repeat the checklist. For the end-user view see the site's [Language Intelligence](../../site/src/content/docs/language-intelligence.md) page.

## Data flow

```
Monaco model ──(MonacoLspClient, JSON-RPC over WS)──▶ /ws/<lang>-lsp[?wt=<path>]
   ▲                                                       │ server.ts routes by ws.data.type
   │                                                       ▼
   └──────── providers / markers ◀── WS ◀── <Lang>LspManager (StdioLspManager subclass)
                                                           │ Content-Length framed stdio
                                                           ▼
                                                 language-server subprocess (cwd = worktree)
```

The server is a thin proxy. It owns process lifetime, framing and a small set of message rewrites (initialize parameters, URI translation, capability scrubbing). All LSP feature logic on the client lives in the `monaco-lsp-client` fork, which registers Monaco providers from the server's advertised capabilities.

## Server side

### `StdioLspManager` base class

[stdio-lsp-manager.ts](../src/server/stdio-lsp-manager.ts) bridges one WebSocket to one subprocess. Public API: `handleMessage(ws, data)`, `detach(ws)` (kill and forget), `destroy()` (kill all, used on server shutdown). Subclasses add their own entry points (`createSession(ws, wtPath)` / `destroySession(ws)` for worktree-scoped managers, `attach(ws)` for YAML) that call the protected `startSession(ws, context)`. `WorktreeLspManager` supplies the one-server-per-worktree plumbing (those entry points, a `WtLspSession`, `wtPath` as the session key, workspace and `cwd`); the managers whose session holds more state (Python, ruff) extend `StdioLspManager` directly.

- **Session model.** `sessions: Map<ServerWebSocket, TSession>`. `BaseLspSession` holds the `ws`, the `proc`, the stdout reassembly buffer and `documentContents` (used only for full-text sync). `WtLspSession` adds `wtPath`.
- **Dedup by key.** `getSessionKey(context)` returns a key (worktree managers return `wtPath`; YAML returns `null`). `startSession` keeps at most one live session per key: if another WebSocket already owns the key, that session is detached and its socket closed with `LSP_REPLACED_CLOSE_CODE` (4000, "Replaced by newer connection"). A server that cannot start (no binary, or `Bun.spawn` throwing because it cannot be executed) releases its key and closes the socket with `LSP_START_FAILED_CLOSE_CODE` (4001), so the client's `initialize` fails instead of hanging. The close codes live in [ws-protocol.ts](../src/api/ws-protocol.ts); see [Lifecycle](#lifecycle) for what the client does with each.
- **Spawn.** `Bun.spawn([resolveBinary(context), ...spawnArgs()])` with piped stdio, `cwd` from `spawnOptions(context)` and the environment from `buildSpawnEnv()` in [shell-env.ts](../src/server/shell-env.ts) (the login-shell environment, see [TERMINALS.md](TERMINALS.md#environment), so servers that run user tools such as basedpyright's interpreter or terraform-ls's `terraform` find them when Loxel was launched from Finder) with `NODE_OPTIONS` cleared. Server startup waits up to `LOGIN_SHELL_ENV_WAIT_MS` for that environment before serving, so the first sessions do not race it. A binary `resolveBundledBinary` cannot find triggers a login-shell refresh, so one installed meanwhile is found on the next start. Default args are `["--stdio"]`. `resolveBinary` may return a promise (ruff looks in the worktree's environment); the client's frames that arrive meanwhile, starting with `initialize`, are held and replayed once the process is spawned, and dropped if the socket closes or a newer one claims the key first.
- **Framing.** `writeToStdin` adds the `Content-Length` header and flushes the `FileSink` per message. `drainMessages` parses frames out of stdout and hands each body to `handleServerFrame`.
- **`initialize` rewriting.** When `getSessionWorkspace(session)` returns a path, missing `rootUri` / `rootPath` / `workspaceFolders` are filled in (client values win), with `file://` URIs percent-encoded the way Monaco writes them (`fileUri` in [lsp-file-uri.ts](../src/server/lsp-file-uri.ts)). `getInitializationOptions(session)` is merged one level deep into the client's `initializationOptions` (client values win). Config that the server only accepts by push goes in `onClientInitialized`, which runs after the client's `initialized` notification is forwarded and typically sends `workspace/didChangeConfiguration`.
- **Workspace folders.** monaco-lsp-client does not implement `workspace/workspaceFolders` either, so when `getSessionWorkspace(session)` returns a path the base answers that request itself with the session's single folder, the same one it injects into `initialize` (Tombi asks for it).
- **Pulled configuration.** monaco-lsp-client does not implement `workspace/configuration`, so a subclass that defines `workspaceConfiguration(session, section)` gets the `workspace.configuration` capability injected into `initialize`, and the base answers the server's requests itself, one section at a time (asynchronously, dropped if the session is gone). `notifyConfigurationChanged(session)` sends `workspace/didChangeConfiguration` with `settings: null`, which makes such a server pull again.
- **Watched files.** monaco-lsp-client cannot watch files, so without help a server never hears about changes to files that are not open: new modules, `git checkout`, an agent's edits, `pyrightconfig.json` / `tsconfig.json`. A subclass that sets `forwardWatchedFiles` (basedpyright, ruff, TypeScript, Tombi) gets the `workspace.didChangeWatchedFiles` capability injected into `initialize`, without `relativePatternSupport`, which keeps servers from asking for most directories outside the worktree. The base takes the server's watcher registrations out of `client/registerCapability` / `client/unregisterCapability` before `handleServerFrame`, so subclasses need no wiring, and keeps them in the session's `WatchedFilesForwarder` from [lsp-watched-files.ts](../src/server/lsp-watched-files.ts). `server.ts` hands each change batch of the worktree's `ProjectFilesService` (`onPathsChanged`) to every worktree manager's `notifyWatchedFilesChanged(wtPath, paths)`. The forwarder keeps the paths some watcher wants, holds changes that arrive before the server has registered its watchers (a server reads the disk before it registers; tsc only once its project has loaded), and sends them debounced as one `workspace/didChangeWatchedFiles` with `file://` URIs. The file watcher does not say whether a path is new, so the forwarder tells created from changed and deleted with `stat`, and reports a path it judges created (atomic saves, checkouts, reinstalled packages) as changed, then created: basedpyright only re-resolves imports for created files, while TypeScript ignores a creation of a file it has already loaded and keeps its old contents unless the change comes first. Only changes inside the session's worktree are reported, outside its git-ignored directories except for dependency installs (below), and only while a client is subscribed to that worktree (when its file watcher runs). Glob matching, limits and timings are documented in the module.
- **Dependency installs.** TypeScript registers `<dir>/node_modules/**/*` for each project and watches nothing itself, so without help a package installed, upgraded or removed stays unresolved until the server restarts. The worktree watcher already receives the events inside git-ignored directories; `ProjectFilesService` drops them in its filter and hands each to `onIgnoredPathChanged`, and the worktree's `NodeModulesChanges` from [node-modules-changes.ts](../src/server/node-modules-changes.ts) turns those under `node_modules` into paths for the same `notifyWatchedFilesChanged`, so nothing watches `node_modules` separately. Each package a path lies in (top-level or scoped, at every `node_modules` level, so a monorepo's per-package `node_modules` count) is reported as its directory and its `package.json`, which makes TypeScript resolve it again, plus the changed file itself when it is a type file (`.ts`, `.d.ts`, `.tsx` and their variants, `.json`), because TypeScript reloads a file it already read only when that file is reported. Dot entries are skipped: pnpm's `.pnpm` store is content-addressed and an upgrade relinks the top-level symlink, and `.bin`, caches, install markers and npm's staging directories carry nothing a server needs. A package directory moved into place whole (bun) brings no events for its files, so a package whose own entry changed with nothing reported inside it has its type files listed from disk, unless it is a symlink. Changes go out once `node_modules` has been quiet for a second (at most ten seconds after the first), since a package reported halfway through an install has to be reported again. This needs no package-manager markers or lockfiles and works the same for npm, pnpm, yarn and bun.
- **Session teardown.** `onSessionClosed(session)` fires when a session is detached, destroyed or its process exits (possibly more than once) for releasing per-session resources such as watchers.
- **`disableSemanticTokens`.** Strips the semantic-tokens client capability from `initialize`, deletes `semanticTokensProvider` from the initialize response, and filters semantic-token entries out of `client/registerCapability`.
- **`suppressedFeatures`.** LSP features (formatting, range formatting, semantic tokens) Monaco must not get from a server: their capability is deleted from the initialize response and their `client/registerCapability` entries are filtered out the same way, since servers differ in which way they advertise them (ruff before 0.17 statically, later dynamically); when no registration is left the base answers the server directly.
- **`requiresFullTextSync`.** The base tracks text from `didOpen`, applies incremental `didChange` ranges locally (clamped), and forwards a single full-text change. A `didChange` for an untracked URI is forwarded unchanged with a warning.
- **Errors.** JSON-RPC error responses from the server are logged at info level before forwarding.
- **stderr.** Each session reads stderr line by line through a token bucket from [stderr-throttle.ts](../src/server/stderr-throttle.ts), which logs a "suppressed N" summary in place of the excess, so a chatty server cannot flood the shared log ring buffer. The most recent lines are kept regardless and logged as a warning if the process exits non-zero.

The TypeScript manager is the outlier. It always overwrites `rootUri` / `workspaceFolders` / `initializationOptions` (it does not use the base merge), passing its preferences as `initializationOptions.userPreferences`, which TypeScript reads as its `js/ts` settings section when the client does not advertise `workspace/configuration`; it answers `workspace/configuration` (the same `js/ts` section) and `window/workDoneProgress/create` itself because TypeScript blocks on them, rewrites `languageId` to `typescriptreact` / `javascriptreact` for `.tsx` / `.jsx`, drops `textDocument/*` messages whose URI does not have a TS/JS/JSON extension, and translates URIs (see [URI schemes](#uri-schemes)). It deliberately forwards `client/registerCapability` so Monaco sees TypeScript's dynamic semantic-tokens registration; the base has already taken TypeScript's file-watcher registrations out by then (see watched files above).

TypeScript indents the code of quick fixes and completions with one set of format settings for the whole server (4 spaces by default), so the manager makes them follow each file's indentation. The TS client sends a `loxel/documentIndentation` notification (`DOCUMENT_INDENTATION_METHOD` in [lsp-indentation-model.ts](../src/api/lsp-indentation-model.ts)) for each live model with its options (`insertSpaces`, `tabSize`, `indentSize`, the indentation `resolveIndentation` gave it, see [EDITOR.md](EDITOR.md#indentation)) when it connects and whenever they change. The manager consumes it and keeps the indentation per file until `didClose`. Before forwarding `textDocument/codeAction`, `textDocument/completion` or `completionItem/resolve` (whose data names the file), it sends `workspace/didChangeConfiguration` with the `js/ts` section and that file's `format` settings if they differ from the last ones sent (sizes capped at 16 columns). A fix that also edits another file indents that file's code the same way, since TypeScript has one setting per request. TypeScript applies a configuration change before it takes the next request's snapshot, and the change only builds a new snapshot (no program rebuild). Formatting requests need none of this: Monaco sends the model's `indentSize` as their `tabSize`.

### Python environment

basedpyright's own environment discovery covers only a root `.venv` and it ignores Loxel's `initializationOptions`; without an interpreter it runs `python3` from its `PATH`. [python-env.ts](../src/server/python-env.ts) is the single resolver of a worktree's interpreter, for every Python feature (language servers, terminals, the built-in coding agent's commands, format on save, the status bar), and returns a `PythonEnv` from [python-env-model.ts](../src/api/python-env-model.ts) (`source`, absolute `pythonPath`, `envPath` prefix or null; a venv's bin directory is `dirname(pythonPath)`).

- **Resolution.** `resolvePythonEnv(wtPath, { overridePath?, env? })` tries, first hit wins: the override (by default the worktree's chosen interpreter; `null` skips it), `VIRTUAL_ENV` then `CONDA_PREFIX` only when they lie inside the worktree (the environment Loxel was launched from must not apply to every worktree), `UV_PROJECT_ENVIRONMENT` then a `.venv` / `venv` / `env` with `pyvenv.cfg` at the worktree root (uv, uv workspaces, PDM, `python -m venv`), Pixi's default environment, Poetry's and Pipenv's environments (asked only when the tool's lock file is at the root and the tool is on `PATH`, since asking spawns it), the virtual environment of a Python project directory below the root when exactly one has one (a monorepo interim: with several, which applies depends on the file, so none is picked), then `python3`, else `python`, on the login-shell `PATH`. A candidate, the override included, counts only if its interpreter is executable and it passes the [environment trust rule](#environment-trust-rule). The resolver never runs the interpreter and never throws.
- **Shared resolution.** `subscribePythonEnv(wtPath, listener)` keeps a worktree's resolution memoized and watched while anyone is subscribed. `getPythonEnv(wtPath)` answers from it (an unsubscribed worktree resolves afresh, since nothing would keep a memo current), and `getPythonEnvNow` answers with the last finished resolution while a newer one runs. The memo is replaced when its environment watch fires, on `refreshPythonEnv` (the override changed), on `refreshAllPythonEnvs(changedNames)` when a login-shell capture changed a variable that resolution reads, and when the settled environment no longer passes the trust rule. Listeners hear every finished resolution as `{ env, first, changed }`, also when the interpreter stayed the same, since packages may have been installed into it. The subscribers are each worktree's resources in [server.ts](../src/server/server.ts), which send `python_env_changed` to the worktree's clients when `changed`, every basedpyright and ruff session, and every built-in coding agent session (see [CODING_AGENT_INTEGRATION.md](CODING_AGENT_INTEGRATION.md#tool-environment)).
- **Watching.** `watchPythonEnv` watches, without recursing, where each candidate environment would appear, the Poetry and Pipenv lock files, and the current environment's interpreter directory and `site-packages` (which also covers environments outside the worktree), debounced, and re-resolution keeps the old watch until the new one is armed, so a change made meanwhile is not lost. The worktree file watcher skips git-ignored directories such as `.venv`, so this watch, not [watched files](#stdiolspmanager-base-class), is what notices `uv sync` creating an environment or packages installed into one.
- **Choosing an interpreter.** `listPythonEnvs(wtPath)` returns `{ candidates, automatic }`, without duplicates and under the same rules: the automatic choice, then `.venv` / `venv` / `env` and Pixi environments at the root and in Python project directories below it (found through git, so ignored trees are skipped), Poetry's environment, the `PATH` interpreter, and last the stored override. `normalizePythonOverride(wtPath, input)` turns a path the user entered (`~/` allowed, or an environment directory) into an interpreter path, or throws a user-facing error; the override route also requires `--version` to report a Python version. [python-override-store.ts](../src/server/python-override-store.ts) stores the choice per worktree in `stores.db`, and it is deleted with the worktree. Because the resolver reads it, every Python feature gets the choice without state of its own: [server.ts](../src/server/server.ts) subscribes `refreshPythonEnv` to `onPythonOverrideChange`, so a change reaches every subscriber (basedpyright re-pulls, ruff re-picks, the UI gets one `python_env_changed`) without a restart.
- **Version.** [python-version.ts](../src/server/python-version.ts) runs `<python> --version` for interpreters the resolver accepted, in the worktree, so a version-manager shim (pyenv, asdf) reports the version the worktree's `.python-version` selects. It is cached per interpreter file and directory, so a recreated venv or an upgraded interpreter is read again.
- **Activation.** [python-env-activation.ts](../src/server/python-env-activation.ts) puts an environment into a spawn environment the way its `activate` script would: `pythonEnvActivation` refuses an interpreter outside any environment and a `bin` git tracks, and `setPythonEnvVars` puts `bin` first on `PATH`, drops `PYTHONHOME` and `VIRTUAL_ENV_PROMPT`, and sets or clears `VIRTUAL_ENV`. New terminal shells activate their worktree's environment from the shared resolution at spawn, override included (see [TERMINALS.md](TERMINALS.md#python-environment)); the built-in coding agent's commands follow it through the session (see [CODING_AGENT_INTEGRATION.md](CODING_AGENT_INTEGRATION.md#tool-environment)).
- **API.** `GET /api/python-env?wt=` returns `{ env, overridePath }` with `env` (the shared resolution) carrying its `version`; `GET /api/python-env/candidates?wt=` returns `{ candidates, automaticPath, overridePath }`; `POST /api/python-env/override` with `{ worktreePath, pythonPath }` validates and stores the choice (`null` clears it) and answers like the first route. `wt` must be a worktree of a registered project, since resolution may run `poetry` there. The renderer side is [python-interpreter.ts](../src/lib/python-interpreter.ts) (labels and the picker, run by the `python.selectInterpreter` action) and [PythonInterpreterStatus.tsx](../src/components/panels/PythonInterpreterStatus.tsx) in the status bar, shown while the active editor's file resolves to Python. Both act on the worktree of the active editor's panel (`params.worktreePath`), not the active worktree, which differs right after a switch; the action falls back to the active worktree when no editor is active. Only a worktree's subscribers get `python_env_changed`, so the renderer invalidates its cached interpreters whenever it subscribes to a worktree ([useWsSubscription.ts](../src/hooks/useWsSubscription.ts)).

#### Environment trust rule

Every feature that runs something from a Python environment applies one rule from [python-env.ts](../src/server/python-env.ts): the resolver (basedpyright executes the interpreter it picks), format on save, terminal and agent activation, ruff's language server and mypy's daemon. `isEnvShippedByRepo(wtPath, envPath, executable)` refuses an environment when git tracks any file inside it, or the executable about to run from it or that executable's symlink target; `isShippedByRepo(wtPath, path)` checks a single path the same way: a ruff or `dmypy` outside any environment, or the `bin` directory activation puts first on `PATH`. Real environments are never committed, so a tracked one is repository content, and running it would run repository code: a committed `.venv/bin/python`, or a `.pth` startup hook in its `site-packages`, would otherwise run as soon as a Python file is opened. An environment whose directory is the worktree itself (`python -m venv .`) shares it with the repository, so only its own entries are checked there. Git is asked through the innermost repository that holds each path (submodules and nested repositories count), about its physical path. A worktree in no git repository has nothing tracked, so every environment passes; inside a repository, a path git cannot answer for counts as tracked, so the caller moves on to its next candidate. Answers are cached per worktree and path until a git index they read changes, which keeps re-checking an environment on every use cheap.

#### basedpyright, ruff and mypy

- **basedpyright.** `PythonLspManager` answers the `python` section of `workspace/configuration` with only `pythonPath` from `getPythonEnvNow`, so the resolver stays the source of truth and a re-resolution in flight does not hold up the first analysis. When nothing resolved it answers a `venvPath` of the worktree with no `venv` instead, which turns off basedpyright's own root `.venv` detection (it would run a committed interpreter) without selecting an environment, and basedpyright is spawned with the worktree's directories removed from `PATH`, so its fallback `python3` cannot be a committed one either. After `initialized`, each later re-resolution calls `notifyConfigurationChanged`, so basedpyright pulls the setting again and re-resolves imports: `uv sync` creating `.venv`, packages installed later, a changed override. A `venvPath` / `venv` in the project's own configuration (`pyrightconfig.json`, `[tool.basedpyright]`, `[tool.pyright]`) still wins inside basedpyright over the interpreter Loxel passes; basedpyright only reads that environment's `site-packages` for analysis and never runs its interpreter, so it needs no trust check.
- **basedpyright settings.** The `basedpyright` section sets `analysis.typeCheckingMode` to `standard` (basedpyright's default `recommended` flags ordinary code) and repeats `autoSearchPaths: true`, which any `analysis` section otherwise resets. basedpyright ignores these analysis settings when the project has a config file, so the project's rules, and basedpyright's own defaults for anything the file leaves out, win.
- **Ruff.** `RuffLspManager` runs `ruff server` next to basedpyright for lint diagnostics, quick fixes, fix all and organize imports (basedpyright offers no organize-imports code action, so they never compete). Its asynchronous `resolveBinary` takes the `ruff` next to the resolved interpreter, so the project's pinned version and rules apply, when it passes the trust rule (the whole environment, or the single file for a ruff outside any environment, whose directory can belong to an unrelated repository such as Homebrew's) and is recent enough for a stable `ruff server`; otherwise the bundled one. The session subscribes to the shared resolution and picks again after each re-resolution; when the pick changes it closes the socket with `LSP_RESTART_CLOSE_CODE` ([ws-protocol.ts](../src/api/ws-protocol.ts)), on which the client reconnects at once (see [Lifecycle](#lifecycle)), so a new session spawns the new binary and the client re-opens its documents. Ruff finds its configuration per file (nearest `.ruff.toml` / `ruff.toml` / `pyproject.toml`), so monorepo subprojects need nothing from Loxel, and reloads it when a config file changes, which reaches it as watched files. Syntax errors are left to basedpyright (`showSyntaxErrors: false`), and ruff's formatting capabilities are suppressed so format on save stays the only Python formatter (see [Formatting](#formatting)).
- **mypy.** mypy has no language server, so [mypy-lsp-manager.ts](../src/server/mypy-lsp-manager.ts) is one, in-process, on its own route (`mypy-lsp`): `MypyLspManager` keeps one session per worktree like the stdio managers (a newer socket replaces the older with `LSP_REPLACED_CLOSE_CODE`), answers `initialize` with open/close sync only, and publishes `textDocument/publishDiagnostics` with source `mypy` and a `codeDescription` link to the error code's entry in mypy's docs. Running it this way, rather than feeding markers from a side channel, puts mypy's diagnostics through the same client as every other server's: markers under their own owner, reconnects, and anything that reads the clients' diagnostics. Each open Python file belongs to the mypy config nearest to it, found the way mypy finds its own by `findMypyConfig` in [mypy-config.ts](../src/server/mypy-config.ts) (per directory up to the worktree: `mypy.ini`, `.mypy.ini`, `pyproject.toml` with `[tool.mypy]`, `setup.cfg` with `[mypy]`), so monorepo subprojects get their own. Each config root with an open file gets a `MypyDaemon` from [mypy-daemon.ts](../src/server/mypy-daemon.ts), set up lazily and stopped when its last file closes or the session ends: it runs the `dmypy` next to the resolved interpreter, when it passes the trust rule, with the environment activated and `cwd` at the config's directory, as `dmypy --status-file <tmp> run -- --output json --show-error-end [targets]` (mypy before 1.11, without JSON output, in its text format with error ends). The status file lives in the system temp directory, so nothing is written to the project but mypy's own `.mypy_cache`; `dmypy run` detaches the daemon, so it is stopped through the pid in that file, and an idle timeout bounds one Loxel could not stop. A root whose config names its targets (`files`, `modules`, `packages`) is checked as configured, the way CI runs mypy, any other on its open files. Checks run (debounced, one at a time per root) when files open or close and when a Python file under the root changes on disk, which arrives as the worktree's watched files (`notifyWatchedFilesChanged`); unsaved edits are not checked, since mypy reads files from disk. A changed config file, or any re-resolution of the shared Python environment, stops the daemons and sets them up again. Each check publishes what mypy reported and clears the files the previous check reported and this one does not. A missing or untrusted `dmypy` and a check mypy could not run (exit code 2: a config error, a plugin that does not load) are sent once each as `window/showMessage`, which the client shows as a toast.
- **mypy and basedpyright.** While a root's daemon can run, `MypyLspManager.ownsTypeChecking(wtPath, file)` is true for its files, and `PythonLspManager`, given it as its `ExternalTypeChecker`, drops basedpyright's rule diagnostics (those with a `code`, other than hints) from the reports for those files: pulled `textDocument/diagnostic` answers, matched to their requests by id, and pushed ones. Syntax errors and the unused, unreachable and deprecated hints stay, as do completion, hover, navigation, code actions and refactors, so the project's own checker, with its plugins (Django, pydantic, SQLAlchemy), is the only one reporting type errors. When that changes, the manager sends the client `workspace/diagnostic/refresh` and drops the client's answer, which basedpyright never asked for; requests go out without `previousResultId`, since an "unchanged" answer would keep a report filtered under the previous rule. A project that configures basedpyright itself (`pyrightconfig.json`, `[tool.basedpyright]` or `[tool.pyright]` at the root, where basedpyright reads them) keeps both checkers' type errors: the project's configuration is the switch, so there is no Loxel setting for it.

### Binary resolution and packaging

`resolveBundledBinary(name, devPath?)` checks, in order: a sibling of `process.execPath` (the packaged layout, where `loxel-server` and all servers are copied side by side), then `devPath` if given (downloaded binaries under `build/`) or else `node_modules/.bin/<name>`, then the login-shell `PATH`. TypeScript uses its own resolver: `typescript-lib/tsc` next to the executable when packaged, else the `@typescript/native` Node shim in dev.

`build:server:standalone` in [package.json](../package.json) produces every binary under `build/`, and [electron-builder.yml](../electron-builder.yml) `extraResources` copies them next to `loxel-server` (plus basedpyright's `typeshed-fallback` and the whole `typescript-lib/`, since the native compiler reads its sibling `lib.*.d.ts`). The scripts fall into three kinds:

- Bun-compiled from npm packages: [build-yaml-lsp.ts](../scripts/build-yaml-lsp.ts), [build-basedpyright-lsp.ts](../scripts/build-basedpyright-lsp.ts), [build-astro-ls.ts](../scripts/build-astro-ls.ts) (bundle with `Bun.build`, using plugins where UMD module loading defeats the bundler, then `bun build --compile`; basedpyright's single pre-bundled file is compiled through a wrapper entry that also replaces `v8.getHeapStatistics`, which is too slow under Bun; packages located with [resolve-package.ts](../scripts/resolve-package.ts)).
- Downloaded native binaries with per-platform SHA256 pins verified before writing or extracting: [download-docker-lsp.ts](../scripts/download-docker-lsp.ts), [download-terraform-ls.ts](../scripts/download-terraform-ls.ts), [download-xml-lsp.ts](../scripts/download-xml-lsp.ts) (GraalVM-native LemMinX, no JRE), [download-ruff.ts](../scripts/download-ruff.ts) and [download-tombi.ts](../scripts/download-tombi.ts) (both through [download-release-binary.ts](../scripts/download-release-binary.ts), which extracts only the binary from the release archive; Tombi publishes static musl builds for Linux).
- Copied: [copy-typescript.ts](../scripts/copy-typescript.ts) copies the platform `@typescript/typescript-<platform>-<arch>` `lib/` directory, so TypeScript ships in lockstep with the server.

Packaging and signing of these extra binaries is covered in [ELECTRON.md](ELECTRON.md) and [RELEASE_SIGNING.md](RELEASE_SIGNING.md).

### WebSocket routes

[server.ts](../src/server/server.ts) creates one instance of each manager at startup. In `fetch`, `/ws/yaml-lsp` upgrades with `data: { type: "yaml-lsp" }`. The `worktreeLspTypes` array (`ts-lsp`, `docker-lsp`, `terraform-lsp`, `python-lsp`, `ruff-lsp`, `mypy-lsp`, `astro-lsp`, `xml-lsp`, `toml-lsp`) maps `/ws/<type>` to an upgrade with `data: { type, wtPath }`, rejecting requests without `?wt=` with 400. `WorktreeLspType` is derived from the `WsData` union in [server-state.ts](../src/server/server-state.ts), so adding a type there and to the array is what makes a route exist. The `websocket.open` / `close` / `message` handlers dispatch on `ws.data.type` to `createSession` / `destroySession` / `handleMessage`; only string frames are forwarded.

### Lifecycle

- **Spawn** happens when a client opens the socket. **Kill** happens when the socket closes (client disposed its transport), when a newer socket claims the same worktree key, or in `shutdown()`.
- **Exit.** A process that exits while its session is still live (a crash, out of memory, killed outside Loxel, not through `detach` / `destroy`) gets its session detached, which releases its key, and its socket closed with `LSP_EXITED_CLOSE_CODE` (4003, "`<name>` exited with code N"). Without that the socket would stay open with nothing answering it.
- **Worktree switch** is driven by the client: it disposes the old client and transport (see [Client side](#client-side)) and connects with the new `wt`; the close handler kills the old subprocess.
- **Reconnect policy.** [lsp-connection.ts](../src/lib/lsp-connection.ts) `createLspConnection` decides, for every socket that closes without the client asking, whether and when to connect again. Each close first disposes the client, so its providers and markers go away instead of hanging or going stale; a reconnect starts a new `MonacoLspClient`, which re-initializes the server, re-opens the synced models and registers providers from the new capabilities. By close code:

  | Close                                                      | Client                                                                                              |
  | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
  | `LSP_RESTART_CLOSE_CODE` (4002)                            | Reconnects at once, without counting a failure                                                      |
  | `LSP_EXITED_CLOSE_CODE` (4003), any other code, open fails | Reconnects after 1 s, doubling per failure in a row; stops (`crashed` / `unreachable`) at the fifth |
  | `LSP_START_FAILED_CLOSE_CODE` (4001)                       | Stops (`start-failed`): starting again would fail the same way                                      |
  | `LSP_REPLACED_CLOSE_CODE` (4000)                           | Stops (`replaced`)                                                                                  |

  A connection that stayed up 60 s ends a run of failures, so a server that crashes now and then always comes back while one that dies on startup stops after about 15 s. A replaced client does not reconnect because the server keeps one session per worktree: the window it took over from would close it with 4000 in turn, and the two windows would trade the server forever. It stays stopped until the user restarts it, which deliberately takes the server back. A Loxel server restart closes every socket abnormally; besides each client's own backoff, [monaco-env.ts](../src/lib/monaco-env.ts) calls `resumeLanguageServers()` on `wsClient.onReconnect`, which reconnects every client waiting to reconnect or stopped for any reason but `replaced`, with a fresh failure count; a client with an attempt in flight retries at once if that attempt fails. Socket closes carry the server's reason, such as "`<name>` exited with code N" or "was killed by SIGKILL".

- **Stopped clients** are listed in [lsp-status.ts](../src/store/lsp-status.ts) by route, which the status bar's `LanguageServerStatus` shows; clicking it calls `restartStoppedLanguageServers()`. A client that stops because its server crashed or could not start also shows a toast, once per stop: the same stop again (a missing binary, met on every reconnect) does not toast again until a connection has stayed up 60 s in between (`createStopToastFilter`), since a socket that opens is no proof the server works. The `language.restartServers` action (Restart Language Servers) calls `restartLanguageServers()`, which restarts every client from scratch.

## Client side

- [lsp-client.ts](../src/lib/lsp-client.ts) `createLspClient({ route, name, languageId, onConnected? })` returns an idempotent `connect(wtPath)` / `disconnect()` pair around one `WebSocketTransport` and one `MonacoLspClient` at a time (`wtPath` null for YAML, which no worktree scopes); `name` is the server's name in notices. Its connection, from `createLspConnection` (see [Lifecycle](#lifecycle)), aborts an attempt that a newer one (another path, a restart) supersedes, closing its socket before a client starts on it, so there is never a second socket for the same route. `getConnectedLspClients(wtPath)` lists the clients connected for a worktree at the moment, which is how features that span servers (Go to Symbol, see [EDITOR.md](EDITOR.md#search)) reach them; `getAllConnectedLspClients()` lists every connected client, YAML's included, which the code action commands use to tell whether the focused file's servers offer a kind (see [KEYBINDINGS.md](KEYBINDINGS.md#editor-code-actions)). Both the worktree switch and `disconnect()` call the client's `dispose()` (unregistering providers and closing synced documents) before disposing the transport, so its `textDocument/didClose` notifications still go out over the live socket. Every client passes [live-editor-model.ts](../src/lib/live-editor-model.ts) `isLiveEditorModel` as the `modelFilter`, so only editor tabs' live models (`file://` or `loxel://HEAD/` without a query or fragment, see [URI schemes](#uri-schemes)) are synced to servers; diff, history and compare sides are not, and get no LSP features. Every worktree client also passes `workspaceFileSystem: createLspWorkspaceFiles(wtPath)`, an `onWorkspaceEditFailure` that shows the reason as a toast, and its route as `markerOwner` (`python-lsp`, `ruff-lsp`, `mypy-lsp`), so the next client of a route takes over the diagnostics owner of the one before. `onConnected(transport)` runs for each connection, reconnects included, and what it returns is disposed with it. Errors and warnings a server sends with `window/showMessage` (mypy's setup problems, ruff's config errors) are shown as toasts, each distinct message once per session. What happens when the socket closes on its own is the [reconnect policy](#lifecycle).
- [lsp-workspace-files.ts](../src/lib/lsp-workspace-files.ts) `createLspWorkspaceFiles(wtPath)` is the disk side of language-server workspace edits (rename, code actions, `workspace/applyEdit`) for files with no editor model. Text goes through the regular file-content and file-write routes, unformatted, so an open editor of the file sees an ordinary external change. Creates, renames, moves and deletes go through the files-panel operations in [file-operations.ts](../src/lib/file-operations.ts), so tabs follow and the files panel's undo history records them; missing parent folders are created first. Edits on disk are confined to the user's own text files in the worktree: `stat` refuses, for every resource an edit touches, a path outside the worktree or under a dependency, environment, git or nested-worktree folder, checked by name and again on the real path so a symlink cannot lead an edit outside, and `readFile` refuses a file that does not read back as UTF-8 text, since the content route decodes it lossily. An open file that is only text-edited is exempt, since its model changes like typing wherever the file is. Text writes to unopened files are not on any undo stack. The YAML client has no worktree and no file system, so its edits are limited to open models.
- The per-language modules ([ts-lsp-client.ts](../src/lib/ts-lsp-client.ts), [python-lsp-client.ts](../src/lib/python-lsp-client.ts), [ruff-lsp-client.ts](../src/lib/ruff-lsp-client.ts), [mypy-lsp-client.ts](../src/lib/mypy-lsp-client.ts), [astro-lsp-client.ts](../src/lib/astro-lsp-client.ts), [docker-lsp-client.ts](../src/lib/docker-lsp-client.ts), [terraform-lsp-client.ts](../src/lib/terraform-lsp-client.ts), [xml-lsp-client.ts](../src/lib/xml-lsp-client.ts), [toml-lsp-client.ts](../src/lib/toml-lsp-client.ts)) only bind a route, the server's name for notices and Monaco language IDs. TypeScript binds `typescript`, `javascript`, `tsx`, `jsx`, `json`, `jsonc`, and reports its models' indentation through `onConnected` with `reportDocumentIndentation` from [lsp-document-indentation.ts](../src/lib/lsp-document-indentation.ts) (see the TypeScript manager above); Docker binds `dockerfile` and `dockerbake`. Python models get three clients, basedpyright, ruff and mypy, each with its own lazy connector (mypy's server starts nothing in a project without a mypy config). [yaml-lsp-client.ts](../src/lib/yaml-lsp-client.ts) connects once per renderer, without a `wt` and never disconnecting, through the same `createLspClient`.
- [monaco-env.ts](../src/lib/monaco-env.ts) is the single wiring point, imported for its side effects. It disables all of Monaco's built-in TS/JS features (no TS worker; the JSON, CSS and HTML workers stay), registers the language IDs Monaco does not ship (`terraform`, `astro`, `tsx`, `jsx`, `dockerbake`, `toml`), and connects the servers. YAML connects at load. TypeScript is eager: it connects to the active worktree and reconnects whenever `activeWorktreePath` changes. Every other server goes through `createLazyLspConnector`, which counts live models (`isLiveEditorModel`) of its languages in the active worktree (plus those of files outside every project, served by the active worktree's server) and connects on the first one, disconnecting at zero. Diff, history and compare models are not counted. It also registers the editor opener from [editor-opener.ts](../src/lib/editor-opener.ts), which turns go-to-definition results and document or hover links to an editor file (`editorFilePath`, see [URI schemes](#uri-schemes)) in another model into `dispatchOpenFile`, which opens files outside every project (stdlib, installed packages) as external files; a target in the source's own model is left to Monaco to reveal in place. It installs the peek model resolver too, which lets peek widgets show files no tab has open (see [EDITOR.md](EDITOR.md#peek-widgets)).
- [packages/monaco-lsp-client](../../monaco-lsp-client/README.md) is a fork of `@vscode/monaco-lsp-client` consumed as TypeScript source. Its main local changes for Loxel are the `languageId` option (`TextDocumentSynchronizer` only syncs models whose language is in the set, which is what lets several servers coexist on one Monaco instance) and the `modelFilter` option above; its README lists the other local changes, including how `workspace/executeCommand` and workspace edits (rename, code actions, `workspace/applyEdit`) are handled. Diagnostics from the server become Monaco markers under the client's `markerOwner` (the route, see above), so servers sharing a model keep separate markers, and a disposed client removes its own. A code action request sends back the server's own diagnostics under the requested range as the server sent them (with `code`, `source` and `data`), which is how ruff finds its quick fixes.
- [ws-shim.ts](../src/lib/ws-shim.ts) is aliased to `ws` in [vite.config.ts](../vite.config.ts) because `@hediet/json-rpc-websocket` imports the Node `ws` package; the browser uses the native `WebSocket`.

## URI schemes

[CodeEditorPanel.tsx](../src/components/code-editor/CodeEditorPanel.tsx) picks the model URI per Monaco language. `useFileScheme` (yaml, json, dockerfile, dockerbake, terraform, astro, xml, python, toml) gives `file://<abs path>`, which those servers need for schema matching, workspace indexing and import resolution. Every other language gets `loxel://HEAD/<abs path>`. Git diff views ([GitSideBySideDiffView.tsx](../src/components/diff-viewer/GitSideBySideDiffView.tsx)) use `loxel://<ref or HEAD>/<repo-relative path>#<side>`, and compare panels ([CompareFilesPanel.tsx](../src/components/compare/CompareFilesPanel.tsx)) `loxel://compare/<abs path>#<panel id>-<side>`; both render through [diff/EditorPanel.tsx](../src/components/diff/EditorPanel.tsx).

Only the TypeScript manager translates (`toServerUris` / `toClientUris` in [ts-lsp-manager.ts](../src/server/ts-lsp-manager.ts)): client-to-server it replaces `loxel://head/` (case-insensitive) with `file:///`; server-to-client it replaces `file:///` with `loxel://HEAD/` except for `.json` / `.jsonc` paths, whose editor models use `file://`. No other manager rewrites URIs, so every other server sees and returns the live models' own `file://` URIs. monaco-lsp-client sends document URIs percent-encoded (Monaco's `Uri.toString()`), the way servers write them, and matches the URIs servers send back to models after re-encoding them the same way, since servers differ in what they escape; the server side builds `rootUri`, `workspaceFolders` and watched-file URIs with `fileUri`, which encodes exactly like Monaco, so they also match document URIs as strings. Paths with spaces, `#`, `%` or non-ASCII characters therefore reach every server intact. One function decides which URIs are editor files: `editorFilePath` in [live-editor-model.ts](../src/lib/live-editor-model.ts) accepts `file:` and `loxel://HEAD` (any casing) with no query or fragment and returns the path. `isLiveEditorModel` (the clients' `modelFilter` and the lazy connector's check), the editor opener, the peek model resolver, Go to Symbol and the workspace-edit file system all use it. A peek widget's snapshot of a file has the file's URI but is not live: `isLiveEditorModel` also rejects models marked with `markPreviewModel`.

## Diagnostics

There are two TypeScript diagnostic paths:

- **Live, per file.** The TS LSP publishes diagnostics, which `monaco-lsp-client` turns into markers under the client's owner.
- **Project-wide snapshot.** `GET /api/diagnostics?wt=&ref=&worktree=` ([routes.ts](../src/server/routes.ts) `handleDiagnostics`) calls `getDiagnostics` in [diagnostics.ts](../src/server/diagnostics.ts), which runs `tsc --noEmit --pretty false` (30 s timeout) and parses lines into `TypeScriptDiagnostic` from [diagnostics-model.ts](../src/api/diagnostics-model.ts) (repo-relative file, 1-based line and column, code, severity, `node_modules` excluded). The code editor and the diff view apply these as `typescript` markers, and only request the snapshot for files `hasTypeScriptDiagnostics` in [typescript-files.ts](../src/lib/typescript-files.ts) accepts: TS/JS sources (`TS_SOURCE_EXTENSIONS`, which the TS manager's routing also extends) and `tsconfig*.json`, where `tsc` reports config errors.

The server skips `tsc` and returns no diagnostics when the worktree, or the `ref`'s tree, has no root `tsconfig.json`. For the working tree (no `ref`) `tsc` runs directly in the worktree and nothing is cached on the server. For a `ref` the server validates it against `REF_PATTERN`, deduplicates concurrent requests, checks the tree for `tsconfig.json` with `git ls-tree` (caching an empty result when it is missing), creates a detached temporary worktree named `${INTERNAL_WORKTREE_PREFIX}diag-<sha8>` in a `mktemp -d` directory, symlinks `node_modules` from the source checkout, runs `tsc`, caches the result by ref in memory for the server's lifetime, and force-removes the worktree. `INTERNAL_WORKTREE_PREFIX` ([worktree-utils.ts](../src/server/worktree-utils.ts)) hides these worktrees from worktree lists, and `pruneOrphanedTempWorktrees` in `server.ts` force-removes all of them when a project is initialized, to clean up after crashes.

On the client the snapshot is a TanStack query under `queryKeys.diagnostics(...)`.

## Formatting

Formatting runs on the server as part of `POST /api/file-write` when the request carries `format: true` and valid `formattingSettings` ([FormattingSettings](../src/lib/formatting-model.ts)). Editors set `saveOptionsRef` (explicit save) and `autoSaveOptionsRef` (auto-save, only when `formatOnAutoSave`) through [use-disk-synced-content.ts](../src/hooks/use-disk-synced-content.ts); [save-editor-content.ts](../src/lib/save-editor-content.ts) sends them, and the response's formatted `content` is merged back into the editor as a programmatic "format-echo" edit (see [EDITOR.md](EDITOR.md#disk-synced-content) for the save state machine). When the save went out unformatted for a reason the user can fix, the response also carries a `formatNotice`, which the client shows as a toast once per distinct message per session. Only files inside the worktree's own tree are formatted; Others folders, drafts and external files are written as-is.

[format-service.ts](../src/server/format-service.ts) `FormatService.format()` returns a `FormatResult` whose `content` is `null` (write unformatted) when disabled, over 1 MB, without an extension, with no match, or when the formatter fails. Only a binary that is missing or cannot start (`Bun.spawn` throws: `ENOENT` for a missing binary or interpreter, which `Bun.which` tells apart, any other code such as `EACCES` / `ENOEXEC` for a file that is not runnable) and a timeout set its `notice`; a non-zero exit or empty output, typically a syntax error the language server already flags, is only logged so it does not repeat on every save. Resolution order:

1. **Manual overrides** from settings, first entry whose comma-separated extension list contains the file's extension. Always run as a command.
2. **Auto-detection** (if `autoDetect`), by config files at the worktree root, evaluated in `DETECTION_RULES` order, first formatter claiming the extension wins: prettier (config files or a `prettier` key in `package.json`), oxfmt (`.oxfmtrc.*` or an `oxfmt` dependency), rustfmt, clang-format, deno. Prettier and oxfmt share `SHARED_FORMAT_EXTENSIONS`; prettier adds `svelte` and `astro`, oxfmt adds `toml`. Because prettier is first, a project with both uses prettier for every shared extension. Detection is cached per worktree, keyed by a fingerprint of config-file sizes and mtimes.
3. **Python** (`.py`, `.pyi`, if `autoDetect`) is resolved per file instead, by `detectPythonFormatter` in [python-formatter.ts](../src/server/python-formatter.ts), walking from the file's directory up to the worktree root so monorepo subprojects are found. Because a ruff config or dependency often exists for the linter alone while black only formats, the nearest directory with a formatting signal decides: a ruff config (`.ruff.toml` / `ruff.toml` or `[tool.ruff]`) with a `format` table selects ruff, a `[tool.black]` table or black dependency selects black. A ruff config without `format`, or a ruff dependency, selects ruff only when no such signal exists up to the root. Dependencies are read from `pyproject.toml` (PEP 621 dependencies and extras, PEP 735 groups, uv, Poetry and PDM dev dependencies, Hatch environments). A bare `pyproject.toml` formats nothing, matching the opt-in signal prettier and oxfmt need. ruff runs as `ruff format --force-exclude --stdin-filename {file}` (without `--force-exclude` ruff ignores its `exclude` settings for stdin) and black as `black --quiet --stdin-filename {file} -`; both resolve their own nested config and infer stub style from the file name. This walk is uncached: a few `existsSync` calls and small TOML parses per save. `getDetectedFormatters` lists the Python formatter detected at the worktree root.

Each rule has a `BackendMode` from [formatter-backends.ts](../src/server/formatter-backends.ts). `command` spawns the tool per request with content on stdin, `{file}` / `{ext}` substituted, the worktree's `node_modules/.bin` prepended to `PATH` (for Python files run by command name, `findVenvBin` in [python-formatter.ts](../src/server/python-formatter.ts) prepends the environment directory holding that command ahead of it, so a project-pinned ruff or black beats a global one: the nearest sub-project `.venv` / `venv` / `env` with a `pyvenv.cfg` between the file's directory and the worktree root, else the worktree's shared resolution (`dirname(pythonPath)`, when it is an environment), else a venv at the root; environments that fail the [environment trust rule](#environment-trust-rule) are skipped), and a 5 s timeout. The two persistent backends are cached per `(worktree, command)`, restarted if dead, and on a `null` result destroyed and replaced by command mode for that request:

- [oxfmt-lsp-backend.ts](../src/server/oxfmt-lsp-backend.ts) keeps an `oxfmt --lsp` process (worktree `node_modules/.bin` first, then `PATH`) and formats via `didOpen` / `textDocument/formatting` / `didClose`, applying the returned edits.
- [prettier-lib-backend.ts](../src/server/prettier-lib-backend.ts) dynamically imports the worktree's own `node_modules/prettier` and calls `resolveConfig` (with `editorconfig: true`, as the prettier CLI does, so a project's `.editorconfig` shapes the output like it shapes the editor, and `useCache: false`, since nothing would clear prettier's config cache when a config file changes) + `format` in-process.

`invalidateCache(wtPath)` (called from worktree teardown) drops detection and destroys backends; `destroy()` runs at shutdown. `GET /api/detected-formatters?wt=` exposes detection to the settings UI.

## Schemas and JSON validation

- [schema-service.ts](../src/server/schema-service.ts) resolves a schema from an HTTP(S) URL (1 h TTL, 5 MB cap, 10 s timeout) or a local path (relative to a base directory, revalidated by mtime). Other URL schemes are rejected.
- `POST /api/schemas/sync` receives the enabled schema settings and routes each glob by `classifySchemaGlob` in [schema-glob.ts](../src/lib/schema-glob.ts) (also behind the Languages column of Settings > Schemas): a glob ending in `.json` / `.jsonc`, `.yml` / `.yaml` or `.toml` (brace alternatives included) goes to those languages, any other glob (`**/*`, `**/Pipfile`) to all three. JSON schemas are resolved inline through the schema service and returned for Monaco. YAML and TOML get a `url → globs` map (absolute local paths as `file://` URLs) pushed to `YamlLspManager.updateSchemas` and `TomlLspManager.updateSchemas`; those servers fetch the schemas themselves, since schemas such as SchemaStore's `pyproject.json` `$ref` siblings by relative URL. `GET /api/schemas/resolve` resolves a single schema.
- [schema-sync.ts](../src/lib/schema-sync.ts) calls the sync endpoint after the settings store hydrates and when settings are saved, coalescing overlapping calls. `selectEffectiveSchemas` lists user mappings before built-in ones: JSON and YAML combine every matching schema, but Tombi applies the first one, so a user mapping overrides a built-in for the same TOML file.
- [json-schema-registry.ts](../src/lib/json-schema-registry.ts) owns the single global `monaco.json.jsonDefaults` schema list (Monaco replaces it wholesale), merging configured glob schemas with per-file `$schema` schemas. `CodeEditorPanel` detects `$schema` in JSON models (debounced), resolves it through the server, and registers it under the URL Monaco's JSON worker would compute relative to the file's `file://` URI; this is one reason JSON is in `useFileScheme`.
- Monaco's JSON diagnostics are permissive (comments and trailing commas ignored) so JSONC files work. [json-strict-validator.ts](../src/lib/json-strict-validator.ts) re-parses files resolved as strict `json` with `jsonc-parser` and adds `json-strict` markers for comments and trailing commas.

### TOML (Tombi)

[toml-lsp-manager.ts](../src/server/toml-lsp-manager.ts) runs [Tombi](https://github.com/tombi-toml/tombi) per worktree. Tombi was chosen over Taplo (Even Better TOML's server) because it is actively released, supports current JSON Schema drafts, and serves pull diagnostics, code actions, go-to-definition and inlay hints besides completion, hover, symbols and folding; Taplo has not had a release since 0.10.0 (May 2025) and takes associations only as regular expressions.

- **Associations.** The schema map reaches Tombi as editor configuration, a `workspace/didChangeConfiguration` with a `tombi` section (`tombiSettings`), sent on `initialized` and on every `updateSchemas()`. Each Loxel glob becomes Tombi patterns (`toTombiPatterns`): brace alternatives are expanded, since Tombi's glob matcher has none, and a plain name (`pyproject.toml`, `.cargo/config.toml`) gets `**/` so it matches at any depth, as Monaco's JSON `fileMatch` does. Tombi matches against the canonical absolute path and its `*` also matches `/`, so a pattern with wildcards is anchored at the session's worktree instead (`config/*.toml` becomes `<worktree>/**/config/*.toml`), keeping it from matching through an ancestor directory; within the worktree a TOML glob's `*` still spans directories, which JSON's does not. Editor configuration replaces the previous one wholesale, so updates and removals apply live, unlike `tombi/associateSchema`, which only appends.
- **Catalogs and strict mode off.** The same configuration sets `schema.catalog.paths = []`, so neither SchemaStore's catalog nor Tombi's embedded one associates schemas: the Schemas settings are the only automatic associations, and disabling a built-in removes its schema. Tombi may still fetch SchemaStore's catalog once while it starts (it loads its default configuration before this one arrives, and caches the catalog for a day); its associations go unused. `schema.strict = false` keeps JSON Schema semantics (Tombi's strict mode treats a missing `additionalProperties` as `false`), so a schema validates TOML as it validates JSON and YAML. `#:schema` directives in a file take precedence over the configuration.
- **Tombi's own configuration wins.** Tombi uses editor configuration only for files that no Tombi config governs: a `tombi.toml` / `.tombi.toml` / `.config/tombi.toml` or a `pyproject.toml` with `[tool.tombi]` in the file's directory or above, or the user's `~/.config/tombi/config.toml`. Those projects keep the behavior of the `tombi` CLI, catalogs included.
- **Diagnostics refresh.** Tombi caches each open document's diagnostics per version, and a configuration change does not clear the cache. After each push the manager therefore sends a `tombi/associateSchema` with no file patterns (it matches nothing), which resets the cache and makes Tombi send `workspace/diagnostic/refresh`, so Monaco pulls fresh diagnostics without an edit. Tombi takes that association only after the configuration is in place (it holds the association list's read lock until then), and keeps every association, so each push leaves one inert entry for the session's lifetime.
- **Flags.** Semantic tokens are off (the TextMate grammar highlights TOML), formatting is suppressed because format on save owns it and Tombi's formatter reorders keys by the schema's `x-tombi-table-keys-order`, and watched files are forwarded so Tombi reloads changed config files and local schemas.

## Highlighting and language resolution

- [highlighter.ts](../src/lib/highlighter.ts) holds a singleton Shiki highlighter (themes `loxel-dark` and `github-dark`, a fixed `BUNDLED_LANGUAGES` list), the `FILENAME_TO_LANG` and `EXT_TO_LANG` tables, `detectLanguage()` (case-insensitive filename, `.d.ts`, `.env*`, then extension) and `highlightCode()` for HTML token output. Language IDs here are Shiki IDs; `toMonacoLanguage()` in [monaco-theme.ts](../src/lib/monaco-theme.ts) maps the few that differ (for example `jsonc` → `json`, `dotenv` → `ini`).
- `monaco-env.ts` passes the highlighter to `shikiToMonaco`, which attaches a TextMate tokenizer to every Monaco-registered language ID that Shiki has loaded, replacing Monarch. Languages Monaco does not ship (`tsx`, `jsx`, `astro`, `terraform`, `toml`) are registered there first so they get one. Languages Shiki does not know get Monarch tokenizers: [hcl-monarch.ts](../src/lib/hcl-monarch.ts) for `dockerbake` and [pip-requirements-monarch.ts](../src/lib/pip-requirements-monarch.ts) for `pip-requirements`.
- Editing behavior comes from Monaco language configurations. Monaco registers its built-in ones lazily when a language is first encountered, and registrations merge field by field with the last one winning, so [python-language-config.ts](../src/lib/python-language-config.ts) re-registers Monaco's Python `conf` with extra auto-closing pairs and `onEnterRules` (triple quotes, dedent after `return`/`pass`/`break`/`continue`/`raise`) only after the built-in registration has run; `python-language-config.test.ts` checks that order and the resulting editing behavior, so a Monaco upgrade that changes either fails there. It also adds a keydown hook, for Python and TOML (whose configuration in `monaco-env.ts` also auto-closes triple quotes), that steps over the rest of a triple-quote delimiter, since Monaco overtypes only the first character of a multi-character auto-closed pair.
- [resolve-language.ts](../src/lib/resolve-language.ts) `resolveLanguage(path, associations, content)` is what the code editor uses: enabled file associations first (first glob match wins, matched with `dot: true` so globs cross dot directories; user entries precede built-ins in `selectEffectiveFileAssociations`), then `detectLanguage`, then content sniffing (shebang, XML prolog). The built-in associations in [settings-store.ts](../src/store/settings-store.ts) are generated from `FILENAME_TO_LANG` / `EXT_TO_LANG` plus glob overrides that exact names cannot express (`tsconfig*.json` → `jsonc`, `*.docker-bake.hcl` → `dockerbake`, `requirements*.txt` → `pip-requirements`).
- [textmate-inspector.ts](../src/lib/textmate-inspector.ts) backs the editor's token-scope inspector using `codeToTokensBase` with explanations.
- [file-icons.tsx](../src/lib/file-icons.tsx) has its own filename, filename-pattern, compound-extension and extension maps (JetBrains icon theme) and is independent of language resolution.
