# Language Servers and Language Intelligence

How Loxel provides language features: language-server subprocesses bridged to Monaco over WebSockets, project-wide TypeScript diagnostics, formatting, JSON/YAML schemas and syntax highlighting.

To add a new language server, follow the [add-language-server skill](../../../.agents/skills/add-language-server/SKILL.md) and its [per-server quirks reference](../../../.agents/skills/add-language-server/references/existing-integrations.md). This doc is the architecture that skill assumes; it does not repeat the checklist. For the end-user view see the site's [TypeScript Intelligence](../../site/src/content/docs/typescript-intelligence.md) page.

## Data flow

```
Monaco model ──(MonacoLspClient, JSON-RPC over WS)──▶ /ws/<lang>-lsp[?wt=<path>]
   ▲                                                       │ server.ts routes by ws.data.type
   │                                                       ▼
   └──────── providers / markers ◀── WS ◀── <Lang>LspManager (StdioLspManager subclass)
                                                           │ Content-Length framed stdio
                                                           ▼
                                                 language-server subprocess (cwd = worktree)
```

The server is a thin proxy. It owns process lifetime, framing and a small set of message rewrites (initialize parameters, URI translation, capability scrubbing). All LSP feature logic on the client lives in the `monaco-lsp-client` fork, which registers Monaco providers from the server's advertised capabilities.

## Server side

### `StdioLspManager` base class

[stdio-lsp-manager.ts](../src/server/stdio-lsp-manager.ts) bridges one WebSocket to one subprocess. Public API: `handleMessage(ws, data)`, `detach(ws)` (kill and forget), `destroy()` (kill all, used on server shutdown). Subclasses add their own entry points (`createSession(ws, wtPath)` / `destroySession(ws)` for worktree-scoped managers, `attach(ws)` for YAML) that call the protected `startSession(ws, context)`.

- **Session model.** `sessions: Map<ServerWebSocket, TSession>`. `BaseLspSession` holds the `ws`, the `proc`, the stdout reassembly buffer and `documentContents` (used only for full-text sync). `WtLspSession` adds `wtPath`.
- **Dedup by key.** `getSessionKey(context)` returns a key (worktree managers return `wtPath`; YAML returns `null`). `startSession` keeps at most one live session per key: if another WebSocket already owns the key, that session is detached and its socket closed with code `4000` ("Replaced by newer connection"). A missing binary closes the socket with `4001`.
- **Spawn.** `Bun.spawn([resolveBinary(), ...spawnArgs()])` with piped stdio, `cwd` from `spawnOptions(context)` and the environment from `buildSpawnEnv()` in [shell-env.ts](../src/server/shell-env.ts) (the login-shell `PATH`, so servers that run user tools such as basedpyright's interpreter or terraform-ls's `terraform` find them when Loxel was launched from Finder) with `NODE_OPTIONS` cleared. Server startup waits up to `LOGIN_SHELL_ENV_WAIT_MS` for that `PATH` before serving, so the first sessions do not race it. Default args are `["--stdio"]`.
- **Framing.** `writeToStdin` adds the `Content-Length` header and flushes the `FileSink` per message. `drainMessages` parses frames out of stdout and hands each body to `handleServerFrame`.
- **`initialize` rewriting.** When `getSessionWorkspace(session)` returns a path, missing `rootUri` / `rootPath` / `workspaceFolders` are filled in (client values win). `getInitializationOptions(session)` is merged one level deep into the client's `initializationOptions` (client values win). Config that the server only accepts by push goes in `onClientInitialized`, which runs after the client's `initialized` notification is forwarded and typically sends `workspace/didChangeConfiguration`.
- **Pulled configuration.** monaco-lsp-client does not implement `workspace/configuration`, so a subclass that defines `workspaceConfiguration(session, section)` gets the `workspace.configuration` capability injected into `initialize`, and the base answers the server's requests itself, one section at a time (asynchronously, dropped if the session is gone). `notifyConfigurationChanged(session)` sends `workspace/didChangeConfiguration` with `settings: null`, which makes such a server pull again.
- **Watched files.** monaco-lsp-client cannot watch files, so without help a server never hears about changes to files that are not open: new modules, `git checkout`, an agent's edits, `pyrightconfig.json` / `tsconfig.json`. A subclass that sets `forwardWatchedFiles` (Python and TypeScript) gets the `workspace.didChangeWatchedFiles` capability (`dynamicRegistration: true`, without `relativePatternSupport`, which keeps servers from asking for most directories outside the worktree; globs that still point outside it never match) injected into `initialize` by `handleMessage`, before `handleClientData`. `drainMessages` takes the server's `workspace/didChangeWatchedFiles` entries out of `client/registerCapability` / `client/unregisterCapability` before `handleServerFrame`, so overriding subclasses need no wiring: their glob watchers are kept per session in a `WatchedFilesForwarder` from [lsp-watched-files.ts](../src/server/lsp-watched-files.ts), and the request is answered directly, or forwarded with only the remaining registrations. The worktree's `ProjectFilesService` reports each watcher batch through `onPathsChanged`; `server.ts` hands it to every worktree manager's `notifyWatchedFilesChanged(wtPath, paths)`, and the forwarder matches it against the watchers (plain globs and absolute globs that spell out the worktree path relative to the worktree, with that path taken literally rather than as glob syntax, other absolute globs from the file system root, relative patterns under their base; case-insensitively on macOS and Windows, where TypeScript registers lowercased paths), drops paths no watcher wants, and sends one `workspace/didChangeWatchedFiles` with `file://` URIs after 250 ms of quiet or at most 1 s after the oldest queued change. The watcher does not say whether a path is new, so the type comes from `stat`: missing is deleted; a last write within 1 s of the birth time (or no birth time), or a metadata change more than 1 s after the last write (a file renamed or moved into place), is created; anything else is changed. Atomic saves therefore arrive as creations. The distinction matters: basedpyright only re-resolves imports for created files. Only changes inside the session's worktree and outside its git-ignored directories are reported, and only while a client is subscribed to that worktree (when its file watcher runs).
- **Session teardown.** `onSessionClosed(session)` fires when a session is detached, destroyed or its process exits (possibly more than once) for releasing per-session resources such as watchers.
- **`disableSemanticTokens`.** Strips the semantic-tokens client capability from `initialize`, deletes `semanticTokensProvider` from the initialize response, and filters semantic-token entries out of `client/registerCapability` (answering the server directly when nothing is left).
- **`requiresFullTextSync`.** The base tracks text from `didOpen`, applies incremental `didChange` ranges locally (clamped), and forwards a single full-text change. A `didChange` for an untracked URI is forwarded unchanged with a warning.
- **Errors.** JSON-RPC error responses from the server are logged at info level before forwarding.
- **stderr.** Each session reads stderr line by line through a token bucket from [stderr-throttle.ts](../src/server/stderr-throttle.ts) (burst 200 lines, refill 50 lines/s, "suppressed N" summary every 5 s and on exit) so a chatty server cannot flood the shared log ring buffer. The last 20 lines are kept regardless and logged as a warning if the process exits non-zero.

The TypeScript manager is the outlier. It always overwrites `rootUri` / `workspaceFolders` / `initializationOptions` (it does not use the base merge), answers `workspace/configuration` and `window/workDoneProgress/create` itself because TypeScript blocks on them, pushes completion preferences after `initialized`, rewrites `languageId` to `typescriptreact` / `javascriptreact` for `.tsx` / `.jsx`, drops `textDocument/*` messages whose URI does not have a TS/JS/JSON extension, and translates URIs (see [URI schemes](#uri-schemes)). It deliberately forwards `client/registerCapability` so Monaco sees TypeScript's dynamic semantic-tokens registration; the base has already taken TypeScript's file-watcher registrations out by then (see watched files above).

### Python environment

basedpyright's own environment discovery covers only a root `.venv` and it ignores Loxel's `initializationOptions`; without an interpreter it runs `python3` from its `PATH`. [python-env.ts](../src/server/python-env.ts) is the single resolver of a worktree's interpreter, meant for every Python feature (language server, terminals, tools), and returns a `PythonEnv` from [python-env-model.ts](../src/api/python-env-model.ts) (`source`, absolute `pythonPath`, `envPath` prefix or null; a venv's bin directory is `dirname(pythonPath)`).

- **`resolvePythonEnv(wtPath, { overridePath?, env? })`** tries, first hit wins: the override (by default the worktree's chosen interpreter from [python-override-store.ts](../src/server/python-override-store.ts); `null` skips it), `VIRTUAL_ENV` only when it lies inside the worktree, a `.venv` / `venv` / `env` directory with `pyvenv.cfg` at the worktree root (covers uv, uv workspaces with one root venv, PDM, `python -m venv`), `.pixi/envs/default`, Poetry's `poetry env info --path` (only with a `poetry.lock` and `poetry` on `PATH`, 10 s timeout), then `python3` / `python` on the login-shell `PATH` (scanned entry by entry). A candidate, including the `PATH` interpreter and the override, counts only if its interpreter is executable (a dangling venv symlink does not) and neither it nor its symlink target is tracked by git, asking the innermost repository that contains it (so submodules and nested repositories count) about its physical path wherever it is (a committed symlink can reach another checkout of the repository, while a `.venv` linked to another worktree's ignored environment is fine), and treating a git error as tracked while the path is inside the worktree: real environments are never committed, and basedpyright executes the interpreter, so a committed `.venv/bin/python` would otherwise run repository code when a Python file is opened. The override is held to the same rules. It never runs the interpreter itself and never throws. Automatic resolution is per worktree: a per-package venv in a monorepo without a root venv is used only once the user chooses it.
- **Choosing an interpreter.** `listPythonEnvs(wtPath)` returns `{ candidates, automatic }`, the candidates without duplicates: the automatic choice, then `.venv` / `venv` / `env` and every `.pixi/envs/*` at the root and in project directories up to three levels deep (directories holding a `pyproject.toml`, `setup.py`, `setup.cfg`, `requirements.txt`, `Pipfile` or `pixi.toml`, found with `git ls-files --cached --others --exclude-standard` so ignored trees are skipped), Poetry's environment, the `PATH` interpreter, and last the stored override when it is none of those, all under the same executable and not-tracked rules. `normalizePythonOverride(wtPath, input)` turns a path the user entered (`~/` allowed, or an environment directory) into an interpreter path, or throws a user-facing error. The override route also requires `--version` to report a Python version. The choice is stored per worktree in `stores.db` under `python-interpreter:<wtPath>` (read back only if absolute) and deleted with the worktree; `onPythonOverrideChange` reports writes. Because the resolver reads it, every Python feature gets the choice without state of its own.
- **Version.** [python-version.ts](../src/server/python-version.ts) runs `<python> --version` (CPython prints it before reading configuration or importing `site`) for interpreters the resolver accepted, cached by path and file identity, so a recreated venv or an upgraded interpreter is read again; a failed read is not cached.
- **`watchPythonEnv(wtPath, current, onChange)`** sets non-recursive watches for the next change: each candidate environment's deepest existing ancestor (for the next path segment) or, once it exists, its `bin` / `pyvenv.cfg` / `conda-meta` entries and the contents of its `bin` (conda and Pixi create `bin` before the interpreter), the root `poetry.lock`, and `current`'s directory entry, `bin` and `site-packages` (which also covers environments outside the worktree), debounced by 1 s. Callers re-resolve and re-watch on every change, keeping the old watch until the new one is armed and passing a `hasPendingChange` to the new watch's debounce with `nudge()`, so changes made during resolution are neither lost nor re-resolved back to back.
- **basedpyright.** `PythonLspManager` spawns basedpyright with the worktree's own directories removed from `PATH` (`pathOutsideWorktree`), so its fallback `python3` lookup when nothing resolved cannot pick a committed interpreter either. It watches the layout and resolves when a session spawns, and answers the `python` section with only `pythonPath`, so the resolver stays the source of truth. When nothing resolved it answers a `venvPath` of the worktree with no `venv` instead: that turns off basedpyright's own root `.venv` detection, which would run a committed interpreter, without selecting an environment. After `initialized`, every watcher change re-resolves, re-arms the watch, then calls `notifyConfigurationChanged`, so basedpyright re-pulls and re-resolves imports: this covers `uv sync` creating `.venv` and packages installed later. A `pyrightconfig.json` / `[tool.basedpyright]` / `[tool.pyright]` `venv` still wins inside basedpyright over the interpreter Loxel passes, whether detected or chosen. The worktree file watcher skips git-ignored directories such as `.venv`, so this environment watch, not watched files, is what tells basedpyright about installed packages.
- **basedpyright settings.** The `basedpyright` section sets `analysis.typeCheckingMode` to `standard` (basedpyright's default `recommended` flags ordinary code) and repeats `autoSearchPaths: true`, which any `analysis` section otherwise resets. basedpyright ignores these analysis settings when the project has a config file, so the project's rules, and basedpyright's own defaults for anything the file leaves out, win.
- **Override changes.** [server.ts](../src/server/server.ts) subscribes to `onPythonOverrideChange`: it calls `PythonLspManager.refreshWorktreeEnvironment(wtPath)`, which re-resolves that worktree's sessions and notifies basedpyright like a watcher change, and sends `python_env_changed` to the worktree's subscribers. The manager also sends `python_env_changed` when a re-resolution yields a different interpreter, so the status bar follows environments created or removed on disk; an interpreter outside any environment is watched by its directory entry so its removal is noticed. Only a worktree's subscribers get the message, so the renderer invalidates its cached interpreters whenever it subscribes to a worktree ([useWsSubscription.ts](../src/hooks/useWsSubscription.ts)).
- **API.** `GET /api/python-env?wt=` returns `{ env, overridePath }` with `env` (a fresh resolution) carrying its `version`; `GET /api/python-env/candidates?wt=` returns `{ candidates, automaticPath, overridePath }`; `POST /api/python-env/override` with `{ worktreePath, pythonPath }` validates and stores the choice (`null` clears it) and answers like the first route. `wt` must be a worktree of a registered project, since resolution may run `poetry` there. The renderer side is [python-interpreter.ts](../src/lib/python-interpreter.ts) (labels and the picker, run by the `python.selectInterpreter` action) and [PythonInterpreterStatus.tsx](../src/components/panels/PythonInterpreterStatus.tsx) in the status bar, shown while the active editor's file resolves to Python.

### Binary resolution and packaging

`resolveBundledBinary(name, devPath?)` checks, in order: a sibling of `process.execPath` (the packaged layout, where `loxel-server` and all servers are copied side by side), then `devPath` if given (downloaded binaries under `build/`) or else `node_modules/.bin/<name>`, then the login-shell `PATH`. TypeScript uses its own resolver: `typescript-lib/tsc` next to the executable when packaged, else the `@typescript/native` Node shim in dev.

`build:server:standalone` in [package.json](../package.json) produces every binary under `build/`, and [electron-builder.yml](../electron-builder.yml) `extraResources` copies them next to `loxel-server` (plus basedpyright's `typeshed-fallback` and the whole `typescript-lib/`, since the native compiler reads its sibling `lib.*.d.ts`). The scripts fall into three kinds:

- Bun-compiled from npm packages: [build-yaml-lsp.ts](../scripts/build-yaml-lsp.ts), [build-basedpyright-lsp.ts](../scripts/build-basedpyright-lsp.ts), [build-astro-ls.ts](../scripts/build-astro-ls.ts) (bundle with `Bun.build`, using plugins where UMD module loading defeats the bundler, then `bun build --compile`; basedpyright's single pre-bundled file is compiled through a wrapper entry that also replaces `v8.getHeapStatistics`, which is too slow under Bun; packages located with [resolve-package.ts](../scripts/resolve-package.ts)).
- Downloaded native binaries with per-platform SHA256 pins verified before writing or extracting: [download-docker-lsp.ts](../scripts/download-docker-lsp.ts), [download-terraform-ls.ts](../scripts/download-terraform-ls.ts), [download-xml-lsp.ts](../scripts/download-xml-lsp.ts) (GraalVM-native LemMinX, no JRE).
- Copied: [copy-typescript.ts](../scripts/copy-typescript.ts) copies the platform `@typescript/typescript-<platform>-<arch>` `lib/` directory, so TypeScript ships in lockstep with the server.

Packaging and signing of these extra binaries is covered in [ELECTRON.md](ELECTRON.md) and [RELEASE_SIGNING.md](RELEASE_SIGNING.md).

### WebSocket routes

[server.ts](../src/server/server.ts) creates one instance of each manager at startup. In `fetch`, `/ws/yaml-lsp` upgrades with `data: { type: "yaml-lsp" }`. The `worktreeLspTypes` array (`ts-lsp`, `docker-lsp`, `terraform-lsp`, `python-lsp`, `astro-lsp`, `xml-lsp`) maps `/ws/<type>` to an upgrade with `data: { type, wtPath }`, rejecting requests without `?wt=` with 400. `WorktreeLspType` is derived from the `WsData` union in [server-state.ts](../src/server/server-state.ts), so adding a type there and to the array is what makes a route exist. The `websocket.open` / `close` / `message` handlers dispatch on `ws.data.type` to `createSession` / `destroySession` / `handleMessage`; only string frames are forwarded.

### Lifecycle

- **Spawn** happens when a client opens the socket. **Kill** happens when the socket closes (client disposed its transport), when a newer socket claims the same worktree key, or in `shutdown()`.
- **Worktree switch** is driven by the client: it disposes the old client and transport (see [Client side](#client-side)) and connects with the new `wt`; the close handler kills the old subprocess.

## Client side

- [lsp-client.ts](../src/lib/lsp-client.ts) `createWorktreeLspClient(wsPath, languageId)` returns an idempotent `connect(wtPath)` / `disconnect()` pair around one `WebSocketTransport` and one `MonacoLspClient`. It guards against a double spawn while a connect is in flight and discards a transport that resolves after the path changed. Both the worktree switch and `disconnect()` call the client's `dispose()` (unregistering providers and closing synced documents) before disposing the transport, so its `textDocument/didClose` notifications still go out over the live socket. Every client passes [live-editor-model.ts](../src/lib/live-editor-model.ts) `isLiveEditorModel` as the `modelFilter`, so only editor tabs' live models (`file://` or `loxel://HEAD/` without a fragment, see [URI schemes](#uri-schemes)) are synced to servers; diff, history and compare sides are not, and get no LSP features.
- The per-language modules ([ts-lsp-client.ts](../src/lib/ts-lsp-client.ts), [python-lsp-client.ts](../src/lib/python-lsp-client.ts), [astro-lsp-client.ts](../src/lib/astro-lsp-client.ts), [docker-lsp-client.ts](../src/lib/docker-lsp-client.ts), [terraform-lsp-client.ts](../src/lib/terraform-lsp-client.ts), [xml-lsp-client.ts](../src/lib/xml-lsp-client.ts)) only bind a route and Monaco language IDs. TypeScript binds `typescript`, `javascript`, `tsx`, `jsx`, `json`, `jsonc`; Docker binds `dockerfile` and `dockerbake`. [yaml-lsp-client.ts](../src/lib/yaml-lsp-client.ts) is separate: one connection per renderer, no `wt`, no disconnect, with the same `modelFilter`.
- [monaco-env.ts](../src/lib/monaco-env.ts) is the single wiring point, imported for its side effects. It disables all of Monaco's built-in TS/JS features (no TS worker; the JSON, CSS and HTML workers stay), registers the language IDs Monaco does not ship (`terraform`, `astro`, `tsx`, `jsx`, `dockerbake`), and connects the servers. YAML connects at load. TypeScript is eager: it connects to the active worktree and reconnects whenever `activeWorktreePath` changes. Every other server goes through `createLazyLspConnector`, which counts live models (`isLiveEditorModel`) of its languages in the active worktree (plus those of files outside every project, served by the active worktree's server) and connects on the first one, disconnecting at zero. Diff, history and compare models are not counted. It also registers the editor opener that turns go-to-definition results and document or hover links with a `loxel:` or `file:` URI in another model into `dispatchOpenFile`, which opens files outside every project (stdlib, installed packages) as external files; a target in the source's own model is left to Monaco to reveal in place.
- [packages/monaco-lsp-client](../../monaco-lsp-client/README.md) is a fork of `@vscode/monaco-lsp-client` consumed as TypeScript source. Its main local changes for Loxel are the `languageId` option (`TextDocumentSynchronizer` only syncs models whose language is in the set, which is what lets several servers coexist on one Monaco instance) and the `modelFilter` option above; its README lists the other local changes, including how `workspace/executeCommand` and `workspace/applyEdit` are handled. Diagnostics from the server become Monaco markers under owner `lsp`.
- [ws-shim.ts](../src/lib/ws-shim.ts) is aliased to `ws` in [vite.config.ts](../vite.config.ts) because `@hediet/json-rpc-websocket` imports the Node `ws` package; the browser uses the native `WebSocket`.

## URI schemes

[CodeEditorPanel.tsx](../src/components/code-editor/CodeEditorPanel.tsx) picks the model URI per Monaco language. `useFileScheme` (yaml, json, dockerfile, dockerbake, terraform, astro, xml, python) gives `file://<abs path>`, which those servers need for schema matching, workspace indexing and import resolution. Every other language gets `loxel://HEAD/<abs path>`. Git diff views ([GitSideBySideDiffView.tsx](../src/components/diff-viewer/GitSideBySideDiffView.tsx)) use `loxel://<ref or HEAD>/<repo-relative path>#<side>`, and compare panels ([CompareFilesPanel.tsx](../src/components/compare/CompareFilesPanel.tsx)) `loxel://compare/<abs path>#<panel id>-<side>`; both render through [diff/EditorPanel.tsx](../src/components/diff/EditorPanel.tsx).

Only the TypeScript manager translates (`toServerUris` / `toClientUris` in [ts-lsp-manager.ts](../src/server/ts-lsp-manager.ts)): client-to-server it replaces `loxel://head/` (case-insensitive) with `file:///`; server-to-client it replaces `file:///` with `loxel://HEAD/` except for `.json` / `.jsonc` paths, whose editor models use `file://`. No other manager rewrites URIs, so every other server sees and returns the live models' own `file://` URIs. The editor opener accepts `file:` and `loxel:` URIs; `isLiveEditorModel` (the clients' `modelFilter` and the lazy connector's check) accepts `file:` and `loxel://HEAD` without a fragment.

## Diagnostics

There are two TypeScript diagnostic paths:

- **Live, per file.** The TS LSP publishes diagnostics, which `monaco-lsp-client` turns into `lsp` markers.
- **Project-wide snapshot.** `GET /api/diagnostics?wt=&ref=&worktree=` ([routes.ts](../src/server/routes.ts) `handleDiagnostics`) calls `getDiagnostics` in [diagnostics.ts](../src/server/diagnostics.ts), which runs `tsc --noEmit --pretty false` (30 s timeout) and parses lines into `TypeScriptDiagnostic` from [diagnostics-model.ts](../src/api/diagnostics-model.ts) (repo-relative file, 1-based line and column, code, severity, `node_modules` excluded). The code editor and the diff view apply these as `typescript` markers, and only request the snapshot for files `hasTypeScriptDiagnostics` in [typescript-files.ts](../src/lib/typescript-files.ts) accepts: TS/JS sources (`TS_SOURCE_EXTENSIONS`, which the TS manager's routing also extends) and `tsconfig*.json`, where `tsc` reports config errors.

The server skips `tsc` and returns no diagnostics when the worktree, or the `ref`'s tree, has no root `tsconfig.json`. For the working tree (no `ref`) `tsc` runs directly in the worktree and nothing is cached on the server. For a `ref` the server validates it against `REF_PATTERN`, deduplicates concurrent requests, checks the tree for `tsconfig.json` with `git ls-tree` (caching an empty result when it is missing), creates a detached temporary worktree named `${INTERNAL_WORKTREE_PREFIX}diag-<sha8>` in a `mktemp -d` directory, symlinks `node_modules` from the source checkout, runs `tsc`, caches the result by ref in memory for the server's lifetime, and force-removes the worktree. `INTERNAL_WORKTREE_PREFIX` ([worktree-utils.ts](../src/server/worktree-utils.ts)) hides these worktrees from worktree lists, and `pruneOrphanedTempWorktrees` in `server.ts` force-removes all of them when a project is initialized, to clean up after crashes.

On the client the snapshot is a TanStack query under `queryKeys.diagnostics(...)`.

## Formatting

Formatting runs on the server as part of `POST /api/file-write` when the request carries `format: true` and valid `formattingSettings` ([FormattingSettings](../src/lib/formatting-model.ts)). Editors set `saveOptionsRef` (explicit save) and `autoSaveOptionsRef` (auto-save, only when `formatOnAutoSave`) through [use-disk-synced-content.ts](../src/hooks/use-disk-synced-content.ts); [save-editor-content.ts](../src/lib/save-editor-content.ts) sends them, and the response's formatted `content` is merged back into the editor as a programmatic "format-echo" edit (see [EDITOR.md](EDITOR.md#disk-synced-content) for the save state machine). When the save went out unformatted for a reason the user can fix, the response also carries a `formatNotice`, which the client shows as a toast once per distinct message per session. Only files inside the worktree's own tree are formatted; Others folders, drafts and external files are written as-is.

[format-service.ts](../src/server/format-service.ts) `FormatService.format()` returns a `FormatResult` whose `content` is `null` (write unformatted) when disabled, over 1 MB, without an extension, with no match, or when the formatter fails. Only a binary that is missing or cannot start (`Bun.spawn` throws `ENOENT`; `Bun.which` tells the two apart) and a timeout set its `notice`; a non-zero exit or empty output, typically a syntax error the language server already flags, is only logged so it does not repeat on every save. Resolution order:

1. **Manual overrides** from settings, first entry whose comma-separated extension list contains the file's extension. Always run as a command.
2. **Auto-detection** (if `autoDetect`), by config files at the worktree root, evaluated in `DETECTION_RULES` order, first formatter claiming the extension wins: prettier (config files or a `prettier` key in `package.json`), oxfmt (`.oxfmtrc.*` or an `oxfmt` dependency), rustfmt, clang-format, deno. Prettier and oxfmt share `SHARED_FORMAT_EXTENSIONS`; prettier adds `svelte` and `astro`, oxfmt adds `toml`. Because prettier is first, a project with both uses prettier for every shared extension. Detection is cached per worktree, keyed by a fingerprint of config-file sizes and mtimes.
3. **Python** (`.py`, `.pyi`, if `autoDetect`) is resolved per file instead, by `detectPythonFormatter` in [python-formatter.ts](../src/server/python-formatter.ts), walking from the file's directory up to the worktree root so monorepo subprojects are found. Because a ruff config or dependency often exists for the linter alone while black only formats, the nearest directory with a formatting signal decides: a ruff config (`.ruff.toml` / `ruff.toml` or `[tool.ruff]`) with a `format` table selects ruff, a `[tool.black]` table or black dependency selects black. A ruff config without `format`, or a ruff dependency, selects ruff only when no such signal exists up to the root. Dependencies are read from `pyproject.toml` (PEP 621 dependencies and extras, PEP 735 groups, uv, Poetry and PDM dev dependencies, Hatch environments). A bare `pyproject.toml` formats nothing, matching the opt-in signal prettier and oxfmt need. ruff runs as `ruff format --force-exclude --stdin-filename {file}` (without `--force-exclude` ruff ignores its `exclude` settings for stdin) and black as `black --quiet --stdin-filename {file} -`; both resolve their own nested config and infer stub style from the file name. This walk is uncached: a few `existsSync` calls and small TOML parses per save. `getDetectedFormatters` lists the Python formatter detected at the worktree root.

Each rule has a `BackendMode` from [formatter-backends.ts](../src/server/formatter-backends.ts). `command` spawns the tool per request with content on stdin, `{file}` / `{ext}` substituted, the worktree's `node_modules/.bin` prepended to `PATH` (for Python files, the `bin` of the nearest `.venv` / `venv` holding a `pyvenv.cfg`, from the file's directory up to the worktree root, is prepended ahead of it, so a project-pinned ruff or black beats a global one; venvs with any file tracked by git are skipped so a cloned repo cannot ship the binary that runs on save, with the `git ls-files` result cached per venv until `invalidateCache`), and a 5 s timeout. The two persistent backends are cached per `(worktree, command)`, restarted if dead, and on a `null` result destroyed and replaced by command mode for that request:

- [oxfmt-lsp-backend.ts](../src/server/oxfmt-lsp-backend.ts) keeps an `oxfmt --lsp` process (worktree `node_modules/.bin` first, then `PATH`) and formats via `didOpen` / `textDocument/formatting` / `didClose`, applying the returned edits.
- [prettier-lib-backend.ts](../src/server/prettier-lib-backend.ts) dynamically imports the worktree's own `node_modules/prettier` and calls `resolveConfig` + `format` in-process.

`invalidateCache(wtPath)` (called from worktree teardown) drops detection and destroys backends; `destroy()` runs at shutdown. `GET /api/detected-formatters?wt=` exposes detection to the settings UI.

## Schemas and JSON validation

- [schema-service.ts](../src/server/schema-service.ts) resolves a schema from an HTTP(S) URL (1 h TTL, 5 MB cap, 10 s timeout) or a local path (relative to a base directory, revalidated by mtime). Other URL schemes are rejected.
- `POST /api/schemas/sync` receives the enabled schema settings, classifies each glob as JSON, YAML or both, resolves JSON schemas inline and returns them, and pushes a `url → globs` map (local paths as `file://`) to the YAML manager's `updateSchemas`. `GET /api/schemas/resolve` resolves a single schema.
- [schema-sync.ts](../src/lib/schema-sync.ts) calls the sync endpoint after the settings store hydrates and when settings are saved, coalescing overlapping calls.
- [json-schema-registry.ts](../src/lib/json-schema-registry.ts) owns the single global `monaco.json.jsonDefaults` schema list (Monaco replaces it wholesale), merging configured glob schemas with per-file `$schema` schemas. `CodeEditorPanel` detects `$schema` in JSON models (debounced), resolves it through the server, and registers it under the URL Monaco's JSON worker would compute relative to the file's `file://` URI; this is one reason JSON is in `useFileScheme`.
- Monaco's JSON diagnostics are permissive (comments and trailing commas ignored) so JSONC files work. [json-strict-validator.ts](../src/lib/json-strict-validator.ts) re-parses files resolved as strict `json` with `jsonc-parser` and adds `json-strict` markers for comments and trailing commas.

## Highlighting and language resolution

- [highlighter.ts](../src/lib/highlighter.ts) holds a singleton Shiki highlighter (themes `loxel-dark` and `github-dark`, a fixed `BUNDLED_LANGUAGES` list), the `FILENAME_TO_LANG` and `EXT_TO_LANG` tables, `detectLanguage()` (case-insensitive filename, `.d.ts`, `.env*`, then extension) and `highlightCode()` for HTML token output. Language IDs here are Shiki IDs; `toMonacoLanguage()` in [monaco-theme.ts](../src/lib/monaco-theme.ts) maps the few that differ (for example `jsonc` → `json`, `dotenv` → `ini`).
- `monaco-env.ts` passes the highlighter to `shikiToMonaco`, which attaches a TextMate tokenizer to every Monaco-registered language ID that Shiki has loaded, replacing Monarch. Languages Monaco does not ship (`tsx`, `jsx`, `astro`, `terraform`, `toml`) are registered there first so they get one. Languages Shiki does not know get Monarch tokenizers: [hcl-monarch.ts](../src/lib/hcl-monarch.ts) for `dockerbake` and [pip-requirements-monarch.ts](../src/lib/pip-requirements-monarch.ts) for `pip-requirements`.
- Editing behavior comes from Monaco language configurations. Monaco registers its built-in ones lazily when a language is first encountered, and registrations merge field by field with the last one winning, so [python-language-config.ts](../src/lib/python-language-config.ts) re-registers Monaco's Python `conf` with extra auto-closing pairs and `onEnterRules` (triple quotes, dedent after `return`/`pass`/`break`/`continue`/`raise`) only after the built-in registration has run. It also adds a keydown hook, for Python and TOML (whose configuration in `monaco-env.ts` also auto-closes triple quotes), that steps over the rest of a triple-quote delimiter, since Monaco overtypes only the first character of a multi-character auto-closed pair.
- [resolve-language.ts](../src/lib/resolve-language.ts) `resolveLanguage(path, associations, content)` is what the code editor uses: enabled file associations first (first glob match wins, matched with `dot: true` so globs cross dot directories; user entries precede built-ins in `selectEffectiveFileAssociations`), then `detectLanguage`, then content sniffing (shebang, XML prolog). The built-in associations in [settings-store.ts](../src/store/settings-store.ts) are generated from `FILENAME_TO_LANG` / `EXT_TO_LANG` plus glob overrides that exact names cannot express (`tsconfig*.json` → `jsonc`, `*.docker-bake.hcl` → `dockerbake`, `requirements*.txt` → `pip-requirements`).
- [textmate-inspector.ts](../src/lib/textmate-inspector.ts) backs the editor's token-scope inspector using `codeToTokensBase` with explanations.
- [file-icons.tsx](../src/lib/file-icons.tsx) has its own filename, filename-pattern, compound-extension and extension maps (JetBrains icon theme) and is independent of language resolution.
