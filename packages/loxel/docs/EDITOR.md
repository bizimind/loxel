# Editing stack

How file-backed panels load, edit, save and reconcile files with disk, and how the file operations, drafts, Others files, localdb and search features around them are built.

## Panels and identity

A file opens in one of four center panel types, chosen by extension in `filePanelType()` ([open-file.ts](../src/lib/open-file.ts)): `.md` opens the markdown editor, `.excalidraw` the drawing editor, media extensions ([media-extensions.ts](../src/lib/media-extensions.ts)) the media viewer, and everything else the code editor. `dispatchOpenFile()` turns that into a `loxel-open-*` event, and `openFileBacked()` ([panel-creators.ts](../src/lib/panel-creators.ts)) creates or focuses the panel.

The absolute file path is the identity of an open file everywhere: the panel id (`${idPrefix}${filePath}`, so a center layout holds at most one panel per path and type), the key of its tab's entry in the editor state store (other editors of the file, the editable sides of diff views, have keys of their own; see [Several editors of one file](#several-editors-of-one-file)), the key of every content cache, and the React Query `fileContent` key. Relative paths only appear in legacy routes and in search/Quick Open payloads relative to the worktree.

Where to look:

- [open-file.ts](../src/lib/open-file.ts), [open-path.ts](../src/lib/open-path.ts): routing a path to a panel, folder or worktree.
- [panel-creators.ts](../src/lib/panel-creators.ts): `openFileBacked`, `handleFileMoved`, `handleFileDeleted`, and the "new note/drawing/code file" creators that create drafts.

## Disk-synced content

Every file-backed editor (code, markdown, drawing, and each editable side of a diff view) is built on [use-disk-synced-content.ts](../src/hooks/use-disk-synced-content.ts). The editor supplies `deserialize`, an optional module-level content cache, optional merge callbacks, and populates `getSerializedContentRef` with a function returning its current serialized text. The hook calls it only to write that text, with a `SaveReason` ([save-editor-content.ts](../src/lib/save-editor-content.ts)): `explicit` for Cmd+S and re-creating a deleted file, `auto` for autosave and for the unmount, path-change and move flushes, so an editor can adjust its content first (the code editor applies [EditorConfig](#editorconfig) save actions). The hook owns the rest:

- **Loading.** A React Query fetch of `GET /api/file-content?path=<abs>&wt=<panel worktree>` with `refetchOnMount: "always"`, so a remounted editor picks up changes made while its worktree was unsubscribed. It uses `networkMode: "always"`: the server is local, so the browser's online state must not pause it. The code editor stays read-only and writes nothing until a load has succeeded or the file is confirmed missing (an empty buffer it may legitimately edit), and after a failed load it shows a banner with Retry.
- **Autosave.** `handleChange()` marks the file dirty and arms two timers: a 250 ms idle debounce (`AUTOSAVE_DEBOUNCE_MS`) and a 5 s cap (`AUTOSAVE_MAX_WAIT_MS`) so continuous typing still saves. `saveNow()` (explicit save) clears both. A pending autosave is flushed on unmount and when the panel's `filePath` changes.
- **Format on save.** Editors call `useFormatOnSave`, which sets `saveOptionsRef` (explicit saves) and `autoSaveOptionsRef` (autosaves, only when `formatOnAutoSave` is on) from the formatting settings. The server formats only files in the worktree's own tree; Others folders, drafts and external files are written as-is. Formatter detection and backends are covered in [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md).
- **Programmatic guard.** `isProgrammaticRef` is set by the editor around imperative content updates so its change listener does not report them as user edits.

### Editor file state

[editor-state.ts](../src/store/editor-state.ts) is a Zustand store with one `EditorFileEntry` per open editor, keyed by editor key: the file path for a file's own tab, `<panel id>:old` or `:new` for a compare panel side, `working-tree:<abs path>:new` for the working-tree side of a git diff (`openFile(key, filePath?)` is idempotent; `closeFile` drops the entry). Every action takes the editor key:

| Field                                     | Purpose                                                                           |
| ----------------------------------------- | --------------------------------------------------------------------------------- |
| `filePath`                                | the file the editor shows; equal to the key for a file's own tab                  |
| `state`                                   | `clean`, `dirty`, `saving` or `diverged`                                          |
| `deleted`                                 | the file is missing on disk; orthogonal to `state`, see below                     |
| `movedTo` / `takePendingEdit`             | rename/move bookkeeping on the old entry, see "Moved files"                       |
| `pendingNonces`                           | nonces of in-flight saves; several can overlap while the user keeps typing        |
| `savedSnapshots`                          | editor content captured per nonce at save start, the merge base for format echoes |
| `baseContent`                             | content at the last clean point, the merge base for external changes              |
| `diskContent`                             | latest external disk content while `diverged`                                     |
| `getEditorContent` / `applyMergedContent` | callbacks registered by text editors for auto-merge; null for the drawing editor  |

`handleDiskChange(path, nonces, content)` is the core transition:

- **Own echo** (a nonce matches): if other saves are still pending the echo is _superseded_ and only its nonces are dropped. Otherwise, if disk differs from the editor (server-side formatting), the formatted text is merged into the editor with `preferOurs` and the per-nonce snapshot as base, so formatting applies only where the user has not typed since; then the file becomes clean once no nonces remain.
- **External change while `dirty`/`saving`:** a line-based 3-way merge (`tryAutoMerge`) of `baseContent`, the editor content and disk. Success applies the result to the editor and advances `baseContent`; a conflict, or an editor that cannot apply it, moves the file to `diverged`.
- **`diverged`:** later changes only refresh `diskContent`. [ConflictBanner.tsx](../src/components/editor/ConflictBanner.tsx) offers `acceptDiskVersion` (editor reloads disk) or `keepMyChanges` (back to dirty with `baseContent` advanced to disk, autosave re-armed).
- **`clean`:** the store does nothing; the editor's own disk-content effect replaces its content (see each editor below). These effects read the state live from the store rather than from render-time values, because a keystroke between commit and effect can flip it to dirty.

[three-way-merge.ts](../src/lib/three-way-merge.ts) diffs base→ours and base→theirs with `diffArrays` and fails on overlapping, non-identical hunks unless `preferOurs` is set, in which case the conflicting "theirs" hunks are dropped.

### Several editors of one file

A file can be open in its tab and in any number of editable diff sides (compare panel sides and the working-tree side of a git diff, [use-editable-side.ts](../src/components/diff/use-editable-side.ts)) at once. Each is an independent editor with its own entry, Monaco model, autosave timers and nonces, passed to `useDiskSyncedContent` as `editorKey`. `saveEditorContent` takes the editor key, so a save's echo is matched to the editor that made it, and the bridge runs `file_content_changed` through every entry whose `filePath` matches: to the other editors the save is an ordinary external change, which a clean editor reloads and a dirty one merges (or shows as a conflict). They share the React Query `fileContent` query, which is keyed by path.

Only a file's own tab is moved or closed by `handleFileMoved` and `handleFileDeleted` ([panel-creators.ts](../src/lib/panel-creators.ts)). Both first mark the path's other editors `deleted`, before their queries notice, so a pending autosave cannot re-create the old path; an editable diff side stays open on it with the deleted banner. Code that needs the set of open files (re-registering external files on reconnect, closing an Others folder) reads `filePath` from the entries (`openEditorPaths`), not the keys.

### Save path and write nonces

1. `saveEditorContent()` ([save-editor-content.ts](../src/lib/save-editor-content.ts)) creates a `crypto.randomUUID()` nonce, calls `markSaving` (which snapshots the editor) and posts `POST /api/file-write { path, content, nonce, worktreePath, format? }`.
2. `handleFileWrite` ([routes.ts](../src/server/routes.ts)) resolves the absolute path with `resolveFilePath` ([server.ts](../src/server/server.ts)): drafts first, then the worktree tree, then Others folders, then individually opened external files. It formats if requested and writes through the owning service's `writeWithNonce`.
3. [file-sync-service.ts](../src/server/file-sync-service.ts) records the nonce for the key (expiring after 5 s), and its next debounced flush reports the change with every nonce pending for that key. The owning service broadcasts `file_content_changed { path, nonces }` to the worktree's subscribers.
4. [ws-bridge.ts](../src/queries/ws-bridge.ts) invalidates the diff view's working-tree content, and for an open file either refreshes the query (clean) or calls `handleDiskChange`.

The HTTP response is not the completion signal: the `saving → clean` transition is driven by the echo. The response's (possibly formatted) content is stashed by nonce for 2 s so the echo handler can use it instead of refetching (`consumeSavedContent`). If no echo arrives within 10 s the nonce is dropped and the file returns to dirty. Pending saves are counted per worktree, and [useWsSubscription.ts](../src/hooks/useWsSubscription.ts) defers unsubscribing a worktree until `onWorktreeSavesDrained` fires so echoes are not lost on a worktree switch. Because all windows share one server and one nonce store, the saving window sees its own echo while other windows see an external change; see [SHARED_SERVER.md](SHARED_SERVER.md) and, for the watchers that produce events, [WATCHERS.md](WATCHERS.md).

A `worktree_files_resynced` message (after a watcher pause/resume) invalidates clean editors' queries and pushes fresh content for every non-clean editor through `handleDiskChange` with no nonces.

### Deleted files

The server does not distinguish a deletion from a modification: both arrive as `file_content_changed`, and the per-file and directory watchers keep reporting a path after it is unlinked (on macOS they survive deletion, re-creation and atomic replace). Existence is tracked on the client instead, as the `deleted` flag on the editor-state entry:

- A clean editor learns of a deletion through its content query: the event invalidates it, the refetch fails while `data` keeps the last content, and the hook sets `deleted`. Any successful fetch of that query clears it again; the effect is keyed on `dataUpdatedAt` because a restore with identical content keeps the same `data` object. A non-clean editor is refetched directly by the bridge (`fetchIntoOpenFile`), which sets the flag itself. Only a confirmed deletion counts: `GET /api/file-content` answers a missing file (or parent) with `404` plus `code: "ENOENT"`, which the client sees as `ApiError` and `isFileMissingError` (not retried). A plain 404 means the path did not resolve, typically because the worktree is not subscribed yet, and keeps the default retry so it is never shown as a deletion; other read failures are server errors.
- `handleDiskChange` clears `deleted` before anything else, so content arriving for any reason (external restore, or the nonce echo of a re-create) resumes normal sync; the merge base is still the pre-deletion `baseContent`, so a restore with different content merges or diverges as usual. When the flag drops while the file is `dirty`, the hook re-arms autosave, since edits made while the file was gone were never written.
- While `deleted`, autosave, the unmount flush and the path-change flush are skipped. `saveNow` (Cmd+S) asks for confirmation through `requestConfirmation` ([confirm-dialog-host.tsx](../src/components/ui/confirm-dialog-host.tsx), the imperative dialog mounted once in `App`) and, if the file came back and diverged while the dialog was open, defers to the conflict banner instead of overwriting; `recreateFile` writes without asking and backs the banner's button. Both go through the normal `saveEditorContent` path, so the write echo is what clears the flag.
- A clean entry that is marked `deleted` does not take the invalidate-only path for its own change events: the bridge fetches its content and runs it through `handleDiskChange`, so a flag set outside its query (by a directory check) is cleared too.
- A removed or re-created directory is reported as one event for the directory, not for the files in it. For every open file under it the bridge only re-checks existence (`checkOpenFileExists`): a confirmed 404 marks it deleted, content for a file that was deleted is fed in like an external restore, and a file that exists and was not deleted is left alone. When the bridge puts fetched content in the query cache it first cancels an in-flight refetch of the same key, so a stale 404 cannot land after the file is back.
- [EditorTab](../src/components/dockview/editor-tab.tsx) strikes through and dims the title, and each editor renders [DeletedFileBanner.tsx](../src/components/editor/DeletedFileBanner.tsx) above its content (it and `ConflictBanner` share [EditorBanner.tsx](../src/components/editor/EditorBanner.tsx)). The markdown and drawing editors keep their editor mounted for a file that loaded before it was deleted and show their "File not found" placeholder only when nothing ever loaded.
- Drafts: `DetachedFilesService` reports a content change for a draft that was deleted or re-created, not only for one that was modified, so draft editors follow the same path.

In-app deletes (file tree, undo/redo) do not use this: they dispatch `loxel-file-deleted` and `handleFileDeleted` closes the tabs.

### Moved files

A rename or move reaches an editor in one of two ways, both ending in `handleFileMoved` ([panel-creators.ts](../src/lib/panel-creators.ts)), which replaces the tab with one for the new path in the same slot:

- The window that performed an in-app rename, move, paste or undo dispatches `loxel-file-moved` itself.
- The server reports moves of files editors have open as `file_moved` (detection is described in [WATCHERS.md](WATCHERS.md#working-tree-file-events)). Every window applies it, so tabs in other windows follow in-app moves too; for the window that made the move, whichever report arrives second finds no tab on the old path and does nothing. Files inside a moved directory are reported one by one.

`handleFileMoved` is asynchronous and ignores a second report of a move it is already applying. It first sets `movedTo` on the old entry, which stops that editor's autosave and makes the bridge ignore disk events for the old path. If the editor has unsaved edits (state `dirty` or `saving`, which also covers edits made while the file was briefly marked `deleted`), it reads the new path and then takes the edits through the entry's `takePendingEdit`, which every editor registers (it cancels the autosave timers and returns the content). If the new path still holds one of the editor's own versions (`baseContent`, or a save snapshot that landed before the move), the edits are written as they are; if another program changed it, they are three-way merged onto that version, which needs a `baseContent` (an editor that never reconciled with disk cannot merge). The write happens before the new tab exists, so the new editor sees it as ordinary disk content; writing after the new entry exists would mark the new editor `saving` before it had content, and it would never apply disk content. A merge conflict, a failed read, or a failed write (the carry-over write is awaited) abandons the move: `movedTo` is cleared and the old entry is marked `deleted`, keeping the edits in place. Otherwise the tab is replaced (after re-checking that the old tab still exists and the new path was not opened meanwhile), and an unmount flush, if any, goes to `movedTo`.

Exceptions:

- A tab in `diverged` state is not moved, because its edits may not overwrite the disk version; it stays on the old path, whose change event then marks it deleted, and keeps its conflict banner.
- If a tab is already open on the new path, a clean old tab is closed; one with unsaved edits stays on its old path, marked deleted, since there is no tab to carry them into.
- An unmount flush is skipped when the entry is already gone, which is what keeps an in-app delete from re-creating the file.

For a move with source `external`, `handleFileMoved` opens the new tab with a `movedFrom` panel parameter, which the panel wrappers pass to the editor (dockview's `getParameters()` only reflects later `updateParameters` calls, so read it from the props), and [MovedFileBanner.tsx](../src/components/editor/MovedFileBanner.tsx) shows both paths until Dismiss clears it with `updateParameters`. Being a panel parameter, it lives and dies with the tab and is saved with the layout, so it survives a reload until dismissed.

## Code editor (Monaco)

[CodeEditorPanel.tsx](../src/components/code-editor/CodeEditorPanel.tsx) creates one Monaco editor per panel once the file's content has loaded or its query has failed (see [URI schemes](LANGUAGE_SERVERS.md#uri-schemes)) and reuses or creates the model for the file's URI:

- `file://<abs path>` for languages whose language server needs real disk paths (`yaml`, `json`, `dockerfile`, `dockerbake`, `terraform`, `astro`, `xml`, `python`, `toml`).
- `loxel://HEAD/<abs path>` for everything else. These and the `file://` ones are the live models of editor tabs, always without a fragment ([live-editor-model.ts](../src/lib/live-editor-model.ts) `editorFilePath`); the diff views' models use `loxel://<ref>/<path>#<side>` for git diffs (a read-only working-tree side included, as `loxel://HEAD/<path>#<side>`), `loxel://working-tree/<abs path>#new` for an editable working-tree side, and `loxel://compare/<abs path>#<panel id>-<side>` for compare panels (see [DIFF_VIEW_SPEC.md](DIFF_VIEW_SPEC.md#components-and-data-sources)).

The model is disposed with the panel, so undo history does not outlive the tab. Go-to-definition targets, a peek widget's picks and document or hover links to an editor file in another model are routed to `dispatchOpenFile` by the editor opener in [editor-opener.ts](../src/lib/editor-opener.ts), which also closes the source editor's peek. `gotoLocation` keeps Monaco's defaults, so several targets open a peek widget (see [Peek widgets](#peek-widgets)). The same file lazily connects expensive language servers by counting live models (`isLiveEditorModel`), the same models every language client syncs; LSP wiring is in [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md).

Language-server workspace edits (rename, code actions) change open models in place, so they autosave and undo like typing; files without a model are written to disk and file operations go through the file-operation routes ([lsp-workspace-files.ts](../src/lib/lsp-workspace-files.ts), see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md#client-side)).

Content flow: user edits call `handleChange(model.getValue())`. Clean-state disk updates use `model.setValue()` under `isProgrammaticRef`. Merges and "accept disk" use [compute-line-edits.ts](../src/lib/compute-line-edits.ts), which turns a line diff into minimal `ISingleEditOperation`s applied with `pushEditOperations`, so Monaco maps the caret through the change instead of resetting it.

Other per-panel behavior: language from `resolveLanguage(path, fileAssociations, content)` mapped by `toMonacoLanguage`; indentation from `resolveIndentation` (see [Indentation](#indentation)), and a ruler at the `.editorconfig`'s `max_line_length`; `$schema` detection for JSON feeding [json-schema-registry.ts](../src/lib/json-schema-registry.ts); strict-JSON markers ([json-strict-validator.ts](../src/lib/json-strict-validator.ts)) for files resolved as `json` rather than `jsonc`; project TypeScript diagnostics applied as markers for TS/JS files ([languages/typescript.md](languages/typescript.md#diagnostics)); and a TextMate scope inspector ([TextMateScopeInspector.ts](../src/components/code-editor/TextMateScopeInspector.ts)).

Themes: [monaco-theme.ts](../src/lib/monaco-theme.ts) registers fallback `loxel-dark` and `loxel-light` themes synchronously and replaces them with the Shiki-converted [loxel-themes.ts](../src/lib/loxel-themes.ts) themes once the highlighter loads, reading editor chrome colors from the theme's UI tokens (`readThemeTokens`) and layering each theme's semantic-token rules; a color theme with syntax colors of its own gets its own Monaco theme ([THEMES.md](THEMES.md#highlighted-code)). `getMonacoThemeName(darkMode)` picks the current mode's, and Monaco themes are global, so every editor follows `darkMode`. `SEMANTIC_TOKEN_STYLING` is the union over both themes, which style the same token types. Monaco would paint a semantic token type with no rule in the default foreground, hiding its TextMate color, and would match modifiers against rules in legend order, so `SEMANTIC_TOKEN_STYLING` tells each language client what the theme styles: other types stay on their TextMate color and other modifiers are dropped. The rules hold only deliberate choices, and a language server needs none. [useThemeSync.ts](../src/hooks/useThemeSync.ts) resolves the `theme` setting (`system` follows the OS) into the UI store's `darkMode` and the `dark` class on `<html>` once the settings hydrate; until then the page keeps the theme that `index.html` applied from the last session's cache ([theme-cache.ts](../src/lib/theme-cache.ts)). Light also shows the caret row JetBrains-style in code editor and library source tabs: [caret-row.ts](../src/components/code-editor/caret-row.ts) gives them `caretOptionsFor(darkMode)` and keeps the row's band while text is selected.

Inlay hints follow the `editor.inlayHints` setting, the values of Monaco's `inlayHints.enabled`. [useInlayHintsOption.ts](../src/hooks/useInlayHintsOption.ts) gives each Monaco editor (code editor, both diff sides, markdown frontmatter) the current value at `create`, so an editor created with hints off does not request them, and applies changes live, including the persisted value once settings hydrate. Off stops the requests in Monaco's controller; the two `UnlessPressed` modes still request them, to show them without delay. The diff sides' models aren't synced to language servers, so the option has nothing to show there today. A peek widget's embedded editor inherits its parent's option.

Fonts follow the `fonts` setting: a family name (null for the bundled font) and a size per surface. [font-settings.ts](../src/lib/font-settings.ts) owns the defaults and size bounds and builds every stack at runtime with the bundled font and a generic family behind the user's family, so a font missing on this machine falls back. [useCodeFontOptions.ts](../src/hooks/useCodeFontOptions.ts) applies the code font to the same Monaco editors as the inlay hints option, at `create` and live. Line height stays 22px, which the diff view's gutters and the frontmatter editor's height rely on; the code size bounds keep text within it. Stylesheets read `--loxel-font-code`, `--loxel-font-prose` and their `-size` variables, which [useFontSettingsSync.ts](../src/hooks/useFontSettingsSync.ts) sets on `<html>`; [milkdown-theme.css](../src/styles/milkdown-theme.css) sizes headings, list markers and the spacing between blocks in multiples of the prose size, so the layout keeps its proportions at any size. The installed-font list for the pickers comes from [local-fonts.ts](../src/lib/local-fonts.ts) and stays in memory: it is never logged, persisted or sent.

[useFileTabRename.ts](../src/hooks/useFileTabRename.ts) gives a file tab a rename handler only for files in the active worktree, its drafts, or its Others folders, and delegates to `renameFile()` (see File operations).

### Peek widgets

Monaco's peek widgets (references, Peek Definition and Implementations, the `Cmd`-hover definition preview) get their models from the standalone text model service, which only finds registered models. [peek-text-models.ts](../src/lib/peek-text-models.ts) wraps its `createModelReference`, installed from `monaco-env.ts`: an editor file (`editorFilePath`) with no registered model gets a snapshot, a `TextModel` under the file's URI, read through `GET /api/file-content?preview=1` (which neither tracks the file for renames nor adds a file outside every tree to Others). The snapshot is never registered with Monaco, so nothing that looks models up by URI sees it: a tab opening the file creates its own model, language clients never sync it, and workspace edits write the file on disk. It is marked a preview model (`markPreviewModel` in [live-editor-model.ts](../src/lib/live-editor-model.ts)), so `isLiveEditorModel` rejects it and language features stay off in the peek, and `keepPreviewModelsReadOnly` makes any editor showing one read-only. Each reference reads its own snapshot and disposes it with itself, which Monaco does when the peek closes; snapshots are not shared, since a reference some Monaco consumer never disposes would otherwise pin an old read for every later peek of the file. Files open in a tab show their live model, editable in the peek like in the tab. A language server's [read-only document](LANGUAGE_SERVERS.md#read-only-documents) with no tab gets the same kind of snapshot, read from its server, and one with a tab shows its live model read-only.

### EditorConfig

`.editorconfig` files are resolved on the server by [editorconfig.ts](../src/server/editorconfig.ts) and exposed as `GET /api/editorconfig?path=<abs>&wt=`, which returns the `EditorConfigProperties` of [editorconfig-model.ts](../src/api/editorconfig-model.ts). The server resolves because it owns the filesystem: the walk from the file's directory up stats a file per level, which from the client would be one request each. The walk stops at a `root = true` file or at the root of the tree that owns the file (the worktree, or an Others folder), never above it; drafts and individually opened external files have no tree and get no properties. Section globs ([editorconfig-glob.ts](../src/server/editorconfig-glob.ts): `*`, `**`, `?`, `[...]`, `{a,b}`, `{n1..n2}`) have their braces expanded into flat token sequences (a section that expands past fixed limits, an oversized section name or an oversized file is ignored), and are matched with a table over token and path position instead of a backtracking regex, so a cloned repository's `.editorconfig` cannot stall the server; and properties are defaulted as the spec says (`indent_size = tab`, `tab_width` from a numeric `indent_size`). Parsed files are cached by path and re-read when their mtime or size changes, so a lookup is current whether or not a watcher covers the tree.

The code editor fetches the properties as the `editorConfig` query. [ws-bridge.ts](../src/queries/ws-bridge.ts) refetches it for open files below an `.editorconfig` that changed (a `file_content_changed` for that path), for open files under a directory that was removed or re-created, and for every file on `worktree_files_resynced`.

`indent_style`, `tab_width` and `indent_size` map to the model's `insertSpaces`, `tabSize` and `indentSize` (see [Indentation](#indentation)), and `max_line_length` to the editor's `rulers`. Until the query's first load settles the editor is read-only (`useFirstLoadGate`), so the first keystroke is already indented by the `.editorconfig`; the gate lifts after at most 500 ms, on an error, or while the query is paused offline, and refetches never re-arm it; the query starts when the panel first renders, together with the file content query, so there is nothing to gain by prefetching it earlier.

The save properties are applied on the client by [editorconfig-save-actions.ts](../src/lib/editorconfig-save-actions.ts), from the code editor's `getSerializedContentRef` under `isProgrammaticRef`, as their own undo step (undo stops on both sides, since a line-ending change undone together with the user's typing corrupts the text) that keeps the cursors: `trim_trailing_whitespace` (spaces and tabs), `insert_final_newline = true` (`false` leaves the file as it is), and `end_of_line` through `model.pushEOL`. They run in the editor rather than in the server's write path for three reasons: the written text then equals the editor's, so no format-echo merge is needed; that merge and `computeLineEdits` split lines on `\n` and could not carry a line-ending change back into the model; and an autosave can leave the whitespace on the cursors' lines alone, where a server-side trim would delete a space the user just typed. The autosave right after an undo or redo skips them, or it would redo what the user just undid. Server-side formatting still runs afterwards on the result. `charset` and `end_of_line = cr` (which Monaco cannot represent) are not applied by the editor; prettier reads `.editorconfig` itself, including `max_line_length`. The markdown and drawing editors serialize their own formats and do not use these properties.

### Indentation

`resolveIndentation` in [settings-store.ts](../src/store/settings-store.ts) is the one precedence function. It resolves `insertSpaces`, `tabSize` and `indentSize` one by one, each from the first layer that sets it, and reports each one's `IndentationSource`:

1. `file`: the choice made with Change Indentation, kept in the panel's state while the tab is open.
2. `editorconfig`: the file's `.editorconfig` properties.
3. `override`: the user's per-extension override.
4. `detected`: [detect-indentation.ts](../src/lib/detect-indentation.ts), run when the panel loads the file's content or replaces it with a newer disk version, not on the echoes of its own saves, so neither typing nor a conversion shifts it. It is adapted from Monaco's internal `guessIndentation` but reports only what the content shows: nothing without indented lines, and no size for tabs.
5. `language`: `BUILTIN_LANGUAGE_INDENTATION`, keyed by resolved language. An entry marked `required` (make, whose recipe lines must start with a tab) comes before `detected` instead, since a Makefile's space-indented continuation lines can outnumber its recipes.
6. `default`: the global default, which sets every property.

`.editorconfig` outranks the per-extension override, as in VS Code and JetBrains IDEs: it is the project's committed convention, shared with its formatters, while an override applies to every project, so an override set once for one project would otherwise rewrite the indentation of every other project's files of that type. The resolution also returns the matching override, so the status item can say when `.editorconfig` outranks it.

Indentation is only ever set with `model.updateOptions`: in standalone Monaco, editor-level `tabSize` and `insertSpaces` are global settings, and changing them resets every open model, so the editor passes only a constant `detectIndentation: false` (Monaco's own detection would replace the resolved values), and sets its model's options after `monaco.editor.create`, since the first editor flipping that flag resets models too. The model's options are therefore the file's indentation, and the TypeScript client reports them to its server so TypeScript's quick fixes indent the same way (see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md#per-language-managers)).

The status bar lives outside the panels, so each code editor tab publishes its resolution, its model's line ending and two callbacks (set the file choice; convert the indentation through Monaco's `editor.action.indentationToSpaces`/`ToTabs` and choose the resulting style and sizes) to [editor-indentation.ts](../src/store/editor-indentation.ts), keyed by file path. [IndentationStatus.tsx](../src/components/panels/IndentationStatus.tsx) shows the active editor's entry, and the `editor.changeIndentation` action runs the quick picks in [indentation-status.ts](../src/lib/indentation-status.ts), which also turns a resolution into the status item's label, source and tooltip.

## Markdown editor (Milkdown)

[MarkdownEditor.tsx](../src/components/editor/MarkdownEditor.tsx) uses Milkdown's Crepe, a ProseMirror editor whose markdown parser and serializer are remark. The image-block and LaTeX features are disabled, code blocks are CodeMirror (mermaid blocks also get a [diagram preview](#mermaid-diagrams), ` ```diff ` and ` ```patch ` blocks a [diff preview](#diff-blocks)), and remark-stringify takes the block-level markers from Settings > Editor > Markdown Output (`markdownOutput` in [formatting-model.ts](../src/lib/formatting-model.ts): bullet, ordered marker, list numbering, code fence, horizontal rule, list item indent, setext headings), applied through `buildRemarkStringifyOptions` in [markdown-stringify-options.ts](../src/components/editor/markdown-stringify-options.ts). The defaults match oxfmt/Prettier. Emphasis and strong markers are not configurable: Milkdown's own handlers keep the marker each run was parsed with. Milkdown builds the serializer once at init, so a settings change recreates the Crepe editor (the mount effect is keyed on the settings values); pending edits and the caret survive through `editorContentCache` and the selection cache, and the source baseline is re-established from the cached content so untouched blocks keep their bytes. The server-side format-on-save path only receives `FormatOnSaveSettings`, the formatting settings without `markdownOutput`. The editor holds a document tree, not text, which drives most of the design below.

### Frontmatter

[frontmatter.ts](../src/lib/frontmatter.ts) splits a leading `---` block positionally (no YAML validation). The body goes to Crepe; the YAML goes to [FrontmatterEditor.tsx](../src/components/editor/FrontmatterEditor.tsx), a Monaco editor on the model `file:///__frontmatter__/<path>.yaml`. `mergeFrontmatter` always writes exactly one blank line after the closing `---` when the body is non-empty, so a file with no blank line there gains one on its first save.

### Byte-identical untouched blocks

Serialization is canonical in the configured markers (by default `*` bullets become `-` and setext headings become ATX; blank-line runs always collapse), so a naive save would rewrite every block of the file on any edit and produce noisy diffs. [markdown-source-preservation.ts](../src/lib/markdown-source-preservation.ts) prevents that:

- On load, `createSourceBaseline` records the source text, its top-level block ranges (from remark positions), and the canonical form of each block. Preservation is disabled for a source whose canonical form splits into a different number of blocks.
- On save, `preserveSource` splits the canonical output into blocks and aligns them with the baseline's canonical blocks by LCS (`alignBlocks`). Unchanged blocks are emitted as their original source bytes; changed or new blocks use serializer output. Separators (blank lines, link reference definitions) between blocks that were adjacent in the source are kept verbatim, including around a block edited in place.
- Blocks are matched by serialized form, not node identity, because Milkdown plugins rewrite attributes after load and programmatic replaces create new node objects.
- The result is validated: `canonicalize(output)` must equal the canonical output, otherwise the canonical output is used. Preservation can therefore only be skipped, never change the document.
- Already-canonical sources (anything the editor or a formatter wrote) short-circuit, and results are memoized per baseline.

The editor-side glue is `serializeBody` (use it instead of `crepe.getMarkdown()`), `setSourceBaseline` (called on load and after every programmatic apply), and `toEditorBody`, which converts raw disk bytes to the form the editor would serialize them in, so disk content can be compared with or used as a merge base against the live document. Trailing newlines are collapsed to one (`normalizeTrailingNewline`) because Milkdown's trailing plugin adds an empty paragraph.

### Applying disk content without moving the caret

`applyBodyToEditor` compares serialized markdown first (parse(serialize(doc)) is not structurally identical to the live doc), then dispatches `createMinimalReplaceTransaction` ([prosemirror-replace.ts](../src/lib/prosemirror-replace.ts)): it replaces only the span between `findDiffStart` and `findDiffEnd`, so ProseMirror maps the selection through the step. It carries the live doc's trailing empty paragraph into the target so the common suffix is found, and falls back to a whole-document replace with the caret clamped to its old offset when the sliced replace does not reproduce the target exactly. The transaction has `addToHistory: false`.

Echo suppression differs from the code editor because Milkdown's `markdownUpdated` listener is debounced and ignores `addToHistory: false` transactions:

- After a programmatic replace a stepless, listener-visible transaction is dispatched so the listener's previous-doc snapshot resyncs; otherwise a later user edit that restores that snapshot would never be reported.
- `lastAppliedBodyRef` holds the body last applied; a listener callback whose live body equals it is ignored as the programmatic echo, and anything else is a user edit.
- In the clean-state disk effect, live edits the debounced listener has not reported yet are 3-way merged onto the disk change (base: `lastSyncedDiskBodyRef`, the editor form of the previous disk content; `preferOurs`), and autosave is armed if the result differs from disk.

"Accept disk version" destroys and recreates Crepe (`crepeKey`). Module-level `editorContentCache` and `editorSelectionCache` keep content and caret across remounts (tab and layout swaps) and are migrated by `renameEditorCacheKey` on moves.

Search navigation uses `rawLineToProsePosition` ([prosemirror-position.ts](../src/lib/prosemirror-position.ts)): it parses the raw file with the editor's remark configuration, finds the text leaf at the target line and column, and walks ProseMirror text nodes in the same order (ordinal matching handles repeated text and nodes with no ProseMirror counterpart). Relative links in the document are opened with `openPath()` instead of navigating.

Line breaks are handled by [soft-line-break.ts](../src/components/editor/soft-line-break.ts). Milkdown models a newline inside a paragraph as a `hardbreak` node with `isInline: true` (serialized as a `"\n"` text node) and a `\` or two-space hard break as `isInline: false` (serialized as `\`+newline); both render as `<br>`. Shift+Enter inserts the `isInline: true` form at a higher keymap priority than Milkdown's hard-break command, removes spaces on either side of the caret, and turns a second press right after the break it just inserted into a paragraph split; that break's position is kept in plugin state and cleared by any other edit or selection change, so a press next to a break already in the document adds another break. It sets Milkdown's `hardbreak` transaction meta, so `hardbreakFilterNodes` (extended with `heading`) blocks it in tables, code blocks, and headings. Milkdown's `hardbreakClearMarkPlugin` is replaced by a copy that keeps the node's attrs, because the original resets a soft break to a hard one when a mark is applied across it. A wrapper around Milkdown's remark-stringify `text` handler keeps soft breaks stable on reload: whitespace before a soft break is dropped (two trailing spaces would reload as a hard break); leading whitespace after a break is kept, since the parser already strips it from the source, a soft break that would leave an empty line (at the start of a block or after another break) is written as `\`+newline because a blank line would split the paragraph, and soft breaks at the end of a block are not written.

Tables are Crepe's GFM table feature (prosemirror-tables) with no custom node; Loxel only restyles them in [milkdown-theme.css](../src/styles/milkdown-theme.css).

### Code block highlighting

[code-block-highlight.ts](../src/components/editor/code-block-highlight.ts) supplies the CodeMirror feature's `languages`. Each language from `@codemirror/language-data` keeps its CodeMirror parser for editing behavior (indentation, comment toggling) but is colored by the code editor's own Shiki highlighter ([highlighter.ts](../src/lib/highlighter.ts)), with the theme `getMonacoThemeName` picks, so a block's tokens get the same grammar and colors as Monaco. The theme follows the app's light or dark setting, and blocks recolor when it changes. Shiki languages that `language-data` lacks are added with a plain parser (mermaid is one: its Shiki grammar is about 5 KB gzipped and has no embedded languages, so it loads eagerly with the others); `language-data` languages Shiki doesn't load keep a fallback palette (`CODE_COLORS`, dark and light colors passed through CSS variables, so a theme change needs no recolor). An empty active `HighlightStyle` stops basicSetup's default CodeMirror colors from painting under Shiki's. Brackets are colored like Monaco's bracket pair colorization: Monaco's default colors cycled by depth across `()[]{}`, red for an unmatched closer, and none for brackets Monaco treats as strings, comments or regexes. `@shikijs/monaco` hands Monaco the scope of the first theme rule with a token's color and style, not the token's own scopes, so the block classifies a token the same way (`isTextToken`) to color the same brackets. Semantic tokens come from language servers and exist only in the code editor.

### Mermaid diagrams

The CodeMirror feature's `renderPreview` is [code-block-preview.ts](../src/components/editor/code-block-preview.ts), which picks a renderer by fence language; languages without one return `null` (no preview panel). [mermaid-preview.ts](../src/components/editor/mermaid-preview.ts) renders ` ```mermaid ` blocks as diagrams in that panel. The preview is view-only: it never touches the node's text, so the block saves like any other code block and untouched fences keep their bytes.

- Mermaid is imported on the first mermaid block and the promise is cached (reset on failure so the next block retries).
- It runs with `securityLevel: "strict"` and `startOnLoad: false`, because repositories can be untrusted; the preview panel sanitizes the SVG again with DOMPurify before inserting it.
- Renders go through one FIFO queue: mermaid keeps global config and renders in a temp node on `document.body`, and the order guarantees a block's latest text lands last. An empty block gets no preview at once and also clears it through the same queue, so a render still in flight cannot land after it. Each render gets a unique id, and the temp node is removed when mermaid throws.
- The panel only re-renders on text or language changes, so each diagram is rendered with mermaid's `default` and `dark` themes and [mermaid-preview.css](../src/styles/mermaid-preview.css) shows the variant matching the editor's `dark` class.
- Code blocks unmount when scrolled off-screen and render their preview again on return, so rendered SVGs are kept in a small LRU keyed by source; a cached SVG is reissued under a fresh id because mermaid scopes its styles and marker references by that id.
- Errors are shown through `textContent`, never as HTML.
- A block shows its diagram alone until its source is being edited, decided in one place: [code-block-source.ts](../src/components/editor/code-block-source.ts), a ProseMirror plugin whose node decorations ([mermaid-preview.css](../src/styles/mermaid-preview.css) reads only those) mark every mermaid block `loxel-mermaid-block` (which hides Crepe's own preview toggle, whose per-Vue-app state resets on teardown and would hide a new block's source as soon as it first renders) and a collapsed one `loxel-code-block-collapsed`. A block hides its source when it has text whose last render did not fail: [mermaid-render-results.ts](../src/components/editor/mermaid-render-results.ts) keeps the failed sources (by text, as Crepe's `renderPreview` has no block identity) and tells editors when one changes, so they recompute. The set is bounded, since most intermediate texts typed fail to parse, and reading a source refreshes it; every recompute reads every mermaid block in the document, the open one included, so a failure still in a document never ages out. Error previews also carry an Edit button, which CSS shows only on a collapsed block, so a block whose text's failure was cleared by the same text rendering elsewhere never leaves its source unreachable. A render still pending counts as a diagram, so a file opens showing its diagrams and a broken one expands once its error arrives; an empty block has no preview at all (`renderMermaidPreview` returns `null` for it synchronously). It is collapsed when it hides its source and is not open. A code block is open while it holds a text selection that a transaction put there (`tr.selectionSet`) or that sits in a block the transaction created or changed (the ` ```mermaid ` input rule and block-type menus only change the node), or that was open and maps onto the same block. Open does not depend on the render result, so a parse error while typing never collapses the block. Programmatic placements open nothing: the initial selection, the caret `MarkdownEditor` places at the end of a newly opened file (`keepSourcesClosed`), and disk changes applied with `addToHistory: false`. A caret such a placement leaves in a collapsed block could not type into its hidden source, so an `appendTransaction` (and, for the initial selection, the plugin view once mounted) moves it to the nearest textblock outside code blocks, after the block (the trailing paragraph, for a file ending in a diagram) or else before it; in a document of one diagram, which has no such textblock until Crepe's trailing plugin first runs, the plugin view dispatches an empty transaction to add it. A node selection (Crepe's block handle) is not editing: a capture-phase focus listener blurs attempts to focus a collapsed CodeMirror source before its focus updates can replace the whole-node selection with a text selection, returning focus to ProseMirror for whole-node keyboard actions. Typing, undo, search navigation and the caret restored after a Crepe recreation open the block they land in. As node decorations, the classes live on the node view and survive CodeMirror's off-screen teardown.
- The browser cannot place the caret in a source that is not displayed, so the plugin's `handleKeyDown` steps an arrow key at a textblock edge into a neighboring block that hides its source (the same decision, so a diff block hidden by Crepe's toggle is left to the browser), at the start of its text going forward and the end going back. The neighbor is the next selection ProseMirror would reach (`Selection.findFrom`), so an atom block in between is selected first; Left and Right are left to the browser in right-to-left text and during composition. It does not call `scrollIntoView`: ProseMirror resolves a position in a node view without content DOM to the view's edge, and focusing CodeMirror brings the caret into view. The toolbar's Edit (`editCodeBlockSource`) puts the caret at the start of the text and focuses the editor; Hide (`hideCodeBlockSource`) moves it to the nearest textblock after the block, or else before it, that is not a code block, so it never opens a neighboring diagram, and adds an empty paragraph after the block when there is none.
- Mermaid measures each HTML label in its temp node on `document.body`, outside the editor, and sizes the label's `foreignObject` to that. The preview CSS keeps the editor's paragraph typography (`.milkdown .ProseMirror p` in [milkdown-theme.css](../src/styles/milkdown-theme.css)) out of label `<p>`s, or they render at the prose size and line height and get clipped by their box.
- The preview holds a static toolbar and both variants on a canvas inside a clipping viewport. CSS sizes the SVG to the panel width but not below 3/4 of its natural width (carried as `--loxel-mermaid-width` from the `viewBox`), so wide diagrams overflow and are panned. [mermaid-preview-controls.tsx](../src/components/editor/mermaid-preview-controls.tsx) handles the toolbar (Edit and Hide, zoom, copy, open; CSS shows Edit or Hide by the block's mark), zoom, pan and click-to-open by delegation from the editor container (Crepe's sanitized panel keeps no listeners), like the [diff blocks](#diff-blocks). Its press handler runs in the capture phase so ProseMirror never starts a selection on a diagram; a click that did not drag opens the viewer. The non-passive wheel listener that zoom and sideways pan need is added to each viewport when the pointer first enters it, so the rest of the editor keeps scrolling off the main thread. A canvas's view lives in a `WeakMap`, so it resets when the panel re-renders the preview.
- [MermaidDiagramViewer.tsx](../src/components/editor/MermaidDiagramViewer.tsx) is the full-size viewer, a `DialogShell` mounted by `MarkdownEditor`. Opening reads the block's text from the document (`codeBlockText`), and `renderMermaidDiagram` returns both variants from the render cache, sanitized with the panel's DOMPurify config before insertion. Copies ([mermaid-export.ts](../src/components/editor/mermaid-export.ts)) serialize the SVG node on screen; the PNG goes through a `data:` URL image, since Chromium taints a canvas drawn from a `blob:` SVG with `foreignObject`.
- Zoom and pan geometry is shared with the media viewer in [components/pan-zoom](../src/components/pan-zoom/): `pan-zoom.ts` (pure math), `usePanZoom` (full-panel views: the media viewer and the diagram viewer) and `ZoomToolbar.tsx`.

### Diff blocks

Through the same `renderPreview` dispatch as [mermaid diagrams](#mermaid-diagrams), [diff-block-preview.tsx](../src/components/editor/diff-block-preview.tsx) renders ` ```diff ` and ` ```patch ` blocks as a diff view in the code block's preview panel. The preview is view-only: it never touches the node's text, so the block saves like any other code block and untouched fences keep their bytes.

- [parse-unified-diff.ts](../src/lib/parse-unified-diff.ts) (`parseUnifiedDiff`) turns the text into the diff panels' `DiffInfo` model ([diff-model.ts](../src/api/diff-model.ts), `baseRef: null`). It is lenient because fenced diffs are rarely valid patches: hunk counts only disambiguate `--- `/`+++ `, blank and unprefixed lines and never truncate a hunk, a `@@` line without numbers or `+`/`-`/` ` lines without any header form an unnumbered hunk (lines carry no line numbers), and a git `format-patch` preamble and signature are skipped. Header paths are decoded with git's C-quoting rules, shared with the server's diff parser in [git-diff-paths.ts](../src/lib/git-diff-paths.ts). It returns `null` when the text has no hunk and no `diff --git` file, and the block then stays a plain code block. `diff`'s `parsePatch` is not used because it throws on wrong hunk counts and drops header-less lines.
- The panel inserts previews as DOMPurify-sanitized HTML, so the view is rendered synchronously to static markup with `react-dom/server`'s `renderToStaticMarkup` from the diff viewer's own pieces: `HunkSection` and `buildFileInlineSegments` for the hunks and intra-line highlights, `FileDiffHeader`, and `DiffViewModeToggle` (see [DIFF_VIEW_SPEC.md](DIFF_VIEW_SPEC.md)). Without file contents there are no gaps to expand and no syntax highlighting. A parse or render failure returns `null`, so the block falls back to a plain code block.
- The markup holds both layouts. The Unified/Split choice is the global `diffViewMode` setting shared with the diff panels, not per block, because the panel re-renders the preview on every edit of the block and would drop per-block state. The editor container carries it as `data-diff-view-mode`, [diff-block-preview.css](../src/styles/diff-block-preview.css) shows the matching layout and marks the active button, and `handleDiffBlockClick`, the container's click handler, sets the setting from the buttons' `data-diff-view-mode-option`. Colors are the diff theme variables, so the view follows light and dark mode without re-rendering.
- The **Open in diff panel** button (`data-diff-block-open`) opens the block's diff in a [patch panel](DIFF_VIEW_SPEC.md#components-and-data-sources). The markup carries no text, since DOMPurify drops attribute values that look like markup (`-->`, common in patches): on a click `handleDiffBlockClick` passes the block's node view element (`.milkdown-code-block`) to the editor, and `codeBlockText` reads the code block node's current text at that element (`posAtDOM`). The editor sends it with its file path as `loxel-open-patch-diff`. The panel keeps that snapshot.

### Directives and the localdb widget

[localdb-directive/remark-plugin.ts](../src/components/editor/localdb-directive/remark-plugin.ts) installs directive syntax restricted to what the editor understands:

- Only flow directives are parsed; text directives (`:name`) are never recognized, so prose like `10:30am` stays text.
- `:::localdb` containers become `localdb-block` nodes carrying their verbatim inner source and whether the fence was closed.
- Every other directive is unwrapped into paragraphs of verbatim inline `html` reproducing its source, so nothing is lost and Milkdown never sees an unknown node type.
- On serialize a line-initial `::` in prose is escaped, so typed text cannot become a directive on reload.

[schema.ts](../src/components/editor/localdb-directive/schema.ts) defines the atom node with attrs `table`, `view`, `viewId`, plus `extra` (unknown body lines kept verbatim) and `closed`. It serializes the block as one verbatim `html` node and widens the fence beyond any colon run in the body. [view.ts](../src/components/editor/localdb-directive/view.ts) renders `LocalDbWidget` in a React root inside a NodeView; widget configuration changes are `setNodeMarkup` transactions and so are saved through the normal markdown path. Round-trip behavior is pinned by `round-trip.test.ts` and `remark-plugin.test.ts`.

## LocalDb

Each project has one SQLite database from [`@bizimind/localdb-sdk`](../../localdb-sdk/README.md), opened at project initialization at `<stateDir>/localdb/<hash12(project cwd)>/localdb.db`. Requests under `/api/localdb` are project-scoped and dispatched by [localdb-routes.ts](../src/server/localdb-routes.ts), which validates payloads with the SDK's zod parsers. Mutations broadcast `localdb_changed { scope, tableName?, tableId? }` to the project; [ws-bridge.ts](../src/queries/ws-bridge.ts) invalidates `["localdb", projectPath, ...]` queries and emits `loxel-localdb-changed`.

The UI is [LocalDbPanel.tsx](../src/components/localdb/LocalDbPanel.tsx) (a singleton center panel) and the shared components in [components/localdb/ui](../src/components/localdb/ui), which talk to the server through `makeRestAdapter("/api/localdb", projectPath)`. ## File operations

Server side, every file tree has a `FileOperationsService` ([file-operations-service.ts](../src/server/file-operations-service.ts)): the worktree's own (`git mv`/`git rm` for tracked paths, plain filesystem calls otherwise) and one per Others folder (`git: false`, so nothing is staged in an enclosing repo). Operations are serialized through a promise queue, validate paths and names, and resolve name collisions (`file 2.ts`, `file (copy).ts`). Each service keeps undo/redo stacks capped at 50 entries and 50 MB; deletes keep file contents and modes in memory so they can be restored. `FileOperationsHistory` orders undo across a worktree's services so undo targets the latest operation wherever it happened; it lives on the server per worktree, so windows on the same worktree share it. Undo and redo return a `FileOperationResult` ([file-operations-model.ts](../src/api/file-operations-model.ts)).

Client side:

- [useFileOperations.ts](../src/hooks/useFileOperations.ts): inline rename, delete confirmation, new file/folder, undo/redo (one request at a time).
- [useFileClipboard.ts](../src/hooks/useFileClipboard.ts) and [useProjectFileDrag.ts](../src/hooks/useProjectFileDrag.ts): cut/copy/paste and drag and drop (MIME types `application/x-project-file` and `application/x-detached-file`). Moves and copies stay within one tree; drafts can only go into the worktree.
- [file-operations.ts](../src/lib/file-operations.ts): `renameFile`, `moveFile` and `deleteFile`, the shared operations (route call, then the client-side follow-up below) used by the tree, tabs, cut/paste, drag and drop, and language-server edits.
- [project-file-helpers.ts](../src/lib/project-file-helpers.ts): `isWithin`, `findTreeRoot`, `fileParentDir` and related path helpers.

After any move, rename or delete the client remaps the UI paths of the worktree the operation was given (`renameProjectPaths`; a language-server edit may finish after a worktree switch), dispatches `loxel-file-moved` or `loxel-file-deleted`, and invalidates parent directory queries. `handleFileMoved` marks the old editor-state entry `movedTo`, carries over any unsaved edits, migrates content caches, and opens the new panel in the old tab's position before closing the old one (see [Moved files](#moved-files)); `handleFileDeleted` closes panels for the path and everything under it. Draft operations go through the drafts routes and are not in the undo history. Tree UI behavior is in [PROJECT_EXPLORER.md](PROJECT_EXPLORER.md) and [FILES_TREE.md](FILES_TREE.md).

## Drafts

Drafts (detached files) are files outside the repository, one flat directory per project and worktree: `<stateDir>/detached/<hash12(projectPath)>/<hash12(worktreePath)>/` (`getDetachedDir` in [config.ts](../src/server/config.ts)). [detached-files-service.ts](../src/server/detached-files-service.ts) watches it non-recursively, ignores dotfiles, and keeps a cached listing.

- Names are `<prefix> <n>[.<ext>]` with the lowest unused `n`. Creation uses the `wx` flag and retries on `EEXIST`, so concurrent creates from several windows cannot collide. The panel creators use `Note` + `md`, `Drawing` + `excalidraw`, and `Untitled` for code files.
- Listing changes broadcast `detached_files_changed`; content changes of existing files go through the shared `file_content_changed` broadcast with nonces, so drafts save exactly like worktree files.
- `moveToProject` refuses to overwrite and falls back to copy + delete across filesystems (`EXDEV`); `copyToProject` uses `COPYFILE_EXCL`. After a move the client dispatches `loxel-file-moved`, so an open draft tab becomes a worktree tab. The Drafts section UI is in [PROJECT_EXPLORER.md](PROJECT_EXPLORER.md).

- **Home's drafts** (plans made in [Home](PANELS_AND_LAYOUT.md#home)) are one more directory, `<stateDir>/detached/home/` (`getHomeDraftsDir`), served by a `DetachedFilesService` the server starts at boot and keeps outside the per-worktree resources (`homeDrafts` in [server.ts](../src/server/server.ts)), since Home has no worktree subscription. `resolveFilePath` checks it before any worktree, the drafts routes take `HOME_KEY` ([home-model.ts](../src/api/home-model.ts)) where they take a worktree path (`draftsFor` in [routes.ts](../src/server/routes.ts)), and its `file_content_changed` and `detached_files_changed` go to every window with `wtPath: HOME_KEY`, so a save in Home gets its echo; [ws-bridge.ts](../src/queries/ws-bridge.ts) matches them to editors with no worktree. Moving or copying one into a project is refused, since Home has none.

[detached-path.ts](../src/lib/detached-path.ts) only holds display-name and directory-normalization helpers.

## External files and Others folders

Files and folders outside every project appear in the active worktree's Others section. Opening from Finder or the `loxel` CLI posts to `POST /api/open`, which sends `open_file` or `open_folder` to the window in use; `openFile`/`openFolder` ([open-path.ts](../src/lib/open-path.ts)) open the path in its owning worktree or in the active worktree's Others section; `openFile` first honors a worktree named by the request (`worktreePath`, from `--worktree` or the command's URLs). An open that takes focus switches to the target worktree; a file opened without focus (`loxel --no-focus`, or any open by a coding agent) is queued in that worktree's `PendingOpen` queue until the user switches there, and a folder is not sent without focus at all. See [ELECTRON.md](ELECTRON.md) and [TERMINALS.md](TERMINALS.md).

- **Others folders.** [external-folders-service.ts](../src/server/external-folders-service.ts) has two layers. `ExternalFolderRegistry` is server-wide: one `ProjectFilesService` with Git status disabled per folder, shared by every worktree listing it, broadcasting its changes to all of them. `ExternalFoldersService` is per worktree: the list of open folders, persisted in the store database under `external-folders:<wtPath>`, never nested (adding a parent replaces open children), each with its own `FileOperationsService` on the worktree's undo history. Watcher details are in [WATCHERS.md](WATCHERS.md).
- **Individual files.** [external-files-service.ts](../src/server/external-files-service.ts) keeps an in-memory set of individually opened files with one `fs.watch` each. It is not persisted. Instead, `resolveFilePathWithHint` in [routes.ts](../src/server/routes.ts) registers an unknown absolute path as an external file whenever the request carries a worktree hint, and the client re-sends `register_external_files` for open out-of-worktree editors on reconnect and when an Others folder that contains them is removed. Closing such a tab sends `close_external_file`. Files inside an open Others folder are served by the folder, not this service.

## Search

**Find in Files.** [SearchModal.tsx](../src/components/search/SearchModal.tsx) debounces queries by 300 ms and aborts the previous request. `GET /api/search` runs ripgrep (`rg --json`, fixed strings unless regex, `--max-count 50` per file, `--max-columns 500`, `maxResults` defaulting to 500 and capped at 2000), streams and parses the JSON lines, converts byte offsets to character offsets, and kills `rg` once the limit is hit. Scopes ([search-scope-model.ts](../src/components/search/search-scope-model.ts)) map to request params: presets (`all` searches the worktree and its drafts, `worktree`, `drafts`, `ignored` adds `--no-ignore`), worktree-relative paths for packages and custom folders, and `--glob` for extensions. Others folders are not searched. `GET /api/search-scopes` lists workspace packages, directories and extensions. [search.ts](../src/store/search.ts) persists only `recentCustomPaths`, through server storage. Response types are in [search-model.ts](../src/api/search-model.ts).

**Quick Open.** [FileSearchModal.tsx](../src/components/file-search/FileSearchModal.tsx) loads `GET /api/file-index` (`rg --files --hidden`, `.git` excluded, capped at 100,000 paths, worktree only) and refetches in the background on each open. [file-search.ts](../src/store/file-search.ts) caches the index and a 15-entry MRU per worktree. Ranking is `fuzzyMatchPath` in [fuzzy-match.ts](../src/lib/fuzzy-match.ts): score tiers from exact filename down to a fuzzy subsequence spread across the path, with a tiebreaker on path length and match spread. A `path:line[:col]` suffix is parsed by `parseQueryLocation`.

**Go to Symbol.** [SymbolSearchModal.tsx](../src/components/symbol-search/SymbolSearchModal.tsx) sends `workspace/symbol` (150 ms debounce) to the clients `getConnectedLspClients` in [lsp-client.ts](../src/lib/lsp-client.ts) returns for the active worktree, and cancels the request in flight on every new query. Only connected servers are asked: TypeScript always (it searches only the projects of its open files), the lazily started ones while a file of their language is open. Spawning a server just to search would mean a cold workspace index on every query and a process the lazy connector would kill again. A client leaves that list when its socket closes. [workspace-symbols.ts](../src/lib/workspace-symbols.ts) merges the answers: `searchWorkspaceSymbols` reports the merged list each time a server answers, so a slow one does not hold back the others, cancels a server that has not answered within 3 s, drops failed servers and URIs that are neither editor files (`editorFilePath`, see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md#uri-schemes)) nor a server's [read-only documents](LANGUAGE_SERVERS.md#read-only-documents), and `rankWorkspaceSymbols` re-scores names with `fuzzyMatch` (servers filter with their own, looser matchers) above an exact-match tier, puts the worktree's own files before those under dependency, environment, git or nested-worktree folders (`PROTECTED_SEGMENTS` in [lsp-workspace-files.ts](../src/lib/lsp-workspace-files.ts)) and outside files, and dedupes a symbol two servers report (keyed by path, name, kind, container and position). Each search session starts empty, and results are kept per worktree, so an earlier session's or worktree's results are never shown. `resolveWorkspaceSymbolLocation` resolves a symbol without a range before opening it, falling back to the top of the file after 2 s.

Quick Open, Go to Symbol and the command palette render through [picker-dialog.tsx](../src/components/ui/picker-dialog.tsx), which owns the dialog, the query input and keyboard navigation (and, for the palette, a free-text input mode and refocusing when it swaps what it shows). Quick Open, Find in Files and Go to Symbol open results through `dispatchOpenFile` with a line and column (a symbol in a read-only document through `dispatchOpenVirtualDocument`); the markdown editor maps them with `rawLineToProsePosition`.

## Invariants

- One open file is one absolute path: one panel per path and type in a layout, one cache key, and one editor-state entry per editor showing it, the tab's keyed by the path. Paths from the server and the client must be normalized the same way (`resolve`, `canonicalPath`).
- Editor writes go only through `saveEditorContent`, which always sends a fresh nonce (`/api/file-write` requires one). A write without a nonce is seen as an external change by every editor, including the one that made it.
- Completion of a save is the nonce echo, not the HTTP response. Do not mark files clean elsewhere.
- An unmounting editor flushes only to its own path or its entry's `movedTo`; never to a path a delete or move handler already closed.
- A file marked `deleted` is never written implicitly: only `saveNow` (after confirmation) or `recreateFile` may re-create it, and only `handleDiskChange` or a successful content fetch clears the flag.
- Imperative editor updates must be invisible to the change listener (`isProgrammaticRef`, or `lastAppliedBodyRef` in markdown) or they trigger save, echo, apply loops.
- Merged or disk content is applied as minimal edits (`computeLineEdits`, `createMinimalReplaceTransaction`), never as a whole-content reset with a restored offset.
- Markdown round trip: blocks the user did not edit are written back byte-for-byte, and preservation is validated so it can only fall back to canonical output. Edited blocks take canonical form, trailing newlines collapse to one, and the frontmatter separator is normalized to one blank line.
