# Architecture

The top-level internal map of `packages/loxel`: processes, source layout, the client-server contract, server composition, observability and tests, with links to the internal docs that cover each area in depth.

## Process topology

Three kinds of process cooperate. A single Bun server per mode (port 7433 prod, 7434 dev, 7435 + n for demo instance n) owns everything that touches the filesystem, Git, language servers and SQLite, and serves the built renderer; the PTYs run in detached [terminal host](TERMINAL_HOST.md) processes it starts and reaches over a socket, so they outlive it. Each Electron window loads the server's URL and runs the React renderer, which talks to the server only over REST (`/api/*`) and WebSocket (`/ws`, plus one socket per language-server session under `/ws/<lsp>`). The Electron main process, one per app, starts the server, which lives as long as the app, and handles native integrations and app updates over IPC. Within the server, the commands in `git-commands/` start on a worker thread so that process creation does not stall the event loop ([GIT.md](GIT.md#git-exec-worker)). The `loxel` CLI ([cli.ts](../src/cli.ts)) is a fourth, short-lived client that posts open requests to a running server ([open-request.ts](../src/open-request.ts)). Process model and updates are in [ELECTRON.md](ELECTRON.md); starting, restarting and stopping the server, and state scopes, are in [SHARED_SERVER.md](SHARED_SERVER.md).

## Source layout

All code lives under one `src/` tree with one [tsconfig.json](../tsconfig.json) (DOM libs included) and the `@/*` path alias, so the server, Electron and renderer typecheck together and can import each other's modules. The same tsconfig covers `scripts/` and `e2e/`, so the typecheck includes the build and demo scripts and the Playwright suite. Boundaries are conventions, not enforced, with one exception: nothing under `src/terminal-host/` may import from `src/server/` ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-boundary)).

## Client-server contract

### Shared models

`src/api/*-model.ts` modules define the request and response shapes that both [client.ts](../src/api/client.ts) and the server handlers import. Two styles coexist:

- **Zod schemas with inferred types** in [project-model.ts](../src/api/project-model.ts), [review-model.ts](../src/api/review-model.ts), [comment-model.ts](../src/api/comment-model.ts) and [open-in-model.ts](../src/api/open-in-model.ts). The schema is canonical and the type is `z.infer`.
- **Plain TypeScript types** everywhere else (`git-models.ts`, `diff-model.ts`, `log-entry-model.ts`, `search-model.ts`, ...).

Request bodies are validated on the server: [review-routes.ts](../src/server/review-routes.ts) and [open-in-routes.ts](../src/server/open-in-routes.ts) `safeParse` request bodies; [routes.ts](../src/server/routes.ts) checks fields by hand (`parseBody`, `requireString`, `requireStringArray`). The client does not validate responses: `fetchJson<T>` returns the parsed JSON as `T`.

### REST

- **Dispatch.** [server.ts](../src/server/server.ts) forwards every `/api/*` request to `handleRequest(req, ctx)` in [routes.ts](../src/server/routes.ts). It first looks up a static `routes[method][pathname]` table, then falls through to hand-written matches: `/api/projects/:id...` regexes, `/api/layout/promote`, `/api/stores/:key`, and prefix-delegated sub-routers [localdb-routes.ts](../src/server/localdb-routes.ts), [review-routes.ts](../src/server/review-routes.ts) and [open-in-routes.ts](../src/server/open-in-routes.ts). Sub-routers take their own narrow context and return `null` when no route matches.
- **Scope.** Worktree- or project-scoped endpoints take `?wt=<worktree path>` or `?project=<path>` (or a `worktreePath` body field); `resolveWorktreeFromReq` / `resolveProjectFromReq` / `resolveProjectFromBody` map that to a `ProjectState` via `findProjectForPath`.
- **Responses.** Handlers return `json(data)` or `error(message, status)` from [response-helpers.ts](../src/server/response-helpers.ts); `error` keeps only the first line of the message, and the client throws `new Error(body.error)`. Exceptions thrown by a static-table handler become a 500 with the error message. [error-message.ts](../src/server/error-message.ts) `describeError` builds a message from an error's cause chain and the failed command's stderr, for failures from Git and `wt`.
- **Dependency injection.** `RouteContext` (defined in `routes.ts`) carries the broadcast functions, project and worktree lookups, lifecycle hooks and formatter/schema services that server.ts owns, which lets route tests build a fake context (for example [routes.detached.test.ts](../src/server/routes.detached.test.ts)).
- **Naming trap.** `GET /api/log` is the Git log, `POST /api/log` ingests a log entry, and `GET /api/logs` returns server log history.

### WebSocket

The app socket (`/ws`) carries JSON text frames typed in [ws-protocol.ts](../src/api/ws-protocol.ts): `WsMessage` (server to client) and `WsClientMessage` (client to server). Terminal I/O uses binary frames on the same socket (`BIN_MSG_OUTPUT`, `BIN_MSG_INPUT`, in [terminal-stream.ts](../src/api/terminal-stream.ts)); their layout is specified in [TERMINALS.md](TERMINALS.md#websocket-protocol). Messages are built inline where they are sent; [ws-messages.ts](../src/server/ws-messages.ts) holds the shared `worktreesChangedMessage` builder.

Server-to-client delivery uses helpers in server.ts, chosen by scope:

- `broadcastToSubscribers(wtPath)`: clients subscribed to a worktree (`status_changed`, `files_dir_changed`, `file_content_changed`, ...).
- `broadcastToProject(projectPath)`: clients subscribed to any worktree of the project, deduplicated (`refs_changed`, `log_changed`, `worktree_status_changed`, `localdb_changed`).
- `broadcastAll`: every app client (`store_updated`, notifications, `log_error_count`).
- `sendToActiveWindow(windowId)`: one window (`open_file`, `open_folder`, `open_terminal`, and `open_url` when no window shows its worktree), see [Per-window identity](#per-window-identity).
- `sendToWorktreeWindows(wtPath, windowId)`: every subscriber showing a worktree, with a different message for the window in use among them (`open_url` with its placement and focus); returns false when no window shows it, and `open_url` then goes through `sendToActiveWindow`.
- `sendTo(ws)`: one socket; a terminal session's events reach every connection attached to it, each through its own sink (see [TERMINALS.md](TERMINALS.md#several-clients)).

The server's first message on every connection is `server_hello`: its `version` and its identity (`ServerIdentity` in ws-protocol.ts), a `serverId` generated once per state directory (`<stateDir>/server-id`, read at startup by [server-identity.ts](../src/server/server-identity.ts)) and a `bootEpoch` new with every server process. `GET /api/version` returns the same fields.

On the client, [client.ts](../src/api/client.ts) exports a singleton `wsClient` (`WsClient`). Its connection state (`connecting` until the first hello, then `connected` or `reconnecting`, in [ws-reconnect.ts](../src/api/ws-reconnect.ts)) drives the top bar's reconnecting indicator and TanStack Query's online state. After a disconnect it retries with exponential backoff (250 ms doubling to 10 s, jittered), or at once when the window becomes visible, the network comes back or the user clicks the indicator. Nothing is sent on a new socket before its hello; JSON messages sent meanwhile are queued. On the hello:

- A different `version` or `serverId` than the last hello reloads the page, to load that server's renderer and state.
- Otherwise it re-sends `subscribe_worktree` for every worktree it is subscribed to (`subscribeWorktree` / `unsubscribeWorktree` keep that list, with the shown worktree last, since the server takes the last subscription as the shown one), then on a reconnect runs the `onReconnect` listeners with `serverRestarted` (the `bootEpoch` changed) so features re-create the rest of their server-side state (log subscription, terminal reattach, window identity, external files) and catch up.
- Finally it sends the queued messages: all of them on the first connection, and after a reconnect only what the user asked for meanwhile (closing a terminal, dismissing a notification), since the listeners re-create the per-connection state and the rest would duplicate it (`sentAfterReconnect`).

- [ws-bridge.ts](../src/queries/ws-bridge.ts) (`useWsBridge`, mounted in [App.tsx](../src/App.tsx)) connects the client and routes push messages into the TanStack Query cache (`setQueryData` or `invalidateQueries`) and into stores (logs, notifications, `store_updated`). Its `switch` ends in a `never` check, so adding a `WsMessage` variant fails typecheck until the bridge handles or explicitly ignores it. After a reconnect it invalidates every query but file contents, since pushes sent while the socket was down are lost whether or not the server restarted, and fetches the projects and their worktree lists again, which releases worktrees removed meanwhile. File contents catch up through the `worktree_files_resynced` the server sends each re-subscribed worktree, which takes editors with unsaved changes through their state machine.
- Terminal messages are ignored by the bridge and consumed by their own `wsClient.subscribe` listeners in [Terminal.tsx](../src/components/terminal/Terminal.tsx).
- [useWsSubscription.ts](../src/hooks/useWsSubscription.ts) subscribes to the active worktree. When the worktree changes it defers unsubscribing the previous one until its pending saves drain (`onWorktreeSavesDrained`), so server resources outlive panel-unmount autosaves, and keeps it when the window switched back meanwhile. When the server resyncs the active worktree (`worktree_files_resynced`, which follows a subscription), it re-registers the open files outside the worktree (`register_external_files`), which the server drops with the worktree's resources.

### Request origin checks

The server serves one `fetch` handler (`serveRequest` in [server.ts](../src/server/server.ts)) on two listeners: the loopback TCP port, for the app's windows and its main process, and a Unix socket for the `loxel` CLI, which only the user's own account can open (see [The CLI socket](#the-cli-socket)). The listener a request arrived on decides its principal (`Principal`): `app` over TCP, `cli` over the socket. [request-origin.ts](../src/server/request-origin.ts) decides which requests each serves at all. `checkRequest` runs before any routing, so the same rules cover REST, WebSocket upgrades and static files; a rejection is returned as the usual `{ error }` JSON:

- **Principals.** Each route lists the principals it serves (`ROUTE_PRINCIPALS`), and a route not listed serves `app` only. `cli` gets what the CLI sends ([cli.ts](../src/cli.ts), [find-server.ts](../src/find-server.ts), [open-request.ts](../src/open-request.ts)): `GET /api/version` and `POST /api/open`. Every other route, WebSocket upgrade and static file answers it `403`. `app` gets every route.
- **Host.** `Host` must be `127.0.0.1`, `localhost` or `[::1]` with the port the server listens on; anything else is a `400`. This keeps a page on another hostname from reaching the server even when that hostname resolves to loopback. This rule and the next two apply to `app` only: no browser can connect to a Unix socket, so there is no page to tell apart there, and `Host` names no address on one.
- **Origin.** This rule only decides requests that carry an `Origin`. A missing `Origin` is not conclusive on its own: browsers attach it to WebSocket upgrades, CORS-mode fetches and non-GET/HEAD requests, but not to no-cors GET subresource loads or navigations, so a request without it may come from a native client (the Electron main process, curl), be a same-origin GET from the renderer, or be a cross-site no-cors GET or navigation. The cross-site cases are handled by the Sec-Fetch-Site rule below; the rest are admitted here. When `Origin` is present it must be the server's own origin on one of the loopback hosts above, otherwise the request is a `403`. A dev server (`LOXEL_DEV=1`) also accepts the Vite dev-server origin (port `5173`, or `LOXEL_VITE_PORT`, read by both through [app-ports.ts](../src/app-ports.ts)), since `pnpm run dev` and `pnpm run dev:app` serve the renderer from there and proxy `/api` and `/ws` to the server with `changeOrigin`, so `Host` names the server; Vite runs with `strictPort` so that origin cannot drift.
- **Cross-site requests.** Any request the browser marks `Sec-Fetch-Site: cross-site` is a `403`, except a top-level document navigation (`Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest: document`), so a link into the app still opens it while cross-site pages cannot fetch endpoints, load them as subresources, or frame them with `<iframe>`, `<object>` or `<embed>`. Content the app loads from itself must therefore come from its own origin: the media viewer's image and video frames keep the server origin (`sandbox="allow-scripts allow-same-origin"`), while the SVG frame stays in an opaque origin because it inlines the file and makes no network requests.
- **Mutations.** For every principal, `POST`, `PUT`, `PATCH` and `DELETE` must declare `Content-Type: application/json` (`415` otherwise). Browsers only send a JSON content type cross-site after a CORS preflight, which the server never answers, so this stops cross-site form and `text/plain` posts even from clients that send neither `Origin` nor `Sec-Fetch-Site`. Every mutating endpoint takes a JSON body, so there is no non-JSON exception; `fetchJson` in [client.ts](../src/api/client.ts) sets the header on every request, and the other callers (Electron, the localdb panel) set it explicitly, including on body-less `DELETE`s.

Rejections are logged at `warn` level with the principal, the offending host, origin, method and path. The server never sends `Access-Control-Allow-Origin`, so cross-origin pages cannot read responses either. The `Host`, `Origin` and `Sec-Fetch-Site` rules keep web pages out; they are not authentication.

#### The CLI socket

The socket is `<stateDir>/run/cli.sock` (`config.cliSocketPath`, from `cliSocketPath` in [socket-paths.ts](../src/socket-paths.ts)), so dev, production and each demo instance have their own. A `LOXEL_STATE_DIR` too deep for a socket path puts it in the temporary directory instead, `loxel-run-<hash of the state directory>`, the way the [terminal hosts' sockets](TERMINAL_HOST.md#files-on-disk) do, and the server logs a warning. Only the user's own account can open it: [cli-socket.ts](../src/server/cli-socket.ts) makes its directory 0700 and checks that the user owns it (`ensurePrivateDir`), and narrows the socket to 0600 once it listens, the private directory covering the moment before.

The newest server takes the socket over, so there is nothing to probe or clean up at startup. `takeOverSocket` listens on a fresh name in the same directory (`cli.sock.<8 hex digits>`, `cliSocketTempPath`; the directory is chosen so that this longer name fits the path limit too), narrows it to 0600, records its inode, and `rename()`s it over `cli.sock`. The rename replaces whatever is there in one step: a stale socket file a killed server left, a file that is not a socket, or the live socket of an older server that is still draining (see [SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)) or shares the state directory on another `LOXEL_SERVE_PORT`. An older server keeps its listening socket and the connections it has, but new connections reach the newest server, and the older one is not reachable by the CLI again: when the newer one stops first, it removes the socket and the CLI finds no server. In teardown a server removes `cli.sock` only while that path still refers to the inode it recorded, so a draining server never removes its replacement's socket; Bun's `stop()` removes only the temporary name, which no longer exists. A stale file left after a kill is harmless: the CLI's connection is refused, the same as no socket. The takeover is synchronous and runs right after the TCP listener starts. When it fails (the directory cannot be made private, the socket cannot be listened on or renamed), the server logs an error and adds a high-urgency notification with source `server`, naming the socket and the reason, which the first window to connect gets with `notifications_sync`. The server keeps serving the app over TCP, and the CLI cannot reach it: there is no fallback to the TCP port. How the CLI finds the socket is in [TERMINALS.md](TERMINALS.md#the-loxel-cli).

### TanStack Query

[query-client.ts](../src/query-client.ts) sets `staleTime: Infinity`, `refetchOnWindowFocus: false` and a 30-minute `gcTime`: data is fresh until a WebSocket push or a mutation's `onSuccess` invalidates it. TanStack's online state follows the server connection instead of the browser's network state (every request goes to the Loxel server, which a laptop with no network still reaches when it is local): queries wait while `wsClient` reconnects and run once it is back, and mutations use `networkMode: "always"`, so a user action runs or fails now rather than landing later. Keys come from [query-keys.ts](../src/queries/query-keys.ts) and lead with the project path (then worktree path where relevant), so repo-wide data such as refs is shared by the project's worktrees. [use-repo-queries.ts](../src/queries/use-repo-queries.ts) wraps `useQuery` with the active scope from [use-scope.ts](../src/queries/use-scope.ts); [use-git-mutations.ts](../src/queries/use-git-mutations.ts) holds mutations.

### Adding an endpoint end-to-end

1. Define the request and response shapes in the matching `src/api/*-model.ts` (a Zod schema if the server should validate the body).
2. Write the handler in [routes.ts](../src/server/routes.ts) (or the matching `*-routes.ts` sub-router), resolve scope with the `resolve*` helpers, and register it in the `routes` table. Reach server state only through `RouteContext`; extend it in routes.ts and supply the implementation in server.ts if needed. A new route serves the app only; list it in `ROUTE_PRINCIPALS` ([request-origin.ts](../src/server/request-origin.ts)) only when the `loxel` CLI sends it.
3. Add a typed function to [client.ts](../src/api/client.ts) using `fetchJson` and `withScope`.
4. For reads, add a key to `queryKeys` and a hook in `src/queries/`; for writes, a mutation that invalidates the affected keys.
5. If other windows must see the change, add a `WsMessage` variant, broadcast it at the right scope, and handle it in ws-bridge (typecheck enforces the last step).
6. Add a route test next to the handler with a fake `RouteContext`.

## Server composition

- [index.ts](../src/server/index.ts) is the process entry. The same executable doubles as the LaunchServices helper, so it checks for the helper flag before loading any server module, then imports [server.ts](../src/server/server.ts).
- [server.ts](../src/server/server.ts) is the composition root, written as module-level state and top-level `await`. Startup: initialise the secret store, start resolving the login-shell environment, load registered projects (plus an optional repo path from `argv[2]`), initialise all projects in parallel, take over the terminals still running in terminal hosts ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-servers-side)), wait up to 2 s for the login-shell environment (so the first terminals and language servers get it), start `Bun.serve` on `127.0.0.1`, wire the logger's broadcast callbacks, recover orphaned layout sessions, and start the perf monitor. Before all of that, a server the desktop app started (`LOXEL_PARENT_PID`) follows the app's channel and watches for the app to exit, so it can be stopped while it starts ([SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)). Non-API paths are served from the renderer build directory (`LOXEL_STATIC_DIR`, else the bundled or `dist/` build) with an `index.html` fallback.
- [config.ts](../src/server/config.ts) derives `isDev`, `stateDir`, `port`, `cliSocketPath`, `parentPid`, `removedWorktreeTerminalDelayMs` and state subdirectories from `LOXEL_DEV`, `LOXEL_DEMO`, `LOXEL_DEMO_INSTANCE`, `LOXEL_STATE_DIR`, `LOXEL_SERVE_PORT`, `LOXEL_PARENT_PID` and `LOXEL_REMOVED_WORKTREE_TERMINAL_DELAY_MS`, and provides `hash12` for state paths.
- [server-state.ts](../src/server/server-state.ts) declares the scope types and pure lookup helpers (`findOwningProject`, `externalFolderConflict`, `listOthers`, `worktreeTree`); server.ts owns the maps.

Services by scope:

| Scope                              | Created                                                                                                                              | Contents                                                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server-wide                        | module load in server.ts                                                                                                             | `TerminalHostPool` and its `TerminalManager`, `NotificationStore`, `SchemaService`, `FormatService`, one manager per language server, `ExternalFolderRegistry`, the client map                                        |
| Per project (`ProjectState`)       | `initializeProject` at startup or registration                                                                                       | Git `FileWatcher`, `ReviewDb`, `LocalDb`, `WorktreeStatusTracker`, worktrees dir                                                                                                                                      |
| Per worktree (`WorktreeResources`) | first `subscribe_worktree`; torn down 5 minutes after the last subscriber leaves ([SHARED_SERVER.md](SHARED_SERVER.md#state-scopes)) | file, file-operations (with undo history), drafts, external files and Others-folder services, a linked worktree's own Git watcher                                                                                     |
| Per connection (`ClientState`)     | WebSocket `open`                                                                                                                     | attached terminals, subscribed worktrees, `windowId`                                                                                                                                                                  |
| Per LSP socket                     | `/ws/<lsp>?wt=...` upgrade                                                                                                           | one language-server session per socket, at most one per worktree path for worktree-scoped servers, which a new socket can take over for a minute after its own closed; see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md) |

`resolveFilePath` maps an absolute path to its owning worktree resources (drafts first, then worktree files, then Others folders and external files, preferring the requester's worktree). Watcher wiring is in [WATCHERS.md](WATCHERS.md); projects and worktrees in [PROJECTS_AND_WORKTREES.md](PROJECTS_AND_WORKTREES.md).

### Per-window identity

[window-id.ts](../src/lib/window-id.ts) exports `WINDOW_ID`: in Electron the main process passes `--loxel-window-id` through `additionalArguments` and the preload exposes it as `window.loxelWindow`; outside Electron a UUID is kept in `localStorage`. [useWindowPresence.ts](../src/hooks/useWindowPresence.ts) sends `window_hello` (stored as `ClientState.windowId`) and `window_focused` (tracked as the last focused client). Terminals receive `LOXEL_WINDOW_ID`, the CLI forwards it in `POST /api/open`, and `sendToActiveWindow` targets that window, else the last focused one, else any client. The same ID keys per-window layout sessions (`/api/layout/promote`, [layout-key-schema.ts](../src/lib/layout-key-schema.ts)); see [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md).

## Observability

- **Server logger** ([logger.ts](../src/server/logger.ts)): `logger.child(category)` emits `LogEntry` records ([log-entry-model.ts](../src/api/log-entry-model.ts)) with a category from the closed `LOG_CATEGORIES` list or a language server's name. Each entry goes to a 5000-entry ring buffer and to an NDJSON file `<stateDir>/logs/server-<instanceId>.log` (rotated to `.log.1` above 5 MB; other instances' files older than 24 h are deleted). Terminal hosts, separate processes, write their own `terminal-host-<hostId>.log` and send their lines at `info` and above to the server, which logs them under `terminal` ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-servers-side)). Entries at `info` and above are batched every 100 ms to sockets that sent `subscribe_logs`; an error-count delta is always broadcast to all clients for the Logs badge, and `subscribe_logs` replies with a `log_error_snapshot` total for reconciliation.
- **Frontend and Electron logs** ([frontend-logger.ts](../src/lib/frontend-logger.ts), [main-perf-monitor.ts](../src/electron/main-perf-monitor.ts)): same `ChildLogger` API, sent fire-and-forget to `POST /api/log` and re-emitted by the server, so all processes share one stream. Entries carry no origin field; the category identifies the source.
- **Logs panel**: [logs.ts](../src/store/logs.ts) loads history with `GET /api/logs` (newest first, paged by `before` id), appends live batches, and refcounts the `subscribe_logs` subscription, resending it on reconnect.
- **Perf monitors**: [perf-monitor.ts](../src/lib/perf-monitor.ts) (renderer: FPS, long tasks, lag, heap), [server-perf-monitor.ts](../src/server/server-perf-monitor.ts) (event-loop lag, memory, subprocess spawning), [host-perf-monitor.ts](../src/terminal-host/host-perf-monitor.ts) (each terminal host's event-loop lag, memory, PTY spawns and sessions, forwarded to the server; see [TERMINAL_HOST.md](TERMINAL_HOST.md#perf-monitor)) and `main-perf-monitor.ts` (per-process CPU and memory) log summaries at `debug` and escalate anomalies to `warn`/`error`, all with `cat: "perf"`. Debug summaries reach the file and ring buffer but not the live stream.
- **Spawn metrics** ([spawn-metrics.ts](../src/server/spawn-metrics.ts)): per 10 s window, the spawn count and rate, the time spawn calls blocked the event loop, the same for spawns on the git exec worker (`workerBlockMs`, which is not event loop time), child wall time and the top labels (git subcommands, `lsp`, `rg`, ...). `spawns` is on the server metrics summary and on the "server event loop lag" warning, so a stall shows how much spawning happened alongside it. `runGit` records wall time; other sites wrap their call in `measureSpawn`, which counts the spawn and its block time only. The remaining `Bun.$` Git calls outside `git-commands/` (explorer file operations, the diagnostics temp worktree, the watcher's and review database's reads) are not counted. Those and the `measureSpawn` sites still spawn on the main thread.
- **Stress detector** ([stress-detector.ts](../src/server/stress-detector.ts)): rate checkpoints (`broadcast`, `api-request`, `git-watch`, `pty-output`, ...) that log when a call rate, or the same key, enters an elevated or high rate and once with a summary (peak, duration) after it stays low for `calmWindows` windows, not once per window; detection only.
- **LSP stderr** is rate-limited per session by [stderr-throttle.ts](../src/server/stderr-throttle.ts) so a chatty server does not flood the ring buffer.
- **Reading logs locally**: open the Logs panel, or read the NDJSON files under `~/.local/state/loxel/loxel-dev/logs/` (dev) or `.../loxel/logs/` (prod), e.g. with `jq`.

## Testing

- **Unit tests** sit next to the code as `*.test.ts`. `pnpm run test` runs `bun test src scripts --parallel` with a worker process per CPU, at most six, each running a file in a fresh global (as `--isolate` does). macOS checks each new executable file the first time it runs, a few hundred milliseconds each and one at a time for the whole system, and the server tests write hundreds of stand-in tools: a test writes one with `writeExecutable` from [executable.ts](../src/test/executable.ts), which hard-links each script from a store kept in the temporary directory between runs, so a script is checked once rather than once per test. Without it, the queue of checks kept more than two workers from paying off and pushed tool runs past the product's own timeouts. The first run on an empty store, as after a restart, still checks every script once: six workers got through that, ten queued behind the checks long enough to time out. A stand-in gains only if it repeats, so keep a test's own paths out of it and read them from `$0` or the environment (`$0` is the path the tool was run by, a symlink included); one naming a temporary path is written as a new file and kept out of the store. The package's `bunfig.toml` preloads three files for every `bun test` run from the package directory, including a single file and `bun test --cwd packages/loxel`, so one file runs as it does in the suite: [temp-state-dir.ts](../src/test/temp-state-dir.ts) keeps the tests' state out of the real state directory, [dom-preload.ts](../src/test/dom-preload.ts) registers happy-dom globally and prints DOM nodes in failure messages as their markup, and [jest-dom-preload.ts](../src/test/jest-dom-preload.ts) adds jest-dom matchers.
- **`*.dom.test.tsx`** marks tests that render React with Testing Library (keybindings, find bar, tree, sidebar, menus, panels). It is a naming convention only: the preloads apply to every test.
- **Server tests** use temporary directories and real Git repos ([git-commands/test-utils.ts](../src/server/git-commands/test-utils.ts)); route tests call `handleRequest` with a fake `RouteContext` (`routes.*.test.ts`).
- **E2E** ([e2e/](../e2e/)): `pnpm run e2e` runs Playwright with [global-setup.ts](../e2e/global-setup.ts), which builds the renderer with `VITE_SCREENSHOT=1`, starts the server from source on a free port in 17434 to 17534 with a throwaway `LOXEL_STATE_DIR` and `LOXEL_STATIC_DIR` set to that build (a Loxel terminal's environment would otherwise serve the installed app's renderer), and waits for `/api/version`. The specs run with one worker against the shared server: those in `e2e/screenshots/` capture app states into `e2e/test-results/screenshots`, and `e2e/mermaid/` renders real Mermaid diagrams (see [EDITOR.md](EDITOR.md#mermaid-diagrams)). The site's screenshots are staged separately, in demo mode ([ELECTRON.md](ELECTRON.md#demo-mode)).
- **Theme screenshots** ([e2e/theme/](../e2e/theme/)): a dev-only harness, never run in CI, that shoots panels in light and dark against a throwaway dev stack (`stack.sh`, which refuses to start while the dev ports are taken), one script per panel in `panels/`. `rate.ts` sends a screenshot to external LLM CLIs (`claude`, `codex`) for scoring.
