# Desktop app (Electron)

How the Electron shell fits around the Bun server and React renderer, how the app updates, and the macOS integrations main owns. Entry point: `src/electron/main.ts`.

## Process model

- **One app process, one server.** A packaged app takes Electron's single-instance lock, and the app spawns its server on launch: the compiled `loxel-server` binary in production, `bun run src/server/index.ts` with `LOXEL_DEV=1` in dev, on the mode's port (7433 prod, 7434 dev, 7435 + n for [demo](#demo-mode) instance n). The server lives as long as the app, and the terminals live in [terminal host](TERMINAL_HOST.md) processes the server starts detached, which outlive it. Every window connects to it, identifies itself with its window ID, and talks to it over REST and WebSocket. Startup, crash restarts, shutdown and state scopes are detailed in [SHARED_SERVER.md](SHARED_SERVER.md).
- **Windows load the server's URL** (`http://127.0.0.1:<port>`), or the Vite dev server's URL under `pnpm run dev:app` (Vite proxies `/api` and `/ws` to the dev server).
- **Electron IPC is only for native integrations** (dock badge, folder dialog, window focus and fullscreen state, opening links in a browser panel, keystrokes inside webviews, copying images from webviews, page dialogs in webviews, app updates, the theme). Channel names live in `src/electron/ipc-channels.ts`, and the renderer-facing API (`window.electronAPI`) is typed in `src/electron-api.d.ts`. Everything else goes through the server.

## Updates

The app updates as a whole. Each release replaces the bundle, with its Electron runtime, main process, preloads, server, terminal host binary, language servers, renderer, `Info.plist` and entitlements. Nothing runs from the bundle once the app has quit: a terminal host, which may keep running (with its shells) for its grace period, runs from a clone of the bundled binary in the state directory ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-process)), so Squirrel can replace the bundle under it. The renderer is served from the bundle (`LOXEL_STATIC_DIR`), so the renderer, the preloads and the main process always come from the same build. Every `window.electronAPI` member therefore exists whenever `window.electronAPI` does, and the renderer calls them without checking; `window.electronAPI` itself is undefined outside Electron.

- **Updater.** [app-updater.ts](../src/electron/app-updater.ts) drives electron-updater, which downloads the new app's zip and hands it to Squirrel.Mac. Squirrel checks that the new bundle is signed by the same Developer ID as the running one, replaces the bundle once the app has quit, and relaunches it. The new bundle never gets the quarantine flag a browser download carries, so macOS does not ask the user to confirm opening it.
- **Feed.** The release manifest (`manifest.json`, written by `release-loxel.yml`) is the only description of a release. `ManifestProvider` in [update-manifest.ts](../src/electron/update-manifest.ts) reads its `update` entries: one zip per architecture, with its base64 SHA-512 and size. electron-updater picks the zip for this Mac, verifies its SHA-512, and downloads only the changed blocks when the zip's block map and a cached zip of the installed version exist, one range per request because the origin rejects multi-range requests. [app-update.yml](../assets/app-update.yml), packaged into the app's resources, names the cache folder; electron-updater reads it for every download. The provider drops the random per-installation `x-user-staging-id` header electron-updater adds to update checks, so a check carries no identifier.
- **State and UI.** Main keeps the `UpdateState` ([update-model.ts](../src/api/update-model.ts)) and sends every change to all windows over IPC (`UPDATE_*` in `ipc-channels.ts`). Settings > General and the top bar's Update button show it through `useUpdateStatus` ([use-update-status.ts](../src/queries/use-update-status.ts)). Downloading and installing happen only when the user asks. `autoInstallOnAppQuit` is off, so an ordinary quit never installs.
- **Automatic check.** Five seconds after launch, a packaged app reads the persisted settings row from its server and checks unless `autoCheckForUpdates` is off (`isAutoCheckEnabled` in [persisted-settings.ts](../src/server/persisted-settings.ts)). The manual check ignores the setting. Unpackaged builds never check.
- **Install location.** Squirrel can only replace a bundle it can write to. A packaged app outside an Applications folder that it cannot write to, such as one opened from the disk image or run from a read-only translocated copy, offers on launch to move itself to `/Applications`. When an install fails, Settings shows the error with a link to the download page.

## Theme

Electron's `nativeTheme.themeSource` follows the Theme setting, so native menus and dialogs, every page's `prefers-color-scheme` (browser panels' and the renderer's own) and window backgrounds match the app instead of the OS. [native-theme.ts](../src/electron/native-theme.ts) owns it:

- **Changes.** `useThemeSync` sends the setting (`dark`, `light` or `system`, the same values as `themeSource`) with `SET_THEME_SOURCE` once the settings load and on every change. With an explicit theme, the renderer's own `(prefers-color-scheme: dark)` query then matches the setting; only `system` reads it.
- **Launch.** Before the first window, main reads the persisted `theme` from the server (`persistedTheme` in [persisted-settings.ts](../src/server/persisted-settings.ts)), so the window and its webviews start in it. If the row can't be read within two seconds, the OS appearance applies until the renderer reports the setting.
- **Window background.** Windows are created with, and keep while `nativeTheme` changes, the background of the renderer's `--background` in the current theme (`WINDOW_BACKGROUND`, kept in step with `src/index.css`), so a new window or a reload paints no flash of the other theme.

## Browser panels

Browser panels host a `<webview>` per tab. `will-attach-webview` in `src/electron/main.ts` strips any preload and Node.js settings a webview asks for, then gives it Loxel's own sandboxed `src/electron/webview-preload.cjs`, which runs in every frame.

- **No reloads.** Re-attaching a `<webview>` to the DOM reloads its page, so browser panels are created with dockview's `renderer: "always"` and activation of an already-active tab goes through `activatePanel()` (`src/store/layout-actions.ts`). Switching worktrees still rebuilds the layout and reloads them.
- **New tabs.** Webviews carry `allowpopups`, so the page's new-tab and new-window requests (⌘-click, middle-click, `target="_blank"`, `window.open`) reach the main process: `src/electron/webview-new-tabs.ts` drops non-`http(s)` URLs and acts as a popup blocker, letting each click or key press in the page (within 5 seconds) open one tab or popup. A popup (`window.open` with window features, reported as `new-window`; a ⇧-clicked link is also `new-window` but has no features) is allowed as a real child window of Loxel's window, since sign-in flows such as Google's return their result through `window.opener`, which a tab cannot keep. The module builds that window itself in the handler's `createWindow`, keeping only the session, security preferences (not the webview preload), size and position Electron worked out, because Electron otherwise turns any window option in the page's features (frameless, always on top, not closable) into a real one. It pins the title to the page's origin since a popup has no address bar, closes it on ⌘W, which no Loxel renderer handles there, and refocuses the opener when it closes. It then applies the same rules to the popup's own requests, replacing the handler `main.ts` gives other windows, so its links open as tabs next to the webview and its popups as child windows of it. It sends the rest to the host renderer with the webview's webContents id and whether the disposition was a background tab. The `BrowserPanel` that owns that webview opens the tab with `openBrowserTab` (`src/lib/panel-creators.ts`), the same placement the context menu's Open in New Tab uses. The renderer sets `allowpopups` only in Electron.
- **Context menu.** The renderer draws the page's right-click menu with the app's own `ContextMenu` from the webview's `context-menu` event (`src/components/browser/BrowserContextMenu.tsx`). The event's `x`/`y` are window coordinates in device-independent pixels, not relative to the webview, so the menu is placed at them divided by the app zoom factor; `copyImageAt` and `inspectElement` take them unchanged. `<webview>` has no `copyImageAt`, so Copy Image asks the main process to call it on the webview's webContents (`src/electron/webview-copy-image.ts`), which only accepts webviews the sending window hosts.
- **Shortcuts** keep working while a page has focus through keystroke forwarding from the main process; see [KEYBINDINGS.md](KEYBINDINGS.md#shortcuts-inside-browser-panels).
- **Page dialogs** (`alert()`, `confirm()`, `prompt()`) are shown by the hosting panel, not by Electron. Electron throws on `prompt()` and shows the other two as native sheets over the whole window. The webview preload replaces the page's dialog functions with a synchronous IPC call (`JAVASCRIPT_DIALOG_RUN`), so the page blocks as with a real dialog. `src/electron/javascript-dialogs.ts` forwards the call to the host renderer and sets the IPC's return value when the panel answers. Only that page's renderer process waits, while the window stays responsive. The message shapes live in `src/electron/javascript-dialog-protocol.ts`, and the renderer side is `src/components/browser/useJavaScriptDialogs.ts`.
  - **Readiness.** Main forwards dialogs only to window renderers that subscribed (`JAVASCRIPT_DIALOG_LISTEN`, sent by the window preload's `onJavaScriptDialog`). A subscription lasts until the window's document is replaced: a committed navigation, not one the window starts and cancels, such as an external link opened in the system browser. Pages of windows without one get the dismissed result instead of blocking on a dialog nobody shows.
  - **Policy.** Main owns the browser-like policy. From a page's second dialog on, the user can block further dialogs until the page navigates, and blocking also dismisses the page's queued dialogs. Once the main frame starts a cross-document navigation, the page's pending dialogs are withdrawn and the outgoing document gets no new ones. Dialogs from frames that are gone when the new document commits are dismissed too.
  - **Toolbar navigation.** A browser-initiated navigation waits for the blocked page (its `beforeunload` round trip), so the panel dismisses its queued dialogs before navigating from the toolbar.
  - **Preload rules.** The preload ignores dialogs during `beforeunload` and `pagehide`. `disableDialogs` is set as a backstop, so frames the preload can't reach (`about:blank` iframes) get no dialog rather than a window-wide sheet.
- **Passkeys** use the macOS Touch ID platform authenticator (`src/electron/webauthn.ts`). This needs a restricted entitlement that only provisioned Developer ID builds carry, so dev runs and unprovisioned local builds have no passkeys; see [RELEASE_SIGNING.md](RELEASE_SIGNING.md).
- **Passkeys from a phone** (FIDO hybrid transport, "use a phone or tablet") come from the `webauthn-hybrid-request` session events, which leave drawing the QR code to the app. `installHybridQrCode` (`src/electron/webauthn.ts`) routes each request to the browser panel whose webview made it, and `PasskeyQrOverlay` draws the code over that panel only, so a background panel cannot put a code in front of the user. The `FIDO:/` string is a per-request secret: it goes to the hosting window's renderer and nowhere else, and is never logged. The events come from the patched Electron releases ship with ([PATCHED_ELECTRON.md](PATCHED_ELECTRON.md)); on stock Electron, as in dev runs and tests, the listeners never fire.
- **Installed fonts.** The font pickers in Settings list installed fonts with the Local Font Access API (`window.queryLocalFonts`, `src/lib/local-fonts.ts`). Electron decides `local-fonts` from the session's permission check handler alone, since its permission status is never "ask", so `src/electron/local-fonts-permission.ts` installs one on the default session that allows only the app origin (and no frame embedded by another origin), and one on `BROWSER_PARTITION` that refuses it. Blink resolves a refused query with an empty list rather than an error.

## macOS integration

- **Open from Finder.** `electron-builder.yml` declares Loxel an _Alternate_ handler for text and source files, `.excalidraw` and folders. The main process receives these as `open-file` events and posts each to `POST /api/open`, the same request the `loxel <path>` CLI sends (`src/open-request.ts`).
- **Reveal in Finder / Open In.** App lists and icons come from LaunchServices through `bun:ffi`, which runs in a helper process (the server executable started with a helper flag, see `src/server/launch-services-client.ts`) so a native crash only kills the helper.

## Demo mode

`LOXEL_DEMO=1` (`IS_DEMO` in `src/electron/env.ts`) starts a Loxel that can run beside the installed app, for staging screenshots: port 7435 and the `loxel-demo` state directory (`src/server/config.ts`), a separate Electron data directory and so a separate single-instance lock and browser session, the fixed dev encryption key instead of the keychain (`src/server/dek-source.ts`), no update checks, and windows that open at the size of the site's screenshots (1920×1200, `DEMO_WINDOW_SIZE`, allowed to be larger than the screen). Unlike dev mode it loads the built renderer, so it shows no DEV badge, and it takes precedence over dev mode: main reads the renderer's dev URL only through `DEV_RENDERER_URL`, which is unset in a demo, so one started from a dev Loxel's terminal ignores the inherited `VITE_DEV_SERVER_URL` and `IS_DEV` stays false. From the source tree it runs the server's source and serves `dist-electron/renderer`; a packaged app uses its bundled server and renderer. `LOXEL_DEMO_INSTANCE=<n>` (`DEMO_INSTANCE`) runs several at once, each on port 7435 + n with its own state (`loxel-demo-<n>`) and data directory; main, the server and the demo scripts share its parser, port and state-directory naming from [demo-instance.ts](../src/demo-instance.ts), which refuses anything but a non-negative integer. `LOXEL_DEMO_HIDDEN=1` (`IS_DEMO_HIDDEN`) gives a window that never shows itself: fully transparent, ignoring the mouse, shown without activating, and no Dock icon, while its page still renders and can be captured. With no one to read a dialog, a hidden demo logs a startup error and exits with status 1 instead of showing an error box.

`scripts/demo/launch.ts` builds and starts a visible demo (instance 0) with fresh state and the demo projects (clones of Loxel and Excalidraw with real PR branches as tasks, from `demo-projects.ts`). `scripts/demo/capture-shots.ts` stages the site's screenshots ([shots.md](../scripts/demo/shots.md)) in hidden demos (instance 1 unless told otherwise) driven by Playwright's Electron driver: each shot is a script in `scripts/demo/shots/` built on `shot-kit.ts`, its content is captured with `webContents.capturePage()`, and `composite.swift` puts it into `window-frame.png`, one real `screencapture` of a demo window (`capture-frame.ts`), so every screenshot keeps macOS's frame without a window ever coming to the front. Both start the app through `demo-app.ts`, which owns the build, registering and trusting the demo projects, and the demo's environment (`demoEnv`): the scripts' own, minus agent and Loxel terminal session markers (`withoutAgentEnv` in `src/coding-agent-env.ts`) and the variables that would point it at another Loxel (`VITE_DEV_SERVER_URL`, `LOXEL_DEV`, `LOXEL_STATE_DIR`, `LOXEL_SERVE_PORT`, `LOXEL_STATIC_DIR`).

## Build and release

`pnpm run build:app` compiles the standalone server and terminal host ([build-server.ts](../scripts/build-server.ts), which embeds the host build ID in both), builds the renderer and packages the app with electron-builder into `release/`, on macOS for this machine's architecture (`build:app:local` builds an unpacked arm64 app only). `release-loxel.yml` releases on every merge to main that touches `packages/loxel/**`; see the [README](../README.md#releases). Releases package a patched Electron rather than the npm package's binary; see [PATCHED_ELECTRON.md](PATCHED_ELECTRON.md).

The server, the terminal host, language server scripts and Go builds all produce binaries for the machine they run on, so each macOS architecture builds on a runner of that architecture. [check-binary-arch.ts](../scripts/check-binary-arch.ts) reads the header of every file in the app and fails the release if a binary doesn't match.
