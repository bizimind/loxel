# Desktop app (Electron)

How the Electron shell fits around the Bun server and React renderer, how the app updates, and the macOS integrations main owns. Entry point: `src/electron/main.ts`.

## Process model

- **One app process, one server.** A packaged app takes Electron's single-instance lock, and the app spawns its server on launch: the compiled `loxel-server` binary in production, `bun run src/server/index.ts` with `LOXEL_DEV=1` in dev, on the mode's port (7433 prod, 7434 dev, 7435 + n for [demo](#demo-mode) instance n). The server lives as long as the app, and the terminals live in [terminal host](TERMINAL_HOST.md) processes the server starts detached, which outlive it. Every window connects to it, identifies itself with its window ID, and talks to it over REST and WebSocket. Startup, crash restarts, shutdown and state scopes are detailed in [SHARED_SERVER.md](SHARED_SERVER.md).
- **Windows load the server's URL** (`http://127.0.0.1:<port>`), or the Vite dev server's URL under `pnpm run dev:app` (Vite proxies `/api` and `/ws` to the dev server). Main adds the app's session secret to every request the windows send to that origin, and sends it on its own requests to the server ([ARCHITECTURE.md](ARCHITECTURE.md#request-admission)); browser panels' partition never gets it.
- **Electron IPC is only for native integrations** (dock badge, window focus and fullscreen state, opening links in a browser panel, the default browser, keystrokes inside webviews, copying images from webviews, loading their favicons, measuring and freezing background webviews, page dialogs and notifications in webviews and their service workers, app updates, quitting and restarting with the question before a quit and the setting it follows, the theme). Channel names live in `src/electron/ipc-channels.ts`, and the renderer-facing API (`window.electronAPI`) is typed in `src/electron-api.d.ts`. Everything else goes through the server.

## Updates

The app updates as a whole. Each release replaces the bundle, with its Electron runtime, main process, preloads, server, terminal host binary, language servers, renderer, `Info.plist` and entitlements. Nothing runs from the bundle once the app has quit: a terminal host, which keeps running with its shells, runs from a clone of the bundled binary in the state directory ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-process)), so Squirrel can replace the bundle under it. The renderer is served from the bundle (`LOXEL_STATIC_DIR`), so the renderer, the preloads and the main process always come from the same build. Every `window.electronAPI` member therefore exists whenever `window.electronAPI` does, and the renderer calls them without checking; `window.electronAPI` itself is undefined outside Electron.

- **Updater.** [app-updater.ts](../src/electron/app-updater.ts) drives electron-updater, which downloads the new app's zip and hands it to Squirrel.Mac. Squirrel checks that the new bundle is signed by the same Developer ID as the running one, replaces the bundle once the app has quit, and relaunches it. The new bundle never gets the quarantine flag a browser download carries, so macOS does not ask the user to confirm opening it.
- **Feed.** The release manifest (`manifest.json`, written by `release-loxel.yml`) is the only description of a release. `ManifestProvider` in [update-manifest.ts](../src/electron/update-manifest.ts) reads its `update` entries: one zip per architecture, with its base64 SHA-512 and size. electron-updater picks the zip for this Mac, verifies its SHA-512, and downloads only the changed blocks when the zip's block map and a cached zip of the installed version exist, one range per request because the origin rejects multi-range requests. [app-update.yml](../assets/app-update.yml), packaged into the app's resources, names the cache folder; electron-updater reads it for every download. The provider drops the random per-installation `x-user-staging-id` header electron-updater adds to update checks, so a check carries no identifier. The manifest's optional `terminal_host_protocol` is the release's `TERMINAL_HOST_PROTOCOL`, which the release workflow reads with [terminal-host-protocol.ts](../scripts/terminal-host-protocol.ts) (failing the release if it cannot); the provider passes it on as `terminalHostProtocol` on the update info, which electron-updater hands to `update-available` as is. Manifests from before it leave it out. The site reads the manifest's `app` installers and `sbom` (see [Build and release](#build-and-release)).
- **Terminals.** An install keeps the terminals running unless the update's terminal hosts cannot take them over. [update-terminals.ts](../src/electron/update-terminals.ts) decides it from versions alone:
  - `updateRestartsTerminals` compares the update's `terminal_host_protocol` major with this build's `TERMINAL_HOST_PROTOCOL` ([terminal-host-protocol-version.ts](../src/api/terminal-host-protocol-version.ts)). Every running host speaks this build's major, since the server ends hosts of any other major at startup and starts hosts only of its own build ([TERMINAL_HOST.md](TERMINAL_HOST.md#versioning)). The answer is `restartsTerminals` on the `available`, `downloading` and `ready` states: `false` for the same major, `true` for another, `"unknown"` for a manifest without the field.
  - `terminalsForInstall` turns it into the install's mode, which Install & Restart records and `terminalsForUpdateInstall()` in [app-updater.ts](../src/electron/app-updater.ts) returns to `will-quit`. Whatever plan the quit had, it stops the server with that mode: `end` for `true`, rather than leave hosts the new server cannot talk to; `keep` otherwise, and the new version's server reattaches them (see [SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)). For `"unknown"` the new server keeps the hosts it can talk to and ends the rest with a notice, so nothing ends that did not have to, and nothing ends unseen.
  - **Before installing.** While `restartsTerminals` is not `false`, the top bar's Update button and Settings > General warn that the update restarts (or may restart) N terminals, counted from `GET /api/terminals` ([running-terminals-model.ts](../src/api/running-terminals-model.ts), kept current by the `terminals_changed` broadcast). Install & Restart then lists the terminals (the button shows a spinner meanwhile) and asks with `requestConfirmation`, in the app, listing the terminals whose terminal host reports a foreground program (capability `foregroundProcess`, read with `?programs`); a terminal whose host cannot tell is only counted. The texts come from [update-terminal-restart.ts](../src/lib/update-terminal-restart.ts).
- **State and UI.** Main keeps the `UpdateState` ([update-model.ts](../src/api/update-model.ts)) and sends every change to all windows over IPC (`UPDATE_*` in `ipc-channels.ts`). Settings > General and the top bar's Update button show it through `useUpdateStatus` ([use-update-status.ts](../src/queries/use-update-status.ts)). Downloading and installing happen only when the user asks. `autoInstallOnAppQuit` is off, so an ordinary quit never installs.
- **Automatic check.** Five seconds after launch, a packaged app reads the persisted settings row from its server and checks unless `autoCheckForUpdates` is off (`isAutoCheckEnabled` in [persisted-settings.ts](../src/server/persisted-settings.ts)). The manual check ignores the setting. Unpackaged builds never check.
- **Install location.** Squirrel can only replace a bundle it can write to. A packaged app outside an Applications folder that it cannot write to, such as one opened from the disk image or run from a read-only translocated copy, offers on launch to move itself to `/Applications`. When an install fails, Settings shows the error with a link to the download page.

## Theme

Electron's `nativeTheme.themeSource` follows the Theme setting, so native menus and dialogs, every page's `prefers-color-scheme` (browser panels' and the renderer's own) and window backgrounds match the app instead of the OS. [native-theme.ts](../src/electron/native-theme.ts) owns it:

- **Changes.** `useThemeSync` sends the setting (`dark`, `light` or `system`, the same values as `themeSource`) with `SET_THEME_SOURCE` once the settings load and on every change. With an explicit theme, the renderer's own `(prefers-color-scheme: dark)` query then matches the setting; only `system` reads it.
- **Launch.** Before the first window, main reads the persisted settings row from the server (`readLaunchSettings` in [settings-row.ts](../src/electron/settings-row.ts)) and applies its `theme` (`persistedTheme` in [persisted-settings.ts](../src/server/persisted-settings.ts)), so the window and its webviews start in it; the same read gives main the "When quitting Loxel" setting ([SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)). If the row can't be read within two seconds, the OS appearance applies until the renderer reports the setting.
- **Window background.** Windows are created with, and keep while `nativeTheme` changes, the background of the renderer's `--background` in the current theme (`WINDOW_BACKGROUND`, kept in step with `src/index.css`), so a new window or a reload paints no flash of the other theme.

## Browser panels

Browser panels host a `<webview>` per tab. `will-attach-webview` in `src/electron/main.ts` strips any preload and Node.js settings a webview asks for, then gives it Loxel's own sandboxed `src/electron/webview-preload.cjs`, which runs in every frame.

- **No reloads.** Re-attaching a `<webview>` to the DOM reloads its page, and a worktree switch (or going Home and back) rebuilds the center layout, so pages don't live in their dockview panels. [browser-pages.ts](../src/store/browser-pages.ts) keeps the window's pages by panel id, and the window-level [BrowserPagePool.tsx](../src/components/browser/BrowserPagePool.tsx) renders each `BrowserPanel`, toolbar included, in a fixed-position host outside the layouts. The dockview panel (`BrowserPageSlot`) only renders a slot and attaches it to its page; the pool lays the host over the slot, at the slot's stacking level, and hides it (`visibility`, keeping its size) while the slot is not shown: a background tab, or a layout that isn't mounted. Chromium hides a `<webview>` whose element is hidden that way as it does a background tab: the page reports `document.visibilityState` `"hidden"` with `visibilitychange`, gets no `requestAnimationFrame` callbacks, and has its timers throttled as in a Chrome background tab. It keeps running and can still notify. When shown again it is visible within a frame, with no reload or resize. Hiding the host with opacity instead would leave the page running as if it were in front of the user.
  - **Placement.** Hosts are re-placed whenever anything may have moved a slot: a `ResizeObserver` on each slot, a window resize, or a `style`, `class` or `hidden` attribute change anywhere in the body (dockview positions, splits and hides content that way). Placement runs in the observer callbacks, before the next paint, so a page moves in the same frame as its slot. The observers run only while a page is shown, and placement writes only changed values, so it settles after one pass. A page hidden while it has keyboard focus is blurred.
  - **Panel API.** `BrowserPanel` takes the dockview panel API only while its slot is attached (`panelApi`, null in the background). Its title and params go to the panel when shown again, and a page in the background opens no new tabs. Focus in a host activates its panel's group, as focus in dockview's own content does, and the host is part of the `center` focus area. While a drag started in the window is in progress, hosts let pointer events through to the slots, where dockview's drop targets see them.
  - **Lifetime.** A page loads the first time its panel is shown in the window, on the panel's `url` param, and stays loaded when its layout is swapped out. It is closed with its panel (`CenterLayout`'s `onDidRemovePanel`) or its worktree (`releaseWorktree`). Pages in the background are kept within a budget (below); an unloaded panel loads its page again when shown, on the last URL the page was on. Browser panels are still created with dockview's `renderer: "always"`, so a background tab's slot, and its page, keep the group's size.
  - **Budget.** Background pages are those of layouts not shown (the layout being switched to doesn't count: during a switch the old layout unmounts before the new one mounts). Every 30 seconds the pool measures them through main ([browser-page-lifecycle.ts](../src/electron/browser-page-lifecycle.ts): each webview's process memory from `app.getAppMetrics()`, and its CPU use since the previous measurement from the process's cumulative CPU time, split between webviews sharing a process) and applies the plan of [browser-page-budget.ts](../src/store/browser-page-budget.ts) for `browser.backgroundTabs`. While the pages together use more than the mode's share of the machine's memory, it unloads the one with the most points, its memory times how long it has been hidden, with pages that can notify (a notification in the center, or a site allowed to), play sound or have DevTools open last. It freezes a page that still uses CPU after the mode's delay, unless it can notify, is on a loopback host (a dev server's live-reload connection would drop), plays sound or has DevTools open: main attaches the DevTools protocol to the guest and sets `Page.setWebLifecycleState` to `frozen`, and resumes and detaches it when the page is shown again, running one page's freezes and resumes in the order asked and answering whether the page froze. Chromium hides a page it freezes and leaves it hidden on resume, so `BrowserPanel` hides its webview for a frame after each resume to show it again; a page shown while it was being frozen is resumed at once. More than 100 background pages are unloaded as a backstop, in case measuring fails: those that can't notify first, then those hidden longest.
- **New tabs.** Webviews carry `allowpopups`, so the page's new-tab and new-window requests (⌘-click, middle-click, `target="_blank"`, `window.open`) reach the main process: `src/electron/webview-new-tabs.ts` drops non-`http(s)` URLs and acts as a popup blocker, letting each click or key press in the page (within 5 seconds) open one tab or popup. A popup (`window.open` with window features, reported as `new-window`; a ⇧-clicked link is also `new-window` but has no features) is allowed as a real child window of Loxel's window, since sign-in flows such as Google's return their result through `window.opener`, which a tab cannot keep. The module builds that window itself in the handler's `createWindow`, keeping only the session, security preferences (not the webview preload), size and position Electron worked out, because Electron otherwise turns any window option in the page's features (frameless, always on top, not closable) into a real one. It pins the title to the page's origin since a popup has no address bar, closes it on ⌘W, which no Loxel renderer handles there, and refocuses the opener when it closes. It then applies the same rules to the popup's own requests, replacing the handler `main.ts` gives other windows, so its links open as tabs next to the webview and its popups as child windows of it. It sends the rest to the host renderer with the webview's webContents id and whether the disposition was a background tab. The `BrowserPanel` that owns that webview opens the tab with `openBrowserTab` (`src/lib/panel-creators.ts`), the same placement the context menu's Open in New Tab uses. The renderer sets `allowpopups` only in Electron.
- **Context menu.** The renderer draws the page's right-click menu with the app's own `ContextMenu` from the webview's `context-menu` event (`src/components/browser/BrowserContextMenu.tsx`). The event's `x`/`y` are window coordinates in device-independent pixels, not relative to the webview, so the menu is placed at them divided by the app zoom factor; `copyImageAt` and `inspectElement` take them unchanged. `<webview>` has no `copyImageAt`, so Copy Image asks the main process to call it on the webview's webContents (`src/electron/webview-copy-image.ts`), which only accepts webviews the sending window hosts.
- **Favicons.** `page-favicon-updated` lists the page's favicons, Chromium's preferred first, and fires again whenever the page changes them. The panel puts the preferred one in its `faviconUrl` param at once, then tries the list in order (`pickFavicon` in [favicon-loads.ts](../src/components/browser/favicon-loads.ts), at most four) and moves to the first that loads if that one doesn't. The tab reads it from the params dockview keeps merged, since a parameter change event carries only the keys that changed. A cross-document navigation clears it, except within the same origin, where the previous favicon stays until the new document reports its own. Loxel's window can't load every favicon itself: it has none of the site's cookies, a site may refuse cross-site loads (`Cross-Origin-Resource-Policy`), and a `blob:` URL only resolves in the page that made it. So in Electron `Favicon` ([Favicon.tsx](../src/components/browser/Favicon.tsx)), shared by tabs, bookmarks and notifications, has main load web favicons (`BROWSER_FAVICON_LOAD`, [browser-favicons.ts](../src/electron/browser-favicons.ts)) through the browser session, as `data:` URLs that must be images within `MAX_FAVICON_BYTES`. A page picks its favicon's URL, so the session's cookies go only with a favicon of the page's own origin (each `Favicon` names the page it belongs to) and never along a redirect, which loads again without them; any other favicon loads without cookies, so a page can't make Loxel send another site a request that carries that site's cookies. The renderer's [favicon-loads.ts](../src/components/browser/favicon-loads.ts) runs a few loads at a time, drops queued ones no `Favicon` shows any more, and keeps recent results per window, so a tab rebuilt by a worktree switch shows its favicon at once. A `blob:` favicon is read in an isolated world of the page that made it, only for a webview of the asking window, and the panel keeps the resulting `data:` URL instead if a bookmark could keep it (`isStorableFavicon`). Only Loxel's own windows are answered.
- **Loading.** A tab shows a spinner in place of its favicon from the start of a navigation of the page to a new document (`did-start-navigation` of the main frame, not in-place) until `did-stop-loading`, as browsers do, so frames and in-page navigations don't make it flicker. The flag is transient per-panel state in [browser-pages.ts](../src/store/browser-pages.ts) (`setBrowserPageLoading`), not a param saved with the layout, and it follows a page loading in the background; an unloaded page is not loading.
- **Shortcuts** keep working while a page has focus through keystroke forwarding from the main process; see [KEYBINDINGS.md](KEYBINDINGS.md#shortcuts-inside-browser-panels).
- **Page dialogs** (`alert()`, `confirm()`, `prompt()`) are shown by the hosting panel, not by Electron. Electron throws on `prompt()` and shows the other two as native sheets over the whole window. The webview preload replaces the page's dialog functions with a synchronous IPC call (`JAVASCRIPT_DIALOG_RUN`), so the page blocks as with a real dialog. `src/electron/javascript-dialogs.ts` forwards the call to the host renderer and sets the IPC's return value when the panel answers. Only that page's renderer process waits, while the window stays responsive. The message shapes live in `src/electron/javascript-dialog-protocol.ts`, and the renderer side is `src/components/browser/useJavaScriptDialogs.ts`.
  - **Readiness.** Main forwards dialogs only to window renderers that subscribed (`JAVASCRIPT_DIALOG_LISTEN`, sent by the window preload's `onJavaScriptDialog`). A subscription lasts until the window's document is replaced: a committed navigation, not one the window starts and cancels, such as an external link opened in the system browser. Pages of windows without one get the dismissed result instead of blocking on a dialog nobody shows.
  - **Policy.** Main owns the browser-like policy. From a page's second dialog on, the user can block further dialogs until the page navigates, and blocking also dismisses the page's queued dialogs. Once the main frame starts a cross-document navigation, the page's pending dialogs are withdrawn and the outgoing document gets no new ones. Dialogs from frames that are gone when the new document commits are dismissed too.
  - **Toolbar navigation.** A browser-initiated navigation waits for the blocked page (its `beforeunload` round trip), so the panel dismisses its queued dialogs before navigating from the toolbar.
  - **Preload rules.** The preload ignores dialogs during `beforeunload` and `pagehide`. `disableDialogs` is set as a backstop, so frames the preload can't reach (`about:blank` iframes) get no dialog rather than a window-wide sheet.
- **Notifications** from pages go to Loxel's notification center, never to the OS. The webview preload replaces the page's `Notification` with one whose permission, `requestPermission()`, construction and `close()` are IPC calls to `src/electron/browser-notifications.ts`, and reports that permission from `navigator.permissions.query()` too. Notifications shown through a service worker registration, from the page or the worker, have their own path (Service workers below). Chromium's own notification permission stays denied (`src/electron/browser-permissions.ts`), so this is the only path. Message shapes are in `src/electron/browser-notification-protocol.ts`, and the renderer side is `src/components/browser/useBrowserNotifications.ts`.
  - **Decisions.** Main decides by the page's origin as it sees it (`senderFrame`), never as the page claims, and settles it before any wait: only secure top-level pages (`https`, or `http` on a loopback host, as browsers require) and their same-origin frames get notifications. Per-site Allow / Block lives in settings (`browser.notificationSites`), which window renderers push to main after hydration and on every change (`setNotificationSites`, accepted only from Loxel's windows), because `Notification.permission` is synchronous. Until the first push, pages read `default` and `requestPermission()` waits. Sites muted or snoozed from a notification's context menu in the notification center (`browser.notificationMutes`, origin → optional `until`; `NotificationSiteMenu.tsx`) keep their decision, so pages still read `granted`, but main drops their notifications, from pages and service workers alike (`isSiteMuted`), before anything is sent or counted toward the rate limit. Renderers push mutes the same way (`setNotificationMutes`), before the decisions, and main checks a snooze's end against the clock on each notification, so no timer is needed.
  - **Asking.** A site without a decision gets a request in the window hosting the page (`BROWSER_NOTIFICATION_PERMISSION_REQUEST`), which the panel shows as a bar under its toolbar (`NotificationPermissionBar.tsx`). Allow or Block is saved for the site and settles every page of it that is waiting; repeated calls while the bar is up share one answer. Closing the bar decides nothing, and the page cannot show it again until it navigates. Requests are withdrawn when their page starts a main-frame navigation or goes away, and when the site gets a decision some other way.
  - **Showing.** Main forwards a granted page's notification (text capped, at most 10 per page per 10 seconds, reloads included) with a ref of its own to the host renderer, whose panel sends it to the server as a `browser` notification source with the panel's id, the worktree whose layout the panel is in (null for Home), whether that layout is shown or not, and the favicon its tab shows if the panel still shows the notifying site. The bell loads that favicon the way tabs and bookmarks load theirs (Favicons above), and ignores the notification's `icon`, which would be a second page-chosen URL for Loxel to load; the server keeps the favicon only if a bookmark could (`isStorableFavicon`). On the server, a tag replaces the site's earlier notification with that tag in the same worktree, and browser notifications evict only each other past their share of the list (`addBrowser`), so a busy site never pushes out terminals' notifications. The page's `close()` leaves the notification in the center, since pages close theirs on a timer or when their tab is shown; it only stops clicks. Clicking it in the notification center switches to the panel's worktree or Home if needed and, once that layout is mounted (`whenBrowserPageAttached`, or after 5 seconds), activates the panel and fires the page's `click` event through main (`clickBrowserNotification`), only from the window the notification went to and only while the page that made it is still loaded.
  - **Readiness.** Main forwards notifications and requests only to window renderers that subscribed (`onBrowserNotifications`), with the same per-document rule as dialogs (`src/electron/listening-renderers.ts`); pages of other windows are denied.
  - **Service workers.** `src/electron/service-worker-notifications.ts` registers `src/electron/service-worker-preload.cjs` on the browser session as a service-worker preload, which replaces the worker's `registration.showNotification()`, `getNotifications()`, `Notification.permission` and `navigator.permissions.query()` answer with IPC to main. A worker's IPC reaches only its own `ServiceWorkerMain.ipc`, so main attaches its listeners when the worker's running status turns `starting`, before the preload's first call. The webview preload routes a page's `registration.showNotification()` and `getNotifications()` to the same module (`REGISTRATION_NOTIFICATION_*`). Main decides by the registration's scope: a worker's as `ServiceWorkerMain` reports it, a page's only when it has the page's own origin. A worker counts only when it is its scope's first-party registration (`startWorkerForScope` finds the same version), so one a site registered while embedded in another site, which Chromium partitions, neither sees nor shows the site's notifications. The same site decisions and rate limit apply. A worker's notification goes to the most recently focused loaded panel of its origin (`trackWebviewFocus`), and nowhere when none is loaded; a page's goes to its own panel. Main keeps the live notifications (texts and `data`, capped, at most 100 per origin) by registration scope, since the browser stops idle workers: `getNotifications()` lists them, a tag replaces the earlier one, `close()` removes one from the list but not from the center, and those of a closed window are dropped. A click from the notification's window (the same `clickBrowserNotification`, also sent after switching worktrees, whose pages stay loaded unless they were unloaded) starts the worker with `startWorkerForScope`, keeps it alive with `startTask()` until the handler's `waitUntil()` promises settle (at most a minute), and has the preload dispatch a script-made `notificationclick`. Chromium gives such an event no working `waitUntil()` and refuses its `clients.openWindow()` and `focus()`, so the preload supplies them: `focus()` resolves, since the click already showed the panel, and `openWindow()` asks main, which opens one `http(s)` tab within `USER_ACTIVATION_MS` of the click, next to the notification's panel or, when that page is gone, the site's most recently focused loaded one. Push (`pushManager`) isn't covered: it needs a push service.
- **Passkeys** use the macOS Touch ID platform authenticator (`src/electron/webauthn.ts`). This needs a restricted entitlement that only provisioned Developer ID builds carry, so dev runs and unprovisioned local builds have no passkeys; see [RELEASE_SIGNING.md](RELEASE_SIGNING.md).
- **Passkeys from a phone** (FIDO hybrid transport, "use a phone or tablet") come from the `webauthn-hybrid-request` session events, which leave drawing the QR code to the app. `installHybridQrCode` (`src/electron/webauthn.ts`) routes each request to the browser panel whose webview made it, and `PasskeyQrOverlay` draws the code over that panel only, so a background panel cannot put a code in front of the user. The `FIDO:/` string is a per-request secret: it goes to the hosting window's renderer and nowhere else, and is never logged. The events come from the patched Electron releases ship with ([PATCHED_ELECTRON.md](PATCHED_ELECTRON.md)); on stock Electron, as in dev runs and tests, the listeners never fire.
- **Permissions.** With no handlers, Electron grants every permission to every page, so [browser-permissions.ts](../src/electron/browser-permissions.ts) installs both of `BROWSER_PARTITION`'s permission handlers. They answer from one decision, `browserPermissionGranted`, so what a page reads matches what requesting gets it. Permissions browsers grant without asking are on an allowlist, and everything else is refused, since Loxel has no permission prompt; the module comments why each is there and which quiet grants are refused anyway. Two are decided apart from the allowlist: `notifications` is refused, because pages get Loxel's own notifications instead (see Notifications above), and `openExternal` (links to other apps, which browsers ask about) is granted to a page's main frame but not to frames embedded in it. `fileSystem` is granted because it has to be: once a check handler exists, Electron decides every file handle's access from it alone, so refusing it would break the File System Access API, and granting it gives read and write access to whatever the user picked or dropped.
- **Installed fonts.** The font pickers in Settings list installed fonts with the Local Font Access API (`window.queryLocalFonts`, `src/lib/local-fonts.ts`). Electron decides `local-fonts` from the session's permission check handler alone, since its permission status is never "ask", so `src/electron/local-fonts-permission.ts` installs one on the default session that allows only the app origin (and no frame embedded by another origin). Browser panels never get it, as it isn't on their allowlist. Blink resolves a refused query with an empty list rather than an error.

## macOS integration

- **Open from Finder.** `electron-builder.yml` declares Loxel an _Alternate_ handler for text and source files, `.excalidraw` and folders. The main process receives these as `open-file` events and posts each to `POST /api/open`, the same request the `loxel <path>` CLI sends (`src/open-request.ts`).
- **Default browser.** `electron-builder.yml` also declares the `http` and `https` URL schemes (`CFBundleURLTypes`), which lists Loxel among the browsers macOS can make the default without changing the default itself (macOS keeps the user's browser until they pick another). Declaring them is one of the criteria for Apple's web browser public-key credential entitlement, which lets browser panels use the passkeys of iCloud Keychain and password managers. [default-browser.ts](../src/electron/default-browser.ts) answers Settings' `DEFAULT_BROWSER_GET` / `DEFAULT_BROWSER_SET` with `app.isDefaultProtocolClient` / `app.setAsDefaultProtocolClient` for both schemes; macOS confirms the change in its own prompt, so Settings reads the status again when its window regains focus. Only a packaged macOS app can be set (`canSet`): a dev run would register Electron. Links then arrive as `open-url` events, which main posts as `{ url }` with no `wtPath`, so the window in use opens the page itself, unchanged, in a browser panel of its active worktree or of Home. Other schemes are ignored.
- **Launch opens.** Files and links that launch the app arrive before it is ready; main keeps them (`launchOpens`) until the startup window exists, then sends them one at a time in the order macOS sent them, each retried by `requestOpen` until the window connects. In the renderer, a page for Home waits in Home's pending opens until its layout mounts.
- **Reveal in Finder / Open In.** App lists and icons come from LaunchServices through `bun:ffi`, which runs in a helper process (the server executable started with a helper flag, see `src/server/launch-services-client.ts`) so a native crash only kills the helper.

## Demo mode

`LOXEL_DEMO=1` (`IS_DEMO` in `src/electron/env.ts`) starts a Loxel that can run beside the installed app, for staging screenshots: port 7435 and the `loxel-demo` state directory (`src/server/config.ts`), a separate Electron data directory and so a separate single-instance lock and browser session, the fixed dev encryption key instead of the keychain (`src/server/dek-source.ts`), no update checks, and windows that open at the size of the site's screenshots (1920×1200, `DEMO_WINDOW_SIZE`, allowed to be larger than the screen). Unlike dev mode it loads the built renderer, so it shows no DEV badge, and it takes precedence over dev mode: main reads the renderer's dev URL only through `DEV_RENDERER_URL`, which is unset in a demo, so one started from a dev Loxel's terminal ignores the inherited `VITE_DEV_SERVER_URL` and `IS_DEV` stays false. From the source tree it runs the server's source and serves `dist-electron/renderer`; a packaged app uses its bundled server and renderer. `LOXEL_DEMO_INSTANCE=<n>` (`DEMO_INSTANCE`) runs several at once, each on port 7435 + n with its own state (`loxel-demo-<n>`) and data directory; main, the server and the demo scripts share its parser, port and state-directory naming from [demo-instance.ts](../src/demo-instance.ts), which refuses anything but a non-negative integer. `LOXEL_DEMO_HIDDEN=1` (`IS_DEMO_HIDDEN`) gives a window that never shows itself: fully transparent, ignoring the mouse, shown without activating, and no Dock icon, while its page still renders and can be captured. With no one to read a dialog, a hidden demo logs a startup error and exits with status 1 instead of showing an error box.

Page visibility can't be measured the way the screenshot scripts drive a demo. macOS reports a hidden demo's transparent window as occluded, so Chromium hides the whole window and every page in it, unless the app is started with `--disable-backgrounding-occluded-windows`. And under Playwright's Electron driver, browser panel pages stay `"visible"` whatever their element does. To check a browser page's `document.visibilityState` or throttling, start Electron on `dist-electron/main/main.js` with `--disable-backgrounding-occluded-windows` and the hidden demo's environment (`demoEnv(<n>, true)`), not through `demo-session.ts`. Have the test page report to a local server, and drive the window only through the CLI or a raw CDP session on the window's own page. Freezing a background page doesn't take under Playwright either, so check it the same way.

`scripts/demo/launch.ts` builds and starts a visible demo (instance 0) with fresh state and the demo projects (clones of Loxel and Excalidraw with real PR branches as tasks, from `demo-projects.ts`). `scripts/demo/capture-shots.ts` stages the site's screenshots ([shots.md](../scripts/demo/shots.md)) in hidden demos (instance 1 unless told otherwise) driven by Playwright's Electron driver: each shot is a script in `scripts/demo/shots/` built on `shot-kit.ts`, its content is captured with `webContents.capturePage()`, and `composite.swift` puts it into `window-frame.png`, one real `screencapture` of a demo window (`capture-frame.ts`), so every screenshot keeps macOS's frame without a window ever coming to the front. Both start the app through `demo-app.ts`, which owns the build, registering and trusting the demo projects, and the demo's environment (`demoEnv`): the scripts' own, minus agent and Loxel terminal session markers (`withoutAgentEnv` in `src/coding-agent-env.ts`) and the variables that would point it at another Loxel (`VITE_DEV_SERVER_URL`, `LOXEL_DEV`, `LOXEL_STATE_DIR`, `LOXEL_SERVE_PORT`, `LOXEL_STATIC_DIR`).

## Build and release

`pnpm run build:app` compiles the standalone server and terminal host ([build-server.ts](../scripts/build-server.ts), which embeds the host build ID in both), builds the renderer and packages the app with electron-builder into `release/`, on macOS for this machine's architecture (`build:app:local` builds an unpacked arm64 app only). `release-loxel.yml` releases on every merge to main that touches `packages/loxel/**`; see the [README](../README.md#releases). Releases package a patched Electron rather than the npm package's binary; see [PATCHED_ELECTRON.md](PATCHED_ELECTRON.md).

The server, the terminal host, language server scripts and Go builds all produce binaries for the machine they run on, so each macOS architecture builds on a runner of that architecture. [check-binary-arch.ts](../scripts/check-binary-arch.ts) reads the header of every file in the app and fails the release if a binary doesn't match.

Each release publishes a CycloneDX SBOM of what each architecture's app ships, `Loxel-<version>-mac-<arch>.cdx.json`, written by [sbom.ts](../scripts/sbom.ts) on that architecture's build, since pnpm installs and lists only the machine's own platform packages (TypeScript's compiler is one). It is uploaded to R2 next to that architecture's installer and attached to the GitHub release; the manifest's `sbom` holds the URL per `<platform>-<arch>`, which the site's download page links to. Its base is pnpm's SBOM of this package's `dependencies`, which here are what ships (Vite bundles them, or a language server is built from them), so a shipped npm package goes in `dependencies` and a build-only tool in `devDependencies`. pnpm reads licenses from the installed packages, so it runs after `pnpm install`. `sbom.ts` adds what the lockfile does not hold: the patched Electron (a devDependency, as electron-builder requires), with its patches as pedigree; the Bun runtime from the root `.bun-version`, which `bun build --compile` puts in the server and the Bun-built language servers; and the component each [language server manifest](LANGUAGE_SERVERS.md#binary-resolution-and-packaging) names. It then reads the build info the Go linker embeds in every Go binary among the staged language servers ([go-build-info.ts](../scripts/go-build-info.ts), the data `go version -m` prints, read from the file so no Go toolchain is needed), and adds the Go standard library and each module compiled in as dependencies of that server's component, or of the root for one built from npm packages (TypeScript's `tsc`). It finds the binaries itself, so a new Go language server needs no change here, and it refuses to run before the language servers are built. pnpm's root names Loxel as an npm package, so its purl is replaced with the GitHub one. It fails when a manifest's npm package is not in `dependencies` or a component is listed twice, and [sbom.test.ts](../scripts/sbom.test.ts) checks every manifest's component is in it.

Each architecture's build scans its SBOM with Trivy before any of the app is uploaded, and fails the app's release when a vulnerability fails the gate in [sbom-vuln-gate.ts](../scripts/sbom-vuln-gate.ts). The gate covers the app only: the standalone server bundle below has no SBOM and ships on its own. A finding fails when its CVSS score is above 4.0. The score is the v4, else v3, score from the source Trivy took the finding's severity from (usually the vendor's), else from GHSA, else NVD, else any other source. A finding with no score fails when its severity is MEDIUM or above, since MEDIUM starts at 4.0, and passes when LOW. A finding with neither a score nor a severity (an unrated Go advisory, say) only adds to a warning's count. The threshold and both no-score rules are constants at the top of the script. A daily `loxel-sbom` job in [vuln-check.yml](../../../.github/workflows/vuln-check.yml) runs the same scan on the latest release's SBOMs, read from the manifest's `sbom`, since advisories appear without code changes. Each vulnerability ID counts once, and fails when it fails for any package it is reported for. A scan that read no components fails too. Workflow logs are public, so the gate prints only counts per severity and the IDs that fail. To see every finding, scan an SBOM locally: `trivy sbom --scanners vuln <sbom.cdx.json>`. An exception for a finding Loxel is not affected by goes in the root `.trivyignore`: the ID, with a comment giving the justification and an `exp:` date after which it fails again. The release gate reads `.trivyignore` from the release's tag, so after a failed release add the exception or the fix on main and release again (`workflow_dispatch`), which takes the next version. The scheduled scan reads main's.

### Standalone server bundle

Each release also publishes the server without the app, for Linux: a bundle to run the server from on a Linux machine. Installing it and running it as a service are outside its scope. [build-loxel-server.yml](../../../.github/workflows/build-loxel-server.yml), which `release-loxel.yml` calls beside the app's jobs, builds it for `linux-x64` and `linux-arm64`, each on a runner of that architecture: `build:server:standalone`, a browser build of the renderer (`vite build`), then [build-server-bundle.ts](../scripts/build-server-bundle.ts), which packages them as `release/server/loxel-server-<version>-<platform>.tar.gz`. The tarball holds one directory, laid out like the app's `Resources`:

| Path                           | What                                                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `loxel-server`                 | The compiled server                                                                                                                      |
| `loxel-terminal-host`          | The terminal host, which the server clones into its state directory before running it ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-process)) |
| `gopls`, `ruff`, `jdtls/`, ... | Every language server staged for the platform (`build/language-servers/`), found beside the server binary as in the app                  |
| `renderer/`                    | The renderer, which a compiled server serves from beside itself when `LOXEL_STATIC_DIR` is unset                                         |
| `LICENSE`, `licenses/`         | Loxel's license, and the license, source and license file each language server's manifest names                                          |

Every binary in it must match the platform ([check-binary-arch.ts](../scripts/check-binary-arch.ts)), and [smoke-test-server-bundle.ts](../scripts/smoke-test-server-bundle.ts) starts it with a throwaway `LOXEL_STATE_DIR`, reads the session token it writes, checks `/api/version`, an `/api` route with and without the token and the renderer, and runs a command in a terminal through the bundled host. Only then are the tarballs uploaded to `loxel/server/<platform>/` on R2, followed by their manifest, `https://loxel.bizimind.io/loxel/server/manifest.json`, apart from the app's:

```json
{
  "version": "0.1.379",
  "released_at": "2026-11-18T12:00:00Z",
  "server": {
    "linux-x64": {
      "url": "https://loxel.bizimind.io/loxel/server/linux-x64/loxel-server-0.1.379-linux-x64.tar.gz",
      "sha256": "…"
    },
    "linux-arm64": {
      "url": "https://loxel.bizimind.io/loxel/server/linux-arm64/loxel-server-0.1.379-linux-arm64.tar.gz",
      "sha256": "…"
    }
  }
}
```

A run of the workflow on its own (`gh workflow run build-loxel-server.yml --ref <branch>`, once it is on main), or a pull request that changes the workflow or a script that builds what the bundle packages, builds and smoke-tests both bundles without uploading anything. The two scripts also run on a Mac, building and testing a bundle for it, to try them locally.
