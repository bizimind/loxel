# Desktop app (Electron)

How the Electron shell fits around the Bun server and React renderer, how the app updates, and the macOS integrations main owns. Entry point: `src/electron/main.ts`.

## Process model

- **One app process, one server.** A packaged app takes Electron's single-instance lock, and the app spawns its server on launch: the compiled `loxel-server` binary in production, `bun run src/server/index.ts` with `LOXEL_DEV=1` in dev, on the mode's port (7433 prod, 7434 dev, 7435 + n for [demo](#demo-mode) instance n). The server lives as long as the app, and the terminals live in [terminal host](TERMINAL_HOST.md) processes the server starts detached, which outlive it. Every window connects to it, identifies itself with its window ID, and talks to it over REST and WebSocket. Startup, crash restarts, shutdown and state scopes are detailed in [SHARED_SERVER.md](SHARED_SERVER.md).
- **Windows load the server's URL** (`http://127.0.0.1:<port>`), or the Vite dev server's URL under `pnpm run dev:app` (Vite proxies `/api` and `/ws` to the dev server). Main adds the app's session secret to every request the windows send to that origin, and sends it on its own requests to the server ([ARCHITECTURE.md](ARCHITECTURE.md#request-admission)); browser panels' partition never gets it.
- **Windows show only the app.** Every window of the windows' session (Loxel's windows, and any other window in it; not DevTools) gets the rules of [app-navigation.ts](../src/electron/app-navigation.ts), applied in `web-contents-created`. Its main frame navigates only to the app's page (`APP_URL`, the URL windows load, any fragment aside); a web link it would navigate to opens in the system browser instead, or in a browser panel with Cmd held. A window it asks to open (`window.open`, a `target="_blank"` link) never opens as its child, so no page gets a `window.opener` into a Loxel window: the app's page becomes a new Loxel window, as New Window opens one, a web link opens outside the app as above, and any other URL, the server's `/api` routes included, opens nothing. A frame showing a document the server sent, such as the media viewer's frame, may navigate only within the app's origin (`will-frame-navigate`); other frames, such as an embedded page, are left alone. Browser panels and their popups have a session of their own and are not held to these rules ([Browser panels](#browser-panels)).
- **Electron IPC is only for native integrations** (dock badge, window focus and fullscreen state, opening links in a browser panel, the default browser, keystrokes inside webviews, copying images from webviews, loading their favicons, measuring and freezing background webviews, page dialogs and notifications in webviews and their service workers, the permission prompts of webviews' pages (camera and microphone, links to other apps, the local network), webviews going fullscreen or locking the pointer, app updates, quitting and restarting with the question before a quit and the setting it follows, the theme). Channel names live in `src/electron/ipc-channels.ts`, and the renderer-facing API (`window.electronAPI`) is typed in `src/electron-api.d.ts`. Everything else goes through the server.
- **IPC trusts only Loxel's windows.** As in Chrome, main treats any renderer as possibly compromised, and browser panels' pages and their popups have renderers of their own. A channel only Loxel's windows send is registered with `onAppWindowMessage` or `handleAppWindowInvoke` ([app-windows.ts](../src/electron/app-windows.ts)), never with `ipcMain` directly: they drop (or reject) every message `isAppWindowSender` refuses, which accepts only a registered Loxel window's own webContents (a page's popup is a window too), from its main frame, with the app's origin loaded. Channels pages use (the webview and service worker preloads') decide by the sending frame (`senderFrame`) or service worker, never by what the page claims, and a message naming a webview acts only on one the sending window hosts (`hostedWebview`).

## Updates

The app updates as a whole. Each release replaces the bundle, with its Electron runtime, main process, preloads, server, terminal host binary, language servers, renderer, `Info.plist` and entitlements. Nothing long-lived runs from the bundle once the app has quit: a terminal host, which keeps running with its shells, runs from a clone of the bundled binary in the state directory ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-process)), so Squirrel can replace the bundle under it. The one exception is the [`loxel` CLI](TERMINALS.md#the-loxel-cli), which Loxel terminals run from `Resources/bin` and which waits through an update for the next server: a run that spans the replacement keeps the old binary open, and the next run finds the new one at the same path. The renderer is served from the bundle (`LOXEL_STATIC_DIR`), so the renderer, the preloads and the main process always come from the same build. Every `window.electronAPI` member therefore exists whenever `window.electronAPI` does, and the renderer calls them without checking; `window.electronAPI` itself is undefined outside Electron.

- **Updater.** [app-updater.ts](../src/electron/app-updater.ts) drives electron-updater, which downloads the new app's zip and hands it to Squirrel.Mac. Squirrel checks that the new bundle is signed by the same Developer ID as the running one, replaces the bundle once the app has quit, and relaunches it. The new bundle never gets the quarantine flag a browser download carries, so macOS does not ask the user to confirm opening it.
- **Feed.** The release manifest (`manifest.json`, written by `release-loxel.yml`) is the only description of a release. `ManifestProvider` in [update-manifest.ts](../src/electron/update-manifest.ts) reads its `update` entries: one zip per architecture, with its base64 SHA-512 and size. electron-updater picks the zip for this Mac, verifies its SHA-512, and downloads only the changed blocks when the zip's block map and a cached zip of the installed version exist, one range per request because the origin rejects multi-range requests. Before a download, [update-edge-priming.ts](../src/electron/update-edge-priming.ts) asks each zip URL for one byte and drops the response once its headers arrive: Cloudflare answers the first range request its edge sees for a URL with the whole zip and a `200`, which electron-updater would count as progress and write into the new zip, failing its checksum and starting over with a full download. [app-update.yml](../assets/app-update.yml), packaged into the app's resources, names the cache folder; electron-updater reads it for every download. The provider drops the random per-installation `x-user-staging-id` header electron-updater adds to update checks, so a check carries no identifier. The manifest's optional `terminal_host_protocol` is the release's `TERMINAL_HOST_PROTOCOL`, which the release workflow reads with [terminal-host-protocol.ts](../scripts/terminal-host-protocol.ts) (failing the release if it cannot); the provider passes it on as `terminalHostProtocol` on the update info, which electron-updater hands to `update-available` as is. Manifests from before it leave it out. The site reads the manifest's `app` installers and `sbom` (see [Build and release](#build-and-release)).
- **Terminals.** An install keeps the terminals running unless the update's terminal hosts cannot take them over. [update-terminals.ts](../src/electron/update-terminals.ts) decides it from versions alone:
  - `updateRestartsTerminals` compares the update's `terminal_host_protocol` major with this build's `TERMINAL_HOST_PROTOCOL` ([terminal-host-protocol-version.ts](../src/api/terminal-host-protocol-version.ts)). Every running host speaks this build's major, since the server ends hosts of any other major at startup and starts hosts only of its own build ([TERMINAL_HOST.md](TERMINAL_HOST.md#versioning)). The answer is `restartsTerminals` on the `available`, `downloading` and `ready` states: `false` for the same major, `true` for another, `"unknown"` for a manifest without the field.
  - `terminalsForInstall` turns it into the install's mode, which Install & Restart records and `terminalsForUpdateInstall()` in [app-updater.ts](../src/electron/app-updater.ts) returns to `will-quit`. Whatever plan the quit had, it stops the server with that mode: `end` for `true`, rather than leave hosts the new server cannot talk to; `keep` otherwise, and the new version's server reattaches them (see [SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)). For `"unknown"` the new server keeps the hosts it can talk to and ends the rest with a notice, so nothing ends that did not have to, and nothing ends unseen.
  - **Before installing.** While `restartsTerminals` is not `false`, the top bar's Update button and Settings > General warn that the update restarts (or may restart) N terminals, counted from `GET /api/terminals` ([running-terminals-model.ts](../src/api/running-terminals-model.ts), kept current by the `terminals_changed` broadcast). Install & Restart then lists the terminals (the button shows a spinner meanwhile) and asks with `requestConfirmation`, in the app, listing the terminals whose terminal host reports a foreground program (capability `foregroundProcess`, read with `?programs`); a terminal whose host cannot tell is only counted. The texts come from [update-terminal-restart.ts](../src/lib/update-terminal-restart.ts).
- **State and UI.** Main keeps the `UpdateState` ([update-model.ts](../src/api/update-model.ts)) and sends every change to all windows over IPC (`UPDATE_*` in `ipc-channels.ts`). Settings > General and the top bar's Update button show it through `useUpdateStatus` ([use-update-status.ts](../src/queries/use-update-status.ts)). Downloading and installing happen only when the user asks. `autoInstallOnAppQuit` is off, so an ordinary quit never installs.
- **Automatic check.** Five seconds after launch, a packaged app reads the persisted settings row from its server and checks unless `autoCheckForUpdates` is off (`isAutoCheckEnabled` in [persisted-settings.ts](../src/server/persisted-settings.ts)). The manual check ignores the setting. Unpackaged builds never check.
- **Install location.** Squirrel can only replace a bundle it can write to. A packaged app outside an Applications folder that it cannot write to, such as one opened from the disk image or run from a read-only translocated copy, offers on launch to move itself to `/Applications`. When an install fails, Settings shows the error with a link to the download page.

## Theme

Electron's `nativeTheme.themeSource` follows the Theme setting, so native menus and dialogs, every page's `prefers-color-scheme` (browser panels' and the renderer's own) and window backgrounds match the app instead of the OS. [native-theme.ts](../src/electron/native-theme.ts) owns it:

- **Changes.** `useThemeSync` sends the setting (`dark`, `light` or `system`, the same values as `themeSource`) with `SET_THEME_SOURCE` once the settings load and on every change. With an explicit theme, the renderer's own `(prefers-color-scheme: dark)` query then matches the setting; only `system` reads it.
- **Launch.** Before the first window, main reads the persisted settings row from the server (`readLaunchSettings` in [settings-row.ts](../src/electron/settings-row.ts)) and applies its `theme` (`persistedTheme` in [persisted-settings.ts](../src/server/persisted-settings.ts)), so the window and its webviews start in it; the same read gives main the "When quitting Loxel" setting ([SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)). If the row can't be read within two seconds, the OS appearance applies until the renderer reports the setting.
- **Window background.** Windows are created with, and keep while `nativeTheme` changes, the background of the renderer's `--background` in the current theme (`WINDOW_BACKGROUND`, kept in step with `src/index.css`), so a new window or a reload paints no flash of the other theme.

## Browser panels

Browser panels host a `<webview>` per tab. `will-attach-webview` in `src/electron/main.ts` hands each webview's preferences to `secureWebviewAttach` ([webview-attach.ts](../src/electron/webview-attach.ts)), whatever the element asks for: it puts the webview in the browser partition, strips any preload, Node.js and Blink feature settings, forces Chromium's secure defaults (web security on, no insecure content on secure pages, no `<webview>` of its own, no experimental features, no plugins, no navigating to a dropped file), and gives it Loxel's own sandboxed `src/electron/webview-preload.cjs`, which runs in every frame. A webview that would start on anything but `about:blank` or a web page doesn't attach; `BrowserPanel` attaches its webviews blank and loads the page afterwards.

- **No reloads.** Re-attaching a `<webview>` to the DOM reloads its page, and a worktree switch (or going Home and back) rebuilds the center layout, so pages don't live in their dockview panels. [browser-pages.ts](../src/store/browser-pages.ts) keeps the window's pages by panel id, and the window-level [BrowserPagePool.tsx](../src/components/browser/BrowserPagePool.tsx) renders each `BrowserPanel`, toolbar included, in a fixed-position host outside the layouts. The dockview panel (`BrowserPageSlot`) only renders a slot and attaches it to its page; the pool lays the host over the slot, at the slot's stacking level, and hides it (`visibility`, keeping its size) while the slot is not shown: a background tab, or a layout that isn't mounted. Chromium hides a `<webview>` whose element is hidden that way as it does a background tab: the page reports `document.visibilityState` `"hidden"` with `visibilitychange`, gets no `requestAnimationFrame` callbacks, and has its timers throttled as in a Chrome background tab. It keeps running and can still notify. When shown again it is visible within a frame, with no reload or resize. Hiding the host with opacity instead would leave the page running as if it were in front of the user.
  - **Placement.** Hosts are re-placed whenever anything may have moved a slot: a `ResizeObserver` on each slot, a window resize, or a `style`, `class` or `hidden` attribute change anywhere in the body (dockview positions, splits and hides content that way). Placement runs in the observer callbacks, before the next paint, so a page moves in the same frame as its slot. The observers run only while a page is shown, and placement writes only changed values, so it settles after one pass. A page hidden while it has keyboard focus is blurred.
  - **Panel API.** `BrowserPanel` takes the dockview panel API only while its slot is attached (`panelApi`, null in the background). Its title and params go to the panel when shown again, and a page in the background opens no new tabs. Focus in a host activates its panel, its group and the editor area in the outer layout (`activateEditorArea`), as a click in dockview's own content does, since dockview never sees clicks on the host. Focus in its toolbar arrives as a focus event, but focus moving into the `<webview>` fires none in the window, so the host learns of it from `onWebviewFocus` ([webview-focus.ts](../src/lib/webview-focus.ts)): main reports the guest's webContents `focus` (`WEBVIEW_FOCUSED`, which also covers a click from another page or another app, when the window has no focus left to lose), and as a fallback the window blurs with the webview left as the active element. The context menu and the keybindings' webview interception follow focus into pages the same way. The host is part of the `center` focus area. While a drag started in the window is in progress, hosts let pointer events through to the slots, where dockview's drop targets see them.
  - **Lifetime.** A page loads the first time its panel is shown in the window, on the panel's `url` param, and stays loaded when its layout is swapped out. It is closed with its panel (`CenterLayout`'s `onDidRemovePanel`) or its worktree (`releaseWorktree`). Pages in the background are kept within a budget (below); an unloaded panel loads its page again when shown, on the last URL the page was on. Browser panels are still created with dockview's `renderer: "always"`, so a background tab's slot, and its page, keep the group's size.
  - **Budget.** Background pages are those of layouts not shown (the layout being switched to doesn't count: during a switch the old layout unmounts before the new one mounts). Every 30 seconds the pool measures them through main ([browser-page-lifecycle.ts](../src/electron/browser-page-lifecycle.ts): each webview's process memory from `app.getAppMetrics()`, and its CPU use since the previous measurement from the process's cumulative CPU time, split between webviews sharing a process) and applies the plan of [browser-page-budget.ts](../src/store/browser-page-budget.ts) for `browser.backgroundTabs`. While the pages together use more than the mode's share of the machine's memory, it unloads the one with the most points, its memory times how long it has been hidden, with pages that can notify (a notification in the center, or a site allowed to), play sound or have DevTools open last. It freezes a page that still uses CPU after the mode's delay, unless it can notify, is on a loopback host (a dev server's live-reload connection would drop), plays sound or has DevTools open: main attaches the DevTools protocol to the guest and sets `Page.setWebLifecycleState` to `frozen`, and resumes and detaches it when the page is shown again, running one page's freezes and resumes in the order asked and answering whether the page froze. Chromium hides a page it freezes and leaves it hidden on resume, so `BrowserPanel` hides its webview for a frame after each resume to show it again; a page shown while it was being frozen is resumed at once. More than 100 background pages are unloaded as a backstop, in case measuring fails: those that can't notify first, then those hidden longest.
- **New tabs.** Webviews carry `allowpopups`, so the page's new-tab and new-window requests (⌘-click, middle-click, `target="_blank"`, `window.open`) reach the main process: `src/electron/webview-new-tabs.ts` drops non-`http(s)` URLs and acts as a popup blocker, letting each click or key press in the page (within 5 seconds) open one tab or popup. The clicks and key presses are tracked once per webContents ([user-activation.ts](../src/electron/user-activation.ts)), and opening a tab uses one up, as a link to another app does (Links to other apps below). A popup (`window.open` with window features, reported as `new-window`; a ⇧-clicked link is also `new-window` but has no features) is allowed as a real child window of Loxel's window, since sign-in flows such as Google's return their result through `window.opener`, which a tab cannot keep. The module builds that window itself in the handler's `createWindow`, keeping only the session, security preferences (not the webview preload), size and position Electron worked out, because Electron otherwise turns any window option in the page's features (frameless, always on top, not closable) into a real one. It pins the title to the page's origin since a popup has no address bar, closes it on ⌘W, which no Loxel renderer handles there, and refocuses the opener when it closes. It then applies the same rules to the popup's own requests, replacing the handler `main.ts` gives other windows, so its links open as tabs next to the webview and its popups as child windows of it. It sends the rest to the host renderer with the webview's webContents id and whether the disposition was a background tab. The `BrowserPanel` that owns that webview opens the tab with `openBrowserTab` (`src/lib/panel-creators.ts`), the same placement the context menu's Open in New Tab uses. The renderer sets `allowpopups` only in Electron.
- **Context menu.** The renderer draws the page's right-click menu with the app's own `ContextMenu` from the webview's `context-menu` event (`src/components/browser/BrowserContextMenu.tsx`). The event's `x`/`y` are window coordinates in device-independent pixels, not relative to the webview, so the menu is placed at them divided by the app zoom factor; `copyImageAt` and `inspectElement` take them unchanged. `<webview>` has no `copyImageAt`, so Copy Image asks the main process to call it on the webview's webContents (`src/electron/webview-copy-image.ts`), which only accepts webviews the sending window hosts.
- **Favicons.** `page-favicon-updated` lists the page's favicons, Chromium's preferred first, and fires again whenever the page changes them. The panel puts the preferred one in its `faviconUrl` param at once, then tries the list in order (`pickFavicon` in [favicon-loads.ts](../src/components/browser/favicon-loads.ts), at most four) and moves to the first that loads if that one doesn't. The tab reads it from the params dockview keeps merged, since a parameter change event carries only the keys that changed. A cross-document navigation clears it, except within the same origin, where the previous favicon stays until the new document reports its own. Loxel's window can't load every favicon itself: it has none of the site's cookies, a site may refuse cross-site loads (`Cross-Origin-Resource-Policy`), and a `blob:` URL only resolves in the page that made it. So in Electron `Favicon` ([Favicon.tsx](../src/components/browser/Favicon.tsx)), shared by tabs, bookmarks and notifications, has main load web favicons (`BROWSER_FAVICON_LOAD`, [browser-favicons.ts](../src/electron/browser-favicons.ts)) through the browser session, as `data:` URLs that must be images within `MAX_FAVICON_BYTES`. A page picks its favicon's URL, so the session's cookies go only with a favicon of the page's own origin (each `Favicon` names the page it belongs to) and never along a redirect, which loads again without them; any other favicon loads without cookies, so a page can't make Loxel send another site a request that carries that site's cookies. The renderer's [favicon-loads.ts](../src/components/browser/favicon-loads.ts) runs a few loads at a time, drops queued ones no `Favicon` shows any more, and keeps recent results per window, so a tab rebuilt by a worktree switch shows its favicon at once. A `blob:` favicon is read in an isolated world of the page that made it, only for a webview of the asking window, and the panel keeps the resulting `data:` URL instead if a bookmark could keep it (`isStorableFavicon`). A favicon on this machine or the local network loads only as far as the page itself may reach it, redirects included (Local network below). Only Loxel's own windows are answered.
- **Loading.** A tab shows a spinner in place of its favicon from the start of a navigation of the page to a new document (`did-start-navigation` of the main frame, not in-place) until `did-stop-loading`, as browsers do, so frames and in-page navigations don't make it flicker. The flag is transient per-panel state in [browser-pages.ts](../src/store/browser-pages.ts) (`setBrowserPageLoading`), not a param saved with the layout, and it follows a page loading in the background; an unloaded page is not loading.
- **Shortcuts** keep working while a page has focus through keystroke forwarding from the main process; see [KEYBINDINGS.md](KEYBINDINGS.md#shortcuts-inside-browser-panels).
- **Page dialogs** (`alert()`, `confirm()`, `prompt()`) are shown by the hosting panel, not by Electron. Electron throws on `prompt()` and shows the other two as native sheets over the whole window. The webview preload replaces the page's dialog functions with a synchronous IPC call (`JAVASCRIPT_DIALOG_RUN`), so the page blocks as with a real dialog. `src/electron/javascript-dialogs.ts` forwards the call to the host renderer and sets the IPC's return value when the panel answers. Only that page's renderer process waits, while the window stays responsive. The message shapes live in `src/electron/javascript-dialog-protocol.ts`, and the renderer side is `src/components/browser/useJavaScriptDialogs.ts`.
  - **Readiness.** Main forwards dialogs only to window renderers that subscribed (`JAVASCRIPT_DIALOG_LISTEN`, sent by the window preload's `onJavaScriptDialog`). A subscription lasts until the window's document is replaced: a committed navigation, not one the window starts and cancels, such as an external link opened in the system browser. Pages of windows without one get the dismissed result instead of blocking on a dialog nobody shows.
  - **Policy.** Main owns the browser-like policy. From a page's second dialog on, the user can block further dialogs until the page navigates, and blocking also dismisses the page's queued dialogs. Once the main frame starts a cross-document navigation, the page's pending dialogs are withdrawn and the outgoing document gets no new ones. Dialogs from frames that are gone when the new document commits are dismissed too.
  - **Toolbar navigation.** A browser-initiated navigation waits for the blocked page (its `beforeunload` round trip), so the panel dismisses its queued dialogs before navigating from the toolbar.
  - **Preload rules.** The preload ignores dialogs during `beforeunload` and `pagehide`. `disableDialogs` is set as a backstop, so frames the preload can't reach (`about:blank` iframes) get no dialog rather than a window-wide sheet.
- **Downloads.** [browser-downloads.ts](../src/electron/browser-downloads.ts) handles `BROWSER_PARTITION`'s `will-download`, which covers webviews and their popups (Loxel's windows are in the default session). Electron has Chromium write a download straight to its save path, with no `.crdownload`, and when a file is already at the path Chromium writes beside it (`name (1).ext`) instead, a path the `DownloadItem` never reports. So Loxel sets the save path itself during the event, where Electron takes it as the download's target: the first `name.ext`, `name (1).ext`, ... in the Downloads folder (`app.getPath("downloads")`, numbered before the extension, with Chrome's double extensions such as `.tar.gz` and `.user.js` kept whole, and cut before the extension to the 255 UTF-8 bytes a file name may take, as Chrome cuts one, since Electron's delegate skips Chromium's own truncation) that nothing is at (`lstat`, so not even a dangling link) and that isn't held by another download. Loxel keeps each download's save path in memory until the download is moved, deleted or ends unfinished (releasing it once, since another download may take it then), and compares those paths ignoring case and Unicode normalization, as APFS does by default. A path set there also replaces Electron's own Save dialog, so the hidden `.<bundle id>.XXXXXX` temporary file Chromium starts every download in (in the session's download folder, before it has a target) is renamed to the save path within a moment, rather than holding the download while a dialog is open. Loxel shows its own Save dialog (`dialog.showSaveDialog`, attached to the window showing the page) beside the running download, suggesting the download's name in the folder it last saved to. When that folder is Downloads, the suggestion is the first free numbered name, and the download itself takes the next one, so the dialog never offers the running download's own file (macOS would ask to replace it). Once both are done it moves the download to the chosen path: onto what is there only when something was there when the dialog returned (macOS's Save dialog asks before it returns such a path) and it isn't another running download's save path; otherwise without ever replacing anything (`link`), taking the next free number beside a file that turned up since and skipping other downloads' paths. On another volume, or a file system without hard links, the file is copied to a hidden name beside the target (`copyFile` with `COPYFILE_EXCL`, which copies no extended attributes), given the original's quarantine attribute there, and only then linked or renamed into place, so it is never at the chosen path unmarked and a mark Chromium wrote is kept. Cancelling the dialog cancels the download, or deletes it once complete. A page's download whose dialog is still open makes Loxel cancel that page's later downloads until the dialog is answered.
- **Quarantine.** The patched Electron gives Chromium a quarantine service ([PATCHED_ELECTRON.md](PATCHED_ELECTRON.md)), which marks a download, with its URLs, only once it is complete, and a file a page writes through the File System Access API; stock Electron (dev runs and tests) gives it none, so Chromium marks nothing. [browser-downloads.ts](../src/electron/browser-downloads.ts) writes `com.apple.quarantine` with `/usr/bin/xattr`, in the format macOS writes for an app's quarantined download (flags `0281`, the time, `Loxel` as the agent, an event id), so Gatekeeper checks the file when opened. The format has no field for the download's URLs. The file is marked from the first progress event that finds it at its save path, not only once complete, so a stalled download is marked too, and again once moved where the user chose. A file that already carries the attribute keeps it, at completion as while downloading: Chromium's own mark, where its quarantine service runs, links to the quarantine event that records the URLs, which a new event id would break. Only a regular file is marked (`lstat`, and `xattr -s`, so never a link's target). A file can still land at the save path before Chromium's does, so until the download is complete a file that is provably older than the download (created more than a minute before it started; file systems store creation times coarsely, from another clock, or not at all) is left alone, and marking is the default when that can't be told. Once complete, the file at the path is the download and is marked whatever its creation time; only a regular file that isn't provably older is moved or deleted.
- **Notifications** from pages go to Loxel's notification center, never to the OS. The webview preload replaces the page's `Notification` with one whose permission, `requestPermission()`, construction and `close()` are IPC calls to `src/electron/browser-notifications.ts`, and reports that permission from `navigator.permissions.query()` too. Notifications shown through a service worker registration, from the page or the worker, have their own path (Service workers below). Chromium's own notification permission stays denied (`src/electron/browser-permissions.ts`), so this is the only path. Message shapes are in `src/electron/browser-notification-protocol.ts`, and the renderer side is `src/components/browser/useBrowserNotifications.ts`.
  - **Decisions.** Main decides by the page's origin as it sees it (`senderFrame`), never as the page claims, and settles it before any wait: only secure top-level pages (`https`, or `http` on a loopback host, as browsers require) and their same-origin frames get notifications. Per-site Allow / Block lives in settings (`browser.notificationSites`), which window renderers push to main after hydration and on every change (`setNotificationSites`, accepted only from Loxel's windows), because `Notification.permission` is synchronous. Until the first push, pages read `default` and `requestPermission()` waits. Sites muted or snoozed from a notification's context menu in the notification center (`browser.notificationMutes`, origin → optional `until`; `NotificationSiteMenu.tsx`) keep their decision, so pages still read `granted`, but main drops their notifications, from pages and service workers alike (`isSiteMuted`), before anything is sent or counted toward the rate limit. Renderers push mutes the same way (`setNotificationMutes`), before the decisions, and main checks a snooze's end against the clock on each notification, so no timer is needed.
  - **Asking.** A site without a decision gets a request in the window hosting the page (`BROWSER_NOTIFICATION_PERMISSION_REQUEST`), which the panel shows as a bar under its toolbar (`NotificationPermissionBar.tsx`). Allow or Block is saved for the site and settles every page of it that is waiting; repeated calls while the bar is up share one answer. Closing the bar decides nothing, and the page cannot show it again until it navigates. Requests are withdrawn when their page starts a main-frame navigation or goes away, and when the site gets a decision some other way.
  - **Showing.** Main forwards a granted page's notification (text capped, at most 10 per page per 10 seconds, reloads included) with a ref of its own to the host renderer, whose panel sends it to the server as a `browser` notification source with the panel's id, the worktree whose layout the panel is in (null for Home), whether that layout is shown or not, and the favicon its tab shows if the panel still shows the notifying site. The bell loads that favicon the way tabs and bookmarks load theirs (Favicons above), and ignores the notification's `icon`, which would be a second page-chosen URL for Loxel to load; the server keeps the favicon only if a bookmark could (`isStorableFavicon`). On the server, a tag replaces the site's earlier notification with that tag in the same worktree, and browser notifications evict only each other past their share of the list (`addBrowser`), so a busy site never pushes out terminals' notifications. The page's `close()` leaves the notification in the center, since pages close theirs on a timer or when their tab is shown; it only stops clicks. Clicking it in the notification center switches to the panel's worktree or Home if needed and, once that layout is mounted (`whenBrowserPageAttached`, or after 5 seconds), activates the panel and fires the page's `click` event through main (`clickBrowserNotification`), only from the window the notification went to and only while the page that made it is still loaded.
  - **Readiness.** Main forwards notifications and requests only to window renderers that subscribed (`onBrowserNotifications`), with the same per-document rule as dialogs (`src/electron/listening-renderers.ts`); pages of other windows are denied.
  - **Service workers.** `src/electron/service-worker-notifications.ts` registers `src/electron/service-worker-preload.cjs` on the browser session as a service-worker preload, which replaces the worker's `registration.showNotification()`, `getNotifications()`, `Notification.permission` and `navigator.permissions.query()` answer with IPC to main. A worker's IPC reaches only its own `ServiceWorkerMain.ipc`, so main attaches its listeners when the worker's running status turns `starting`, before the preload's first call. The webview preload routes a page's `registration.showNotification()` and `getNotifications()` to the same module (`REGISTRATION_NOTIFICATION_*`). Main decides by the registration's scope: a worker's as `ServiceWorkerMain` reports it, a page's only when it has the page's own origin. A worker counts only when it is its scope's first-party registration (`startWorkerForScope` finds the same version), so one a site registered while embedded in another site, which Chromium partitions, neither sees nor shows the site's notifications. The same site decisions and rate limit apply. A worker's notification goes to the most recently focused loaded panel of its origin (`trackWebviewFocus`), and nowhere when none is loaded; a page's goes to its own panel. Main keeps the live notifications (texts and `data`, capped, at most 100 per origin) by registration scope, since the browser stops idle workers: `getNotifications()` lists them, a tag replaces the earlier one, `close()` removes one from the list but not from the center, and those of a closed window are dropped. A click from the notification's window (the same `clickBrowserNotification`, also sent after switching worktrees, whose pages stay loaded unless they were unloaded) starts the worker with `startWorkerForScope`, keeps it alive with `startTask()` until the handler's `waitUntil()` promises settle (at most a minute), and has the preload dispatch a script-made `notificationclick`. Chromium gives such an event no working `waitUntil()` and refuses its `clients.openWindow()` and `focus()`, so the preload supplies them: `focus()` resolves, since the click already showed the panel, and `openWindow()` asks main, which opens one `http(s)` tab within `USER_ACTIVATION_MS` of the click, next to the notification's panel or, when that page is gone, the site's most recently focused loaded one. Push (`pushManager`) isn't covered: it needs a push service.
- **Camera and microphone** (`getUserMedia()` and the `<usermedia>`, `<camera>` and `<microphone>` elements) are decided per site and device by [browser-media.ts](../src/electron/browser-media.ts), from the browser session's `media` check and request handlers. A click on one of these elements reaches the request handler as one `media` call per device with no `mediaTypes`, but in the same task Chromium first checks each device the element asks for, and those checks carry their `mediaType`. The check handler records the devices it checks per guest, in order, until main's next turn (Node's next immediate, which can come a few tasks late, so the record can also hold an element's registration checks or the page's `navigator.permissions.query()`). The typeless calls of one turn are gathered and ask for the last devices checked before the first of them, one per call, so a `<usermedia>` element's two calls share one prompt for the camera and microphone and a `<camera>` element's asks for the camera alone. The element's own stream and the page's later `getUserMedia()` are answered from that decision. Calls with fewer checks before them (for example under a DevTools permission override, which skips Electron's checks) name no device and are refused with a warning. A request from a site with no decision is held while main forwards it to the window hosting the guest, which shows a bar in that panel (`src/components/browser/useBrowserMediaPermissions.ts`). Requests from the same guest and site join the open prompt, so one answer covers both devices. Allow and Block are saved in settings (`browser.mediaSites`), which windows send back to main like the notification decisions. Allow this time is held in main per guest and dropped when the guest leaves the site. The site deciding is the top-level page's origin, for secure origins only, and Chromium enforces the frame's permissions policy: Blink refuses a frame the policy doesn't delegate the device to before asking, and the browser process drops such devices from a grant. On macOS a granted request also needs the app's own access (`systemPreferences`), which needs the camera and audio-input entitlements and the usage texts in `electron-builder.yml`. When macOS refuses, the panel offers to open System Settings. Electron's checks answer only granted or denied, so the webview preload overrides `navigator.permissions.query()` for `camera` and `microphone` with a synchronous call to main that answers `prompt` for undecided devices. Message shapes are in `src/electron/browser-media-protocol.ts`, and the answer and withdrawal in `src/electron/site-permission-protocol.ts`.
- **Permission prompts.** The notification, camera and microphone, and site access prompts share their plumbing. In main, [permission-prompts.ts](../src/electron/permission-prompts.ts) keeps a kind's open prompts (each shown in the window hosting the page's webview under an id, answered by id and only from that window, withdrawn when answered some other way) and its mirror of the settings' decisions, which pages wait for until a window has sent them. A prompt asks again under a new id whenever what it asks for changes (`reprompt`), so an answer only covers what the user saw. Page channels check their sender with `webviewSenderFrame` ([webview-sender.ts](../src/electron/webview-sender.ts)). In the renderer, [webview-messages.ts](../src/components/browser/webview-messages.ts) routes main's messages to the panel of their webview, holding them until it subscribes, keeps each panel's queue of open requests, and sends settings to main after hydration and on every change; page dialogs use the same router. [SitePermissionBar.tsx](../src/components/browser/SitePermissionBar.tsx) is the bar under the toolbar every prompt uses. Notifications stay apart where they differ: the preload reads their permission synchronously, and they offer no Allow this time.
- **Links to other apps** (`mailto:`, `zoommtg:`, `vscode:`) reach the browser session's `openExternal` permission request, which [browser-external-apps.ts](../src/electron/browser-external-apps.ts) decides, asking through [browser-site-access.ts](../src/electron/browser-site-access.ts) (Site access below). Electron's `HandleExternalProtocolInUI` passes the request no user gesture, so a launch needs the page's own transient activation (`user-activation.ts`), checked and used up when the request arrives, even for an allowed site. Only main frames ask, as the requester Electron reports; a page that moved on to another site by the time the request arrives is refused. The bar names the app from `app.getApplicationNameForProtocol`, or the link's scheme when the OS names none. Decisions are kept by origin and scheme (`browser.externalAppSites`). A popup window has no panel to ask in, so it opens only the links its site was allowed.
- **Local network** access is gated by [browser-local-network.ts](../src/electron/browser-local-network.ts) and by Chromium's own Local Network Access checks (`kLocalNetworkAccessChecks`), which Electron turns off unless the app enables them, which only the patched Electron allows; `main.ts` enables them before the app is ready. Chromium checks each request once it has connected, from the address it reached, and before it sends anything, through the browser session's permission check (`local-network`, `loopback-network`), which `localNetworkPermitted` answers from the site's decision without asking. Asking is the `webRequest` gate's job, and on stock Electron (dev runs and tests) that gate alone applies. A public site that isn't a secure context (plain `http:` off this machine) is refused without asking, as Chromium refuses it. A frame of another origin than its page, or a sandboxed one, follows the page's decision but never asks, since Chromium lets it use the permission only when the page delegates it (`allow="local-network"`), which the gate can't see. A worker's check counts Allow this time given in any panel on its site. WebTransport never reaches `webRequest`, so only Chromium's check, with the saved decision, gates it. Through a proxy, the server's address isn't visible, so neither gate can tell where a proxied request goes, as in Chrome. The gate follows Chrome's model with [address-space.ts](../src/electron/address-space.ts)'s three spaces, Chromium's ranges included: a request from a public initiator to a local or loopback address needs the site's permission, asked through Site access below. As in current Chromium (`IsLessPublicAddressSpaceLNA`), local and loopback count as one for this, so a dev server opened on its LAN address reaches its API on `localhost`. It is a `webRequest` `onBeforeRequest` listener on the browser session, not the webview preload, which `about:blank` frames never run: it sees subresources, fetches, websockets, subframes, and dedicated, shared and service workers' requests, redirects included (each hop is a new `onBeforeRequest` with the same id). `mainFrame` requests aren't gated.
  - **Who decides.** A frame's request names its webview or popup (`details.webContents`), whose top-level origin decides; the initiator is `initiatorOrigin`, which the page can't set. A request with no webContents and an initiator is a worker's, decided by the worker's origin and asked in a panel already asking for it or showing that site. A request with neither is main's own: [browser-favicons.ts](../src/electron/browser-favicons.ts) registers each favicon fetch with `fetchForPage`, so it counts as the page's (by URL, then by request id across redirects) and follows the page's decision without asking. Any other request of no page, a favicon of no page included, counts as a public site's that can't be asked.
  - **Spaces.** A target host that names its space (an IP literal, `localhost` and `*.localhost`, `*.local`) is classified as is; any other name by the most private address `session.resolveHost` returns (looked up for each request, concurrent lookups shared), so a public name resolving to a private address counts as private. A document's own space comes from the address its response came from (`onHeadersReceived` of `mainFrame` and `subFrame` requests, whose `ip` Electron reports though its types leave it out): an IP literal or `localhost` names it, a `.local` name counts by its address, and a non-public address counts only when `session.resolveProxy` says the origin's requests go direct (kept a minute per origin). It is kept per webContents and origin: a main frame's from when its page commits (`did-navigate`, so a response that never commits, such as a download, changes nothing) until the next page commits, so a name that later resolves elsewhere doesn't change a loaded page's space. A caller with no such document (a service worker, a page a service worker served) counts by the least private address its name resolves to, so a name that also resolves to this machine can't make it local. A request let through without asking is remembered by id until it ends (`onCompleted`, `onErrorOccurred`), and its response refused when it came from a more private address than that, directly, and the site isn't allowed.
  - **Waiting.** An undecided request waits in `onBeforeRequest` on the prompt; requests of one page and site share it. Allow and Allow this time release them, Block and dismissing fail them (`cancel`), and so does the main frame starting a cross-document navigation. After a dismissal, the page's requests fail without asking until it navigates.
  - **Ownership.** This module owns the browser session's `webRequest` listeners (`onBeforeRequest`, `onHeadersReceived`, `onCompleted`, `onErrorOccurred`); Electron keeps one listener per event per session, so other modules route through it instead of setting their own. A fetch main makes through the browser session for a page registers with `fetchForPage`, or it counts as a public site's.
- **Site access** ([browser-site-access.ts](../src/electron/browser-site-access.ts)) is the prompt links to other apps, the local network and file access use (`SITE_ACCESS_*`), with its message shapes in `src/electron/site-permission-protocol.ts` and its renderer side in `src/components/browser/useSiteAccess.ts` and `SiteAccessBar.tsx`. A request (`SiteAccessRequest`) carries a `kind`. Allow and Block are saved by the renderer in settings (`browser.externalAppSites`, `browser.localNetworkSites`), which windows send back to main in one message like the other decisions. Allow this time answers only the open prompt for a link; for the local network it is held in main per guest and dropped when the guest leaves the site. File access is never saved: Chromium keeps the bar's Allow or Block for as long as the page holds the file or folder, and a refused page can't ask again meanwhile. A page's request to read and then write the same file or folder (`requestPermission({ mode: "readwrite" })`) becomes one prompt to write.
- **Passkeys** use the macOS Touch ID platform authenticator (`src/electron/webauthn.ts`). This needs a restricted entitlement that only provisioned Developer ID builds carry, so dev runs and unprovisioned local builds have no passkeys; see [RELEASE_SIGNING.md](RELEASE_SIGNING.md).
- **Passkeys from a phone** (FIDO hybrid transport, "use a phone or tablet") come from the `webauthn-hybrid-request` session events, which leave drawing the QR code to the app. `installHybridQrCode` (`src/electron/webauthn.ts`) routes each request to the browser panel whose webview made it, and `PasskeyQrOverlay` draws the code over that panel only, so a background panel cannot put a code in front of the user. The `FIDO:/` string is a per-request secret: it goes to the hosting window's renderer and nowhere else, and is never logged. The events come from the patched Electron releases ship with ([PATCHED_ELECTRON.md](PATCHED_ELECTRON.md)); on stock Electron, as in dev runs and tests, the listeners never fire.
- **Permissions.** With no handlers, Electron grants every permission to every page, so [browser-permissions.ts](../src/electron/browser-permissions.ts) installs both of `BROWSER_PARTITION`'s permission handlers. They answer from one decision, `browserPermissionGranted`, so what a page reads matches what requesting gets it. Permissions browsers grant without asking are on an allowlist, and everything else is refused, since Loxel has no permission prompt for them; the module comments why each is there and which quiet grants are refused anyway. `media` (camera and microphone) and the `openExternal` request (links to other apps) are handed to [browser-media.ts](../src/electron/browser-media.ts) and [browser-external-apps.ts](../src/electron/browser-external-apps.ts), passed in by `main.ts`, which ask the user (see Camera and microphone and Links to other apps above). `notifications` is refused, because pages get Loxel's own notifications instead (see Notifications above). Chromium's own local network permissions go to `localNetworkPermitted` (Local network above). The `fileSystem` check is granted: on the patched Electron it can only take access away, keeping what a picker, a drop or the user's answer granted, and refusing it would break the File System Access API. A `fileSystem` request, for access the page doesn't have yet (writing a file picked for reading, reading a picked folder, or a handle kept from an earlier visit), goes to [browser-file-access.ts](../src/electron/browser-file-access.ts), which asks in the panel's bar (Site access above). On stock Electron the check alone decides, so dev runs grant those without asking.
- **Client certificates.** When a TLS server asks for a client certificate, Electron emits `select-client-certificate` and, unless a listener calls `preventDefault()`, gives the site the first matching identity in the keychain. [browser-client-certificates.ts](../src/electron/browser-client-certificates.ts) handles the `app` event, which covers every webContents and main-process `net` requests. A browser panel page (a webContents in `BROWSER_PARTITION`: a webview or one of its popups) gets a native dialog, attached to the window showing the page, that lists each certificate's subject, issuer and expiry, with "Don't Use a Certificate" as the default and cancel button. Everything else (Loxel's own windows, main-process requests, and service workers, which have no webContents) is refused without a dialog.
  - **Question.** The dialog names the server (`host:port`, the port left out when it is 443). For a request to a server other than the page's top-level document's, it names the page's host too, so a page can't pass off a request to another site as its own. A request for the document the main frame is navigating to names only the server: main follows each browser panel page's main-frame navigations (`did-start-navigation` and redirects) to tell them apart.
  - **Memory.** The answer, a certificate or none, is kept per server in memory for the app run, the key Chromium also keeps each answer under, so it doesn't ask again for that server. Requests for a server whose question is open share its answer, and a kept certificate a request doesn't list is asked about again.
  - **Floods.** A page shows one question at a time and its other requests wait their turn, while other pages ask independently. Once the user declines two of a page's questions (`MAX_DECLINES_PER_PAGE`), its further requests get none without asking until its main frame commits a navigation, as with page dialogs.
- **Fullscreen and pointer lock notices.** Electron draws no exclusive-access bubble (its `WebContents::EnterFullscreen` is empty), so [exclusive-access.ts](../src/electron/exclusive-access.ts) tells the panel, and [ExclusiveAccessNotice.tsx](../src/components/browser/ExclusiveAccessNotice.tsx) shows which site took the screen, the pointer or both, and that Esc gives it back, for 4 seconds.
  - **Window.** When a page's main frame calls `requestFullscreen()`, Electron puts the window into macOS fullscreen (unless it already is) and the webview's frame fills it from the window document's top layer. A frame inside the page that goes fullscreen fills only the page area, since Chromium tells the embedder only about the guest's main frame. The notice is a `popover="manual"` shown after that, and shown again on each `fullscreenchange`, because the top layer stacks in the order elements enter it. It sits at the top of the window while the webview is the document's fullscreen element, and otherwise over the page area through CSS anchor positioning, no wider than the area. Its countdown lives in the store, so a remounted panel doesn't show it again.
  - **When.** Every fullscreen entry (the guest's `enter-html-full-screen`; `leave-html-full-screen` hides it), every frame that takes over a page already fullscreen (a granted `fullscreen` request, for which Electron emits no second entry), and the first input (`before-input-event`, `before-mouse-event`) after 15 minutes without any while fullscreen or holding the pointer lock, as Chrome does, and the window gaining focus while it is either (`noteWindowFocused`, from the window's `focus`), as the user comes back from another window or app. Pointer lock has no event, so its notice comes from the `pointerLock` permission request, which Electron makes on every `requestPointerLock()`; a lock taken by the fullscreen frame shows one notice for both. `installBrowserPermissions` reports grants (`onGranted`) before answering, since a fullscreen grant enters fullscreen synchronously. The webview preload's `pointerlockchange` would not do for entry, since the preload doesn't run in `about:blank` frames.
  - **Unlock.** Main gets no signal when a lock ends, so the webview preload reports each trusted `pointerlockchange` of its frame, with whether that frame's `pointerLockElement` is set, read in the preload's isolated world (`POINTER_LOCK_CHANGE`, a page channel decided by `senderFrame`). A renderer can report late, after the browser has already released its lock, so a report can only end the tracking of a lock, never hide a notice, and it counts only from the frame that asked: Electron names the requester by URL, so main looks for the page's one frame at that URL when it grants. That frame must report taking the lock after the grant and then losing it. A lock whose requester can't be told apart (no frame, or several, at that URL), or that never reported, as one taken by an `about:blank` frame or a grant no lock followed, is tracked until the page's main frame navigates.
  - **Origin.** The requests name the frame that asked by its committed URL, so the notice names that frame's origin, as Chrome does, never the page's title. A URL with an opaque origin (`about:blank`, `about:srcdoc`) is looked up among the page's frames, whose `origin` Chromium inherited from their creators, preferring one other than the page's own, so an embedded frame is never shown as its host; failing that, it names the page's origin.
  - **Refused.** Popup windows get neither fullscreen nor pointer lock, as they have no panel to show the notice. Keyboard lock, which would turn "Press Esc" into "press and hold Esc", is refused too: Chromium already refuses `navigator.keyboard.lock()` to `<webview>` guests before asking the permission handler.
- **Loxel's own permissions.** With no handlers, Electron grants every permission to every page, frames inside Loxel's windows included, so [app-permissions.ts](../src/electron/app-permissions.ts) installs both of the default session's permission handlers from one decision: the permissions the app's page uses (installed fonts for the font pickers in Settings, clipboard reads and writes, fullscreen for an embed in a drawing, and the File System Access API for the drawing editor's export and image pickers), for the app origin's main frame only. Frames inside it, even at the app's URL (media frames), and every other permission (camera and microphone, notifications, links to other apps) are refused. Electron decides `local-fonts` (`window.queryLocalFonts`, `src/lib/local-fonts.ts`) from the check handler alone, since its permission status is never "ask", and Blink resolves a refused query with an empty list rather than an error. Electron checks a File System Access grant with no frame, by the origin that holds it, so the `fileSystem` check is decided by origin alone; the request that grants it comes from the main frame.

## macOS integration

- **Open from Finder.** `electron-builder.yml` declares Loxel an _Alternate_ handler for text and source files, `.excalidraw` and folders. The main process receives these as `open-file` events and posts each to `POST /api/open`, the same request the `loxel <path>` CLI sends (`src/open-request.ts`).
- **Default browser.** `electron-builder.yml` also declares the `http` and `https` URL schemes (`CFBundleURLTypes`), which lists Loxel among the browsers macOS can make the default without changing the default itself (macOS keeps the user's browser until they pick another). Declaring them is one of the criteria for Apple's web browser public-key credential entitlement, which lets browser panels use the passkeys of iCloud Keychain and password managers. [default-browser.ts](../src/electron/default-browser.ts) answers Settings' `DEFAULT_BROWSER_GET` / `DEFAULT_BROWSER_SET` with `app.isDefaultProtocolClient` / `app.setAsDefaultProtocolClient` for both schemes; macOS confirms the change in its own prompt, so Settings reads the status again when its window regains focus. Only a packaged macOS app can be set (`canSet`): a dev run would register Electron. Links then arrive as `open-url` events, which main posts as `{ url }` with no `wtPath`, so the window in use opens the page itself, unchanged, in a browser panel of its active worktree or of Home. Other schemes are ignored.
- **Launch opens.** Files and links that launch the app arrive before it is ready; main keeps them (`launchOpens`) until the startup window exists, then sends them one at a time in the order macOS sent them, each retried by `requestOpen` until the window connects. In the renderer, a page for Home waits in Home's pending opens until its layout mounts.
- **Reveal in Finder / Open In.** App lists and icons come from LaunchServices through `bun:ffi`, which runs in a helper process (the server executable started with a helper flag, see `src/server/launch-services-client.ts`) so a native crash only kills the helper.

## Demo mode

`LOXEL_DEMO=1` (`IS_DEMO` in `src/electron/env.ts`) starts a Loxel that can run beside the installed app, for staging screenshots: port 7435 and the `loxel-demo` state directory (`src/server/config.ts`), a separate Electron data directory and so a separate single-instance lock and browser session, the fixed dev encryption key instead of the keychain (`src/server/dek-source.ts`), no update checks, and windows that open at the size of the site's screenshots (1920×1200, `DEMO_WINDOW_SIZE`, allowed to be larger than the screen). Unlike dev mode it loads the built renderer, so it shows no DEV badge, and it takes precedence over dev mode: main reads the renderer's dev URL only through `DEV_RENDERER_URL`, which is unset in a demo, so one started from a dev Loxel's terminal ignores the inherited `VITE_DEV_SERVER_URL` and `IS_DEV` stays false. It runs from the source tree only, running the server's source and serving `dist-electron/renderer`: a packaged app ignores `LOXEL_DEMO` and every other variable in [loxel-overrides.ts](../src/loxel-overrides.ts) (dev mode's `VITE_DEV_SERVER_URL`, the state directory, port, renderer and key file), since main reads Loxel's variables only through `LAUNCH_ENV`, which drops them when `app.isPackaged`, and starts its server with it. `LOXEL_DEMO_INSTANCE=<n>` (`DEMO_INSTANCE`) runs several at once, each on port 7435 + n with its own state (`loxel-demo-<n>`) and data directory; main, the server and the demo scripts share its parser, port and state-directory naming from [demo-instance.ts](../src/demo-instance.ts), which refuses anything but a non-negative integer. `LOXEL_DEMO_HIDDEN=1` (`IS_DEMO_HIDDEN`) gives a window that never shows itself: fully transparent, ignoring the mouse, shown without activating, and no Dock icon, while its page still renders and can be captured. With no one to read a dialog, a hidden demo logs a startup error and exits with status 1 instead of showing an error box.

Page visibility can't be measured the way the screenshot scripts drive a demo. macOS reports a hidden demo's transparent window as occluded, so Chromium hides the whole window and every page in it, unless the app is started with `--disable-backgrounding-occluded-windows`. And under Playwright's Electron driver, browser panel pages stay `"visible"` whatever their element does. To check a browser page's `document.visibilityState` or throttling, start Electron on `dist-electron/main/main.js` with `--disable-backgrounding-occluded-windows` and the hidden demo's environment (`demoEnv(<n>, true)`), not through `demo-session.ts`. Have the test page report to a local server, and drive the window only through the CLI or a raw CDP session on the window's own page. Freezing a background page doesn't take under Playwright either, so check it the same way.

`scripts/demo/launch.ts` builds and starts a visible demo (instance 0) with fresh state and the demo projects (clones of Loxel and Excalidraw with real PR branches as tasks, from `demo-projects.ts`). `scripts/demo/capture-shots.ts` stages the site's screenshots ([shots.md](../scripts/demo/shots.md)) in hidden demos (instance 1 unless told otherwise) driven by Playwright's Electron driver: each shot is a script in `scripts/demo/shots/` built on `shot-kit.ts`, its content is captured with `webContents.capturePage()`, and `composite.swift` puts it into `window-frame.png`, one real `screencapture` of a demo window (`capture-frame.ts`), so every screenshot keeps macOS's frame without a window ever coming to the front. Both start the app through `demo-app.ts`, which owns the build, registering and trusting the demo projects, and the demo's environment (`demoEnv`): the scripts' own, minus agent and Loxel terminal session markers (`withoutAgentEnv` in `src/coding-agent-env.ts`) and the variables that would point it at another Loxel (`VITE_DEV_SERVER_URL`, `LOXEL_DEV`, `LOXEL_STATE_DIR`, `LOXEL_SERVE_PORT`, `LOXEL_STATIC_DIR`).

## Build and release

`pnpm run build:app` compiles the standalone server and terminal host ([build-server.ts](../scripts/build-server.ts), which embeds the host build ID in both) and the CLI, builds the renderer and packages the app with electron-builder into `release/`, on macOS for this machine's architecture (`build:app:local` builds an unpacked arm64 app only). `release-loxel.yml` releases on every merge to main that touches `packages/loxel/**`; see the [README](../README.md#releases). Releases package a patched Electron rather than the npm package's binary; see [PATCHED_ELECTRON.md](PATCHED_ELECTRON.md).

The app ships the [`loxel` CLI](TERMINALS.md#the-loxel-cli) at `Resources/bin/loxel`, which electron-builder signs with the rest of the bundle. Each release also publishes that build of the CLI on its own: `release-loxel.yml` signs it with the Developer ID under the identifier `com.bizimind.loxel-cli` (the app's is `com.bizimind.loxel`) with [codesign-release.ts](../../cli-common/scripts/codesign-release.ts), notarizes it, and uploads it to `loxel/cli/darwin-<arch>/<version>/loxel` on R2. The manifest's `cli` holds its URL and SHA-256 per `<platform>-<arch>`, and the GitHub release links to it.

The server, the terminal host, the CLI, language server scripts and Go builds all produce binaries for the machine they run on, so each macOS architecture builds on a runner of that architecture. [check-binary-arch.ts](../scripts/check-binary-arch.ts) reads the header of every file in the app and fails the release if a binary doesn't match.

Each release publishes a CycloneDX SBOM of what each architecture's app ships, `Loxel-<version>-mac-<arch>.cdx.json`, written by [sbom.ts](../scripts/sbom.ts) on that architecture's build, since pnpm installs and lists only the machine's own platform packages (TypeScript's compiler is one). It is uploaded to R2 next to that architecture's installer and attached to the GitHub release; the manifest's `sbom` holds the URL per `<platform>-<arch>`, which the site's download page links to. Its base is pnpm's SBOM of this package's `dependencies`, which here are what ships (Vite bundles them, or a language server is built from them), so a shipped npm package goes in `dependencies` and a build-only tool in `devDependencies`. pnpm reads licenses from the installed packages, so it runs after `pnpm install`. `sbom.ts` adds what the lockfile does not hold: the patched Electron (a devDependency, as electron-builder requires), with its patches as pedigree; the Bun runtime from the root `.bun-version`, which `bun build --compile` puts in the server, the CLI and the Bun-built language servers; and the component each [language server manifest](LANGUAGE_SERVERS.md#binary-resolution-and-packaging) names. It then reads the build info the Go linker embeds in every Go binary among the staged language servers ([go-build-info.ts](../scripts/go-build-info.ts), the data `go version -m` prints, read from the file so no Go toolchain is needed), and adds the Go standard library and each module compiled in as dependencies of that server's component, or of the root for one built from npm packages (TypeScript's `tsc`). It finds the binaries itself, so a new Go language server needs no change here, and it refuses to run before the language servers are built. pnpm's root names Loxel as an npm package, so its purl is replaced with the GitHub one. It fails when a manifest's npm package is not in `dependencies` or a component is listed twice, and [sbom.test.ts](../scripts/sbom.test.ts) checks every manifest's component is in it.

Each architecture's build scans its SBOM with Trivy before any of the app is uploaded, and fails the app's release when a vulnerability fails the gate in [sbom-vuln-gate.ts](../scripts/sbom-vuln-gate.ts). The gate covers the app only: the standalone server bundle below has no SBOM and ships on its own. A finding fails when its CVSS score is above 4.0. The score is the v4, else v3, score from the source Trivy took the finding's severity from (usually the vendor's), else from GHSA, else NVD, else any other source. A finding with no score fails when its severity is MEDIUM or above, since MEDIUM starts at 4.0, and passes when LOW. A finding with neither a score nor a severity (an unrated Go advisory, say) only adds to a warning's count. The threshold and both no-score rules are constants at the top of the script. A daily `loxel-sbom` job in [vuln-check.yml](../../../.github/workflows/vuln-check.yml) runs the same scan on the latest release's SBOMs, read from the manifest's `sbom`, since advisories appear without code changes. Each vulnerability ID counts once, and fails when it fails for any package it is reported for. A scan that read no components fails too. Workflow logs are public, so the gate prints only counts per severity and the IDs that fail. To see every finding, scan an SBOM locally: `trivy sbom --scanners vuln <sbom.cdx.json>`. An exception for a finding Loxel is not affected by goes in the root `.trivyignore`: the ID, with a comment giving the justification and an `exp:` date after which it fails again. The release gate reads `.trivyignore` from the release's tag, so after a failed release add the exception or the fix on main and release again (`workflow_dispatch`), which takes the next version. The scheduled scan reads main's.

### Standalone server bundle

Each release also publishes the server without the app, for Linux: a bundle to run the server from on a Linux machine. Installing it and running it as a service are outside its scope. [build-loxel-server.yml](../../../.github/workflows/build-loxel-server.yml), which `release-loxel.yml` calls beside the app's jobs, builds it for `linux-x64` and `linux-arm64`, each on a runner of that architecture: `build:server:standalone`, a browser build of the renderer (`vite build`), then [build-server-bundle.ts](../scripts/build-server-bundle.ts), which packages them as `release/server/loxel-server-<version>-<platform>.tar.gz`. The tarball holds one directory, laid out like the app's `Resources`:

| Path                           | What                                                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `loxel-server`                 | The compiled server                                                                                                                      |
| `loxel-terminal-host`          | The terminal host, which the server clones into its state directory before running it ([TERMINAL_HOST.md](TERMINAL_HOST.md#the-process)) |
| `bin/loxel`                    | The `loxel` CLI, which the server's terminals get on `PATH` ([TERMINALS.md](TERMINALS.md#environment))                                   |
| `gopls`, `ruff`, `jdtls/`, ... | Every language server staged for the platform (`build/language-servers/`), found beside the server binary as in the app                  |
| `renderer/`                    | The renderer, which a compiled server serves from beside itself when `LOXEL_STATIC_DIR` is unset                                         |
| `LICENSE`, `licenses/`         | Loxel's license, and the license, source and license file each language server's manifest names                                          |

Every binary in it must match the platform ([check-binary-arch.ts](../scripts/check-binary-arch.ts)), and [smoke-test-server-bundle.ts](../scripts/smoke-test-server-bundle.ts) starts it with a throwaway `LOXEL_STATE_DIR`, reads the session token it writes, checks `/api/version`, an `/api` route with and without the token and the renderer, and runs a command in a terminal through the bundled host. Only then are the tarballs uploaded to `loxel/server/<platform>/` on R2, followed by their manifest, `https://loxel.bizimind.io/loxel/server/manifest.json`, apart from the app's:

```json
{
  "version": "0.1.379",
  "released_at": "2026-11-18T12:00:00Z",
  "server": {
    "linux-x64": {
      "url": "https://loxel.bizimind.io/loxel/server/linux-x64/loxel-server-0.1.379-linux-x64.tar.gz",
      "sha256": "…"
    },
    "linux-arm64": {
      "url": "https://loxel.bizimind.io/loxel/server/linux-arm64/loxel-server-0.1.379-linux-arm64.tar.gz",
      "sha256": "…"
    }
  }
}
```

A run of the workflow on its own (`gh workflow run build-loxel-server.yml --ref <branch>`, once it is on main), or a pull request that changes the workflow or a script that builds what the bundle packages, builds and smoke-tests both bundles without uploading anything. The two scripts also run on a Mac, building and testing a bundle for it, to try them locally.
