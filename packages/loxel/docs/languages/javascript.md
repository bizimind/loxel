# JavaScript

JavaScript shares the TypeScript server and manager, see [typescript.md](typescript.md); ESLint runs next to it for JavaScript and TypeScript files alike. Shared language-server architecture: [LANGUAGE_SERVERS.md](../LANGUAGE_SERVERS.md). This file covers what is specific to JavaScript projects.

## Node version

[node-env.ts](../../src/server/node-env.ts) is the single resolver of the Node a worktree uses, from its root only, and returns a `NodeEnvResponse` from [node-env-model.ts](../../src/api/node-env-model.ts). It reads files and directories, and runs a `node` only to read a version no directory name gives.

- **Resolution.** `resolveNodeEnv(wtPath, { overridePath?, env? })`, first hit wins: the override chosen for the worktree; the root's pin matched against what the managers have installed, a partial pin taking the highest match; `node` on the login-shell `PATH`. A pin nothing satisfies, the `PATH` `node` included, falls back to `PATH` and reports `pinProblem`, the message with the command to run: Loxel never installs a version. `engines` selects nothing.
- **Pins.** Files are read in this order, single-purpose files before shared ones, and the first with a Node pin wins: `.nvmrc`, `.node-version`, a `nodejs` or `node` line in `.tool-versions`, `node` under `[tools]` in `mise.toml` then `.mise.toml`, `volta.node` in `package.json`. Reads go through `readConfigFile`. `parseNodeSpec` is a strict grammar of versions and aliases (`22`, `v22.1`, `22.x`, `node`, `latest`, `stable`, `lts`, `lts/*`, `lts/iron`, `lts-iron`), and only what it accepts is shown or put in the suggested command, since that text comes from the repository and the user may paste it into a terminal. `system` means no pin. Of several versions on a line or in a list, the first counts.
- **Installed versions.** `managerDirs` lists where each manager keeps versions, honoring its variables: nvm (`$NVM_DIR/versions/node/v*`), fnm (`$FNM_DIR`, else `$XDG_DATA_HOME/fnm`, `~/.local/share/fnm`, `~/.fnm` and on macOS `~/Library/Application Support/fnm`, each `node-versions/v*/installation`), Volta (`$VOLTA_HOME/tools/image/node/*`), asdf (`$ASDF_DATA_DIR/installs/nodejs/*`), mise (`$MISE_INSTALLS_DIR/node/*`, else `$MISE_DATA_DIR` or `$XDG_DATA_HOME/mise`, then `installs/node/*`), n (`$N_CACHE_PREFIX`, else `$N_PREFIX`, else `/usr/local`, then `n/versions/node/*`). The version comes from the directory name, so nothing runs; names that are not a full release version (mise's alias symlinks, pre-releases) do not count. Equal versions from several managers keep that order. LTS pins read `NODE_VERSION_LTS_CODENAME` from the `include/node/node_version.h` each installation ships, so no list of codenames goes stale.
- **`PATH` and shims.** A `PATH` `node` that resolves to a manager's installation takes its version from there. Any other answers `node --version`, asked from the filesystem root rather than the worktree or the home directory: asdf, mise and Volta shims act on the pin files of the directory they run in and those above it, which can mean downloading a version, and pins were already matched above, so what remains to learn is the user's default, which they keep outside those files.
- **Trust.** `isShippedByRepo` applies to every candidate: a `node` git tracks is skipped, and on `PATH` the search goes on to the next entry. Relative `PATH` entries are ignored. Since the resolver runs nothing from the repository and downloads nothing, it needs no repository trust.
- **Shared resolution.** `subscribeNodeEnv(wtPath, listener)` keeps a worktree's resolution memoized and watched while anyone is subscribed, and `getNodeEnv(wtPath)` answers from it. It starts over when the override changes or the repository starts tracking the settled `node`. Listeners hear every finished resolution as `{ env, changed }`; the `node` to put first on `PATH` is in `env.nodePath`.
- **Watching.** `watchNodeEnv` watches, without recursing, the pin files at the root, each manager's versions directory (or the deepest existing ancestor when it does not exist yet), a version's directory while it has no `node` yet (n and asdf fill it in place), each absolute `PATH` directory for a `node` appearing there, and the current `node`, debounced. Each resolution re-arms it.
- **Choosing a version.** `listNodeEnvs(wtPath)` returns the installed versions, newest first, then the `PATH` `node`. The override route accepts only a path from that list, so there is no free-form entry to validate. [node-override-store.ts](../../src/server/node-override-store.ts) stores the choice per worktree in `stores.db`, and a stored choice that stops being usable is reported as such while detection takes over.
- **Terminals.** [node-toolchain-env.ts](../../src/server/node-toolchain-env.ts) is Node's entry in the [toolchain environments](../TERMINALS.md#toolchain-environments). It calls `resolveNodeEnv` with `selectedOnly`, not the shared `getNodeEnv`: every new shell in any repository asks, it has no use for the `PATH` `node`'s version, and this answer runs no `node`. A `pin`, or an `override` to a manager's version, puts the `dirname` of `nodePath` first on `PATH`. A `system` resolution changes nothing, including one reporting `pinProblem`, and neither does an override to the `PATH` `node`, the only choice the picker offers with no manager: its directory can be `/usr/bin` or a shim directory, and moving that would reorder every other command. `node_modules/.bin` is never added: what is in it is the repository's to choose, and `npx` and package scripts reach it anyway. `isShippedByRepo` is applied to the whole `bin` here, not only `node` as in the resolver, since everything in that directory now shadows the user's commands. Characters a shell would interpret are refused by the shared `PATH` check. There is no setting to turn this off, and no zsh shim: `PATH` is only what the shell starts with, and a version manager's hook in the user's startup files is left to change it. A pinned `bin` put first means the worktree's commands no longer pass through a shim.
- **Status item.** Node's entry in the [toolchain status items](../LANGUAGE_SERVERS.md#toolchain-status-items) is [node-toolchain-status.ts](../../src/server/node-toolchain-status.ts) on the server, with its routes (`GET /api/node-env?wt=`, `GET /api/node-env/candidates?wt=`, `POST /api/node-env/override`), and [node-toolchain-status.ts](../../src/lib/node-toolchain-status.ts) in the renderer, with [node-env-client.ts](../../src/api/node-env-client.ts), [node-version.ts](../../src/lib/node-version.ts) (labels and the picker, run by `node.selectVersion`) and [NodeVersionStatus.tsx](../../src/components/panels/NodeVersionStatus.tsx). It shows while the active editor's file is JavaScript or TypeScript, with or without a `package.json`: a script with no manifest still runs on this Node, and a manifest says nothing about which runtime a project uses.

## ESLint

[eslint-lsp-manager.ts](../../src/server/eslint-lsp-manager.ts) runs the ESLint language server from `microsoft/vscode-eslint`, next to the TypeScript server the way ruff sits next to basedpyright, on `javascript`, `jsx`, `typescript` and `tsx`. [eslint-project.ts](../../src/server/eslint-project.ts) reads what a project says about ESLint, from disk and without running anything.

- **Binary.** [build-eslint-language-server.ts](../../scripts/build-eslint-language-server.ts) bundles the server from a release tag pinned by SHA256 into `eslint-language-server/eslintServer.cjs`, with its npm dependencies pinned to that tag's in `package.json`. Compiling it to a binary does not work: it resolves ESLint by forking `process.execPath`, and bare imports from the project's files on disk then fail.
- **Runtime.** The bundle runs under the worktree's Node from [node-env.ts](../../src/server/node-env.ts), from the filesystem root, so that a version manager's shim does not act on the worktree's pin files; the server moves to each project's folder to lint. A change of Node restarts it. A Node too old for the bundle's syntax counts as none. There is no fallback to Bun's Node mode: a project with ESLint installed already implies a Node, and Bun's fidelity for arbitrary plugins is unproven.
- **Held connections.** Loading a project's ESLint runs its config and plugins, so a process runs only when the repository is trusted and a Node exists. Otherwise the manager holds the connection itself, as a server with no capabilities, and reads each `didOpen`: a file under an ESLint config reports the restriction (`reportsRestrictionAtStart` is false) or says what Node it needs. A change of trust or Node closes the socket with `LSP_RESTART_CLOSE_CODE`.
- **Which files lint.** The server pulls settings per file with `workspace/configuration`. `validate` is `on` when a config lies between the file and the worktree root (`eslint.config.{js,cjs,mjs,ts,mts,cts}`, `.eslintrc*`, an `eslintConfig` key in `package.json`) and `node_modules/eslint` resolves from the file, unless a repository nested in the worktree holds the file; with `off`, the server loads nothing for that file. A config with no ESLint installed gets a `window/showMessage` with the command to run; the client shows each distinct one once. `workingDirectory: auto` lets the server pick each package's folder in a monorepo. The server has defaults for what the manager leaves out; `packageManager` holds no real manager's name, so the server runs no `npm` to find a global folder and only the project's ESLint resolves.
- **Protocol.** Diagnostics are pull only, and fixes reach the client as direct edits (`source.fixAll.eslint`) or through `workspace/executeCommand`. The custom requests the VS Code extension answers get `null` and its notifications stop at the manager; `eslint/status` above ok, a failed lint such as a broken config, and `eslint/noLibrary` become a warning. Formatting is suppressed, since format on save owns it.
- **URIs.** These languages' models keep `loxel://HEAD/`, for TypeScript (`keepsEditorUris`). The manager parses each frame and translates only `uri` fields and the keys of a workspace edit's `changes`, not the whole text as TypeScript does, because a fix's new text is the user's code and may hold a `file:///` string. `tsx` and `jsx` documents get React language ids through `setReactLanguageId`.
- **Reloading.** The server registers no watchers, so `watchedFileGlobs` lists the config files; a change makes it drop its settings and send `workspace/diagnostic/refresh`. It caches each loaded ESLint by path and Node caches plugins, so any change `NodeModulesChanges` reports restarts the server. Modules a config imports from elsewhere in the project are not watched.
- **Network.** [audit-eslint-lsp.ts](../../scripts/network-audit/audit-eslint-lsp.ts) proves at the socket level that the server contacts nothing, with a positive control. What a project's own plugins do is theirs.

## Tool config files

Each tool's own parser decides how Loxel treats its config, in `FILENAME_TO_LANG` in [highlighter.ts](../../src/lib/highlighter.ts):

- `jsonc`, so [json-strict-validator.ts](../../src/lib/json-strict-validator.ts) adds no markers, for tools that accept comments: `.eslintrc` and `.eslintrc.json` (ESLint strips comments, then parses as YAML and `JSON.parse` respectively), `.babelrc`, `.babelrc.json` and `babel.config.json` (JSON5), `.jshintrc`, `.mocharc.json`, `.swcrc`, `.oxlintrc.json`, `.oxfmtrc.json`, `lerna.json`, `bun.lock`. Monaco has no comments-only or JSON5 mode, so `jsonc` is the closest for `.eslintrc.json`, which rejects trailing commas, and Babel, which also takes unquoted keys.
- `json` for parsers that reject comments: `.c8rc`, `.nycrc`, and by extension `biome.json` (Biome allows comments only in `biome.jsonc` by default), `.prettierrc.json`.
- `yaml` for extensionless files read with a YAML parser: `.prettierrc`, `.lintstagedrc`, `.releaserc`, `.commitlintrc`. JSON is valid there too, so both forms are clean, while `json` would mark every line of the YAML form.

An `.eslintrc` can also be YAML, but stays `jsonc`: the JSON form is the common one and relies on `//` comments, which YAML would reject.

`.nvmrc` and `.node-version` have icons and no language, as with `.python-version`: they hold a version string.

## Built-in schemas

`BUILTIN_SCHEMA_DEFAULTS` in [settings-store.ts](../../src/store/settings-store.ts) only points at `json.schemastore.org`, the host the privacy policy names, and `settings-store.test.ts` enforces that. Tools whose schema lives elsewhere (Biome, oxlint, SWC, Turborepo) rely on the file's own `$schema`, which also keeps a versioned schema in step with the project's tool.

A tool has one row, with one glob covering its file names (`**/.prettierrc{,.json,.yml,.yaml}`), so it has one toggle and the JSON route fetches its schema once. A glob without a final extension routes to JSON, YAML and TOML (see [Schemas and JSON validation](../LANGUAGE_SERVERS.md#schemas-and-json-validation)); the server for the file's language is the one that applies it.

ESLint's schema is YAML-only (`**/.eslintrc.{yml,yaml}`): it `$ref`s the sibling `partial-eslint-plugins.json`, which the YAML server fetches itself, while Monaco gets schemas inline with requests off and would report the reference on every file.
