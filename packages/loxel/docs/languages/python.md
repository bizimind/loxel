# Python

The three servers behind Python files (basedpyright, ruff, mypy) and the per-worktree Python environment and interpreter choice every Python feature shares. Shared language-server architecture: [LANGUAGE_SERVERS.md](../LANGUAGE_SERVERS.md). Python formatters are part of [Formatting](../LANGUAGE_SERVERS.md#formatting).

## Managers

| Manager                                                         | Binary                                                | Args      | Scope    | Flags and config                                                                                                                                                                            |
| --------------------------------------------------------------- | ----------------------------------------------------- | --------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [python-lsp-manager.ts](../../src/server/python-lsp-manager.ts) | `basedpyright-langserver`                             | `--stdio` | worktree | answers `workspace/configuration`: `python.pythonPath` from the [Python environment](#python-environment), `basedpyright` defaults; drops type errors where mypy type-checks; watched files |
| [ruff-lsp-manager.ts](../../src/server/ruff-lsp-manager.ts)     | `ruff`, see [Python environment](#python-environment) | `server`  | worktree | init options: `settings.showSyntaxErrors: false`; suppresses formatting and range formatting; watched files                                                                                 |
| [mypy-lsp-manager.ts](../../src/server/mypy-lsp-manager.ts)     | none: in-process, runs the environment's `dmypy`      |           | worktree | see [mypy](#basedpyright-ruff-and-mypy)                                                                                                                                                     |

## Python environment

basedpyright's own environment discovery covers only a root `.venv` and it ignores Loxel's `initializationOptions`; without an interpreter it runs `python3` from its `PATH`. [python-env.ts](../../src/server/python-env.ts) is the single resolver of a worktree's interpreter, for every Python feature (language servers, terminals, the built-in coding agent's commands, format on save, the status bar), and returns a `PythonEnv` from [python-env-model.ts](../../src/api/python-env-model.ts) (`source`, absolute `pythonPath`, `envPath` prefix or null; a venv's bin directory is `dirname(pythonPath)`).

- **Resolution.** `resolvePythonEnv(wtPath, { overridePath?, env? })` tries, first hit wins: the override (by default the worktree's chosen interpreter; `null` skips it), `VIRTUAL_ENV` then `CONDA_PREFIX` only when they lie inside the worktree (the environment Loxel was launched from must not apply to every worktree), `UV_PROJECT_ENVIRONMENT` then a `.venv` / `venv` / `env` with `pyvenv.cfg` at the worktree root (uv, uv workspaces, PDM, `python -m venv`), Pixi's default environment, Poetry's and Pipenv's environments (asked only when the tool's lock file is at the root and the tool is on `PATH`, since asking spawns it), the virtual environment of a Python project directory below the root when exactly one has one (a monorepo interim: with several, which applies depends on the file, so none is picked), then `python3`, else `python`, on the login-shell `PATH`. A candidate, the override included, counts only if its interpreter is executable and it passes the [environment trust rule](#environment-trust-rule). The resolver never runs the interpreter and never throws.
- **Shared resolution.** `subscribePythonEnv(wtPath, listener)` keeps a worktree's resolution memoized and watched while anyone is subscribed. `getPythonEnv(wtPath)` answers from it (an unsubscribed worktree resolves afresh, since nothing would keep a memo current), and `getPythonEnvNow` answers with the last finished resolution while a newer one runs. The memo is replaced when its environment watch fires, on `refreshPythonEnv` (the override changed), on `refreshAllPythonEnvs(changedNames)` when a login-shell capture changed a variable that resolution reads, and when the settled environment no longer passes the trust rule. Listeners hear every finished resolution as `{ env, first, changed }`, also when the interpreter stayed the same, since packages may have been installed into it. The subscribers are each worktree's resources in [server.ts](../../src/server/server.ts), which send `python_env_changed` to the worktree's clients when `changed`, every basedpyright and ruff session, and every built-in coding agent session (see [CODING_AGENT_INTEGRATION.md](../CODING_AGENT_INTEGRATION.md#tool-environment)).
- **Watching.** `watchPythonEnv` watches, without recursing, where each candidate environment would appear, the Poetry and Pipenv lock files, and the current environment's interpreter directory and `site-packages` (which also covers environments outside the worktree), debounced, and re-resolution keeps the old watch until the new one is armed, so a change made meanwhile is not lost. The worktree file watcher skips git-ignored directories such as `.venv`, so this watch, not [watched files](../LANGUAGE_SERVERS.md#stdiolspmanager-base-class), is what notices `uv sync` creating an environment or packages installed into one.
- **Choosing an interpreter.** `listPythonEnvs(wtPath)` returns `{ candidates, automatic }`, without duplicates and under the same rules: the automatic choice, then `.venv` / `venv` / `env` and Pixi environments at the root and in Python project directories below it (found through git, so ignored trees are skipped), Poetry's environment, the `PATH` interpreter, and last the stored override. `normalizePythonOverride(wtPath, input)` turns a path the user entered (`~/` allowed, or an environment directory) into an interpreter path, or throws a user-facing error; the override route also requires `--version` to report a Python version. [python-override-store.ts](../../src/server/python-override-store.ts) stores the choice per worktree in `stores.db`, and it is deleted with the worktree. Because the resolver reads it, every Python feature gets the choice without state of its own: [server.ts](../../src/server/server.ts) subscribes `refreshPythonEnv` to `onPythonOverrideChange`, so a change reaches every subscriber (basedpyright re-pulls, ruff re-picks, the UI gets one `python_env_changed`) without a restart.
- **Version.** [python-version.ts](../../src/server/python-version.ts) runs `<python> --version` for interpreters the resolver accepted, in the worktree, so a version-manager shim (pyenv, asdf) reports the version the worktree's `.python-version` selects. It is cached per interpreter file and directory, so a recreated venv or an upgraded interpreter is read again.
- **Activation.** [python-env-activation.ts](../../src/server/python-env-activation.ts) puts an environment into a spawn environment the way its `activate` script would: `pythonEnvActivation` refuses an interpreter outside any environment and a `bin` git tracks, and `setPythonEnvVars` puts `bin` first on `PATH`, drops `PYTHONHOME` and `VIRTUAL_ENV_PROMPT`, and sets or clears `VIRTUAL_ENV`. New terminal shells activate their worktree's environment from the shared resolution at spawn, override included (see [TERMINALS.md](../TERMINALS.md#python-environment)); the built-in coding agent's commands follow it through the session (see [CODING_AGENT_INTEGRATION.md](../CODING_AGENT_INTEGRATION.md#tool-environment)).
- **API.** `GET /api/python-env?wt=` returns `{ env, overridePath }` with `env` (the shared resolution) carrying its `version`; `GET /api/python-env/candidates?wt=` returns `{ candidates, automaticPath, overridePath }`; `POST /api/python-env/override` with `{ worktreePath, pythonPath }` validates and stores the choice (`null` clears it) and answers like the first route. `wt` must be a worktree of a registered project, since resolution may run `poetry` there. The renderer side is [python-interpreter.ts](../../src/lib/python-interpreter.ts) (labels and the picker, run by the `python.selectInterpreter` action) and [PythonInterpreterStatus.tsx](../../src/components/panels/PythonInterpreterStatus.tsx) in the status bar, shown while the active editor's file resolves to Python. Both act on the worktree of the active editor's panel (`params.worktreePath`), not the active worktree, which differs right after a switch; the action falls back to the active worktree when no editor is active. Only a worktree's subscribers get `python_env_changed`, so the renderer invalidates its cached interpreters whenever it subscribes to a worktree ([useWsSubscription.ts](../../src/hooks/useWsSubscription.ts)).

### Environment trust rule

Every feature that runs something from a Python environment applies one rule from [python-env.ts](../../src/server/python-env.ts): the resolver (basedpyright executes the interpreter it picks), format on save, terminal and agent activation, ruff's language server and mypy's daemon. `isEnvShippedByRepo(wtPath, envPath, executable)` refuses an environment when git tracks any file inside it, or the executable about to run from it or that executable's symlink target; `isShippedByRepo(wtPath, path)` checks a single path the same way: a ruff or `dmypy` outside any environment, or the `bin` directory activation puts first on `PATH`. Real environments are never committed, so a tracked one is repository content, and running it would run repository code: a committed `.venv/bin/python`, or a `.pth` startup hook in its `site-packages`, would otherwise run as soon as a Python file is opened. An environment whose directory is the worktree itself (`python -m venv .`) shares it with the repository, so only its own entries are checked there. Git is asked through the innermost repository that holds each path (submodules and nested repositories count), about its physical path. A worktree in no git repository has nothing tracked, so every environment passes; inside a repository, a path git cannot answer for counts as tracked, so the caller moves on to its next candidate. Answers are cached per worktree and path until a git index they read changes, which keeps re-checking an environment on every use cheap. The rule is about executables; tools that load project code by design do so as when run by hand: mypy imports the plugins the project's config names (django-stubs' plugin loads the Django settings module). mypy runs only from the project's untracked environment, which installing the project's dependencies creates, and that install already runs the project's build code.

## basedpyright, ruff and mypy

- **basedpyright.** `PythonLspManager` answers the `python` section of `workspace/configuration` with only `pythonPath` from `getPythonEnvNow`, so the resolver stays the source of truth and a re-resolution in flight does not hold up the first analysis. When nothing resolved it answers a `venvPath` of the worktree with no `venv` instead, which turns off basedpyright's own root `.venv` detection (it would run a committed interpreter) without selecting an environment, and basedpyright is spawned with the worktree's directories removed from `PATH`, so its fallback `python3` cannot be a committed one either. After `initialized`, each later re-resolution calls `notifyConfigurationChanged`, so basedpyright pulls the setting again and re-resolves imports: `uv sync` creating `.venv`, packages installed later, a changed override. A `venvPath` / `venv` in the project's own configuration (`pyrightconfig.json`, `[tool.basedpyright]`, `[tool.pyright]`) still wins inside basedpyright over the interpreter Loxel passes; basedpyright only reads that environment's `site-packages` for analysis and never runs its interpreter, so it needs no trust check.
- **basedpyright completions.** `PythonLspManager` sets `disableCompletionSnippets`: basedpyright's snippets are method overrides, whose only tab stop is at most a selected `pass` body and whose default values it does not escape, so plain text costs that selection and keeps `x="$HOME"` intact.
- **basedpyright settings.** The `basedpyright` section sets `analysis.typeCheckingMode` to `standard` (basedpyright's default `recommended` flags ordinary code) and repeats `autoSearchPaths: true`, which any `analysis` section otherwise resets. basedpyright ignores these analysis settings when the project has a config file, so the project's rules, and basedpyright's own defaults for anything the file leaves out, win.
- **Ruff.** `RuffLspManager` runs `ruff server` next to basedpyright for lint diagnostics, quick fixes, fix all and organize imports (basedpyright offers no organize-imports code action, so they never compete). Its asynchronous `resolveBinary` takes the `ruff` next to the resolved interpreter, so the project's pinned version and rules apply, when it passes the trust rule (the whole environment, or the single file for a ruff outside any environment, whose directory can belong to an unrelated repository such as Homebrew's) and is recent enough for a stable `ruff server`; otherwise the bundled one. The session subscribes to the shared resolution and picks again after each re-resolution; when the pick changes it closes the socket with `LSP_RESTART_CLOSE_CODE` ([ws-protocol.ts](../../src/api/ws-protocol.ts)), on which the client reconnects at once (see [Lifecycle](../LANGUAGE_SERVERS.md#lifecycle)), so a new session spawns the new binary and the client re-opens its documents. Ruff finds its configuration per file (nearest `.ruff.toml` / `ruff.toml` / `pyproject.toml`), so monorepo subprojects need nothing from Loxel, and reloads it when a config file changes, which reaches it as watched files. Syntax errors are left to basedpyright (`showSyntaxErrors: false`), and ruff's formatting capabilities are suppressed so format on save stays the only Python formatter (see [Formatting](../LANGUAGE_SERVERS.md#formatting)).
- **mypy.** mypy has no language server, so [mypy-lsp-manager.ts](../../src/server/mypy-lsp-manager.ts) is one, in-process, on its own route (`mypy-lsp`): `MypyLspManager` keeps one session per worktree like the stdio managers (a newer socket replaces the older with `LSP_REPLACED_CLOSE_CODE`), answers `initialize` with open/close sync only, and publishes `textDocument/publishDiagnostics` with source `mypy` and a `codeDescription` link to the error code's entry in mypy's docs. Running it this way, rather than feeding markers from a side channel, puts mypy's diagnostics through the same client as every other server's: markers under their own owner, reconnects, and anything that reads the clients' diagnostics. Each open Python file belongs to the mypy config nearest to it, found the way mypy finds its own by `findMypyConfig` in [mypy-config.ts](../../src/server/mypy-config.ts) (per directory up to the worktree: `mypy.ini`, `.mypy.ini`, `pyproject.toml` with `[tool.mypy]`, `setup.cfg` with `[mypy]`), so monorepo subprojects get their own; where two roots report on one file (a config whose `files` reach into a nested project), the file gets both roots' diagnostics. Each config root with an open file gets a `MypyDaemon` from [mypy-daemon.ts](../../src/server/mypy-daemon.ts), set up lazily and stopped when its last file closes or the session ends: it runs the `dmypy` next to the resolved interpreter, when it passes the trust rule, with the environment activated, the worktree's directories removed from `PATH` and `cwd` at the config's directory, as `dmypy --status-file <file> run -- --python-executable <interpreter> --output json --show-error-end [targets]` (mypy before 1.20, whose JSON output has no error ends, in its text format, which has them). `--python-executable` makes mypy read the resolved environment's packages and keeps it from running an interpreter the config names (`python_executable`) or one it would infer from `python_version`. Each daemon's status file is its own, in a private `dmypy` directory of Loxel's state directory, so nothing is written to the project but mypy's own `.mypy_cache`; `dmypy run` detaches the daemon, so it is stopped through the pid in that file, and an idle timeout bounds one Loxel could not stop. A root whose config names its targets (`files`, `modules`, `packages`) is checked as configured, the way CI runs mypy, any other on its open files. Checks run (debounced, one at a time per root, stopped after 15 minutes) when files open or close and when a Python file under the root changes on disk, which arrives as the worktree's watched files (`notifyWatchedFilesChanged`); unsaved edits are not checked, since mypy reads files from disk. A changed config file, or any re-resolution of the shared Python environment, stops the daemons and sets them up again: `dmypy` notices changed mypy options itself, but not a plugin's own settings (`[tool.pydantic-mypy]`). Each check publishes what mypy reported and clears the files the previous check reported and this one does not. A missing or untrusted `dmypy` and a check mypy could not run (exit code 2: a config error, a plugin that does not load; or exit code 1 with no reports, when `dmypy` refuses options such as `follow_imports = silent`) are sent once each as `window/showMessage`, which the mypy client, created with `showMessages`, shows as a toast.
- **mypy and basedpyright.** A root owns type checking once its daemon is set up, gives it back when a check fails (until one succeeds) or mypy becomes unavailable (whose diagnostics are then cleared), and then owns only the files it checks: with targets in the config, those they cover (`coversFile`: `files` entries, and where the `modules` and `packages` it names are found under the config's directory, `src` and `mypy_path`: a module's file or package `__init__`, since `modules` is not recursive, and a package's whole directory), plus any module its last check reported on after following an import; otherwise every file of the root. `MypyLspManager.ownsTypeChecking(wtPath, file)` answers that, and `PythonLspManager`, given it as its `ExternalTypeChecker`, drops basedpyright's rule diagnostics (those with a `code`, other than hints) from the reports for owned files: pulled `textDocument/diagnostic` answers, matched to their requests by id (read from the start of each frame, so other answers are not parsed again), and pushed ones. Syntax errors and the unused, unreachable and deprecated hints stay, as do completion, hover, navigation, code actions and refactors, so the project's own checker, with its plugins (Django, pydantic, SQLAlchemy), is the only one reporting type errors. When ownership changes, the manager sends the client `workspace/diagnostic/refresh` and drops the client's answer, which basedpyright never asked for; a document's next request goes out without `previousResultId` when its ownership differs from its last report's, since an "unchanged" answer would keep a report filtered under the other rule. A project that configures basedpyright itself (`pyrightconfig.json`, `[tool.basedpyright]` or `[tool.pyright]` at the root, where basedpyright reads them) keeps both checkers' type errors: the project's configuration is the switch, so there is no Loxel setting for it.
