# Rust

The per-worktree Rust toolchain every Rust feature shares, rust-analyzer, Rust's format on save, and its editing behavior. Shared language-server architecture: [LANGUAGE_SERVERS.md](../LANGUAGE_SERVERS.md).

## Rust toolchain

[rust-toolchain.ts](../../src/server/rust-toolchain.ts) is the single resolver of a worktree's toolchain and returns a `RustToolchain` from [rust-toolchain-model.ts](../../src/api/rust-toolchain-model.ts), a union on `status`: `active` (`source`, `name`, `version`, `rustcPath`, `sysroot`, `toolchainFile`, `tools`), `not-installed` (selected but missing; `name`, `source`, `toolchainFile`), `refused` (the repository ships it; `name`, `rustcPath`) and `none` (`rustupPath`, rustup's `detail`).

- **Resolution.** `resolveRustToolchain(wtPath, { chosen?, env? })` looks up `rustup` and `rustc` on the login-shell `PATH`, then in `$CARGO_HOME/bin`, then in `~/.cargo/bin`, entry by entry under the [toolchain rule](#toolchain-rule). `findInstall` lets the first `rustc`, the one a terminal would run, decide. When it is a rustup proxy (a link to rustup, symbolic or hard, normally next to it) that rustup answers, whichever `rustup` comes first: running a proxy in a worktree runs what the worktree's toolchain file names, so a proxy is never treated as a compiler. A proxy with no usable rustup is `none`. A `rustc` that is no proxy is an install without rustup (Homebrew, a distro package), or one earlier on `PATH` than rustup's proxies: its version, sysroot and tools come from `rustc` and the same lookup, there is nothing to choose, and a stored choice does not apply. Otherwise rustup answers, run in the worktree so it honors `rust-toolchain.toml`, `rust-toolchain`, directory overrides and its default: `rustup show active-toolchain` for the name and why, `rustup which rustc` for the toolchain's root. `rustc --version` then runs from that root, not through a proxy, with the filesystem root as its directory, as does everything run from an install without rustup, so no file in the worktree selects anything for it. rustup has no JSON output; `parseActiveToolchain` and `parseToolchainList` read its text, and what they do not recognize becomes the `unknown` source or `none` with rustup's first line as `detail`. The resolver never throws.
- **Never downloading.** Loxel never fetches a toolchain or component. rustup does, from a pinned toolchain file, in `rustc`, `rustup show active-toolchain` and `rustup toolchain list`. Every command this module runs therefore carries `RUSTUP_AUTO_INSTALL=0`, and `rustup toolchain list` also runs from the filesystem root, where no toolchain file selects anything. That variable exists from rustup 1.28.1; 1.28.0 installs nothing by itself, and an older rustup installs whatever the variable says, so `rustupRefusal` keeps one from running in a worktree at all, and a version it cannot read counts the same: the result is `none` with a `detail` saying why. The version comes from `rustup --version` with `RUSTUP_HOME` at an empty temporary directory and no `RUSTUP_TOOLCHAIN`, since that command also runs the active `rustc`.
- **Commands.** These are the only rustup commands this module runs: `--version` (empty home), `show active-toolchain`, `which rustc`, `which rust-analyzer`, `toolchain list -v`. Never add `show active-toolchain -v` or a plain `rustup --version` to the worktree path: both execute the selected toolchain's `rustc`, before anything could check it.
- **Tools.** An `active` toolchain's `tools` are `cargo`, `rustfmt`, `cargoClippy`, `rustAnalyzer` (paths, null when unavailable) and `rustSrc`. rustup's proxies exist whether or not the component is installed, so availability comes from the toolchain itself, its `bin` directory or for `rustAnalyzer` `rustup which`, and the path handed out is the proxy, which sets up the toolchain for what the tool runs in turn. When the toolchain has no rust-analyzer, or without rustup, `rustAnalyzer` is the first one in the lookup directories that is no rustup proxy, such as Homebrew's. Without rustup the other tools are found the same way, since a proxy would pick its own toolchain. A standalone tool earlier in the lookup is not the toolchain's, so its own `bin` path is handed out instead. `rustSrc` is the presence of `lib/rustlib/src/rust/library` in the sysroot.
- **Spawning.** `rustToolEnv(toolchain)` is what a Rust tool Loxel starts gets: `RUSTUP_AUTO_INSTALL=0`, plus `RUSTUP_TOOLCHAIN` when the user chose a toolchain. `rustChosenEnv(toolchain)` is only the choice, the part that suits a terminal, where a user's own `cargo` keeps rustup's normal behavior. Both read a resolved toolchain, so a choice that is no longer installed reaches no process, where rustup would try to install it.
- **Terminals.** [rust-toolchain-env.ts](../../src/server/rust-toolchain-env.ts) is Rust's [toolchain environment contributor](../TERMINALS.md#toolchain-environments). With a stored choice it reads `getRustToolchain` and sets what `rustChosenEnv` returns, `RUSTUP_TOOLCHAIN`, and nothing else: not `PATH`, since rustup's proxies read the variable, and not `RUSTUP_AUTO_INSTALL`, since `cargo` in a terminal is how the user downloads. Without a choice it runs nothing and an inherited `RUSTUP_TOOLCHAIN` stays. A choice that resolves to anything but an `active` chosen toolchain (removed, refused, or an install without rustup, where a stored choice does not apply) sets nothing. The variable applies at spawn, so an open terminal keeps what it started with, and shell startup files run after it, so one that exports `RUSTUP_TOOLCHAIN` wins.
- **Shared resolution.** `subscribeRustToolchain(wtPath, listener)` keeps a worktree's resolution memoized and watched while anyone is subscribed; subscribing resolves nothing, so a worktree without Rust files costs nothing. `getRustToolchain(wtPath)` answers from it (an unsubscribed worktree resolves afresh), and `getRustToolchainNow` answers with the last finished resolution while a newer one runs. The memo is replaced when its watch fires, on `refreshRustToolchain` (the choice changed), on `refreshAllRustToolchains(changedNames)` when a login-shell capture changed `PATH`, `HOME`, `CARGO_HOME` or a `RUSTUP_*` variable, and when the settled toolchain no longer passes the trust rule. Listeners hear every finished resolution as `{ toolchain, first, changed }`. Each worktree's resources in [server.ts](../../src/server/server.ts) subscribe through its status module and send `rust_toolchain_changed` to the worktree's clients when `changed`.
- **Watching.** `watchRustToolchain` watches, without recursing and debounced: `rust-toolchain` and `rust-toolchain.toml` in the worktree, a selecting toolchain file above it, rustup's `toolchains` directory (or its deepest existing ancestor before the first install), `settings.toml` in rustup's home (`rustup default`, `rustup override set`), the current toolchain's `lib/rustlib` (`rustup component add` and `rustup update` keep the toolchain's directory), for an install without rustup the tools next to its `rustc`, and while there is no toolchain, `rustc` and `rustup` in the lookup directories. Re-resolution keeps the old watch until the new one is armed, so a change made meanwhile is not lost.
- **Choosing a toolchain.** `listRustToolchains(wtPath)` returns the installed toolchains the [toolchain rule](#toolchain-rule) accepts, empty without rustup. [rust-toolchain-store.ts](../../src/server/rust-toolchain-store.ts) stores the choice per worktree in `stores.db`, and it is deleted with the worktree. The resolver checks it against the same list on every resolution, so a toolchain removed since falls back to detection, and a list that fails is `none` rather than silently dropping the choice. The choice becomes `RUSTUP_TOOLCHAIN`, which beats a toolchain file in both directions, also for `rustfmt` and `cargo`. A new choice re-resolves through the status module (`onRustChoiceChange`, `refreshRustToolchain`).
- **API.** `GET /api/rust-toolchain?wt=` returns `{ toolchain, chosen }`; `GET /api/rust-toolchain/candidates?wt=` returns `{ candidates, automatic, chosen }`; `POST /api/rust-toolchain/choice` with `{ worktreePath, toolchain }` validates against the installed list and stores the choice (`null` clears it), answering like the first route. `wt` must be a worktree of a registered project, since resolution runs rustup there. Rust's entry in the [toolchain status items](../LANGUAGE_SERVERS.md#toolchain-status-items) is [rust-toolchain-status.ts](../../src/server/rust-toolchain-status.ts) on the server, which holds these routes, and [rust-toolchain-status.ts](../../src/lib/rust-toolchain-status.ts) in the renderer, with [rust-toolchain.ts](../../src/lib/rust-toolchain.ts) (labels, tooltips and the picker, run by the `rust.selectToolchain` action) and [RustToolchainStatus.tsx](../../src/components/panels/RustToolchainStatus.tsx), shown while the active editor's file resolves to Rust. Its routes are called from [rust-toolchain-client.ts](../../src/api/rust-toolchain-client.ts).

### Toolchain rule

Nothing that belongs to the worktree runs: `isRepoLocal` is the [environment trust rule](python.md#environment-trust-rule), through `isShippedByRepo` in [shipped-by-repo.ts](../../src/server/shipped-by-repo.ts), plus anything physically inside the worktree, tracked or not. Every lookup goes through `findTool`, which also drops `PATH` entries in the worktree with `pathOutsideWorktree` and tries the next entry after a hit it refuses, also for a `PATH` entry that reaches the worktree through a link. A toolchain file can name a toolchain by an absolute `path`, and `rustup toolchain link` can install one of a repository's directories, so a rustup toolchain counts only if neither its `rustc` nor its root belongs to the worktree (`isToolchainRepoLocal`); a committed symlink to a toolchain counts as belonging. A selected toolchain that fails is `refused`: nothing runs from it, not even `rustc --version`, and there are no tools to hand out. Choosing an installed toolchain in the picker gets past a refused file, because `RUSTUP_TOOLCHAIN` beats it. An install without rustup has only its `rustc` and tools checked, since its root can be a shared directory such as `/usr`. A linked toolchain that fails is not offered and is not usable as a choice. Lookups also take only real binaries: `isVersionManagerShim` in [rust-tool-shim.ts](../../src/server/rust-tool-shim.ts) refuses a script (asdf's shims, and also wrappers such as Nix's) and a link to `mise` or `rtx`. A refused `rustup` leaves the next hit or an install without rustup, a refused tool is null, and with nothing else found the result is `none` with a `detail` saying so.

## rust-analyzer

[rust-lsp-manager.ts](../../src/server/rust-lsp-manager.ts) runs the user's rust-analyzer, one per worktree, and [rust-analyzer-run.ts](../../src/server/rust-analyzer-run.ts) decides how. Nothing is bundled, so there is no manifest under `scripts/language-servers/`. The server always runs in a restricted mode, in which it runs nothing the repository provides and reaches no network.

- **Binary.** `planRustAnalyzer` takes `tools.rustAnalyzer` of an `active` toolchain, and otherwise returns a `refuse` plan whose reason `serverFailureReason` shows, saying what to run. A toolchain named by an absolute `path` is refused even outside the worktree unless the source is known to be the user's (`USER_SELECTED_SOURCES`), since a toolchain file's is still the repository's pick of a binary.
- **Version floor.** The settings below are what the mode rests on, and a toolchain file can select an older installed toolchain, so `MIN_RUST_ANALYZER_DATE` (the oldest version tested) is enforced. The date in `rust-analyzer --version` is the one thing every kind of build reports; a version that cannot be read counts against it. The check runs from the filesystem root with `RUSTUP_TOOLCHAIN` set to the resolved toolchain, so a rustup proxy answers for the binary the session runs and not for the default toolchain.
- **Settings.** They go in `initializationOptions`, since rust-analyzer pulls configuration only after `didChangeConfiguration`: `checkOnSave`, `cargo.buildScripts.enable` and `procMacro.enable` off, `cargo.sysroot`, `cargo.target` and `linkedProjects`. Listing the projects keeps rust-analyzer from searching, either at startup or from an opened file, so `rust-project.json` is not read: `findRustManifests` lists the worktree's `Cargo.toml`, or else those one directory down, and an empty inline project stands in when there is nothing else. A manifest appearing or going away there restarts the server. The sysroot is named so rust-analyzer does not search for it, and is left null when the toolchain has no `rust-src`, because a search would install the component and a named sysroot without sources fails the whole project. `diagnostics.experimental.enable` stays off: it would mark unknown names, but without proc macros it gave 75 false errors across axum's 117 source files, and it does not mark an unimported type.
- **Projects of opened files.** Listing every manifest up front would load test fixtures and vendored crates, and a project the size of ripgrep takes 500 MB or more, so the rest are loaded lazily. The manager follows the client's `didOpen` and `didClose`, and `findRustProject` in [rust-project-lookup.ts](../../src/server/rust-project-lookup.ts) says what an open file needs:
  - The nearest manifest up to the worktree root, read under the [project file rule](#project-files). A listed member resolves to its workspace's manifest, from the `members`, `exclude` and `package.workspace` keys, so it adds nothing once that is loaded. Anything less clear stays the crate's own manifest, and Cargo decides: linking a member as well is harmless, since rust-analyzer loads both as one workspace.
  - Nothing for a file outside the worktree (the standard library, the registry), reached through a link leaving it, or in a build directory (`target` with Cargo's `CACHEDIR.TAG`), `node_modules`, other dependency folders, a nested worktree (a `.git` file ending in `worktrees/<name>`, unlike a submodule's) or a vendored crate (`.cargo-checksum.json`).
  - Without a manifest, the file is loose: all such files share one inline project, with `crates` at edition 2024 and no dependencies, and the resolved sysroot. It takes no cargo in the file's directories, and its frontmatter is not read, so a cargo script's own dependencies are unknown.
  - **Applying.** The manager calls `notifyConfigurationChanged`, the one source of that notification (the client's stays blocked), and `workspaceConfiguration` answers the pull with the whole of the restricted settings, since a pulled value replaces what the server started with. This reloads the workspaces without a restart; unchanged projects keep their analysis, and removed ones unload. The set lives on the session: a restart starts from the worktree's manifests, and the client's re-opened documents bring the rest back.
  - **Checking first.** rust-analyzer takes in no new workspace while any linked one fails, and its status names no culprit, so one broken manifest would end the loading of every project after it. `rustManifestProblem` therefore runs `cargo metadata --no-deps --offline` with the server's environment, from the manifest's folder as the server does, and a failure gets a notice naming the folder. A new manifest that fails stays out, and so does one from the start at the first refresh, since it has never loaded. A manifest that breaks after it loaded stays linked: the server keeps its last good state, and nothing new loads until it is fixed.
  - **Changes.** Any `Cargo.toml` change, including in a git-ignored folder outside `target`, checks the linked and refused manifests again and looks up the open files: a deleted manifest drops out, its files fall to a manifest above or become loose, and a manifest appearing around a loose file takes it over. The refresh does this rather than the notification, so a check already running cannot overwrite the outcome. A project stays after its files close, since unloading would mean indexing it again. A loose file does not, since it costs nothing to bring back.
  - **Limit.** `MAX_OPENED_RUST_PROJECTS` caps what a session adds, with one notice, and the inline project of all loose files counts as one. A restart brings it back down to what is open.
- **Environment.** `rustAnalyzerEnv` pins the toolchain and takes the tool settings away from cargo's configuration files, which cargo reads even for `cargo metadata`: `RUSTUP_TOOLCHAIN`, `CARGO`, `RUSTC`, empty `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `CARGO_ENCODED_RUSTFLAGS` and `CARGO_ENCODED_RUSTDOCFLAGS`, `CARGO_TARGET_APPLIES_TO_HOST` and `CARGO_UNSTABLE_HOST_CONFIG`, `CARGO_NET_OFFLINE` and `CARGO_NET_GIT_FETCH_WITH_CLI`, and a `PATH` without worktree entries. `cargo.target` rather than `CARGO_BUILD_TARGET` overrides the target, since cargo joins that variable with a list in the configuration. The cost is that flags and a cross target from cargo's configuration do not apply to what the server sees.
- **Formatting.** `suppressedFeatures` drops `textDocument/formatting` and `textDocument/rangeFormatting`, which `rust-analyzer.toml` can point at a command of its own.
- **Client methods.** `blockedClientMethod` keeps out what could start something or undo the settings, whether or not Loxel's client sends it today: `didSave` (the server then reads `checkOnSave` per source root, where `rust-analyzer.toml` applies), `didChangeConfiguration`, formatting, `executeCommand` and the server's own `rust-analyzer/` and `experimental/` methods. The client's own `initializationOptions` are dropped too.
- **Client capabilities.** `withRustClientCapabilities` adds to `initialize` what only this server wants. `serverStatusNotification` is the only way it reports dependencies it could not read, and `readServerStatus` turns the status into what to run, per project, naming the folder of any but the worktree's own; the frame goes no further. `documentation` in `resolveSupport` is because rust-analyzer offers `completionItem/resolve`, and so auto-imports, only when a property other than `additionalTextEdits` is resolvable.
- **Restarts.** The manager re-plans after each toolchain resolution (`subscribeRustToolchain`) and closes with `LSP_RESTART_CLOSE_CODE` when the plan's `key` changes or the plan is now a refusal. A failed check restarts too. A server that could not start reconnects from the client when its worktree's toolchain changes ([rust-lsp-client.ts](../../src/lib/rust-lsp-client.ts)). A toolchain gone to `none` leaves the running server alone, since it may be an install in progress and the server is pinned to what it was given.
- **Watched files.** `forwardWatchedFiles`: rust-analyzer registers absolute globs for `.rs` and `.md` files, manifests and its own config, per crate root as well as per workspace. `didSaveOnFileChange` must stay off, see the client methods above.

### Project files

A manifest counts when it is a regular file of at most 1 MiB, through `readConfigFile`, whose real path stays in the worktree. That holds for the ones found at startup too.

## Formatting

[rust-formatter.ts](../../src/server/rust-formatter.ts) is the `LanguageFormatter` for `.rs` (see [Formatting](../LANGUAGE_SERVERS.md#formatting)). It targets what `cargo fmt` would produce for the file, through `rustfmt` on stdin, since `cargo fmt` itself rewrites files on disk and ignores stdin.

- **Detection.** `detect` walks from the file's directory to the worktree root for a `Cargo.toml` or a rustfmt config, read with `readConfigFile`, so only a regular file of at most 1 MiB counts. It runs on every save, uncached.
- **Edition.** `--edition` comes from the nearest manifest's `[package] edition`, `edition.workspace = true` from the nearest ancestor's `[workspace.package] edition`, and a package naming none gets `2015`, as Cargo does. It goes along even when the config sets `edition`: `cargo fmt` passes the flag too and the flag wins, which was checked across crate and config edition combinations. A manifest without `[package]` passes none. When the edition can't be told (a broken manifest, a missing workspace, a value that is not a year), `detect` returns null: formatting with a wrong edition would rewrite the file in that edition's style. Per-target editions in `[lib]` or `[[bin]]` are out of scope.
- **Config.** `--config-path` is the nearest `.rustfmt.toml` or `rustfmt.toml`, in rustfmt's own preference order, relative to the worktree because format-service splits args on whitespace. A relative path that still has whitespace declines with a notice. With no config in the worktree rustfmt searches from its cwd, the worktree root, upward, which is the same as `cargo fmt` above the root.
- **Spawning.** `spawnOptions` takes `tools.rustfmt` of an `active` toolchain from `getRustToolchainNow`, makes its directory the whole `PATH`, and sets `rustToolEnv` plus `RUSTUP_TOOLCHAIN` at the resolved name, also without a user choice, so the run uses the toolchain that was resolved and the status bar shows. Any other status, a null tool, a failed lookup, or a lookup slower than 3 s skips the spawn rather than falling back to a `rustfmt` on `PATH`; the first save of a worktree is what can wait on a resolution, and the skip keeps it from holding up the write. A command other than `rustfmt` is a manual override and only gets `RUSTUP_AUTO_INSTALL=0`.
- **Notices.** `skip` covers what the toolchain already knows (`unusableNotice`, `missingComponentNotice`). `failureNotice` covers rustup's own errors for a toolchain or component removed since the resolution, recognized at the start of a stderr line, because rustfmt quotes source lines with a prefix. Every other non-zero exit stays quiet, syntax errors and a broken rustfmt config included.

## Editing behavior

[rust-language-config.ts](../../src/lib/rust-language-config.ts) re-registers Monaco's Rust `conf` after the built-in registration, in the same order as Python's (see [Highlighting and language resolution](../LANGUAGE_SERVERS.md#highlighting-and-language-resolution)). `rust-language-config.test.ts` checks that order and the resulting editing behavior.

- **On-enter rules** continue `///`, `//!`, `/** */` and `/*! */`. A `*` line continues only when its star sits one space past an even indent and the line above is part of the comment, which keeps rustfmt's `    * factor` lines out.
- **Auto-closing pairs** add `/**`, `/*!` and backticks. `'` is left out because it starts lifetimes. The block comment pairs use `notIn: ["string"]` only: Monaco checks the token before the cursor, which after `/*` is already a comment.
- **Folding markers** are `// region` and `// endregion`, replacing the C `#pragma region` markers in Monaco's `conf`.
- **A keydown hook** makes the `/` that ends an auto-closed block doc comment replace the inserted ` */`, since Monaco overtypes only the first character of a multi-character pair. It skips string tokens, where nothing was auto-closed, and tracks comment nesting on the line, so closing a plain comment inside a doc comment keeps the outer close.

## File recognition

`.cargo/config`, Cargo's older config name, resolves to TOML through a glob association in [settings-store.ts](../../src/store/settings-store.ts), since `config` alone says nothing about the format. A bare `rust-toolchain` stays plain text because its legacy format, a single channel name, is not TOML.
