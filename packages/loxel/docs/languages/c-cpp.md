# C and C++

C, C++ and Objective-C files are served by clangd. Shared language-server architecture: [LANGUAGE_SERVERS.md](../LANGUAGE_SERVERS.md).

## Manager

| Manager                                                         | Binary   | Args                                                                                                                                                                                       | Scope    | Flags and config                                                                                                                 |
| --------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| [clangd-lsp-manager.ts](../../src/server/clangd-lsp-manager.ts) | `clangd` | `--resource-dir=<dir>` (bundled) `--compile-commands-dir=<dir>` (see Compile database) `--limit-references=0 --rename-file-limit=0 --header-insertion-decorators=0 --query-driver=<globs>` | worktree | suppresses formatting and range formatting; untrusted: validates compile flags from project configuration before starting clangd |

[clangd-lsp-client.ts](../../src/lib/clangd-lsp-client.ts) binds the Monaco languages `c`, `cpp`, `objective-c` and `objective-cpp`, and shows the server's `window/showMessage` warnings. clangd ignores `languageId` and takes each file's language from its compile command.

## clangd

- **Binary.** On macOS, [download-clangd.ts](../../scripts/download-clangd.ts) ships the release's binary, thinned to the build machine's architecture and stripped, with its `lib/clang/<major>` minus the sanitizer runtimes as `clangd-resource`. A version upgrade changes no path, since the resource directory's name has no version in it. The manifest is limited to `darwin` with `platforms`, so other platforms build nothing for it. `resolveBinary` depends on [repository trust](../LANGUAGE_SERVERS.md#repository-trust). In a trusted repository it takes the login-shell `PATH`'s clangd, Xcode's included, if `checkClangd` passes it, and otherwise falls back as below; nothing is fetched in either mode. In an untrusted one `resolveBundledBinary("clangd")` looks for a sibling of the server, then the `PATH`, and Xcode's isn't taken, under any path. `checkClangd` reads `--version` from the filesystem root in both modes, and without the developer tools refuses `/usr/bin/clangd` on macOS without running it, since Apple's stub can raise the install dialog. `resolveBinary` returns null with a reason for `serverFailureReason`, which the start-failed path shows: what to install when none is found; that Xcode's clangd isn't supported; the minimum for a clangd older than 16, which would exit at once on the flags below; a version it can't read; and Windows, whose user config directory no environment variable selects (see Compile flags).
- **Trust.** `repoTrustRestriction` opts in to restarting on a change of trust. `reportsRestrictionAtStart` is off, since only `resolveBinary` knows whether anything is held back: it reports when the user has a clangd that would pass, saying the bundled one runs instead, or, with nothing bundled (Linux), that only system compilers are asked. With no usable clangd of the user's it reports nothing, so the UI doesn't ask. What trust changes is the binary, the `--query-driver` value and whether the Compile flags config applies; a trusted repository that falls back to the bundled binary still gets the last two.
- **Resource directory.** clangd finds the compiler's own headers, such as `stdarg.h`, relative to itself, and the bundled binary has no such tree beside it, so without one even C files fail to parse. `--resource-dir` points at `clangd-resource` when that directory is beside the bundled binary that resolved. A clangd from `PATH` keeps its own headers, which must match it. `share/` stays in the tree because clang's driver reports an error for `-fsanitize=cfi` without its ignorelist. An in-place update replaces the directory whole (`UPDATE_RESOURCE_DIRS` in [main.ts](../../src/electron/main.ts)).
- **Flags.** The defaults cap references at 1000 and renames at 50 files, which cuts results short on real projects, hence `--limit-references=0` and `--rename-file-limit=0`. `--header-insertion-decorators=0` keeps completion labels free of the marker clangd adds for an inserted include. The background index stays on (the default).
- **`--query-driver`.** clangd asks a compiler for its include paths when the path of the compiler a compile command names matches these globs, by running it. In a trusted repository the value is `**`, so that a cross-compiler or wrapper works under any name and in any location, the project included. Otherwise `queryDriverGlobs` lists only compiler names (`*gcc*`, `*g++*`, `*clang*`) in `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin`, and never widens to a whole directory, `**` or anything inside a worktree.
- **Compile flags.** In a trusted repository clangd starts with the user's own `HOME` or `XDG_CONFIG_HOME` and reads their config itself, with none of what follows. Otherwise, compile flags that make the compiler write output files have no place in an editor session, and clangd takes flags from several places: compile databases, `compile_flags.txt`, `.clangd`, response files and compiler config files. `prepareClangdUserConfig` removes them where clangd combines those sources, in clangd's user config, which applies after every project's. Each spawn writes `<state dir>/clangd-config/.../clangd/config.yaml` and points clangd's process at it: `HOME` on macOS, `XDG_CONFIG_HOME` elsewhere, the variables clangd finds its user config directory through. Failing to write the file fails the start. The file holds `CompileFlags` with `Remove` and `Add`, then the user's own clangd config, as a later document, so a user's config that does not parse cannot affect the first one, and edits to it apply at the next start. Flags reached through `-Xclang` are listed by their frontend spelling, which makes clangd drop the `-Xclang` and any value with them; `-Xclang` itself stays because real builds use it (CMake's precompiled headers). `-Xpreprocessor`, `-Wp,` and `/clang:` are removed whole. Two flags on which clangd never finishes a file are removed too. The tests in [clangd-lsp-manager.test.ts](../../src/server/clangd-lsp-manager.test.ts) run real clangd over each source when one is on `PATH`.
- **Environment.** The redirected `HOME` on macOS, in an untrusted repository, only affects what clangd resolves through it: the user config, and the default module and global index caches, which end up under the state directory. The SDK comes from `xcrun`, which clangd runs at every start and which needs `/usr/bin` on `PATH`; the spawn's login-shell environment provides it, also when Loxel starts from Finder.
- **No developer tools.** `/usr/bin` holds Apple's stubs, which offer to install the developer tools when they are missing, and the bundled clangd, or one from Homebrew, runs on Macs without them. When `xcode-select -p` fails, clangd starts with `/usr/bin` removed from its `PATH` and from `--query-driver` (in a trusted repository, whose `**` would match it, a list of the top-level directories compilers live in replaces `**`), so it runs neither `xcrun` nor a stub compiler a compile database names, and the git check for the index directory (below) runs with the same `PATH`, with the background index off if that leaves no git. It then has no SDK, so standard headers are not found, and `onClientInitialized` sends a `window/showMessage` warning saying what to run. The check runs again at each start.
- **Formatting.** clangd advertises formatting, range formatting and on-type formatting. The first two are suppressed, since format on save owns formatting ([Formatting](#formatting)). The on-type provider stays registered and does nothing, as Loxel's editors do not enable `formatOnType`.
- **Completion.** Snippets stay on for argument placeholders. clangd escapes placeholders but writes names into snippets unescaped, so `escapeSnippetDollars` escapes a `$` that is neither one of its tabstops nor already escaped in completion results, which keeps `my$fn` from inserting a snippet variable. Includes for symbols from the index arrive as `additionalTextEdits`.
- **Semantic tokens.** On. clangd's legend includes `macro`, `modifier`, `operator`, `bracket`, `label`, `concept` and `unknown`, and `#if 0` regions arrive as `comment` tokens.
- **Index.** The background index is written to `.cache/clangd/index/` under the directory holding the compile database, with its own `.gitignore`, so it stays out of git status and the worktree watcher's change batches. Without a compile database clangd writes no index. `indexDirectoryIsSymlink` skips the background index (`--background-index=false`) when that directory or a parent up to `.cache` is a symlink, at the worktree's root, beside a database passed with `--compile-commands-dir`, or tracked by git at any depth, or when the folders down to such a database inside the worktree include one, so index files aren't written outside the project tree. In an untrusted repository it is also off when a `.clangd` names a database folder outside the worktree. The check runs at each start, when one of those paths changes, and when a database or `.clangd` does (see Changes on disk).
- **Diagnostics and code actions.** Diagnostics are push only, `.clang-tidy` checks run inside clangd with no separate binary, and unused includes arrive tagged as unnecessary with a removal fix. Quick fixes come back only when the request echoes the diagnostic, which monaco-lsp-client does, as inline `edit.documentChanges`. Tweaks are commands (`clangd.applyTweak`) that reach the client back as `workspace/applyEdit`. clangd registers no file watchers.
- **Changes on disk.** clangd registers no file watchers, ignores `workspace/didChangeWatchedFiles`, and the client never sends `textDocument/didSave`, so `ClangdLspManager` overrides `notifyWatchedFilesChanged` and `notifyIgnoredPathChanged` and acts on changes itself instead of telling the server, which leaves it no use for `forwardWatchedFiles`. Paths in git-ignored directories are where compile databases and generated headers are, and also dependency trees, so they cause everything below except the restart for the index. [clangd-file-changes.ts](../../src/server/clangd-file-changes.ts) classifies each path and owns one set of timers per session, which closing the session cancels; the manager tracks the session's open documents. Clangd's own index writes under `.cache/clangd/` and anything that is neither C-family nor configuration are dropped. Paths are recognized by name, so a header without an extension, or a directory moved or swapped whole (which reports only the directory), triggers nothing until another change does.

  | Change                                           | Trigger                                                                                                                   | When                               | Why then                                                                                                                                                                             |
  | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | C-family source or header, open or not           | `didSave` of one open document, which makes clangd check them all                                                         | 500 ms of quiet, at most 5 s       | A `git checkout` arrives in several batches                                                                                                                                          |
  | `compile_commands.json`, `compile_flags.txt`     | the same `didSave`, twice                                                                                                 | 6 s and 31 s after the last change | clangd caches a file it found for 5 s and one it did not for 30 s, and a trigger inside the window is lost, so each change is covered for both rather than working out which applies |
  | Any of those four files                          | the compile database resolution and the index directory check again, and a restart if the flag or the index should change | 200 ms after the last change       | See Compile database                                                                                                                                                                 |
  | `.clangd`, `.clang-tidy`                         | `didChange` with no `contentChanges` and `forceRebuild: true`, per open document                                          | 6 s after the last change          | `didSave` does not re-run diagnostics when the compile command is unchanged, so a `.clang-tidy` or a `Diagnostics`-only `.clangd` needs a rebuild                                    |
  | `.cache`, `.cache/clangd`, `.cache/clangd/index` | `indexDirectoryIsSymlink` again, and on yes a restart                                                                     | 100 ms and 3 s                     | The session respawns under the check its start makes; again at 3 s, since a `git checkout` updates git's index last                                                                  |
  | Source or header that is not open                | a restart                                                                                                                 | 60 s of quiet                      | See below                                                                                                                                                                            |

  The rebuild carries the version the client last sent, which the manager tracks: without one clangd numbers the rebuild itself and stamps its quick fixes with a version the client does not have, and monaco-lsp-client refuses those. An unsaved open header is not seen by other open files; only what reaches the disk is.

- **Index freshness.** The index notices a disk edit to a file that is not open only when the file is opened or the index loads, and no trigger above reaches it. Loading compares every shard with its file's content and reindexes only what differs, so a restart (`LSP_RESTART_CLOSE_CODE`) brings it current: the load finished in under a second on fmt (33 commands) and curl (362), while the client reconnects and opens its documents again, whose preambles clangd then rebuilds, which is the larger cost on heavy C++. So only files that are not open and not git-ignored count (the open file's text already reaches the index, and a dependency install is no reason to restart), it waits for 60 s of quiet so that a burst of edits costs one, and there is at most one per worktree every 5 minutes. With nothing open it stays pending for the next file opened. With the index off, or no `compile_commands.json` found from any open file or in the folder passed to clangd, it does not happen.

## Compile database

Without a database clangd guesses a file's flags, with wrong errors and missing includes, and nothing says why. [compile-database.ts](../../src/server/compile-database.ts) works out what clangd will use and the status item ([c-cpp-toolchain-status.ts](../../src/server/c-cpp-toolchain-status.ts), [c-cpp-compile-database.ts](../../src/lib/c-cpp-compile-database.ts), [CompileDatabaseStatus.tsx](../../src/components/panels/CompileDatabaseStatus.tsx)) shows it, through the [toolchain status seam](../LANGUAGE_SERVERS.md#toolchain-status-items). Nothing is run or written; there is no activation step, so no toolchain environment contributor either.

- **Mirroring clangd.** No client-visible signal says which database a file uses (`clangd.fileStatus` has none, only `--log=info` lines), so the resolver follows clangd's rules, measured on 23.1.0. In each folder from the file's upward, the first of `compile_commands.json`, `build/compile_commands.json`, `compile_flags.txt` wins, even when the file isn't listed in it; `build/compile_flags.txt` is not looked at. A `compile_commands.json` clangd cannot load is passed over for the next one, so both ends of the file are checked for a JSON array rather than parsing what can be hundreds of megabytes. The nearest `.clangd` with `CompileFlags.CompilationDatabase` goes first: a path, relative to that file, is the only place looked at, and `None` turns the database off. A `.clangd` document with an `If` isn't evaluated for the status, since that means running a repository's regular expressions, but it still keeps the flag away (below). The user's own clangd config isn't read.
- **`--compile-commands-dir`.** It applies to every file of a session and beats `.clangd`, so it would override per-file discovery: in a monorepo, one subproject's flags get "inferred" for another's files. It goes only where clangd finds nothing anywhere in the worktree. `resolveCompileDatabases` searches the source tree for what clangd would find (`findClangdsOwn`). It has no depth limit, since a project missed would lose its database, but limits on the folders walked and the `.clangd` bytes read; past either, `searchCut` keeps the flag away, as does a `.clangd` that can't be read whole if it may name a database. It also looks for non-standard candidates directly under the root: `cmake-build-*/`, `build-*/`, `build/*/`, `out/*/`, `out/build/*/`, and any folder a configure step has marked with `CMakeCache.txt`, `build.ninja` or `meson-info`, each with a real `compile_commands.json`. A marked folder below the root with no `CMakeLists.txt` or `meson.build` of its own is build output, not a project, as clangd finds a database in it only for files inside it; a worktree nested in this one isn't a project either. Build output is still looked through for `.clangd` files, for the index rule below. Both use `fs`, since these folders are git-ignored, and neither follows a symlink. Exactly one candidate is used by itself, the same rule as Python's environments; with several, none is. A choice stored per worktree ([compile-database-store.ts](../../src/server/compile-database-store.ts)) comes first, may be outside the worktree, and overrides per-file discovery by being explicit.
- **Per file and per worktree.** The seam's status route is per worktree; `POST /api/compile-database/file` answers for the active file, with what to run when it has none. Its query key extends the status's, so the changed message refreshes both. Each request and each clangd start resolves afresh rather than keeping a memo, since a session's events are all that could keep one current and none arrive without a session; requests arriving during a look share the one after it.
- **Keeping current.** `databasesChanged` in [clangd-file-changes.ts](../../src/server/clangd-file-changes.ts) re-resolves on the events `notifyWatchedFilesChanged` and `notifyIgnoredPathChanged` bring, with paths inside git-ignored directories included: that is where build folders are. Such an event also counts as a change for the status item, as it can change one file's answer and not the worktree's. Each session subscribes and restarts when the folder it started with is no longer the one to use, or the index should go off or come back. A writer that truncates its database first can cost two restarts, one when the file stops looking loadable and one when it is complete. A session also resolves once on subscribing, for a change between its start's look and the subscription. A choice outside the worktree has no events, so it is only looked at again on a request or start.

## Formatting

[clang-formatter.ts](../../src/server/clang-formatter.ts) is the `LanguageFormatter` for the C-family extensions of `EXT_TO_LANG`, which a test keeps in step since the server does not import the highlighter. `.m` and `.i` are left out: they are also MATLAB and SWIG, which clang-format rewrites with exit 0, so they format only through a manual override, which then runs with the seam's defaults (seam: [Formatting](../LANGUAGE_SERVERS.md#formatting)).

- **Detection.** clang-format applies LLVM style and exits 0 when it finds no config, so the module only returns it when a `.clang-format` or `_clang-format` lies between the file and the worktree root. clang-format itself then finds the nearest config from `--assume-filename` and handles `InheritParentConfig`.
- **Binary.** The user's `clang-format` from `PATH`, with the worktree's directories removed and `binDirs` empty. It runs from `/` with an absolute `{file}`, so that what it resolves to does not depend on files in the repository. It reads config only and runs no repository code, so it does not depend on repository trust. A manual override of `clang-format` runs the same way, since `spawnOptions` covers overrides, so a relative path in its args is relative to `/`.
- **Ignore files.** Current clang-format honors `.clang-format-ignore` on stdin only for a file already on disk, and older versions not at all, so a first save or an older binary would rewrite an ignored file. `detect` applies the nearest ignore file itself and returns null with no notice. The matcher follows clang's `MatchFilePath.cpp`, matching bytes as it does, with memoized positions and a budget of steps since the patterns come from the repository, and the walk stops at the worktree root. Setting `LOXEL_TEST_CLANG_FORMAT` to a binary makes the tests compare their cases with its `--list-ignored`.
- **Failures.** A syntax error in the code never fails: clang-format formats what it can and exits 0. A non-zero exit whose stderr has one of its config error lines is a config it cannot use, and `failureNotice` passes that line on. The client shows a notice's text once per session.
