# Java

Java files are served by Eclipse JDT LS (jdtls), which Loxel bundles and runs on the user's JDK, and every Java feature shares one per-worktree JDK choice. Maven and Gradle projects load only in a trusted repository, from what is already on the machine. Shared language-server architecture: [LANGUAGE_SERVERS.md](../LANGUAGE_SERVERS.md).

## Manager

| Manager                                                     | Binary                    | Args        | Scope    | Flags and config                                                                                                                                                  |
| ----------------------------------------------------------- | ------------------------- | ----------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [java-lsp-manager.ts](../../src/server/java-lsp-manager.ts) | the user's JDK 25+ `java` | `jdtlsArgs` | worktree | watched files; settings at `initialize` and pushed after `initialized` and when JDKs change; per-file indentation pulled; drops `willRename` and two code actions |

## Binary

[download-jdtls.ts](../../scripts/download-jdtls.ts) fetches the jdtls release, one archive for every platform, unmodified apart from an added `LICENSE` and `NOTICE` at its top level, about 53 MiB. The `jdtls` directory is in `UPDATE_RESOURCE_DIRS`, since stale jars next to new ones would break the server. The macOS natives inside its jars are signed by the Eclipse Foundation, and natives for other platforms stay inside jars, so no foreign binary sits loose in the app.

## Choosing the JVM

jdtls itself needs Java 25, although `bin/jdtls.py` says 21: on 21 the JVM exits with code 13 without answering `initialize`, and the reason is only in a log. `resolveBinary` runs the newest entry of `listJavaRuntimes` at that level or above, by absolute path through `javaExecutable`, which the [trust rule](#jdk-detection) has already passed. In an untrusted repository `isJdkInWorktree` also rules out a JDK inside the worktree, by real path, through `canRunJdtls`, which the status item uses too. There is no `PATH` lookup and nothing else runs a `java`. Without one it starts nothing and `serverFailureReason` says what to install, or, through `noJdkReason`, that the JDK it found is inside the repository.

The client then stops. `subscribeJavaStatus` in [java-toolchain-status.ts](../../src/server/java-toolchain-status.ts) reports a change when a JDK that can run the server appears or goes, including when trust changes which ones can, even though the worktree's own JDK stays the same, and [toolchain-server-recovery.ts](../../src/lib/toolchain-server-recovery.ts) reconnects the Java client on that message if it stopped because it could not start, so installing one brings the server back. A client stopped for another reason stays stopped, in particular one another window took over.

## Java levels

`javaRuntimesSetting` turns `listJavaRuntimes` into `java.configuration.runtimes`: the newest JDK of each level, with `sources` from its `src.zip`, which is where hover documentation comes from. The worktree's JDK from `getJavaEnv` takes its level's place and is `default`, so the JVM's own level does not decide what a project compiles against. The manager follows `subscribeJavaEnv` and pushes the setting when it differs, so a JDK installed or chosen while the server runs applies without a restart. The exception is a change of the chosen JDK in a trusted repository with a Gradle project, which restarts the server: Gradle's daemon runs on that JDK, and jdtls checks the pairing only as it starts.

## Starting the server

The JDK's `java` runs directly, with `-jar` on the launcher and no shell.

- `-configuration` is writable, in `<state>/jdtls/configuration/<core plugin file name>`, because the signed app is not. `osgi.sharedConfiguration.area` points read-only at the bundled `config_<platform>`.
- `-data` is per worktree path, `<state>/jdtls/data/<hash>`, since two same-named projects in one directory collide. A trusted server has its own, `<state>/jdtls/data-trusted/<hash>`, because a workspace goes on holding the projects it imported, and that one is deleted when its server closes after trust is taken back. Both are deleted when the worktree is removed, in Loxel or from outside it, or when the server exits if it was still running then. A moved worktree starts a new one. A new server waits for the previous one on its worktree to exit first, since the directory takes one server at a time, and the JVM's working directory is this directory rather than the worktree.
- `serverFailureReason` reports the last `!MESSAGE` of the newest log written since the server started in the configuration directory, which is the only place a JVM that cannot start explains why.
- `-Xmx1G` with `ParallelGC` tuned to return memory. Resident memory is about 900 MB on a project of 300 files, most of it not heap: a cap of 512 MB saves 50 MB and one of 256 MB starts slower and still leaves 640 MB. A trusted server gets `-Xmx2G`, for a loaded project's model: gson and retrofit reach about 1.2 GB resident, with Gradle's daemon on top.

## Project import

`repoTrustRestriction` opts the manager into [repository trust](../LANGUAGE_SERVERS.md#repository-trust), so a server's settings, flags and workspace directory are fixed by `repoTrusted` for its life and it restarts when the answer changes. `reportsRestrictionAtStart` is false: the manager calls `reportRepoRestriction` itself once `findBuildProjects` finds a build file, or when one appears, so a repository of loose Java files is not asked about. The status bar stays out of it while the repository is untrusted, where the trust UI explains what is left out.

### Untrusted

The server starts with project import off and makes no network requests.

- `java.import.maven.enabled` and `java.import.gradle.enabled` are false, `java.import.exclusions` is `["**"]` and `java.autobuild.enabled` is false. Each session gets them in `initializationOptions`, because jdtls reads those before its first import, and again through `workspace/didChangeConfiguration`. `notifyConfigurationChanged` sends `settings: null`, which jdtls ignores.
- `-Djava.import.generatesMetadataFilesAtProjectRoot=false` is a JVM property, not a setting; as a setting it does nothing.
- `-Djdk.net.hosts.file` points at a file naming only `localhost`.
- [audit-jdtls.ts](../../scripts/network-audit/audit-jdtls.ts) checks all of this through the built `loxel-server`, on opening files and on every command a user can reach, with `--control` as its positive control. Run it after changing the pin or the manager.

Each folder gets one invisible project. jdtls infers its source root from the first Java file it hears about, and `initialize` comes before any file opens, so `firstJavaFile`, a pruned walk that runs while the session's frames are held, passes one as `triggerFiles`. A file with a build file in its folder or above stays outside any project, and reports "non-project file" or "not on the classpath", "only syntax errors are reported".

### Trusted

Maven and Gradle projects load through `trustedJavaSettings`, with the exclusions back at jdtls's defaults and autobuild on, and nothing is fetched. [java-project-import.ts](../../src/server/java-project-import.ts) holds what follows; `audit-jdtls.ts --trusted` checks it, down to Gradle's daemons, with `--trusted --control` as the positive control.

- **Offline.** `java.import.maven.offline.enabled` and `java.import.gradle.offline.enabled` are on, and downloading sources and updating snapshots are off. `importJavaToolOptions` goes in `JAVA_TOOL_OPTIONS`, so every JVM under the server has it: the hosts file above and an HTTP proxy that goes nowhere. It cannot go in `java.import.gradle.jvmArguments`, which replace the repository's `org.gradle.jvmargs`.
- **What can load.** `findBuildProjects` finds build files by name and `planImport` holds back a Gradle root that would need to fetch Gradle to start: `wrapperDistribution` looks for the wrapper's own `.ok` marker, under the hash of `distributionUrl` as its `PathAssembler` computes it. A root without a wrapper needs `localGradleHome`, an installation found from `GRADLE_HOME` or `PATH` by looking for `lib/gradle-launcher-*`, since jdtls would otherwise use its bundled version, which Gradle's tooling API downloads. A held-back root goes in `java.import.exclusions`, or turns Gradle off when it is the worktree itself, because an exclusion cannot name the folder the server is rooted at. Setting `java.import.gradle.version` is not an option: it asks `services.gradle.org` for the list of versions.
- **Which JVM.** `java.import.gradle.java.home` is the worktree's JDK, since the daemon otherwise takes the server's and old Gradle cannot run on it. `java.configuration.runtimes` does not reach Gradle's toolchains, so `-Porg.gradle.java.installations.paths` lists the JDKs in `java.import.gradle.arguments`, next to `auto-download=false`.
- **Daemons.** `gradleClientFlags` sets `org.gradle.daemon.registry.base` and `org.gradle.daemon.idletimeout` on the server's JVM rather than in `java.import.gradle.arguments`, because Gradle's client reads them from its own system properties on every connection. A worktree's daemons register in `<data>/gradle-daemons`, so they are never reused by or from the user's. `stopGradleDaemons` runs when the server has exited, and `destroy` waits for it: it stops the process ids named by the `daemon-<pid>.out.log` files there, once `lsof` shows that process holds that log, since a daemon has its log open and a process that took the id later does not. Removing a worktree stops them the same way before deleting the directory. A daemon that outlives that, because Loxel died or on Windows, leaves on its idle timeout of 10 minutes.
- **What the server says.** `ServiceReady` fires after a failed import too, so `importSignal` reads `language/status` `ProjectStatus`, `language/eventNotification` 300 (Gradle cannot run on the JDK), and errors in `publishDiagnostics` on anything that is not a Java file, since build problems go to `pom.xml`, `build.gradle` and project folders. `projectIssue` turns those and the held-back roots into `JavaEnvResponse.projectIssue`, and a change sends `java_env_changed`. [JavaRuntimeStatus.tsx](../../src/components/panels/JavaRuntimeStatus.tsx) shows it while a Java file is active, and clicking it calls `POST /api/java-env/reload-projects`, which restarts the server. Other errors on a build file, such as a plugin that failed to run, don't count while the import succeeded.
- **Following changes.** `java.configuration.updateBuildConfiguration` is `automatic`, so jdtls follows edits to the build files it knows. `notifyWatchedFilesChanged` plans again when a build file or a wrapper's properties change, pushes the settings if what is held back changed, and sends `java.project.import` for a build file in a new folder, which a watched-file event alone does not import; the answer never reaches the client. `watchedIgnoredGlobs` covers generated sources, which are usually ignored by git. A checkout of 264 files settles in seconds with no restart.

`-Djava.import.generatesMetadataFilesAtProjectRoot=false` applies here too, so `.project`, `.classpath`, `.settings` and `.factorypath` stay out of the tree. `target/`, `bin/` and `.gradle/` are written, as a build would.

## Formatting

[java-formatter.ts](../../src/server/java-formatter.ts) is the `LanguageFormatter` for `.java` (seam: [Formatting](../LANGUAGE_SERVERS.md#formatting)), with [java-format-declaration.ts](../../src/server/java-format-declaration.ts) reading what a project declares. A project opts in, because many Java projects declare no formatter and formatting them would rewrite every file saved. Spotless and the project's build are never run: Spotless's IDE hook runs build code, is slow from cold, and can report a dirty file clean when Gradle considers its task up to date.

Detection is `findJavaFormatDeclaration`, text only and synchronous. It walks `dirsUpToRoot` and the nearest directory with something to say decides, each `pom.xml`, `build.gradle.kts` and `build.gradle` parsed once per content. It recognizes Spotless's `googleJavaFormat` and `palantirJavaFormat`, in an applied Maven plugin's `<java>` block and as Gradle calls with their chained options, `fmt-maven-plugin` from `com.spotify.fmt`, `com.spotify` or `com.coveo`, and Palantir's `com.palantir.java-format` plugin. A `pluginManagement` entry counts only for a POM that applies the plugin, from that POM up, and `apply false` makes a Gradle plugin no signal until a module applies it. Spotless with only other steps says nothing, while Spotless formatting Java with `eclipse` or `prettier` ends the walk, so a module doing that does not inherit its parent's formatter. Configuration in convention plugins, `apply from` scripts or a parent POM not in a directory above is not seen, by design: following them is the build's job.

A version comes from the same text: a literal, a Maven property in this POM or one above it, a Gradle variable from the script or `gradle.properties`, a version catalog entry, or, for Palantir's plugin, the plugin's own version, since the two are released together. A value must look like a version, as it goes into a cache path and a notice. A reference that cannot be followed declines, as does an option value that is not a literal, and the `toggleOffOn` and `groupArtifact` settings and Palantir's `formatJavadoc`, none of which the command line can reproduce. Spotless with no version declines, because it picks one itself by its own release and the JVM, which no file shows, and any other version could rewrite the project. `fmt-maven-plugin` with no override takes the version named by the plugin's published POM in the user's Maven cache, and declines when that is not there. So a declaration always ends in a pin or a decline.

Flags reproduce the build rather than the command's defaults. Spotless leaves long strings alone and always removes unused imports. It sorts imports in Google order unless `reorderImports` asks for the style's, so AOSP without it adds `--skip-sorting-imports`, because the command would sort in AOSP order; an `importOrder` step adds it too, as that step has the last word. `fmt-maven-plugin` also defaults to leaving long strings alone. The Palantir command defaults to Google style, so `--palantir` is explicit. These flags left gson and retrofit unchanged on every sampled file, and conjure-java on all but its generated sources.

A save also checks that the file is one the declaration formats, and if it is not, the file goes out unformatted with no notice. Spotless for Maven covers its `<includes>`, by default `src/main/java` and `src/test/java`, minus its `<excludes>`, and `fmt-maven-plugin` the same two folders. Spotless for Gradle covers `target` minus `targetExclude`, by default any file, since source sets cannot be read as text, and never a project's `build` directory. Globs are relative to the declaring project's directory, or for Maven and a Gradle script with `subprojects`, `allprojects` or `configure`, to any directory between it and the file that has a build file. A form that cannot be read as plain globs (a variable, `fileTree`, `targetExcludeIfContentContains`, Maven's `<skip>` set, or the fmt plugin's settings that move its files) covers nothing, since a file it excludes could be rewritten. Settings passes no file name, so this check does not apply to what it lists.

The formatter's `prepare` picks what runs, since it needs to run things. Unlike `FormatterSpawnOptions.skip`, it can replace the command and arguments, which the cache route needs, and it never runs for a manual override, which a project's pin does not bind. `FormatService` caps the whole of it for a save at 5 s and declines with a notice past that. What it leaves running can still finish, so a slow first check serves the next save:

1. A tool on the trusted part of `PATH` (`trustedPath`), without version managers' shims, in a `shims` directory or linked to one. A launcher script is fine, as Homebrew's is one. The first whose `--version` matches runs, asked from the filesystem root by absolute path and cached by path, size and mtime.
2. For google-java-format, the jar a build left in `~/.m2/repository` or Gradle's `modules-2/files-2.1`, with the newest guava, failureaccess and commonmark jars in the same caches, none of which shape the output. Palantir's jar has no such small dependency set, so it has no cache route. Which JDK runs a version follows no simple rule (1.23 fails on Java 25, 1.30 needs 21), so `jdkRunning` tries the worktree's JDK and then the newest, on a small source reaching the late-loaded classes, keeps a JDK that ran it while that `java` stays the same file, and an answer of none while the JDKs on offer stay the same, unless a try timed out. A jar inside the worktree is not used. A cache path holding whitespace or `:` is skipped, as the seam splits arguments on whitespace.
3. Otherwise a decline naming the version and how to get it, since another version would rewrite what the pinned one left alone.

Everything spawned starts from the filesystem root with a `PATH` holding no worktree directory, so nothing from the repository runs and no repository trust is involved. A syntax error exits 1 with empty stdout and only logs. Format Document stays with jdtls's own formatter.

## Terminals

[java-toolchain-env.ts](../../src/server/java-toolchain-env.ts) is Java's [toolchain contributor](../TERMINALS.md#toolchain-environments). It contributes only when `getJavaEnv` answers with `source: "override"`, as Go's does for a chosen Go, and with no setting, like Go's and Node's.

- **Detection changes nothing.** `resolveJavaEnv` takes the newest JDK and reads no version pins, while the shell's `java` or `JAVA_HOME` may be what a project builds with, so a detected JDK would change a working build. It also means a new shell with no choice reads one store key and starts no process, in every repository.
- **A choice that stops qualifying.** Resolution falls through to detection, so `source` differs and the shell keeps its `JAVA_HOME`, stale or not.
- **Which JDKs.** The resolver's [trust rule](#jdk-detection) already refuses one with files git tracks. On top of that, `isJdkInWorktree` refuses one whose home or `bin` is in the worktree, by real path, unless `isRepoTrusted`, and `reportRepoRestriction` says so. `commitToolchainEnvChange` checks the path's characters and leaves the whole contribution out, `JAVA_HOME` included. A path holding `PATH`'s delimiter is left out too.

## Client capabilities

`extendedClientCapabilities` is not sent, so code actions come back with `data` and resolve to plain edits. jdtls resolves only the actions of its latest answer.

- `workspace.fileOperations.willRename` is removed from the `initialize` response. jdtls's rename edit already holds every reference, and `WorkspaceEditApplier` asks `willRenameFiles` for each rename operation in an edit, so a class rename would be applied twice.
- `dropUnusableActions` removes the actions that run `java.action.applyRefactoringCommand`, a client command that needs a prompt, and `Ignore compiler problem(s)`, which has neither an edit nor a command.
- Lenses are off (`referencesCodeLens`, `implementationCodeLens`), since their commands are the client's own in VS Code.
- `language/status`, `language/eventNotification` and the other custom notifications reach the client, which drops them with a debug log. `ServiceReady` does not mean analysis finished or that a project loaded, so tests wait for diagnostics on an opened file.

## Settings it pulls

jdtls pulls only `java.format.tabSize` and `java.format.insertSpaces`, per file, to indent the code it generates. `workspaceConfiguration` answers from the file's first indented line.

## Watched files

jdtls registers its watchers after `ServiceReady`, as `**/*.java`-style globs, absolute globs, and `{baseUri, pattern}` entries in `file:/` single-slash form. The base forwards all three. Changes from `git checkout` and agents reach it the same way.

## JDK detection

[java-env.ts](../../src/server/java-env.ts) is the single resolver of a worktree's JDK, and of the JDKs on the machine, for every feature that needs one. It returns a `JavaEnv` from [java-env-model.ts](../../src/api/java-env-model.ts): a `JavaRuntime` (`path` of the JDK home, `majorVersion`, `version`, `implementor`) and its `source`.

- **What counts as a JDK.** `readJdk` reads a home without running anything: `bin/java` and `bin/javac` executable, `lib/ct.sym` or a `jmods` directory (JDK 24 made `jmods` optional and Temurin 25 has none; earlier builds have both), and a `release` file whose `JAVA_VERSION` parses. A JRE and a `jlink` runtime have no `javac` or `ct.sym`, and a wrapper script has no `release`. `jdkAt` accepts a directory as the home itself, as a macOS bundle (`Contents/Home`), or as Homebrew's formula directory (`libexec/openjdk.jdk/Contents/Home`, or `libexec` on Linux).
- **Resolution.** `resolveJavaEnv(wtPath, options)` tries, first hit wins: the chosen override, `JAVA_HOME`, the JDKs `/usr/libexec/java_home -V` lists, the JDK of the first real `java` on the login-shell `PATH`, then the install locations of `javaInstallRoots`. Several in one source: the newest wins, by Java level and then the rest of the version. That needs no configuration and matches `java_home`'s own default; pinning a version per project is out of scope here. It never throws. An invalid `JAVA_HOME` is reported as `ignoredJavaHome`, since a stale value is common and otherwise looks like a detection bug.
- **Nothing is run.** No `java` is ever executed. The only process resolution starts itself is `java_home`, which on a Mac without Java prints an error and exits 1 without a dialog (the dialog is `--request`, never passed); git runs for the trust rule below. `isMacOsJavaStub` recognizes `/usr/bin/java`, Apple's launcher that may offer to install Java when run. A version manager's shim is a script outside any JDK, so it fails `readJdk` and the search moves to the next `PATH` entry. Nothing is downloaded or installed: Loxel never fetches a toolchain itself.
- **Trust rule.** `isJdkShippedByRepo` applies the [environment trust rule](python.md#environment-trust-rule) through `isEnvShippedByRepo` from [shipped-by-repo.ts](../../src/server/shipped-by-repo.ts): a JDK with any file git tracks, or whose `java` or its symlink target is tracked, is refused from every source. It also refuses a home that is, or holds, the worktree, where that rule looks only at a Python environment's own entries. The path a JDK was found through is checked as well, and on `PATH` the `java` itself, since a committed symlink can reach a real JDK.
- **Shared resolution.** `subscribeJavaEnv(wtPath, listener)` keeps a worktree's resolution memoized while anyone is subscribed, and `getJavaEnv(wtPath)` answers from it (an unsubscribed worktree resolves afresh). Subscribing starts nothing: the first `getJavaEnv` does, so a worktree without Java spawns nothing and adds no watches. The memo is replaced on the shared watch, on `refreshJavaEnv` (the override changed), on `refreshAllJavaEnvs(changedNames)` when a login-shell capture changed a variable resolution reads, and when `getJavaEnv` finds the repository now tracks the settled JDK. Listeners hear every finished resolution as `{ env, first, changed }`, also when the JDK stayed the same, since another may have appeared. Through [java-toolchain-status.ts](../../src/server/java-toolchain-status.ts), each worktree's resources subscribe and send `java_env_changed` when `changed` (see [Toolchain status items](../LANGUAGE_SERVERS.md#toolchain-status-items)).
- **All JDKs.** `listJavaRuntimes(wtPath)` returns every usable JDK from every source, each once by physical path, newest first, so the first of a `majorVersion` is the newest of that level. It is what a feature needing one JDK per Java level consumes.
- **Watching.** One watch serves every resolved worktree (`syncSharedWatch`), rebuilt only when its targets change, and debounced: each install root, unfiltered; a missing root's deepest existing ancestor, for the next path segment; an entry of a root that is not a complete JDK yet, since an installer filling it is not reported by the root's non-recursive watch; and each `JAVA_HOME`, chosen or resolved home, for being removed, replaced or created. Roots are this platform's only, a filesystem root is never watched, and a replaced watch overlaps its replacement for a moment, since a platform watch can start late. A `java` appearing on `PATH` is not watched: the login-shell capture covers a changed `PATH`, and JDKs reach `PATH` through the watched locations. A non-recursive watch of a home directory costs little: 80,000 file events below the watched directory took about 250 ms of CPU, measured on macOS.
- **Choosing a JDK.** `normalizeJavaOverride(wtPath, input)` turns a path the user entered (`~/` allowed, a home, bundle, Homebrew directory or `bin/java`) into a JDK home, or throws a user-facing error. [java-override-store.ts](../../src/server/java-override-store.ts) stores the choice per worktree in `stores.db`, and it is deleted with the worktree. Because the resolver reads it, every feature gets the choice without state of its own. An override that stops qualifying falls through to detection and stays stored, so the status bar can warn.
- **API.** `GET /api/java-env?wt=` returns `{ env, overridePath, ignoredJavaHome, projectIssue }`; `GET /api/java-env/candidates?wt=` returns `{ candidates, automatic, overridePath }`; `POST /api/java-env/override` with `{ worktreePath, javaHome }` validates and stores the choice (`null` clears it) and answers like the first route; `POST /api/java-env/reload-projects` with `{ worktreePath }` restarts the server so its projects load again. `wt` must be a worktree of a registered project. The routes are in [java-toolchain-status.ts](../../src/server/java-toolchain-status.ts), and the renderer calls them from [java-env-client.ts](../../src/api/java-env-client.ts). The renderer side is [java-runtime.ts](../../src/lib/java-runtime.ts) (labels and the picker, run by the `java.selectRuntime` action) and [JavaRuntimeStatus.tsx](../../src/components/panels/JavaRuntimeStatus.tsx) in the status bar, shown while the active editor's file resolves to Java or [Kotlin](kotlin.md#jdk), both registered in [java-toolchain-status.ts](../../src/lib/java-toolchain-status.ts).
