# Shared server and multiple windows

How every Loxel window shares one Bun server process, how the app starts, restarts and stops that server, and why this design was chosen over one server per window.

## Model

One server runs per mode, on a well-known port: `7433` in production, `7434` in dev and `7435 + n` for [demo](ELECTRON.md#demo-mode) instance n (`src/server/config.ts`; `LOXEL_SERVE_PORT` overrides it for a standalone server, but Electron and the `loxel` CLI always use the well-known ports). Each mode also has its own state directory (`~/.local/state/loxel/loxel-dev`, `.../loxel`, and `.../loxel-demo` or `.../loxel-demo-<n>`), so no two share a server or its state. The app is a single Electron process, and every window it opens ("New Window" in the File and Dock menus, or a native window tab) connects to that one server over WebSocket and REST.

Running one server instead of one per window removes a whole class of cross-process problems for every feature that touches the filesystem or persistent state:

- **Git** — all Git commands run in one process, so windows never contend for `index.lock`.
- **Watchers** — one set of watchers and one `git status` per event, whatever the window count (see [WATCHERS.md](WATCHERS.md)).
- **Write nonces** — all clients share one nonce store, so the window that saved a file suppresses its own echo while every other window viewing the file receives `file_content_changed` as an external change.
- **Caches** — directory caches and Git status snapshots are shared rather than duplicated.

## One app process

A packaged app takes Electron's single-instance lock (`src/electron/main.ts`). A second launch of the same app, such as `open -n` or the binary run directly, focuses a window of the running one and exits. So exactly one Electron process owns the server, and no other process runs from the bundle when a full-app update replaces it (see [ELECTRON.md](ELECTRON.md#updates)). Dev builds take no lock, because vite-plugin-electron starts a rebuilt Electron before the old one has exited. They keep their own Electron data directory (the app's with a `-dev` suffix), so a dev app's browser panels never share a profile with the installed app's. A second dev app finds the first one's app-owned server on the dev port and fails to start once the 15-second wait runs out.

## Starting and restarting the server

`startAppServer()` in `src/electron/main.ts` runs on app start, before the first window opens. It spawns the server and waits until `GET /api/version` answers. In dev that is `bun run src/server/index.ts` with `LOXEL_DEV=1`, and in [demo mode](ELECTRON.md#demo-mode) from the source tree the same source with the built renderer. In production it is the bundled `loxel-server` binary, with `LOXEL_STATIC_DIR` set to the bundled renderer.

- **A server already on the port.** `GET /api/version` reports `appOwned` for a server an app started, and `shuttingDown` once it is draining before it exits. The `loxel` CLI treats a draining server as gone and waits for its replacement, its open requests retrying while no server answers. The app does not take a draining server for a foreign one: it waits for it to exit before starting its own, since the port stays bound until then. Such a server is one a previous run of the app left shutting down, including, in dev, the one an Electron restarted on a main-process rebuild leaves behind. Launch waits up to 15 seconds for it to go, then fails with a startup error naming the port. Any other server was not started by an app. In dev, it is a dev server started by hand (`pnpm run dev:server`), and the app uses it without restarting or stopping it. When it later shuts down (a hand-started server does when idle), the next window the app opens starts the app's own server. In production, it is one from an earlier version, which can stay up for 5 minutes after its last window closed, or one started by hand, so launch fails at once with an error saying so.
- **One start at a time.** Startup, reopening from the Dock and New Window all join the start already in flight (`startAppServer()`), so the app never spawns two servers. New Window requests that arrive before startup has opened the first window are ignored, as are second launches.
- **Crashes.** Any exit the app did not ask for counts as a crash. The app restarts the server with linear backoff (1s, 2s, 3s), with a single restart in flight at a time. Terminals survive it: they run in [terminal hosts](TERMINAL_HOST.md), and the restarted server reattaches them. A server that stayed up for a minute gets a fresh retry budget. After three crashes in quick succession, the app reports the failure and quits. A quit while a restart is pending starts the server at once, only to hand it the shutdown message, so the terminals get the fate the quit asked for rather than their hosts' grace period.

## Server lifecycle

The server lives as long as the app:

- **The app's channel.** The app spawns its server with a fourth pipe, the server's file descriptor 3 (`PARENT_CHANNEL_FD` in [parent-channel-protocol.ts](../src/parent-channel-protocol.ts)), open for the server's whole life, with one JSON message per line; the only one is `shutdown`, with what happens to the terminals (`end` or `keep`). [parent-channel.ts](../src/server/parent-channel.ts) reads it in a server the app started, from the first line of `server.ts`, so a quit while the server is still starting stops it too: it waits until startup has found the terminal hosts, leaves them as the message asks, and exits without serving. Meanwhile it holds the port, answering `/api/version` with `shuttingDown`, so an app relaunched in that time waits for it rather than start a server that takes the hosts while this one leaves them; one that finds the port taken leaves the hosts alone. A server that has not reached them within 30 seconds exits anyway, leaving the terminals to their grace period. The channel is not stdin, which carries only the data encryption key and is closed after it ([STATE_AND_STORAGE.md](STATE_AND_STORAGE.md#secrets)): `Bun.$` and `Bun.spawn` with `stdin: "inherit"` give the server's children its stdin, so an open one would reach every git command, hook and credential helper, which could read the app's messages or wait on them. Bun passes no descriptor above 2 to a child, which [parent-channel.test.ts](../src/server/parent-channel.test.ts) pins.
- **Quit.** There are three ways to leave, which `QuitPlans` in [quit-plan.ts](../src/electron/quit-plan.ts) tells apart: Quit (⌘Q, and every quit the app did not start itself, such as the Dock's or logout's) ends the terminals; Quit and Keep Terminals (⌥⌘Q) keeps them; Restart Loxel keeps them and calls `app.relaunch()`. The app menu and the command palette (over IPC) request a plan just before `app.quit()`, and `before-quit` takes it, so a quit that a window cancelled leaves nothing behind for the next one. On `will-quit`, after every window has closed, the app waits up to 2 seconds for the layout promotes the windows sent as they closed, then writes the shutdown message and closes the channel. Restart arms its relaunch there, once the quit is certain. The server keeps answering API requests until none has been in flight or started for 300 ms (5 seconds at most; `/api/version` polls do not count), so a save that is still formatting or a closing window's last store write lands, then tears down, ends or keeps every terminal through its host, and exits on its own. SIGTERM still shuts the server down ending the terminals. During an update install the app does not wait for promotes, and one that did not land is recovered when the next server starts (see [STATE_AND_STORAGE.md](STATE_AND_STORAGE.md)). A relaunched app finds the old server still draining and waits for it, as on any launch (see [Starting and restarting the server](#starting-and-restarting-the-server)).
- **An app that crashed or was killed.** Its end of the channel closes without a shutdown message, and the server shuts down. As a backstop, the app passes its process ID in `LOXEL_PARENT_PID`, and the server checks every 2 seconds that it is still that process's child, and shuts down once it has been reparented, which a reused process ID cannot fake (`src/server/server.ts`). Either way it leaves the terminals to their hosts' grace period, as after a crash, so a relaunched app within 10 minutes reattaches them. It removes the variable from its environment at startup (`src/server/config.ts`), so a server started from a Loxel terminal does not take the app for its parent.
- **No windows.** macOS keeps the app running with every window closed. When the last app client disconnects, detached terminal sessions get 5 minutes to be reattached, for example by a window opening again or the machine waking from sleep. Then they are destroyed, including a terminal that was still starting when the last window closed. The server itself keeps running.

A server started without `LOXEL_PARENT_PID`, such as `pnpm run dev` in a browser or a test server, shuts itself down instead. That happens 30 seconds after the last app client disconnects, or at the end of the 5-minute grace period when detached sessions are alive.

The renderer's WebSocket client reconnects on its own, so windows survive a server restart. On reconnect it compares the server version with the one it first saw and reloads the page when it changed.

## State scopes

The server keeps state at these scopes (`src/server/server-state.ts`):

| Scope                    | Lifetime                              | Shared across windows?                                                                                                                             |
| ------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ProjectState`           | per registered repo, server lifetime  | Yes — one watcher, review database and worktree status list per repo                                                                               |
| `WorktreeResources`      | first subscriber to last              | Yes — file services and undo/redo history are shared by every window on the worktree                                                               |
| `ClientState`            | per app WebSocket connection          | No — its terminals, subscriptions and window ID belong to that connection                                                                          |
| Terminal sessions        | create to destroy, in a terminal host | No — output goes to the owning connection; sessions detach on disconnect and can be reattached, also by the next server process                    |
| Language-server sessions | per language-server WebSocket         | Partly — worktree-scoped managers keep one process per worktree path (see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md)); only YAML is per connection |

Undo/redo is per worktree, so two windows on the same worktree share one history; that matches the single filesystem they both edit.

## Persistent state

Only the server opens the SQLite databases (WAL mode, 5-second busy timeout); what lives in the state directory is listed in [STATE_AND_STORAGE.md](STATE_AND_STORAGE.md#server-state-directory). Server logs are written per process to `logs/server-{instanceId}.log`, and log files of other instances are cleaned up after 24 hours, so overlapping processes (for example a server shutting down while its replacement starts) never write the same file. Terminal hosts, which can run for days, log to `logs/terminal-host-{hostId}.log`, which that cleanup skips; the server removes a host's log a day after the host is gone ([TERMINAL_HOST.md](TERMINAL_HOST.md#files-on-disk)).

Internal temporary worktrees (used for diagnostics of past commits) are named with `INTERNAL_WORKTREE_PREFIX`, hidden from worktree lists, and pruned when a project is initialized, so ones left behind by a crash do not accumulate. Pruning must not remove a temp worktree that another server using the same repository (for example the dev and production servers) is still using.
