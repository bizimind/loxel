# Terminal host

The terminal host is the part of Loxel that owns terminal sessions: the PTY and its program, the headless emulator, stream offsets and epochs, the resume ring, snapshots, flow control, and detection of notification sequences. Everything else about terminals is policy and stays in the server: which shell runs and with what environment, toolchains and the Python shim, which clients a session streams to (one attachment in the host, fanned out by the server), orphans, worktree lifecycle, settings and notifications. The server reaches sessions only through the `TerminalHost` interface.

The sessions run in `loxel-terminal-host`, a separate process started detached from the server, so a server crash, a restart or a dev `--watch` reload leaves every shell running, and the next server reattaches to them. Inside it, `InProcessTerminalHost` runs the sessions; the server reaches it over a Unix socket through `SocketTerminalHost`, one per host, and `TerminalHostPool` puts every host the server uses behind the one interface. What a session does with its bytes (attach, snapshot, resume, flow control) is in [TERMINALS.md](TERMINALS.md#server-terminal-sessions).

## The boundary

Nothing under `src/terminal-host/` imports from `src/server/`, directly or through what it imports, so the host can run without the server and outlive it. The host's own entry point makes the bundler hold to it too: `loxel-terminal-host` contains only what `main.ts` reaches. [import-boundary.test.ts](../src/terminal-host/import-boundary.test.ts) walks the import graph of every file in the folder, type imports included, and fails with the chain of imports that reaches a server module. What both sides need lives where neither pulls in the other, and imports nothing itself:

- [terminal-stream.ts](../src/api/terminal-stream.ts): `TerminalState`, what a `state` event carries and `terminal_state` forwards, next to the binary frame codec the renderer and the server share.
- [terminal-limits.ts](../src/api/terminal-limits.ts): the size and scrollback bounds and their clamps, which the host enforces whatever it is sent.

The host never reads settings. What the process running it provides is passed in as a `TerminalSessionRuntime`: a logger (typed by `ChildLogger` from [log-entry-model.ts](../src/api/log-entry-model.ts)), which the host process gives from its `HostLog`, and `measureSpawn`, which wraps each PTY spawn for the host's [perf monitor](#perf-monitor). The server counts output for the stress detector from the `output` events it receives.

## The interface

Everything that crosses the interface is plain data: strings, numbers, JSON objects and `Uint8Array` payloads. Commands return nothing or a promise of data, and everything the host has to say arrives as an event, so the interface is carried over a socket without callbacks into the server. The data types are inferred from zod schemas in [terminal-host.ts](../src/terminal-host/terminal-host.ts), which the protocol validates against.

**Commands**

| Command                                                                                               | Effect                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `spawn({ id, epoch, argv, cwd, env, cols, rows, scrollbackLines, meta, input? })`                     | Start a session and resolve to its `TerminalSessionInfo`. The caller picks the `epoch`, a random UUID per spawn. `argv` and `env` are complete: the host adds no shell and inherits no environment. `input` is written to the PTY first, typed ahead. Rejects, with the cause, if the ID is in use or the program cannot start |
| `list()`                                                                                              | Every session: `{ id, epoch, offset, pid, cols, rows, meta, ended? }`; `ended { exitCode, outputKept }` marks a session that ended while no server was connected (see [Ended sessions](#ended-sessions))                                                                                                                       |
| `attach({ id, attachment, since? })`                                                                  | Bind the client, replacing any attached one; resolves once its `state` event is out, or once it was superseded. An ended session sends its state and the output the client missed, then its `exit`                                                                                                                             |
| `detach(id)`                                                                                          | Stop sending output; the program keeps running and its output keeps being parsed                                                                                                                                                                                                                                               |
| `write(id, data)`, `resize(id, cols, rows)`, `setScrollback(id, lines)`, `ack(id, syncOffset, bytes)` | As in [TERMINALS.md](TERMINALS.md#server-terminal-sessions)                                                                                                                                                                                                                                                                    |
| `destroy(id)`                                                                                         | Hang up and kill the program, or forget an ended session; the session is gone at once                                                                                                                                                                                                                                          |
| `setMeta(id, meta)`                                                                                   | Replace the session's meta                                                                                                                                                                                                                                                                                                     |
| `foregroundProcesses()`                                                                               | Each session's foreground program by ID: its name, or null when the shell is at its prompt. A host that cannot tell (one without capability `foregroundProcess`) leaves its sessions out                                                                                                                                       |
| `onEvent(listener)`                                                                                   | Subscribe to events; returns the unsubscribe function                                                                                                                                                                                                                                                                          |

A command naming an unknown ID does nothing, since a session can end on its own at any time.

**Events**

| Event                                       | When                                                                                                                                                                                                                                                                                |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state { attachment, state }`               | For every attach and every flow-control resync, before any output at or past `state.offset`                                                                                                                                                                                         |
| `output { id, offset, data, frame }`        | Output for the attached client, in offset order, only after that client's `state`. `frame` is the renderer's binary output frame, encoded once by the session; `data` is a view of its payload, not a copy. The server sends `frame` to the WebSocket as is                         |
| `exit { id, epoch, exitCode }`              | The program ended on its own, after a final snapshot to its attachment, if any; the session is already gone. For one that ended while no server was connected, after the attach that drained it                                                                                     |
| `ended { id, epoch, exitCode, outputKept }` | A session the client knew running is listed ended when its connection is restored; the host keeps it for an attach to drain. Only `SocketTerminalHost` reports it, and it never crosses the socket                                                                                  |
| `lost { id, epoch, reason }`                | The session is gone without its exit code: its host is gone, the program with it (`host_lost`), or it ended while the server was not connected to a host that did not keep it (`exit_unknown`). Only `SocketTerminalHost` reports it, never a host, and it never crosses the socket |
| `unresponsive { id, epoch }`                | The session's host stopped answering, or cannot be reached while its process runs ([Unresponsive hosts](#unresponsive-hosts)). Nothing ended: output resumes once the host answers. Only `SocketTerminalHost` reports it, and it never crosses the socket                           |
| `osc { id, epoch, code, data }`             | The emulator parsed OSC 9, 777 or 99, attached or not; `data` is the raw payload                                                                                                                                                                                                    |

**Meta.** Each session carries a JSON object the server sets at spawn and with `setMeta`, and reads back with `list()`. The host stores it as given and never looks inside, so the server can keep new fields there without changing the host. The server's shape is `TerminalMeta` in [terminal-manager.ts](../src/server/terminal-manager.ts): the panel's `worktreePath` (null for a Home terminal), the shell's starting `cwd`, and the creating `windowId`.

**Notifications are reported raw.** The host reports every OSC 9, 777 and 99 sequence with its payload, unfiltered and unparsed. The manager drops the ones the settings disable and reads the rest with [osc-notification-parser.ts](../src/lib/osc-notification-parser.ts), so a change to the settings or the parsers never involves the host.

## Ordering

The interface promises an order that does not depend on the host running in the same process:

- Commands apply in the order they are sent. `spawn()` registers the session before it returns, so a `write`, `attach` or `destroy` sent before it resolves applies to the new session. Events of the new session, an `exit` included, can likewise arrive before the spawn's answer.
- A session's `state` precedes the output that follows it, and its `exit` comes last.

The manager relies on that order, not on timing, to tell which events are current, because events already on their way can be stale by the time they arrive:

- **Attachments.** Every attach carries an `attachment` number, unique across the manager's attaches, and the host echoes it on every `state` that attach produces. The manager forwards a state only when it matches the session's latest attach, so a resync meant for an attachment since replaced never reaches a client. Output frames carry no attachment: the manager forwards them to its live clients, which a replaced attachment's frames still suit, since the host sends the new attach's state only once everything before its offset went to the attachment it replaces; once the last client has detached, it forwards nothing until the next attachment's state. Numbers only have to be unique among the attaches one caller sends to one host: the host keeps only the latest attach per session and never compares numbers, so a server that starts over begins its own sequence. Output frames themselves stay in the renderer's frame layout, without an attachment.
- **Epochs.** `exit` and `osc` carry the session's epoch. The manager picks the epoch of each spawn, so it knows it before any event of the session can arrive, and a session destroyed and respawned under the same ID gets a new one: an exit or notification from the earlier spawn does not end or notify its replacement.
- **Destroy is silent.** A destroyed session never sends `exit`, even when its program ends later. This is part of the contract: the manager removes the session itself when it asks for the destroy, and the `onExit` hook is only for programs that ended on their own.

## The process

`loxel-terminal-host` is its own binary, compiled from [main.ts](../src/terminal-host/main.ts), not the server started with a flag: the host outlives the server and may be of another version than it, and it shows up under its own name in Activity Monitor and `ps`. It is started with `--run-dir`, `--socket-dir`, `--host-id` and `--log-file`, listens on `<socket-dir>/<host-id>.sock`, writes its entry to `<run-dir>/<host-id>.json`, and prints `ready` on stdout once both exist; then it points stdout at `/dev/null`. It ignores SIGHUP, takes SIGTERM and SIGINT as an order to end every session and exit, and logs an uncaught exception rather than exit with every shell.

[host-launcher.ts](../src/terminal-host/host-launcher.ts) starts it with `Bun.spawn({ detached: true })`, which calls `setsid`, so the host leads its own session and no signal to the server's process group reaches it, and `unref()`s it. It gets `/` as its working directory and only `HOME`, `TMPDIR` and `LANG` of the environment, since every session brings its whole environment; its stdin is closed and its stderr goes to `<log-file>.stderr`, for what the runtime itself prints, such as a crash report. What starts it depends on how the server runs:

| Server                                                           | Host                                                                                                                     |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Packaged (`loxel-server`, a compiled binary)                     | The `loxel-terminal-host` bundled next to it, cloned to `<stateDir>/terminal-host/bin/<hostBuildId>/` and run from there |
| Built as a bundle (`pnpm run build`, `bun dist/server/index.js`) | `dist/server/terminal-host.js`, with the same Bun                                                                        |
| From source (dev, tests)                                         | `src/terminal-host/main.ts`, with the same Bun; nothing is copied                                                        |

**The clone.** A packaged host never runs from the app bundle, so an update can replace the bundle under running hosts (the invariant in [ELECTRON.md](ELECTRON.md#updates)), and no host depends on a deleted file staying mapped. `installHostBinary` copies the bundled binary with `COPYFILE_FICLONE`: on APFS a copy-on-write clone that takes no space, elsewhere a plain copy. It copies to a temporary name and renames it into place, so a binary at the final path is always whole, and it copies only once per build. The clone keeps the binary's code signature, which notarization covers like the rest of the bundle. electron-builder signs `Resources/` binaries with its default inherited entitlements (JIT, unsigned executable memory, no library validation), never the app's restricted ones, so the clone needs no provisioning profile to launch.

**The host build ID.** A hash of the host's minified bundle, the Bun version and the CPU architecture, so comments, formatting and releases that do not touch the host keep the ID, while an app moved to another architecture (an Intel build under Rosetta that electron-updater moves to the Apple silicon one) neither reuses a host nor a clone of the other's. The architecture is that of the process computing the ID: the release builds each architecture on a machine of its own, and a server run from source runs its host with its own Bun. [build-server.ts](../scripts/build-server.ts) computes it with `computeHostBuildId` and embeds it in both the server and the host as `LOXEL_TERMINAL_HOST_BUILD_ID`; run from source, the server computes it at startup the same way (a bundle of the host's source, about 10 ms) and passes it to the host with `--build-id`.

## Generations

Hosts are one per host build ID, not one per terminal (a Bun runtime per shell would cost too much with many agents) and not one per app release:

- New sessions spawn in the current generation's host: a running host whose build ID is this build's, or else one started the first time a session is spawned. A release that leaves the host's code and the Bun version alone keeps the ID, so its server reuses the hosts already running on the same architecture.
- A host of another build keeps serving the sessions it has; once its last session ends, the server disconnects from it with `end`, and it exits. Host fixes so reach every new terminal at once, and no host is ever upgraded in place.
- At startup the server removes `bin/<hostBuildId>/` directories that are neither this build's nor run by a live host. A host it could not check counts as live with the build its entry names; while a host that may be running has no known build (no entry, and no answer), it removes none.
- `runsOnOtherBuild(id)` tells a session in a host of another build. `GET /api/terminals` reports it as `otherHostBuild` ([running-terminals-model.ts](../src/api/running-terminals-model.ts)), and the terminal's tab says so in its tooltip and offers Restart Terminal ([restart-terminal.ts](../src/lib/restart-terminal.ts)). It asks first, naming the foreground program when the host can tell; then the panel's session is destroyed and the panel takes a new terminal ID, so its next attach spawns a shell from the same spawn target in the current host, and output of the old session still on its way never reaches the new xterm.

## Protocol

A host speaks over its socket in frames: a 4-byte big-endian body length, then the body. A body starting with `{` is a JSON message; any other body is a binary terminal frame in the renderer's layout ([terminal-stream.ts](../src/api/terminal-stream.ts)): keyboard input as input frames `[0x02][id][payload]` to the host, output as output frames `[0x01][id][u64 offset][payload]` from it, which the server forwards to the renderer as they came. The JSON messages are zod schemas in [protocol.ts](../src/terminal-host/protocol.ts), the single source of truth for them; the version, `TERMINAL_HOST_PROTOCOL` (`1.3.0`), is in [terminal-host-protocol-version.ts](../src/api/terminal-host-protocol-version.ts), which imports nothing, so the Electron updater and the release workflow read the same constant (see [Versioning](#versioning)).

**The bootstrap layer is frozen**, so that any server can identify and stop any host, even one of an incompatible major version: the framing, and

| Message                                                                     |                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `initialize { protocol, build, capabilities }`                              | The server's first message; nothing else is valid before it, and a connection that sends something else is closed                                                                                                 |
| `initialize_result { protocol, hostBuildId, pid, capabilities, sessions? }` | The host's answer, whatever protocol the server speaks: the server decides whether it can go on. `sessions` (since 1.1.0) is how many sessions it runs, so a server that ends it can say how many terminals ended |
| `disconnect { sessions: "end" \| "keep" }`                                  | The server is leaving, ending its sessions or keeping them                                                                                                                                                        |
| `terminate`                                                                 | End every session and exit                                                                                                                                                                                        |
| `superseded`                                                                | From the host to a server another server has taken it over from, right before it closes that connection: the server must not reconnect                                                                            |

Frozen means only ever gaining optional fields: no field of the bootstrap layer is removed, renamed or retyped, and every reader tolerates an optional field's absence, since a peer from before it leaves it out (a 1.0.0 host sends no `sessions`). The schema guard holds the layer to it.

**The versioned layer** carries the interface. Requests carry a `requestId` and are answered by `result { requestId, value }` or `error { requestId, message, cause? }`, and the requester parses `value` with the schema of what it asked for.

| Server to host                                                                                                                      | Host to server                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spawn { requestId, request }` (typed-ahead input follows as an input frame), `list { requestId }`, `attach { requestId, request }` | `result`, `error`                                                                                                                                                                   |
| `detach`, `resize`, `set_scrollback`, `ack`, `destroy`, `set_meta` (no answer); input frames                                        | `state`, `exit`, `osc` events, output frames, and `log { level, msg, ctx, cat? }` (`cat` since 1.3.0)                                                                               |
| `foreground_processes { requestId }`, capability `foregroundProcess` (1.1.0)                                                        | `result` with `{ [id]: program \| null }`                                                                                                                                           |
|                                                                                                                                     | Capability `endedSessions` (1.2.0): `ended` in `list`'s sessions. To every server: `osc` events queued while no server was connected, right after `initialize_result` (since 1.2.0) |

**Compatibility.** `compatibility(host, server)` is the one function that decides: a different major, or a version that is not semver, is `incompatible`, and the server ends the host with `terminate` (a SIGTERM to its pid if it does not close its socket within 2 seconds). Otherwise the result is `compatible`, or `degraded` when one side has capabilities the other lacks; either way each side uses only the capabilities both advertise, checked by name, never by comparing versions (see [Capabilities](#capabilities)).

## Versioning

`TERMINAL_HOST_PROTOCOL` is semver, and says what a peer of another version can still read. Every merge to main releases the app, so each version ships the moment it lands, and a host of any earlier version may still be running somewhere with its shells.

| Change                                                                                         | Bump                                                       |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| A fix that changes no message                                                                  | patch                                                      |
| A new optional field, a new message, a new capability                                          | minor, with a new capability gating any new message        |
| A message, field or capability removed; a field renamed, retyped, or made required or optional | major: an older peer would misread it                      |
| The bootstrap layer                                                                            | only ever a new optional field (minor); nothing else, ever |

A major bump is costly: a server cannot talk to a host of another major, so installing the update ends every running terminal (the app warns first, see [ELECTRON.md](ELECTRON.md#updates)), and a server that meets such a host at startup ends it. Prefer a capability.

**The schema guard.** [protocol-schema.test.ts](../src/terminal-host/protocol-schema.test.ts) compares the message schemas and each request's answer (`RESULT_SCHEMAS` in protocol.ts, which the client parses answers with), as JSON Schema, and the capabilities with [protocol-schema.snapshot.json](../src/terminal-host/protocol-schema.snapshot.json). It fails when they changed without the bump [protocol-snapshot.ts](../src/terminal-host/protocol-snapshot.ts) works out, naming the bump and the version to set, and also for a new message without a new capability and for any change to the bootstrap layer other than an optional field, a new bootstrap message included. The binary frames' layout is not JSON and not covered: it changes only with a major bump. After the bump, `UPDATE_PROTOCOL_SNAPSHOT=1 bun test src/terminal-host/protocol-schema.test.ts` refreshes the snapshot.

**Releases.** The release manifest's `terminal_host_protocol` is the version a release speaks, and the app updater compares its major with this build's before installing ([ELECTRON.md](ELECTRON.md#updates)). Every running host speaks this build's major, because the server ends any other at startup and starts hosts only of its own build, so that one comparison says whether an update restarts the terminals.

**Ended hosts.** When `start()` ends incompatible hosts (after a downgrade, or an update whose manifest did not say), it reports them with the session count each gave in `initialize_result`, and the server raises one notification, "N terminals were ended (incompatible terminal host)", from [ended-hosts-notice.ts](../src/server/ended-hosts-notice.ts). It is kept in the notification store, so the first window to connect gets it. Without a count from every host (a 1.0.0 one gives none), it says "Terminals were ended" instead.

### Capabilities

A capability is an optional feature of the versioned layer, named in `TERMINAL_HOST_CAPABILITIES` in [protocol.ts](../src/terminal-host/protocol.ts) and advertised by both sides in the handshake. Its messages go only to a peer that advertises it too, so an older peer without it and a newer peer with capabilities this side does not know both keep working. `foregroundProcess` is the first, and the reference for the pattern:

- **Name it.** Add the name to `TERMINAL_HOST_CAPABILITIES` with the version it came in, and bump the minor version.
- **Add its messages** to the versioned layer, saying which capability they belong to. The host implements them and, by listing the name, advertises them.
- **Gate the server's use.** `SocketTerminalHost` keeps, per connection, the capabilities both sides advertise (`sharedCapabilities()`), and `supports(name)` checks one. A method of the capability returns a fallback without it and never sends the message: `foregroundProcesses()` answers `{}`, also while the connection is being restored, since the caller is waiting, and its callers fall back to what they know without it (the update and quit confirmations then only count the terminals).
- **The other direction.** A capability the host uses on its own, an event for example, is checked the same way against the capabilities in the server's `initialize`.
- **Test both skews**, as [capabilities.test.ts](../src/terminal-host/capabilities.test.ts) does: a host without the capability is never sent its messages, and a host with a capability the server does not know is used for the ones it does.

`endedSessions` is one the host uses on its own: see [Ended sessions](#ended-sessions). The server sends nothing new for it, and reads `ended` wherever a host gives it; the host checks the server's `initialize` for it, and a server without it gets no ended sessions, as from a host before it.

`foregroundProcess` reports each session's foreground program for the confirmations before an update install and a quit: the PTY's foreground process group (`ps -o tpgid`) named by its leader (`ps -o comm`), or null when that group is the session's own program as it was spawned, a shell at its prompt; a session whose program `exec`'d another reports that one. A terminal whose program cannot be named (its terminal or the group's leader gone) is left out. The pool takes each session's answer from the host it routes the session to.

## Lifetime

A host serves one server at a time. The connection that sent the latest `initialize` is its server; one that was connected before is sent `superseded` and closed, and whatever it sent that the host reads afterwards is ignored, so a replaced server cannot end or touch the sessions its successor took over. Whenever its server changes or leaves, the host detaches every session, so no `state` or output meant for an earlier server's client reaches the next one, and the new server's attachment numbers start their own sequence. Events go to the current server; answers go to the connection that asked.

| The server...                                                                                                | The host                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| sends `disconnect { sessions: "end" }` (a quit that ends the terminals, a standalone server's idle shutdown) | Ends every session                                                                                                            |
| sends `disconnect { sessions: "keep" }` (a quit that keeps the terminals, Restart Loxel, an update install)  | Keeps the sessions with no deadline, until a server comes back                                                                |
| closes its connection without one (a crash, the app crashing, a dev `--watch` restart)                       | Keeps the sessions for `TERMINAL_HOST_GRACE_MS` (10 minutes); a server that connects meanwhile cancels it, otherwise they end |
| sends `terminate`                                                                                            | Ends every session and exits                                                                                                  |

A host with neither a server nor sessions left exits, removing its socket and entry. A new host waits the grace period for its first server.

### Ended sessions

While no server is connected, what the sessions do waits for the next one (capability `endedSessions`), so a restart, a crash or a reconnect does not swallow an agent's closing output, its exit code or the notification it raised:

- **Exits.** `TerminalHostService` has `InProcessTerminalHost` keep a session whose program ends, its PTY closed, instead of reporting its exit: `list()` reports it with `ended { exitCode, outputKept }`, the next attach gets its state and the output its client missed, resuming or with a snapshot like any attach, and then its `exit`, and `destroy` forgets it. Only an attach that is still the session's once its client is synced reports the exit: each attach gets a token of its own from `TerminalSession`, which any later attach (whatever its attachment number, since a restored connection re-sends one under the same number), detach or destroy makes stale, so whatever came after decides. Once a server is connected, exits are reported as they happen again; sessions that ended before stay until attached or destroyed.
- **The server learns of it at once**, from the list it takes at startup (`adopt`) or when it restores a connection (an `ended` event from `SocketTerminalHost`). `TerminalManager` records how it ended: it is no longer listed as running, and it is not an orphan, so no orphan timer ends it. It waits for its panel, which may mount much later (a terminal in a worktree the window is not showing), and whose attach drains it.
- **Notifications.** `osc` events raised meanwhile wait in a `NotificationQueue` and go to the next server right after `initialize_result`, with or without the capability, since every server reads them, with their epochs, so the manager still drops stale ones. At most 256, and 1 MiB of payload: past that, the oldest are dropped, and the host logs how many.
- **Limits.** No session is spawned while no server is connected, so the ended sessions never hold more than the same sessions did running; the limits only bound what accumulates across servers that never attach to them. Past 128 ended sessions with their output, or 128 MiB of their rings, the oldest let go of their ring and screen: it is listed with `outputKept: false`, an attach gets only its exit, and the panel says its output was not kept. Past 1000, the oldest is forgotten, and a server that knew it reports it `lost` with `exit_unknown`.
- **Lifetime.** An ended session lives until an attach drains it, its terminal is closed or its worktree removed, or its host ends; one whose panel never comes back stays, within the limits, as long as its server runs, and keeps a host of another build from being let go meanwhile. A host ends them: a host whose only sessions left are ended ones, with no server, waits the grace period for one, then exits, even after a `keep`; and a quit that ends the terminals ends them with the rest.
- **An older server**, one without the capability, would take an ended session for a running one. When one connects, the host forgets its ended sessions, and the server reports the sessions it knew `lost` with `exit_unknown`, as with a host from before the capability.

## The server's side

[server.ts](../src/server/server.ts) builds one `TerminalHostPool` and hands it to `TerminalManager` as its host. Before serving, it calls `start()`, which finds the hosts in the run directory, handshakes with each, ends incompatible ones (and reports them, for the [notice](#versioning)), removes the files of hosts that refuse connections, and hands every compatible host's sessions to `TerminalManager.adopt()`. The pool holds back their events until `adopt` returns, so none arrives for a session the manager does not know yet. Adopted sessions have no client, so they are orphans (unless their panel waits in the [open inbox](TERMINALS.md#the-open-inbox)): the server starts the 5-minute orphan timer, which the first window to connect cancels, and each panel's reattach resumes from the ring or gets a snapshot. An adopted session whose meta the server cannot read is ended. A host that accepts the connection but does not answer the handshake or the list (stalled, or stopped), and whose entry names a running process, is logged as an error with its ID and pid and kept as an [unresponsive](#unresponsive-hosts) host, with its files and binary: it gets no new sessions, the client keeps reconnecting to it, and the sessions it lists once it answers are adopted then (a session whose ID a panel has meanwhile given a new shell is ended, with a warning: that panel shows the new one). Until it answers or is gone, the pool's `sessionsKnown` is false, and `onSessionsKnown` listeners are called once every host's sessions are known again, for what must not take an unadopted session for an ended one (the [open inbox](TERMINALS.md#the-open-inbox)). Without a running process in its entry, it is left alone.

**Shutdown.** `shutdown()` takes what happens to the terminals. The app's shutdown message on its channel ([SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle)) says `end` for a quit that ends the terminals, and `keep` for one that keeps them, Restart Loxel and an update install; SIGTERM and SIGINT, and a standalone server's idle shutdown, mean `end`. Either way the server `disconnect`s every host with that mode and waits for each to close its socket, at most `LEAVE_TIMEOUT_MS` (2 seconds, well within the 4 seconds the server's teardown gives them); with `end`, a host that has not closed its socket by then gets a SIGTERM. A host the server is reconnecting to, or one found not answering, gets a SIGTERM with `end`, by the pid of its handshake or of its entry; with `keep`, the message goes over the connection being restored, or over one of its own once the reconnect attempt under way has settled, since the host is in its grace period from the drop. A `keep` that cannot reach the host within the bound is logged, and the host keeps the sessions for its grace period from the dropped connection. A server that cannot have its port fails before it touches the hosts, so a second server never takes them from the running one. A crash (an uncaught exception) and an app that is gone (its channel closing without a shutdown message, or the server reparented) close the connections without a `disconnect`, so the terminals wait out the grace period for the next server. A shutdown message that arrives while the server is still starting waits until `start()` has found the hosts, then disconnects them with its mode, and the server exits without serving, holding the port meanwhile so that no other server takes the hosts as it leaves them; that is also how the app carries a quit that comes between a crash and its restart: it starts the server at once to hand it the message ([SHARED_SERVER.md](SHARED_SERVER.md#starting-and-restarting-the-server)).

**A restart's overlap.** After Restart Loxel or an update, the old server may still be shutting down when the new one starts: it frees its port before its `disconnect { sessions: "keep" }` has reached every host. Either order keeps the shells. A `keep` that lands first leaves the sessions waiting for the new server, and one that lands after the new server's `initialize` comes from a replaced connection, which the host ignores.

**One host's connection.** `SocketTerminalHost` frames commands in call order. A command sent while the connection is not up (a host still starting, or a connection being restored) waits in order, and requests are answered once it is. A connection that closes unasked does not mean the sessions are gone: the client reconnects at once, then after 250 ms, 1 s and every 5 s, lists the host's sessions and reconciles: a spawn whose answer was lost resolves if the host runs it, a session that ended meanwhile is reported `ended` and, if it had a client, attached again like the others and drained before its `exit` ([Ended sessions](#ended-sessions)), one the host no longer has is reported `lost` with `exit_unknown`, and every session that had a client is attached again with the same attachment number, resuming from the last output that client got. A session the host runs that the client does not know of, one whose `destroy` was lost with the connection, is destroyed. Keyboard input, resizes and acks sent on the closed connection are not replayed. The first failed attempt is logged, then a summary every 5 minutes, and a host unreachable for 30 seconds (`STALLED_AFTER_MS`) while its process runs is [unresponsive](#unresponsive-hosts), and retried every 30 seconds for as long as its process runs. Only when the host is confirmed gone, its pid not running or its socket refusing connections, or it was `superseded`, does the client report its sessions `lost` with `host_lost`, with no exit code (the panel says the terminal host stopped, rather than show a code the program never chose), and log it with the host's build ID and how many sessions it had. The next spawn then starts a new host.

### Unresponsive hosts

A host whose socket stays open while its event loop does not run (stopped with SIGSTOP, wedged in a synchronous parse or snapshot, blocked in a PTY spawn, which macOS serialises system-wide) never closes its connection, so only time tells it apart from a slow one. Every request has a timeout (`REQUEST_TIMEOUTS_MS` in [socket-terminal-host.ts](../src/terminal-host/socket-terminal-host.ts)), from when it is made, or for a host still starting, whose launch is bounded on its own, from when its first connection is up: 10 seconds for `spawn` and `list`, 30 for `attach`, since a snapshot of a large scrollback is legitimately slow, and 5 for `foreground_processes`, which the update confirmation waits on. A `spawn` or `list` that times out fails with an error that says so; a spawn's is followed by a `destroy`, so the host ends it should it get to it later, and the panel whose attach waited on that spawn shows the error. An `attach` that times out keeps waiting, its panel still the session's client, and gets the session once the host answers. A `foreground_processes` request that times out fails alone and leaves the host as it was, since its `ps` can be slow on a busy machine while the host is fine; the caller then knows no programs, as without the capability. A connection being restored whose `list` times out is one more failed reconnect attempt.

**Sleep.** A laptop's sleep must not make a host look unresponsive: the connection survives it, and on wake an event loop runs its due timers before it reads the socket data that arrived meanwhile. So every timeout here (the requests', the handshake's and leaving's) is an `awakeTimeout` from [awake-timer.ts](../src/lib/awake-timer.ts): a window in which the wall clock ran ahead of the monotonic clock, which stops while the machine sleeps, starts over however often, one whose timer fired more than 2 seconds late with no sleep in it (this process was stopped or its event loop blocked) starts over once, so a server blocked again and again still times out, and an expiry waits for the I/O already pending, so an answer read on wake settles the request first. The durations that decide a host is stalled are measured on the monotonic clock.

A host that does not answer a `spawn`, `list` or `attach` in time, one unreachable for `STALLED_AFTER_MS`, and one found not answering at startup are unresponsive: the client logs it once as an error with the host's ID, build and pid and how many sessions it has, and tells every one of its sessions (an `unresponsive` event, which the panel shows as a line saying the terminal continues once the host answers), and every panel that attaches to one of them while it stays unresponsive. It asks it for no foreground programs meanwhile. It gets no new sessions: the next spawn starts another host in the same generation, and an unresponsive host left with no session is let go with `end`. Nothing else ends its sessions, since their programs usually still run, agents among them, and the host may well recover: the next answer it gives, or a restored connection, makes it responsive again, logged with how long it was not, and its clients get their output again, or are attached again over the restored connection. Only `end` (Quit, or a host with no sessions left) ends an unresponsive host, with a SIGTERM to its pid when it cannot hear the `disconnect`.

**Logs.** The host's log lines go to `logs/terminal-host-<hostId>.log` (rotated at 5 MB like the server's, with [log-file.ts](../src/lib/log-file.ts)). Lines at info and above are also sent to the current server as `log` messages, which it logs under `terminal` with the host's ID, so they show in the Logs panel; at most 50 a second, so a flood of log lines cannot crowd output off the socket, and a line then says how many were held back. A line of another category carries it as `cat`, and the server logs `perf` lines under `perf`, and any category it does not know under `terminal`, as a server from before `cat` does with every line.

### Perf monitor

One host serves every session of a build, so its stalls and its growth reach every terminal at once, and it holds every emulator and ring. [host-perf-monitor.ts](../src/terminal-host/host-perf-monitor.ts) measures it like the server's own monitor: every 30 seconds a `debug` line "terminal host metrics" of category `perf`, which the host forwards to the current server (debug and up, for this logger only) next to the server's "server metrics", with the event loop lag (`computeLagStats` from [perf-lag-stats.ts](../src/lib/perf-lag-stats.ts), and the time stalled), RSS and heap, the PTY spawns and the time they blocked the host, and the sessions running and ended, with their rings' size and their emulators' lines. A window whose longest stall passes 100 ms is logged as a warning, and so is each new 512 MB step of RSS past 1 GB. The lag probe is a timer that re-arms itself every 100 ms, so a stall anywhere in the window delays it. A tick the machine slept through is sleep, not lag: it counts as no sample, and the summary says how long the host slept (`sleptMs`). Nothing of it runs on the output path, and with no server connected its lines go only to the host's log file.

**The manager's bookkeeping.** `TerminalManager` keeps, per session, the meta, the epoch, the host's answer to the spawn, its clients (a `TerminalFanout`, see [TERMINALS.md](TERMINALS.md#several-clients)), the latest attachment and the attach whose state has not arrived yet. A client is attached from the moment it attaches, before the host has answered the spawn: a detach in that window takes effect, the session is not an orphan meanwhile, and the clients still attached once the spawn is answered share one attach in the host. An attach waiting on a spawn the host refuses fails with it. Pending starts (a shell waiting for its toolchain environments) live only in the manager: the host is asked to spawn once the environment is ready, with the latest size, the command and any input typed ahead, in that order. A worktree move updates the meta in both places; removal and orphan cleanup call `destroy`.

## Files on disk

[host-files.ts](../src/terminal-host/host-files.ts) owns the layout under the state directory, which keeps every mode (prod, dev, demo) apart:

| Path                                                       | Contents                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `terminal-host/run/` (0700)                                | Each running host's entry `<hostId>.json` (`{ pid, build, protocol, socket }`) and socket `<hostId>.sock` (0600). The handshake is the truth about a host; the entry names the socket, and the process and build of a host that does not answer, so its binary is kept |
| `terminal-host/bin/<hostBuildId>/loxel-terminal-host`      | The clone a packaged host runs from                                                                                                                                                                                                                                    |
| `logs/terminal-host-<hostId>.log`, `.log.1`, `.log.stderr` | The host's log, its rotation, and what its runtime printed. Removed a day after the host is gone, never while it runs                                                                                                                                                  |

Host IDs are 8 hex characters, so a socket path stays under macOS's 104-byte limit for `sun_path`. The default state directories always keep their sockets in the run directory. Only a `LOXEL_STATE_DIR` override so deep that a socket path there would pass the limit keeps its sockets in the user's temporary directory instead, `loxel-terminal-host-<hash of the state directory>`, which every server for that state directory finds; the entries stay in the run directory, and the server logs a warning when it starts. macOS may purge a file there that has not been used for a few days, socket included: a host whose entry names a running process but whose socket is gone can no longer be reached, so the server logs it as an error at startup and keeps its entry and binary, and a server connected to it reports its sessions ended. Both directories must be the user's own, and are made 0700 if they are not. The path limit and that check are in [socket-paths.ts](../src/socket-paths.ts), shared with the server's [CLI socket](ARCHITECTURE.md#the-cli-socket).
