# Terminals

How terminal panels work end to end: terminal sessions and the server-side emulator, the login-shell environment Loxel captures for everything it spawns, Python environment activation in new shells, the attach/snapshot/resume protocol, the xterm.js client and its colors, terminal notifications, and the `loxel` CLI that runs inside terminals.

## Overview

A terminal panel is an xterm.js instance in the renderer bound to a terminal session in the shared Bun server (see [SHARED_SERVER.md](SHARED_SERVER.md)) by a UUID, the `terminalId`. For an ordinary terminal the renderer mints it once ([panel-creators.ts](../src/lib/panel-creators.ts) `createTerminal`); for `loxel terminal` the server mints it and the renderer adopts it. Either way it is stored in the Dockview panel params together with the worktree path and, when the shell starts elsewhere, the `cwd`, and the persisted layout keeps them across reloads. The session lives as long as the server, until the panel is closed, or until its worktree is removed; the xterm.js instance lives only while the panel is mounted.

The server, not the renderer, owns the screen. Within the server, sessions run in the terminal host, which the rest of the server reaches only through the `TerminalHost` interface ([TERMINAL_HOST.md](TERMINAL_HOST.md)); everything below holds whichever side of it a step happens on. Each session pairs the PTY with a headless xterm (`@xterm/headless`) that parses every byte the shell produces, so the server always knows the current screen, scrollback, cursor, modes and size. The renderer's xterm is a view of that state: when it mounts it receives a serialized snapshot, and from then on the live output stream. Raw history is never replayed into a fresh xterm. This matters because a terminal byte stream is a sequence of commands, not a document: replaying old output re-executes every side effect in it, so a background-color query or cursor-position request a program sent days ago would be answered again, into a shell that is no longer expecting it, and old notifications would fire again. tmux, mosh and VS Code's pty host all keep the emulator on the surviving side for the same reason.

## Server: terminal sessions

[terminal-session.ts](../src/terminal-host/terminal-session.ts) implements one session inside the terminal host; [terminal-manager.ts](../src/server/terminal-manager.ts) keys them by `terminalId`, decides what to spawn, spawns the shell on first attach (or up front, for `loxel terminal`), forwards each session's output to its client and tracks orphans.

- **Spawn.** The manager has the host run `$SHELL -il` (falling back to `/bin/bash`) as an interactive login shell in the requested `cwd`, with Bun's built-in `terminal` option providing the PTY. Nothing else is wrapped around the shell, except a zsh startup shim when a Python environment is activated (see [Python environment](#python-environment)). `cwd` and the environment apply only at spawn. The spawn waits for the worktree's [toolchain environments](#toolchain-environments) to resolve, at most `TOOLCHAIN_ENV_TIMEOUT_MS`; attaches and spawns for the same ID that arrive meanwhile share that one spawn, and a session destroyed meanwhile never starts. Meanwhile the pending start keeps the latest client (a detach clears it, so a client gone by spawn time is not bound), the latest size, which the shell starts at, and any input, which the spawn types ahead after the command it types in (`loxel terminal`, see [The `loxel` CLI](#the-loxel-cli)).
- **Emulator.** Every output chunk is written to the session's headless xterm, sized like the PTY and with the client's scrollback setting (clamped to 1,000–100,000 lines by `clampScrollbackLines` in [terminal-limits.ts](../src/api/terminal-limits.ts)). The emulator's own replies to terminal queries are discarded: while a client is attached, its xterm is the one that answers, and while nobody is attached a querying program simply times out, as it would in a detached tmux pane. If a flood outruns the parser (xterm's write queue discards past tens of megabytes unparsed), the session logs it once and the screen is stale until the next snapshot.
- **Stream offsets and the resume ring.** Output bytes are numbered from spawn, and every spawn gets a random `epoch` so offsets from a shell that no longer exists can never be mistaken for offsets into its replacement. The last `RESUME_RING_BYTES` (1 MiB) are kept in an `OutputRing`, oldest chunk evicted first, newest chunk always retained, so a client that still has a current xterm can be given exactly the bytes it missed.
- **Attach.** An attach replaces any previous client; the session counts as attached from that call on. Bytes sent to catch a client up count against the flow-control budget like live output. If `since` names this epoch and an offset still covered by the ring, the client gets `terminal_state { mode: "resume" }` followed by the missed bytes. Otherwise the session serializes the emulator (`@xterm/addon-serialize`, after everything written so far has been parsed) and sends `terminal_state { mode: "snapshot", snapshot, offset }`, then any bytes produced while serializing, then goes live. A snapshot contains screen contents, colors, cursor and modes, never requests, so nothing in it can be answered twice. While a snapshot is being produced the ring is pinned at the snapshot offset, so a flood during serialization cannot evict the bytes that have to follow it; the ring briefly grows past its capacity instead, bounded by how long one serialization takes.
- **Flow control.** The attached client acknowledges bytes it has parsed (`terminal_ack`, quoting the `offset` of the `terminal_state` it is working under; acks for an older sync are ignored). Above `FLOW_HIGH_WATER_BYTES` (2 MiB) unacknowledged, the session stops forwarding output; the emulator keeps parsing. Once acks bring the backlog under `FLOW_LOW_WATER_BYTES` (128 KiB) the client is resynced with a fresh snapshot and streaming resumes. Bun's PTY cannot be paused, so the shell is never slowed down; the renderer is never more than 2 MiB behind what it has parsed, and a flood costs it one snapshot instead of the whole backlog.
- **Detach.** A detach drops the client. Output keeps being parsed and ringed; nothing is sent. A session without an attached client is an orphan for `hasOrphanSessions()` and `destroyOrphans()`.
- **Resize and scrollback.** `resize()` applies to the PTY and the emulator (no-op when unchanged, so no spurious `SIGWINCH`); the manager applies the size and scrollback setting from every `terminal_attach`, so a reattached terminal always matches its new xterm. Sizes are clamped by `clampTerminalSize` in [terminal-limits.ts](../src/api/terminal-limits.ts) (2–1,000 columns, 1–500 rows) because the emulator allocates its cell grid eagerly; a clamped size is reported back in `terminal_state`, and the client refits.
- **Destroy.** `destroy()` disposes the emulator (settling any snapshot still in flight), closes the PTY, which hangs up the foreground job, and kills the process. A natural exit first resyncs a paused client with a final snapshot, so the tail of a flood is not lost; then the host removes the session and reports the exit, and the manager sends `terminal_exit` to the attached client and invokes its `onExit` hook.
- **Input.** `write()` passes the frame payload to `terminal.write` verbatim.

The sessions run in the terminal host process, apart from the server, which is what lets them outlive it ([TERMINAL_HOST.md](TERMINAL_HOST.md)). Every output chunk the server receives from the host is counted by the stress detector under `pty-output` ([stress-detector.ts](../src/server/stress-detector.ts)); the detector only logs, it never throttles.

### Ownership and lifetime in server.ts

[server.ts](../src/server/server.ts) maps each terminal to exactly one owning WebSocket (`terminalOwners`) and records the IDs in that connection's `ClientState.terminals`.

- `terminal_attach` registers ownership, builds a `TerminalSink` for that socket (state and exit as JSON, output as binary frames) and calls `terminalManager.attach()`. Any connection that attaches an existing ID becomes its owner; the previous owner stops receiving output.
- `terminal_detach`, `terminal_resize`, `terminal_ack` and binary input are ignored unless they come from the current owner. `terminal_destroy` is also accepted for a session nobody owns, because the panel's unmount detaches before the panel-removed handler sends destroy.
- On socket close, `detachClientTerminals()` detaches (never destroys) that connection's sessions.
- When the last app client disconnects and orphaned terminal sessions exist, the server waits 5 minutes (`ORPHAN_CLEANUP_MS`) and then destroys them. The server the desktop app started keeps running; a standalone server then shuts down. Any client connecting cancels the timer. See [SHARED_SERVER.md](SHARED_SERVER.md#server-lifecycle).
- At startup, before serving, the server takes over the sessions still running in the terminal hosts (`TerminalManager.adopt()`), so a panel's reattach after a restart finds its shell. They are orphans until then, under the same 5-minute timer.
- `shutdown()` on a quit (SIGTERM or SIGINT) or a standalone server's idle shutdown ends every session in the hosts. A crash, or an app that is gone, leaves them to the hosts' grace period instead, for the next server to reattach (see [TERMINAL_HOST.md](TERMINAL_HOST.md#lifetime)).
- Removing a worktree ends its sessions, whichever way it was removed: `completeWorktreeRemoval` calls `TerminalManager.endWorktreeSessions()` (see [WATCHERS.md](WATCHERS.md#worktree-lifecycle)). A session belongs to the panel's worktree (`worktreePath`, kept in the session's meta), not to the directory its shell is in, and follows the worktree through a move (`retargetWorktree` sets the new meta). A shell not yet spawned never starts. An in-app removal ends them at once, having already finished. A removal seen from outside the app ends them after `removedWorktreeTerminalDelayMs` (1 minute): the terminal may be the one running `wt rm`, with its branch still to delete when Loxel sees the removal, or a command chained after it. No signal says when that is over, since a branch deletion is optional. Only the sessions there at that moment end, so a worktree recreated at the path meanwhile keeps its own. `wt` itself survives the hang-up if that is not long enough, but a git command it has running does not, which can leave the branch behind.

### Environment

`buildTerminalEnv()` starts from `buildShellSpawnEnv()` in [shell-env.ts](../src/server/shell-env.ts) and sets `TERM=xterm-256color` if unset.

An app launched from Finder or the Dock inherits launchd's minimal environment, so `resolveLoginShellEnv()` captures the user's login-shell environment when the server starts. It runs `$SHELL -l -i -c "/bin/sh -c '…'"`: a bare path with one single-quoted argument parses the same way in sh, bash, zsh, fish, nu and PowerShell (which honors `-l` only as the first argument), and sh prints `env -0` between random sentinels, so greeting output is ignored and values may contain newlines (only `PATH` where `env` lacks `-0`). The shell runs in its own process group, killed after `CAPTURE_TIMEOUT_MS` with a logged warning, and reading stops at the closing sentinel, so neither a hung startup file nor a background job left holding stdout stalls it. A shell that cannot run the command (tcsh rejects the flags) or times out leaves the inherited environment. Of the result only the variables whose value the shell changed are kept, minus shell session state (`PWD`, `OLDPWD`, `SHLVL`, `_`). The capture is redone only by `refreshLoginShellEnv()` when a lookup on the spawn `PATH` misses (a language-server binary, a formatter), at most every `MIN_REFRESH_INTERVAL_MS`: every capture runs the user's startup files, including any daemon they start (`eval "$(ssh-agent -s)"`), so there is no periodic refresh. Concurrent requests share one capture, and a failed one keeps the previous result. `onLoginShellEnvChange(listener)` is called with the names of the variables a capture changed, for caches derived from the spawn environment; some startup files export a value that differs on every run (starship's session key), so a cache checks the names it depends on. `server.ts` subscribes the shared Python environment resolution's `refreshAllPythonEnvs` this way (see [LANGUAGE_SERVERS.md](LANGUAGE_SERVERS.md)). Windows has no login shell to ask, so nothing is captured there.

`buildSpawnEnv()`, used for everything else Loxel spawns (language servers, formatters, worktree hooks), applies every captured variable over the server's `process.env`. `buildShellSpawnEnv()` applies only `PATH`: a terminal's login shell runs the user's startup files itself, and re-applying their other variables first would make steps that stack, such as `conda activate`, run twice. Both prepend `~/.local/bin` if missing and guarantee `HOME`.

`server.ts` then adds per-terminal overrides:

| Variable          | Value                                                     | Why                                                                               |
| ----------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `LOXEL`           | `1`                                                       | Lets the CLI (and user scripts) detect they run inside a Loxel terminal           |
| `LOXEL_PORT`      | `config.port`                                             | The CLI talks to the exact server that owns the terminal (dev and prod differ)    |
| `LOXEL_WORKTREE`  | the panel's worktree (`msg.worktreePath`, else `msg.cwd`) | CLI fallback for URL requests when the shell's cwd is not inside a git repository |
| `LOXEL_WINDOW_ID` | the creating window's `WINDOW_ID`, if any                 | Routes `loxel <file>` back to the window the terminal belongs to                  |

These are fixed at spawn. A session reattached by another window keeps the original `LOXEL_WINDOW_ID`.

#### Toolchain environments

Every toolchain that adds to a new shell's environment is one [`ToolchainEnvContributor`](../src/server/toolchain-env-contributor.ts) in the list in [toolchain-envs.ts](../src/server/toolchain-envs.ts), which the manager gets as its `toolchainEnvs` hook. A new toolchain is one new file plus one entry there. The manager skips a contributor whose `enabledInTerminal` turns it off for the spawn's settings, resolves the others side by side with one shared timeout of 3 s, after which a shell starts without the ones still resolving, then applies the answers in list order, since several can change the same variable. A contributor that fails is logged and skipped. Each contribution runs on a copy of the environment and `commitToolchainEnvChange` in [toolchain-env-contributor.ts](../src/server/toolchain-env-contributor.ts) takes it only if every directory it adds to `PATH` or moves forward passes the shared path check: none may hold a character a login shell would interpret (macOS startup `eval`s `path_helper`'s double-quoted `PATH`, and branch names, so worktree directories, can contain quotes or `$`). A contribution that fails it is left out whole. Login shells can reorder `PATH` during startup (see below), so a `PATH` entry set this way is not guaranteed to stay first.

#### Python environment

Unless the spawn request carries `activatePythonEnv: false` (the `terminal.activatePythonEnv` setting, sent with `terminal_attach` like `scrollbackLines`; for a `loxel terminal` shell the server reads both from the persisted settings), the Python contributor (see [Toolchain environments](#toolchain-environments)) gets the environment of the panel's worktree (`worktreePath`, else `cwd`) from `getPythonEnv`, the shared per-worktree resolution that also feeds the language servers and format on save (see [languages/python.md](languages/python.md#python-environment)), so an interpreter chosen for the worktree applies too. When the result has an `envPath` and the worktree's repository is trusted, `activatePythonEnv()` in [terminal-python-env.ts](../src/server/terminal-python-env.ts) sets what a venv's `activate` script exports, as variables only (the part shared with mypy's daemon lives in [python-env-activation.ts](../src/server/python-env-activation.ts)): the interpreter's directory moves to the front of `PATH`, `VIRTUAL_ENV` is set for a venv in zsh only (a conda-style environment such as Pixi's, and any environment in other shells, only goes on `PATH`, and an inherited `VIRTUAL_ENV` is dropped), and `PYTHONHOME` and `VIRTUAL_ENV_PROMPT` are removed. Nothing is activated for an interpreter outside any environment or for a directory holding files git tracks, on top of the [shared path check](#toolchain-environments): activation checks the whole interpreter directory with the [environment trust rule](languages/python.md#environment-trust-rule), since it goes first on `PATH` and a tracked file there (a `git`) would shadow the real command; this also covers an environment whose directory is the worktree itself, where the resolver checks only the environment's own entries, and files written after resolution. In an untrusted repository nothing is activated and the restriction is reported, since an environment holds the project's dependencies (see [Environment trust rule](languages/python.md#environment-trust-rule)). The shared resolution follows environments created later, and trust is asked at each spawn, so both reach new terminals; open terminals keep theirs.

Login shells reorder an inherited `PATH`: on macOS, `/etc/zprofile` and `/etc/profile` run `path_helper`, which puts the system directories first. For zsh, the manager therefore points `ZDOTDIR` at a shim whose startup files source the user's own files unchanged and, after the last one (`.zlogin`), move the environment's directory back to the front of `PATH` unless the user's files activated a different `VIRTUAL_ENV`; how the shim stays invisible to the user's files is documented in [terminal-python-env.ts](../src/server/terminal-python-env.ts). A user file that `exec`s another program (`exec tmux`) ends startup before `.zlogin`, so that shell keeps the inherited order, and tools that activate on the prompt hook (direnv, mise) run after startup, so their environment wins. Other shells get only the `PATH` entry: where their login startup reorders `PATH` (bash's `/etc/profile`, fish's `/etc/paths` handling) the directory stays on `PATH` but not first, and a `VIRTUAL_ENV` naming the environment would then contradict the `python` and `pip` the shell runs.

#### Java JDK

A JDK the user chose for the worktree reaches new shells through [java-toolchain-env.ts](../src/server/java-toolchain-env.ts), as `JAVA_HOME` and its `bin` first on `PATH`; a detected JDK changes nothing. Its rules are in [languages/java.md](languages/java.md#terminals). There is no zsh shim here, so `bin` loses first place to login startup, and a startup file that exports `JAVA_HOME` replaces the value. macOS's `/usr/bin/java`, which startup then finds first, follows `JAVA_HOME`.

## WebSocket protocol

Terminal messages are part of the main app socket (`/ws`). Message types live in [ws-protocol.ts](../src/api/ws-protocol.ts), and `TerminalState` and the binary frames in [terminal-stream.ts](../src/api/terminal-stream.ts); note that [ws-messages.ts](../src/server/ws-messages.ts) only builds the `worktrees_changed` message and has nothing terminal-specific.

- **JSON control frames (client to server):** `terminal_attach { id, cols, rows, cwd, worktreePath?, scrollbackLines?, windowId?, activatePythonEnv?, sinceEpoch?, sinceOffset? }` binds a mounted xterm, spawning the shell in `cwd` if needed (`worktreePath` is the panel's worktree, which the renderer always sends; it defaults to `cwd`, and the shell starts there instead when a persisted `cwd` no longer exists); `sinceEpoch`/`sinceOffset` are sent only by a reconnecting client whose xterm is still current. `terminal_detach { id }` is sent on unmount. `terminal_resize { id, cols, rows }`, `terminal_destroy { id }` and `terminal_ack { id, syncOffset, bytes }` (flow control).
- **JSON control frames (server to client):** `terminal_state { id, epoch, mode, offset, snapshot?, cols, rows }` answers every attach and every flow-control resync; `mode` is `snapshot` (reset the xterm and write `snapshot`) or `resume` (nothing to replay). `offset` is the stream position the xterm is current to once the message is applied. `terminal_exit { id, exitCode }` is sent only to the owner.
- **Binary frames** for I/O, to avoid JSON overhead and keep raw bytes. Output (server to client) is `[0x01][terminalId: 36 ASCII bytes][offset: u64 big-endian][payload]`, where `offset` is the stream position of the payload's first byte. Input (client to server) is `[0x02][terminalId][payload]`, UTF-8 keystrokes or the xterm's replies to terminal queries. `encodeOutputFrame` / `parseOutputFrame` / `encodeInputFrame` / `parseBinaryHeader` are shared by the renderer and the server, which is why terminal IDs must be 36-character UUIDs.

Ordering is what makes the offsets work: the server sends `terminal_state` before any output frame at or past its `offset`, and the client applies frames strictly in offset order after the state they belong to.

On the client, [client.ts](../src/api/client.ts) routes binary output to at most one handler per terminal (`onTerminalOutput`, registered by a mounted `Terminal`), passing the offset along. `sendTerminalInput` drops input while disconnected rather than queueing it; JSON `send` queues until the first connection only.

## Client: the Terminal component

[Terminal.tsx](../src/components/terminal/Terminal.tsx) is mounted by `TerminalPanelComponent` in [panels.tsx](../src/components/dockview/panels.tsx), which provides the panel's `worktreePath` param through `PanelContext` and passes the optional `cwd` param as a prop. The shell starts in `cwd`, else in the worktree path; if the worktree path is missing, no `terminal_attach` is sent and the panel stays empty.

### Lifecycle

1. Construct `XTerm` with the colors of the current mode's theme (`xtermColorOptions` in [loxel-theme.ts](../src/lib/loxel-theme.ts); see [Colors](#colors)), the fit, search and web-links addons and the file-path link provider.
2. Wait for the font (below), then `terminal.open()`, attach WebGL if visible, and on the next animation frame `fit()` and send `terminal_attach` with the fitted size, the scrollback setting and `WINDOW_ID`. Until the matching `terminal_state` arrives, incoming output frames are queued.
3. On `terminal_state`: a `snapshot` is written as an in-band full reset (`ESC c`) followed by the snapshot, so anything still queued in xterm's asynchronous write buffer is parsed before the screen is cleared; `resume` writes nothing. Queued frames older than `state.offset` are dropped, the rest are written in order, and the component records the epoch and the offset it is now current to (`offset + payload length` after each frame). If the xterm was refitted while the attach was in flight, so `cols`/`rows` in the state differ from its own, it sends `terminal_resize`.
4. Input from `terminal.onData` (keystrokes and the xterm's replies to queries in live output) goes out as binary frames until `terminal_exit` arrives, after which the component prints `[Process exited with code N]` and stops sending.
5. Every 64 KiB of live output written (measured in xterm's write callback, so it counts parsed bytes) the component sends `terminal_ack` quoting the current sync's offset; bytes written under an earlier sync are not counted.
6. On WebSocket reconnect (same server version; a changed version reloads the page instead), it sends `terminal_attach` again with the epoch and offset it is current to, without resetting. This resumes from the ring, or snapshots if the gap was evicted, against the same server or a restarted one, since the session lives in the terminal host. Only when the session is gone (the shell exited, or a quit ended it) is a fresh shell with a new epoch spawned, and the snapshot branch clears the old screen.
7. Unmount sends `terminal_detach` and disposes the xterm instance and handlers. The shell keeps running and the server stops streaming to nobody.

Sizing: a `ResizeObserver` and a device-pixel-ratio media query schedule a 100 ms debounced `fit()`; `terminal_resize` is sent only when cols or rows actually changed. Colors, scrollback and font options are updated in place when dark mode or the setting changes; the server-side emulator picks the scrollback setting up at the next attach. A font change refits a terminal that is on screen; one that is hidden refits when shown.

### Font loading

xterm measures the cell grid and the WebGL renderer rasterizes its glyph atlas at `open()`, and neither re-measures when a web font arrives. `loadTerminalFont()` therefore loads the `JetBrains Mono NL` `FontFace` objects directly (Chromium's `document.fonts.load()` matches nothing for this family because of a `local()` fallback face in [index.css](../src/index.css)) and races them against a 2 second timeout before opening. A terminal font from Settings (`resolveFont` in [font-settings.ts](../src/lib/font-settings.ts)) is put in front of `JetBrains Mono NL` in the stack: it is installed and needs no loading, and the bundled faces still back the glyphs it lacks.

### Colors

A terminal draws in the colors of the current mode's theme ([THEMES.md](THEMES.md)): the theme's terminal colors over its base's, on the theme's `editor-surface` token, which `readThemeTokens` resolves for that theme without depending on what the document has applied yet (a child's effects run before `useThemeSync` restyles the page). The panel's padding takes the same background. The theme object is the built-in constant or the stored one, so the component's selector only changes reference when the colors do; `minimumContrastRatio` is 4.5 for light themes and 1 for dark ones.

### WebGL renderer and fallback

[webgl-renderer.ts](../src/components/terminal/webgl-renderer.ts) wraps `@xterm/addon-webgl`. WebGL is used because it draws box-drawing and block glyphs as exact-cell custom glyphs; a Vite plugin in [vite.config.ts](../vite.config.ts) (`xtermWebglPixelGrid`) patches the addon to snap glyphs and cell width to whole device pixels, and, when a minimum contrast ratio is set (light themes), to hold dim text to that ratio as drawn at 50% opacity rather than checking the undimmed color against half of it. The plugin also gives the glyph atlas's canvas font an explicit `normal` style: the addon leaves the style empty for upright text, so the value starts with a space, which Electron 45's Chromium rejects ([electron/electron#55616](https://github.com/electron/electron/issues/55616)), and the atlas would draw every glyph in the canvas default of 10px sans-serif. Chromium caps live WebGL contexts per window (about 16) and force-loses the oldest, so a terminal holds a context only while its panel is visible: `onDidVisibilityChange` attaches on show and detaches on hide, and detach explicitly calls `WEBGL_lose_context` so the context does not count against the cap until GC. If the addon throws, or the context is lost (GPU reset, cap), the terminal stays on xterm's DOM renderer; on context loss the component refits because DOM cell metrics differ. Showing the panel again retries WebGL.

### Links

- **URLs** come from `WebLinksAddon` and xterm's `linkHandler` (OSC 8 hyperlinks); both call `openUrl()`, which accepts only `http:`/`https:`. Cmd+click dispatches `loxel-create-browser` (handled in [useLoxelEventListeners.ts](../src/hooks/useLoxelEventListeners.ts), which opens a browser panel); a plain click calls `window.open`, which the Electron main process turns into `shell.openExternal` through `setWindowOpenHandler` in [main.ts](../src/electron/main.ts); main also accepts only `http:`/`https:` there, so no other scheme ever reaches the OS.
- **File paths** come from [file-link-provider.ts](../src/components/terminal/file-link-provider.ts). Pass 1 always links tokens starting with `/`, `./`, `../` or `~/`, trimming trailing punctuation but keeping a `:line[:col]` suffix. Pass 2 links bare tokens with an extension (`CLAUDE.md`, `src/index.ts:12`) only if they match the worktree's file index by full relative path or by basename (first match wins). The index comes from the file-search store cache or `api.getFileIndex`. Column ranges are mapped back from ANSI-stripped text to raw cell positions. Links activate on Cmd+click only.
- Explicit relative paths (`./`, `../`) resolve against the **terminal's starting directory** (its `cwd`), and bare names matched through the file index against the **panel's worktree root**; neither follows the shell's live current directory (the renderer does not track `cd`). `~/` is left for the server to expand. Activation calls `openPath()` in [open-path.ts](../src/lib/open-path.ts), which asks `GET /api/path-info` whether the path is a directory: folders go to `openFolder()`, everything else to `dispatchOpenFile(path, location)` in [open-file.ts](../src/lib/open-file.ts), so the `:line:col` location reaches the editor. Missing files still open an editor, which reports the error.

### Keys and selection

`attachCustomKeyEventHandler` translates a few Cmd/Alt combinations into control sequences or xterm calls; app-level shortcuts are passed through to the global keybinding system (see [KEYBINDINGS.md](KEYBINDINGS.md); terminals are a find target via `usePanelFind`). Shift+Enter sends `ESC CR` and Ctrl+Enter sends the CSI-u sequence `ESC [13;5u`, which TUI coding agents read as "newline without submit". The handler returns `false` for modified Enter on keydown, keypress and keyup alike, so xterm never emits its own CR as a second newline; only keydown writes the sequence. `macOptionIsMeta` is on. There is no terminal-specific copy or selection code: copying relies on xterm's selection and the Electron Edit menu roles.

## Notifications

Terminal programs can raise notifications with OSC sequences; they become badge dots and entries in the notification center.

- **Parsing.** The manager reads each payload with the pure parsers in [osc-notification-parser.ts](../src/lib/osc-notification-parser.ts) for OSC 9 (iTerm2, whole payload is the body), OSC 777 (`notify;title;body`, anything else ignored) and OSC 99 (Kitty; `p=` selects title or body; multi-part `d=0` sequences are not coalesced).
- **Detection is server-side, once.** The session's headless emulator registers parser hooks for 9, 777 and 99, and the host reports each sequence's raw payload, unfiltered, so a sequence is seen exactly once no matter how many windows are open, whether the panel is mounted, or how often it remounts; the xterm in the renderer has no notification hooks. Split sequences are no concern because the emulator is a real parser, not a chunk scanner.
- **Settings.** Each sequence can be disabled in settings (`terminal.notificationSequences`, all on by default); the manager drops a disabled one before parsing it. The server reads the persisted settings store ([terminal-settings.ts](../src/server/terminal-settings.ts)), caching the parsed flags until the store row is written again (`onStoreChange` in [store-db.ts](../src/server/store-db.ts)), so toggling takes effect immediately and a flood of sequences costs no database reads.
- **The bell.** A bare BEL (`0x07`) is not a notification; there is no `onBell` handler. BEL appears only as an OSC terminator.
- **Server store.** The manager's `onNotification` hook adds `{ kind: "terminal", panelId: terminalId, worktreePath }` to [notification-store.ts](../src/server/notification-store.ts), where `worktreePath` is the one in the session's meta: the panel's worktree as sent in `terminal_attach` or picked by `POST /api/open` for `loxel terminal`, defaulting to the spawn `cwd`. The store keeps an in-memory, newest-first list capped at 200 and loses it on restart; `server.ts` broadcasts every change to all clients and sends `notifications_sync` on connect. The model is [notification-model.ts](../src/api/notification-model.ts).
- **Client mirror.** [panel-notifications.ts](../src/store/panel-notifications.ts) mirrors the server list and derives `panelIndex` and `worktreeIndex`. The terminal tab ([terminal-tab.tsx](../src/components/dockview/terminal-tab.tsx)) shows a dot when its terminal is in `panelIndex` and the tab is inactive, and dismisses that panel's notifications whenever the tab becomes active. The sidebar shows a dot for worktrees in `worktreeIndex`. In Electron the count also drives the Dock badge (`useLoxelEventListeners`).
- **Navigation.** [notification-navigation.ts](../src/lib/notification-navigation.ts) `navigateToNotification()` switches to the source worktree if needed, then activates the source terminal's tab, retrying once after 150 ms because the swapped-in layout may not be mounted yet. It is used by the notification center items and the "recent notification" action.
- **Cleanup.** Closing a terminal panel calls `unregisterPanel`, which sends `notification_dismiss_panel`.

## The `loxel` CLI

The CLI entry is [cli.ts](../src/cli.ts); `pnpm run build:cli` compiles it with `bun build --compile` to `build/loxel`. Bundling it with the app and installing it on `PATH` is planned (#322). The user-facing [`loxel` agent skill](../../../skills/loxel/SKILL.md) teaches agents the CLI, so update it when a command, flag or behavior below changes.

- **No argument:** runs `open -a Loxel`.
- **Finding the server:** inside a Loxel terminal (`LOXEL=1` and `LOXEL_PORT` set) it uses `LOXEL_PORT` directly. Otherwise it probes `GET /api/version` on 7433, then 7434 (1 second each), runs `open -a Loxel` to focus or launch the app (only when the open takes focus; without it, it runs `open -g -a Loxel` only if nothing answered, asking macOS to launch the app without activating it), and if nothing answered waits up to 15 seconds for port 7433.
- **Arguments** are parsed by [cli-args.ts](../src/cli-args.ts) before anything is launched, so bad flags fail fast with a usage line. `loxel <target>...` takes one or more targets, with open flags before, between or after them (`--` ends the flags), and `--replace` takes only one, since each target would close the tab the one before it opened; `loxel terminal` reads its flags until `--` or the first non-flag argument.
- **Focus** is `--focus`/`--no-focus` if given, else on unless the caller is a coding agent: `isCodingAgent()` in [coding-agent-env.ts](../src/coding-agent-env.ts) checks the variables agents set for their commands (`CLAUDECODE`, `CODEX_*`, `GEMINI_CLI`, `AI_AGENT`, ...), leaving out ones a user's shell can carry. Every request carries `focus`.
- **Several targets** become one request each, sent in order by `requestOpenAll()`, each once the last is accepted, so panels open in command order. A target that fails is reported with its name and does not stop the others; the exit code is then 1. All of them share one worktree resolution, one wait for a window and one `placement`, and warnings are deduplicated. With `--split`, the CLI adds a `batch` token to the placement, so they share one new split (see [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md#creating-and-opening-panels)).
- **Worktree:** `--worktree <path>` is normalized with `git rev-parse --show-toplevel` and sent on every request: as `wtPath` on a URL, and as `pinWtPath` on a file or terminal, which pins it there. (`wtPath` on a file means nothing: older CLIs send it, so it stays ignored.) Without it, the worktree is resolved only for a command with a URL (a command of only files has none, and each file opens in its own): `git rev-parse --show-toplevel` of the cwd, falling back to `LOXEL_WORKTREE` inside a Loxel terminal.
- **URLs** (`http:`/`https:`, per [url-utils.ts](../src/url-utils.ts)): `{ url, wtPath, windowId?, placement?, focus }`, with `wtPath` the command's worktree. If it cannot be resolved the URL fails, before anything launches when there are no other targets.
- **Everything else** is treated as a path: `{ filePath: resolve(arg), pinWtPath?, commandWtPath?, windowId?, placement?, focus }`. `commandWtPath` is the command's worktree when it was resolved without `--worktree`, so a file stays with the URLs of its command; unlike `pinWtPath` it is dropped if it names no project's worktree, since the file can open by itself. `LOXEL_WINDOW_ID` is included only inside a Loxel terminal, for every request kind.
- **`loxel terminal [--cwd <dir>] [--title <name>] [open flags] [--] [command...]`** opens a terminal panel: `{ terminal: { cwd, command?, title? }, pinWtPath?, windowId?, placement?, focus }`. The command line is built from what follows the flags: one argument is used verbatim, several are joined with `shellQuote` applied only to arguments that need it (`SAFE_WORD`), so the command word stays bare and alias expansion still happens. `cwd` defaults to the `--worktree` directory if given, else to the process cwd.
- **Layout flags** (`--split <dir>`, `--replace`, `--group <tab>`) become the request's `placement`, a `PanelPlacement` from [panel-placement-model.ts](../src/api/panel-placement-model.ts). `--group` sends the value both as typed (`name`, matched against tab titles) and resolved against the cwd (`path`, matched against open files). `--split` and `--replace` are exclusive. How a placement is resolved in the layout is in [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md#creating-and-opening-panels).

[open-request.ts](../src/open-request.ts) `requestOpen()` posts to `POST /api/open` and, on `503` (no window connected yet) or when no server answers, as between a server that is exiting and its replacement, retries every 300 ms for up to 30 seconds, then fails with `Cannot reach Loxel at <url>` if no server ever answered. It resolves to the reply's `warning`, which the CLI prints to stderr. `requestOpenAll()` sends several requests with it (see **Several targets** above). The Electron main process reuses it for files macOS hands to the app (see [ELECTRON.md](ELECTRON.md)); those requests carry no `focus`, which means focus.

`handleOpen` in [routes.ts](../src/server/routes.ts) validates `placement` with `parsePanelPlacement` and `focus` as a boolean (400 if malformed), and canonicalizes `group.path` like an opened path, dropping it when nothing exists there. `wtPath` and `pinWtPath` are resolved to the worktree holding them from the project's current worktree list (`namedWorktree()`), so a worktree created a moment ago counts and a nested repository cannot be mistaken for one; a path naming none is a 404. The placement rides along unchanged in `open_url`, `open_file` and `open_terminal`, and so does `focus: false` (`focus` is omitted when on):

- URL: rejects non-http(s), requires `wtPath`, and sends `open_url` to every client showing that worktree (`shownWorktree`; a window that left it can stay subscribed until its saves finish) with `sendToWorktreeWindows()`; only the one in use among them (`windowId`'s, else the most recently focused) gets the placement and focus, the others `focus: false`, so a `--replace` cannot close tabs in other windows and a page does not take over a window the user did not target. With no such window the message goes to the window in use with `sendToActiveWindow()`, or the reply is a 503, which the CLI retries. [ws-bridge.ts](../src/queries/ws-bridge.ts) hands it to `openUrl` in [open-path.ts](../src/lib/open-path.ts), which opens it in that worktree like a file (see [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md#routing-paths-to-panels)); `createBrowser` itself only knows the mounted center.
- Path: `stat`s it (404 if missing; 400 for anything that is not a regular file or directory, since pipes and devices would hang the editor), canonicalizes it (`~/` expansion, `realpath`), and calls `sendToActiveWindow()` in `server.ts` with `open_file` (carrying `worktreePath` from `pinWtPath`, or from `commandWtPath` if that names a worktree) or `open_folder`. A folder drops the placement and `pinWtPath` with a `warning` in the reply, and without focus it is not sent at all (revealing it in the tree takes focus), again with a `warning`. That targets every connection whose `window_hello` reported the given window ID, else the most recently focused window (`window_focused`, from [useWindowPresence.ts](../src/hooks/useWindowPresence.ts)), else any client; with no client it returns 503.
- Terminal: canonicalizes `cwd` and requires it to be a directory, then picks the terminal's worktree: `pinWtPath` if given, else the one holding `cwd`, from its project's current worktree list (`listProjectWorktrees`, so a worktree `wt add` created a moment ago counts), else the one the window in use shows (`activeWindow()` in `server.ts`: the worktree its last `subscribe_worktree` named, `shownWorktree`), or a 503 when there is neither, which the CLI retries like a window that has not connected yet, since a launching window shows its worktree a moment later. It mints the `terminalId`, sends `open_terminal { terminalId, cwd, worktreePath, title?, placement? }` to the window the same way, and in the same tick starts the shell itself (`startTerminal()`: `TerminalManager.ensureSpawned()` at 80x24 until the first attach resizes it, with that worktree and window as `LOXEL_WORKTREE` and `LOXEL_WINDOW_ID`, and the scrollback and Python settings [terminal-settings.ts](../src/server/terminal-settings.ts) reads from the persisted settings). The command goes to that spawn only and is typed into the PTY with a trailing newline, ahead of the prompt, so it lands in the shell's history like user input. Starting the shell here rather than on the panel's attach is what makes the command run whether or not the panel ever mounts: a background tab, a worktree the user is not on, and a window that is not painting (the xterm attaches from an animation frame) all hold the attach back, for hours if the user does not look. The reply waits for the shell to be running, so the CLI fails (500) when it cannot start. The command never reaches the renderer or the persisted layout, so a reload or a respawn after a server restart gets a plain shell and cannot run it twice.

In the renderer, `openFile()` and `openFolder()` in [open-path.ts](../src/lib/open-path.ts) pick the owning worktree, or fall back to the active worktree's Others section (`openFile()` honoring a named worktree first, see [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md#routing-paths-to-panels)), and `openTerminal()` and `openUrl()` take the worktree the server sent, first refreshing that project's worktree list if it is not listed yet, since `wt add` from a shell may have created it a moment ago. Each switches to its worktree if needed (a file, URL or terminal without focus is instead queued there until the user switches; a folder is never sent without focus). A file, URL or terminal for a worktree whose center Dockview is not mounted yet is queued in the worktree UI store (`queueOpen`, a `PendingOpen`, placement included) and created once the layout is restored, so the placement is resolved against the target worktree's layout; `createTerminal()` in [panel-creators.ts](../src/lib/panel-creators.ts) takes the server's `terminalId`, the `cwd`, the title, the placement and focus. The panel's first `terminal_attach` binds to the session the server already started. Panel creation itself is covered in [PANELS_AND_LAYOUT.md](PANELS_AND_LAYOUT.md); worktree switching in [PROJECTS_AND_WORKTREES.md](PROJECTS_AND_WORKTREES.md).

## Opening things in external apps

"Open In" (reveal in Finder, open with another app) is served under `/api/open-in/*` by [open-in-routes.ts](../src/server/open-in-routes.ts), with request and response schemas in [open-in-model.ts](../src/api/open-in-model.ts). It is macOS-only (`routes.ts` returns 501 elsewhere). Targets must be normalized absolute paths that Loxel manages (bodies follow the server-wide [request origin checks](ARCHITECTURE.md#request-origin-checks)), and `open -a` only launches an app the route itself offered for that target. App lists for files come from LaunchServices (see [ELECTRON.md](ELECTRON.md)). Folders get no LaunchServices lookup: [folder-apps.ts](../src/server/folder-apps.ts) checks a curated list of terminals (Terminal, iTerm, Ghostty, Warp) and editors for an installed `.app` in `/Applications`, `~/Applications` and `/System/Applications/Utilities`.

## Invariants

- **Survives reloads and server restarts, not a quit.** Terminal IDs are persisted in the layout's panel params and the session is keyed by them, so a renderer reload, a WebSocket drop or a server crash or restart reattaches: with a snapshot into a fresh xterm, or by resuming the missed bytes into a live one. The sessions run in the terminal host, which outlives the server (for up to 10 minutes with no server connected). A quit ends every session; after one, the client's attach spawns a fresh shell under the same ID, in the same worktree.
- **History is state, not a stream.** The only thing ever written into a fresh xterm is a serialized snapshot. Old output is never replayed, so queries, bells and notifications in it never fire twice.
- **Removal ends shells; a switch or a move does not.** Only a worktree git no longer has registered ends its sessions, never a failed removal or another `worktrees` event.
- **Worktree switches keep shells running.** Switching worktrees swaps the center layout and unmounts terminal components, which detach; `CenterHost` skips `terminal_destroy` during layout swaps. The server keeps parsing output into the emulator and sends nothing until the panel remounts and takes a snapshot.
- **Per-worktree cwd.** A terminal's cwd and `LOXEL_WORKTREE` are the panel's `worktreePath` param at creation; a terminal opened with `loxel terminal --cwd` keeps the directory in its `cwd` param while `LOXEL_WORKTREE`, the notification source and the file index stay on the worktree. Links with an explicit `./` or `../` prefix resolve against the starting directory (never the live shell cwd); bare names resolved through the file index are worktree-root relative.
- **Many terminals.** Only mounted terminals cost bandwidth; every live session costs one headless emulator plus a 1 MiB resume ring on the server. The emulator stores 12 bytes per cell for every line it has filled, so a terminal that has scrolled through its full default 50,000 lines at 200 columns holds about 120 MB; the scrollback setting is the lever, and an idle shell costs almost nothing. WebGL contexts are held only by visible terminals.
- **The renderer is never flooded.** Unacknowledged output is capped at 2 MiB per terminal; past that the client is brought back with a snapshot instead of a backlog.
- **Modified Enter.** Shift+Enter and Ctrl+Enter are forwarded as `ESC CR` and `ESC [13;5u` at the key-handler level; there is no per-program detection.
